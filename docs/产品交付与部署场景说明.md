## 0. 核心结论（先看这里）

| 结论 | 说明 |
|---|---|
| 产品是一个**单机部署的服务**，不是分布式系统 | 后端 Spring Boot 2.7.18（Java 8，端口 8091）+ 前端 Vue3 打进同一个 JAR + MySQL 8；一台机器承载全部组件，数据落在一块**独立数据盘** `/main` |
| 交付包分**全量**与**增量**两类，另有**离线全量**变体 | 全量 tar.gz 用于新机/重装；增量 zip 用于日常升级（53MB→约 2MB）；离线全量 = 全量包内附 deb 依赖，客户内网无外网时用 |
| 支持 **6 种部署场景**，覆盖新机、升级、重装、迁移 | 见 §3 场景矩阵；**先按 §2 决策树选场景，再按 §4 对应步骤执行** |
| 有**两条交付线**，必须分开管 | 主程序（tar.gz / update.zip）走 §3～§5；授权（机器码包 / 授权包 / 密钥）走 §6，二者只在验收签字处汇合 |
| 有三个**硬性前置**，不满足就不要开跑 | 独立数据盘挂 `/main`（禁 `nofail`）、8091 不对公网暴露、管理员口令真正落库（非种子 `123456`） |
| 交付完成有统一判据 | `verify.sh` 45 项 + 浏览器回归 + 无 `ZZTEST*` 残留 + 授权 `--delivery` 49 项（授权交付时）+ 客户签字，详见 §5 |

## 2. 部署前必须确认（所有场景通用）

| 项 | 要求 | 不满足的后果 | 怎么确认 |
|---|---|---|---|
| **独立数据盘** | 一块单独物理盘挂到 `/main`，fstab **绝不加 `nofail`** | 数据静默写系统盘，盘修好后被盖住，表现为「数据全丢且无报错」 | `findmnt -n -o SOURCE,OPTIONS /main`；`sudo findmnt --verify --verbose` 必须 Success |
| **网络边界** | 8091 只在受控内网可达，**不对公网暴露** | 图片上传接口目前只校验 `Bearer ` 前缀、不与令牌比对，任何能访问 8091 的人都能写数据 | 服务器 `ss -lntp \| grep 8091`；外网机 `curl -m 5 http://<公网IP>:8091/api/version` 应超时/拒绝。此项脚本无法证明，须人工留档 |
| **口令** | 数据库 root 口令 + 管理员口令显式提供；管理员口令由 p7 `reset-password.sh` 真正 BCrypt 落库 | 不传则种子弱口令留在生产库；传了 `--app-password` 但没落库则登不上 | 部署日志确认 p7 成功；用新口令登录一次 |
| **版本/架构** | 离线包适用 **Ubuntu 22.04 amd64**；在线包支持 22.04/24.04 | 离线 deb 与目标机版本不符会装不上 | `cat /etc/os-release`、`dpkg --print-architecture` |
| **授权** | 新机默认 TRIAL（60 天 / 30 相机）；正式交付需按 §6 导入授权 | 60 天后需走签发流程；默认 `warn` 策略不装授权也能全功能跑 | 页面「服务器授权」或 `GET /api/license` |
| **备份点** | 升级前先备份；新机部署确认备份定时器在跑 | 升级失败无法回滚 | `systemctl list-timers camera-detection-backup` |

> 口令不进命令行历史、不进仓库：优先 `config/offline.env`（600）或环境变量；
> 唯一密钥源 `/etc/default/camera-detection`（640 root:root），由 systemd `EnvironmentFile` 注入。

## 3. 支持的部署场景矩阵

| # | 场景 | 目标机器状态 | 网络 | 用哪个包 | 入口脚本 | 典型命令 |
|---|---|---|---|---|---|---|
| **A** | 全新机在线一键 | 空机，有一块独立数据盘 | 有外网 | 全量包 | `deploy.sh` | `deploy.sh --disk /dev/sdb --db-password … --app-password …` |
| **B** | 全新机离线一键 | 空机，客户内网 | **无外网** | 离线全量包 | `deploy.sh --offline` | `deploy.sh --offline --disk /dev/sdb --yes` |
| **C** | 已有环境·日常升级 | 已装过，统一布局 `/main/app` | 不限 | 增量包 zip | `deploy_jar.sh` | `deploy_jar.sh /tmp/update-*.zip` |
| **D** | 已有环境·全量升级 | 已装过 | 不限 | 全量 JAR | `deploy_jar.sh` | `deploy_jar.sh /tmp/time-bucket-demo.jar` |
| **E** | 只重装应用 | 依赖/MySQL 已就绪 | 不限 | 全量包 | `install.sh` | `install.sh --base /main/app` |
| **F** | 老布局迁移 | `/opt` + `/data` 旧布局在跑 | 不限 | 全量包 | `migrate-to-main-app.sh` | dry-run → 执行（见 `服务器文件布局.md` §15） |

> 场景 A/B 是**宿主机级**部署（装依赖、挂盘、装 MySQL）；C/D/E 是**应用级**部署（替换 JAR/classes）。
> 判断当前是哪种布局：`findmnt -n -o TARGET,SOURCE /data /main`。老布局**不要直接跑 install.sh**。

### 场景选择决策树

```
要部署到一台新机器吗？
├─ 是 → 机器能访问外网？
│        ├─ 能 → 场景 A（全量包 + deploy.sh 在线）
│        └─ 不能 → 场景 B（离线全量包 + deploy.sh --offline）
│        新机器是一块空盘还是要保留数据？
│        └─ 盘上已有 /opt+/data 老布局在跑 → 先走场景 F 迁移
└─ 否（已装过，只是更新）
         ├─ 只改了业务代码/前端，依赖没变 → 场景 C（增量包，推荐）
         ├─ 依赖/配置有大改，或增量合成失败 → 场景 D（全量 JAR）
         ├─ 只要重装应用，依赖和库都现成 → 场景 E（install.sh）
         └─ 还在老布局 /opt+/data → 场景 F（迁移到 /main）
```

## 4. 各场景部署流程

### 场景 A · 全新机在线一键

**前置**：独立数据盘（如 `/dev/sdb`）、外网可达软件源、已备好全量包。

```bash
# 1) 上传并解压（口令走环境变量/600 临时文件，不进命令行历史）
scp camera-detection-system-<版本>.tar.gz <user>@<server>:/tmp/
ssh <user>@<server>
sudo tar -xzf /tmp/camera-detection-system-<版本>.tar.gz -C /tmp
cd /tmp/camera-detection-system

# 2) 一键部署（数据盘必须 --disk 显式指定，不自动猜盘）
sudo bash scripts/deploy.sh --disk /dev/sdb \
  --db-password '<库口令>' --app-password '<管理员口令>'
```

`deploy.sh` 串起 8 个**幂等**阶段：
`p1 依赖 → p2 挂盘 → p3 时区 → p4 MySQL → p5 应用 → p6 建库 → p7 调优+口令落库 → p8 验收`。
中途失败按日志提示 `--from pN` 续跑（不会重做已完成阶段），全过程写
`/var/log/camera-detection-deploy.log`，最后成功阶段记在 `/var/lib/camera-detection/.deploy-state`。

**关键行为**：
- 盘已挂 `/data` 且为空（只剩 `lost+found`）→ 自动改挂 `/main`；非空则拒绝，给出迁移/umount 两条出路。
- 建库按 `01→05` 顺序导入（`02` 会 DROP 重建 21 张表，**仅空库执行**）；06 为幂等补丁，07 由应用启动补建。
- 管理员口令在 p7 真正落库；p8 验收失败返回非零（不再静默通过）。

### 场景 B · 全新机离线一键（无外网）

**前置**：先在**联网的 Ubuntu 22.04 amd64 构建机**生成离线全量包（一次性动作）。

```bash
# 构建机：生成离线依赖并打全量包
sudo bash installer/linux/fetch-offline-deps.sh        # 或 bash ... --docker（Windows 构建机）
bash installer/linux/build-release.sh                  # offline/ 自动并入

# 客户机：离线部署
sudo tar -xzf camera-detection-system-<版本>.tar.gz -C /tmp && cd /tmp/camera-detection-system
cp config/offline.env.example config/offline.env
# 编辑 config/offline.env：去掉 <> 占位，填 MYSQL_PASSWORD / ADMIN_PASSWORD，chmod 600
sudo bash scripts/deploy.sh --offline --disk /dev/sdb --yes
```

**关键行为**：
- p0 校验包内 deb 的 `manifest.sha256`；p1 只用 `dpkg` 从 `offline/debs/` 本地装，**全程不联网**。
- p1 末尾硬校验 `mysql/mysqldump/mysqlbinlog/rsync/zstd/curl` 真存在，缺一个即停，不留「装一半」的现场。
- `--offline` 口令走 `config/offline.env`（离线口令是允许的交付方式）；部署后口令已写入服务器
  `/etc/default/camera-detection`（640 root），把 `config/offline.env` 从发布目录删除即可。
- `--skip-apt`：依赖已由运维预装时跳过 p1，仅做就绪校验。
- **边界**：离线 deb 是 Ubuntu 22.04/amd64 专属，目标机版本/架构不同须重新生成。

### 场景 C · 已有环境日常升级（增量包，推荐）

**前置**：已装过系统、统一布局、依赖指纹与线上一致。

```bash
# 构建机：产出增量包
bash installer/linux/build-release.sh --update-only

# 服务器：deploy_jar.sh 按扩展名自动识别
SUDO_PASSWORD='<sudo口令>' bash deploy_jar.sh /tmp/update-*.zip
```

增量包只含 `BOOT-INF/classes/**`（自研类 + 前端，约 2MB，**含目录条目**，否则类不进 classpath）。
服务器与线上 fat jar 在线合成，依赖指纹一致才允许；合成成功才停服替换，合成失败**不碰服务**。
依赖指纹变化时明确报错 → 改走场景 D。

### 场景 D · 已有环境全量升级

```bash
SUDO_PASSWORD='<sudo口令>' bash deploy_jar.sh /tmp/time-bucket-demo.jar
# 备份 → 停服 → 原子替换 → 启动+健康检查 → 失败自动回滚
```

升级后如需让旧页面继续可用（恢复历史前端 chunk）：

```bash
sudo python3 recover_legacy_chunks.py      # 从历史 JAR 备份恢复，增量写不破坏 MANIFEST
sudo python3 prune_legacy_chunks.py 3      # 按版淘汰，保留最近 3 版
sudo systemctl restart camera-detection    # 必须重启才生效
```

> 顺序：**部署完成后**才执行恢复，且执行完必须重启；禁止用 `jar cf` 重打包 Spring Boot JAR。

### 场景 E · 只重装应用

依赖和 MySQL 已就绪时，无需跑完整的 `deploy.sh`：

```bash
tar -xzf camera-detection-system-<版本>.tar.gz && cd camera-detection-system
sudo env MYSQL_PASSWORD='<库口令>' bash scripts/install.sh --base /main/app
# MySQL 未就绪时脚本装完应用后以 DB_PENDING 退出（退出码 1 ≠ 失败），可二次执行
```

### 场景 F · 老布局迁移到统一布局

旧布局（`/opt/camera-detection-system` + `/data/camera-detection` + `/var/lib/camera-detection-system`）
不要直接跑 `install.sh`，走 `migrate-to-main-app.sh`（默认 dry-run、可回滚、支持断点续跑）。
**完整步骤与实测数字见 [`服务器文件布局.md`](服务器文件布局.md) 第十五节**，此处不重复。

## 5. 部署后验证与验收

### 5.1 必跑验证

```bash
# 统一自检（45 项，root + 正确口令）
sudo env VERIFY_PASSWORD='<应用口令>' MYSQL_PASSWORD='<库口令>' \
  bash /main/app/dist/scripts/verify.sh

# 授权交付时另跑（+4 项断言，写 licenseSelfCheck.json）

  bash /main/app/dist/scripts/verify.sh --delivery

# 对应浏览器回归脚本（按本次变更选，如产线统计、日报、授权）
node docs/scripts/verify_line_analytics_browser.cjs
```

### 5.2 验收 DoD（五项全满足才算交付完成）

| 维度 | 判据 |
|---|---|
| 功能 | 需求状态「已实现」，追溯矩阵指向具体端点/页面/SQL |
| 质量 | 后端 `mvn -B test`、前端 `npm test`/`lint`/`build` 全绿；浏览器回归 0 JS 错误 |
| 口径 | 统计类与 PRD 的分母/分子/时间窗逐项对齐；多选、空数据、无样本三态有断言 |
| 现场 | `verify.sh` 45 项全绿（授权交付另跑 `--delivery`、四项断言全绿且 `overall=PASS`）；可回滚；cron/systemd 已同步现场文件；**无 `ZZTEST*` 残留** |
| 交付件 | PRD/方案/测试/评审/发布记录/验收单齐全并归位；一次性文档已入 `archive/`；git 推送已获显式授权 |

## 6. 授权交付线（与主程序分开）

新机默认 TRIAL（60 天 / 30 相机），正式交付走离线四步：

| 步 | 动作 | 执行方 | 门禁 |
|---|---|---|---|
| ① 定档 | 商务给单号、客户、期限、相机数、过期策略 | 客户 / PO | 写进合同 |
| ② 生成机器码包 | 页面「服务器授权 → 下载机器码包」回传研发 | 客户运维 | 校验 `MANIFEST.sha256` |
| ③ 签发授权包 | `issue_license.py issue` + `inspect` 自检 + 台账登记 | 研发（厂商机） | 用 `--secret-file`，载荷 v2，字段与合同逐项一致 |
| ④ 导入授权 | 页面预览 → 确认导入；无浏览器时手工投放 + reload | 客户运维 | 验签通过、状态 `VALID`、旧件备份、零重启 |

- **一客户一密钥**，密钥只存厂商 `secrets/`（600），客户侧无密钥文件。
- **切 `LICENSE_SECRET` 前必须完成存量授权迁移**（现场默认密钥自签的授权会立即失效），按
  [`templates/10-客户密钥台账模板.md`](templates/10-客户密钥台账模板.md) 五步序执行。
- 客户操作见 [`templates/09-客户版授权交付手册.md`](templates/09-客户版授权交付手册.md)，协议字段见
  [`服务器授权设计.md`](服务器授权设计.md)。

## 7. 回滚与恢复

| 情况 | 处置 |
|---|---|
| 升级后服务异常 | `sudo bash /main/app/dist/scripts/service.sh rollback [版本]`（推荐统一入口）；或 `deploy_jar.sh` 已自动回滚 |
| 需要恢复数据库 | `restore-database.sh --latest --verify --compare-with wms-new` 恢复到**临时库**逐表比对，目标库白名单只允许 `restore_check_*`/`ZZTEST_*`，绝不覆写生产库 |
| 授权导入失败 | 旧件已自动备份 `license.lic.bak-<时间戳>`，换回即可；或临时切 `warn` 重启 |
|  migrating 中断 | `migrate-to-main-app.sh` 支持断点续跑，按提示继续 |

> 备份链路（每日 01:00）：DB 全量 14 份 + binlog 14 天 + 近 30 天图片 + 跨盘副本；
> `/var/backups/camera-detection` 是唯一抗单盘故障的副本，**绝不删**。备份有效性只有演练能回答，建议每月 `--verify` 一次。
