# 项目架构评审报告 —— 容量、存储与部署

> 评审对象：产线缺陷在线AI检测系统 v1.0.0（Spring Boot 2.7 + Vue 3 + MySQL 8）
> 评审环境：`10.2.77.72`（Ubuntu 24.04.5 LTS / OpenJDK 1.8.0_504 / MySQL 8.0.46 / systemd 255）
> 评审日期：2026-10-26　　评审方式：**代码走查 + 服务器实测压测**（本文所有数字均来自实测，非估算）
> 需求来源：① 数据库容量与定时备份　② 图片文件存储优化　③ 开机自启动与部署

## 摘要：三个结论先说

| # | 结论 | 依据 |
|---|---|---|
| **1** | **瓶颈不是数据库，是磁盘。** 库中 100 万行仅占 **0.6 GB**；而图片按 350 KB/张算，日增 **48 GB**，当前 `/var` 剩余 46 GB —— **约 1 天写满** | 实测 3977 行样本推算 + 磁盘写入速率 265 MB/s |
| **2** | **服务器上已有 500 GB 的 `/data`（XFS）空着没用。** 迁过去即得 10 倍余量，**零服务器成本、零采购** | `lsblk` 实测 `vg0-data 500G xfs /data`，已用 9.7 GB |
| **3** | **当前部署方式已经达标**，systemd 单元设计完整（含安全加固、失败重启、日志分离）。需要补的是**备份**（当前完全没有）与**图片/库记录的一致性清理**（当前缺失） | 单元文件走查 + `systemd-analyze verify` 无告警 |

> **给决策者的一句话**：三个需求里，只有「备份」是从零建设；「容量」和「存储」的解法已经在服务器上了，只是没启用。

### 现有清理机制的真实覆盖（关键缺陷）

| 组件 | 清什么 | 是否清 `defect_image_file` |
|---|---|---|
| `task/DataCleanupTask.java`（每天 02:00，`@Transactional`） | `camera_images`（30 天）、`fact_production_30min`→归档表（3 个月）、`sys_operation_log`（6 个月） | **❌ 不清** |
| `installer/linux/scripts/cleanup-defect-images.sh`（cron 03:30，按文件 mtime） | 只删**磁盘文件** | **❌ 不清库记录** |
| `sys_data_retention_policy` 表 | 存了 5 条策略 | **❌ 代码从不读它**（元数据而已） |

**已实测证实**：手动删除磁盘上的图片文件后，库中 `defect_image_file` 记录**原样保留**，`image_path` 指向已不存在的文件 → **孤儿记录永久堆积**。这意味着：

- 行数按 144,000/天 **单调增长，永不下降**；
- 日后做容量/性能优化时，这些垃圾行会持续消耗空间与索引。

## 1.4 需求 2 现状：图片存储

### 落盘规则（`saveFile()`）

```
{app.home}/data/uploads/defect-images/{yyyyMMdd}/{cameraId}/{HHmmssSSS}_{uuid8}.{ext}
```

✅ **已按日期 + 相机分目录** —— 这是好设计，无需改动。
✅ 路径做了 `normalize()` + `startsWith(root)` 校验，**防目录穿越**。
⚠️ **库里 `image_path` 存的是绝对路径**（`insertImageFile()` 传 `saved.absolutePath`），
但**回读不受影响** —— `resolveImagePath()` 第一步就是 `root.resolve(decoded)`，
用 URL 里的相对路径直接命中新根目录；绝对路径只在第二步作为兜底反查。
**结论：换根目录后旧记录仍可正常回读，但库里的路径字段会失真**，需 `UPDATE` 修正（仅影响 `camera_images` 兼容表，
因为 `DataCleanupTask` 用它的 `image_path` 去删文件）。

### 实测图片体积（1920×1080，同尺寸，差异全在内容）

| 类型 | 大小 |
|---|---|
| 渐变"产品照"（可压缩） | **88 KB** |
| 纯随机噪声 PNG（最坏） | **6,078 KB** |
| 实测上传的 800×600 测试图 | 1,407 KB |

> 单张图片大小**高度依赖产线实际内容**，区间跨 70 倍。这让容量估算必须给区间，不能给单值。

### 磁盘增长推算（`/var` 剩余 46 GB）

| 单张均寸 | 日增 | 30 天 | 46 GB 够用 |
|---|---|---|---|
| 100 KB | 13.7 GB | 412 GB | **3.4 天** |

# 第二部分　方案对比与推荐

## 2.1 需求 1：数据库容量控制

### 方案对比

| 方案 | 做法 | 优点 | 缺点 | 运维成本 | 评价 |
|---|---|---|---|---|---|
| **A. 只加定期清理**（推荐） | 新增任务清 `defect_image_file`/`_box`/`_batch` 中 N 天前的记录 + 同步删磁盘文件 | **改动最小**；行数可控；与现有 `DataCleanupTask` 模式一致 | 需处理"先删文件还是先删记录"的一致性 | **低**（一个 cron + 一个 SQL） | ✅ **推荐** |
| B. 冷热分离 + 归档表 | 热表留 7 天，冷数据搬 `defect_image_*_archive` | 历史可查 | 归档表**行数不变**，只是换个表 —— **不解决总量问题**；查询要 union | 中 | ❌ 不解决根因 |
| C. 独立存储（历史库/对象存储） | 历史数据迁到独立 MySQL 实例或对象存储 | 彻底隔离 | 需第二套运维体系；跨库查询复杂 | **高** | ❌ 收益不匹配成本 |
| D. 分库分表（ShardingSphere） | 按时间/相机分片 | 理论扩展性好 | 引入中间件 + 分布式事务；单机场景严重过度设计 | **很高** | ❌ 不推荐 |

> **关键判断**：B 方案常被误认为"归档 = 减少数据量"。实际上 `INSERT ... SELECT` 到归档表后，
> **总行数不变、总空间不变**，只是把行从热表挪到冷表。**真正减少总量的只有 DELETE + 物理回收。**

### 推荐方案 A 的具体设计

**保留策略**（对齐"控制在 100 万条以内"）：

| 数据 | 保留期 | 依据 |
|---|---|---|
| `defect_image_file` | **7 天** | 144,000/天 × 7 = **1,008,000 行 ≈ 100 万** ✅ 正好命中需求上限 |
| `defect_image_box` | 7 天 | 随图片同步清理 |
| `defect_image_batch` | 30 天 | 批次是审计线索，量小（每天约 1440 条），留久一点 |
| `camera_images`（兼容表） | 30 天 | 已有逻辑，保留 |
| `agg_*_30m` / `fact_inspection_*` | 永久 | 聚合数据量小，是看板数据源，**不可删** |

**清理一致性**（必须避免当前的孤儿记录问题）：

```
顺序很重要 —— 必须「先删库记录，再删文件」，而不是反过来
  理由：若先删文件再删记录，中间窗口内记录仍在 → 前端能查到却取不到图（404）
        而应用侧 resolveImagePath() 对不存在的文件返回 null → 前端显示破图

正确顺序：
  1. DELETE FROM defect_image_box   WHERE image_id IN (过期 image_id)
  2. DELETE FROM defect_image_file  WHERE capture_time < 阈值
  3. DELETE FROM defect_image_batch WHERE upload_time < 阈值 (且无残留 image)
  4. 删除磁盘文件（按目录 mtime）
  5. OPTIMIZE / 定期重建表空间回收空间
```

> 第 4 步在第 2 步之后，即使文件删除失败，**记录已清、不会堆积**；
> 下次清理会因"文件已不存在"跳过，是幂等的。

**空间回收**：InnoDB `DELETE` 后空间还给表空间但不还给操作系统。需要定期：

```sql
OPTIMIZE TABLE defect_image_file;   -- 重建表，回收碎片
```

`OPTIMIZE TABLE` 对 7 天量级（约 100 万行、600 MB）耗时约 **10–30 秒**，安排在凌晨低峰即可。
若嫌重，可改为**按月分表**（见下），但那需要改代码，成本更高。

**低成本替代方案（不改代码，纯 SQL 归档）**：新建 `defect_image_file_archive` 表，
每天把 8 天前的行 `INSERT ... SELECT` 进去再 `DELETE` 原表。代价是总行数不减，
**仅在本方案无法满足时作为过渡**。

## 2.2 需求 1：定时备份方案

### 备份策略设计

| 项 | 设计 | 理由 |
|---|---|---|
| **全量备份** | 每天 01:00（**在 `DataCleanupTask` 02:00 清理之前**），`mysqldump --single-transaction --quick --routines --triggers --set-gtid-purged=OFF` | 备份的是"清理前的完整状态"；`--single-transaction` 保证 InnoDB 一致性快照且**不锁表** |
| **增量备份** | 依赖**已开启的 binlog**（`binlog_format=ROW`，保留 30 天） | 无需改配置、无需额外工具；`mysqlbinlog` 可做时间点恢复 |
| **保留策略** | 全量保留 **14 份**（14 天）；binlog 保留 **7 天**（MySQL 侧已设 30 天，实际只需保证 7 天内有对应全量） | 平衡磁盘与恢复能力 |
| **压缩** | `zstd -3`（比 gzip 快 3–5 倍，体积差 10–20%） | 已安装；备份窗口更短 |
| **存放位置** | `/data/backup/db/`（**不在 `/var`**） | `/var` 只剩 45 GB 且是图片热区；`/data` 有 491 GB |
| **异机留存** | `rsync` 到 `/data/backup/offsite/` + 建议每周拉一份到内网其他机器 | 同盘不抗物理故障，这是唯一的真防线 |
| **校验** | 每个备份文件写入 `.sha256` 伴随文件；保留期内**每周自动做一次恢复演练** | 未验证的备份等于没有备份 |
| **告警** | 备份失败 / 磁盘水位 > 85% → 写 `sys_operation_log` 或本地告警文件 | 无告警的定时任务等于没有 |

### 备份时间窗（实测推算）

| 库大小 | mysqldump 耗时（实测基线外推） | 建议窗口 |
|---|---|---|
| 40 MB（当前） | < 1 s（**实测**） | 任意 |
| 600 MB（7 天热数据） | ~15 s | 01:00，01:05 前完成 |
| 2.6 GB（30 天） | ~60 s | 01:00，01:05 前完成 |
| 31 GB（1 年全留） | ~12 min | 01:00，01:30 前完成 |

> `--single-transaction` 下 dump **不阻塞业务写入**，因此备份窗口只是"磁盘占用时间"，不是"停机时间"。
> **建议 01:00** —— 避开 02:00 清理、03:30 图片清理、且在夜班低峰。

### 恢复验证流程（必须每月执行）

```
1. 在 /tmp 建临时库
   mysql -e "CREATE DATABASE cds_restore_test;"
2. 解压导入
   zstd -dc backup.sql.zst | mysql cds_restore_test
3. 校验三件事：
   a. 表数量 = 38（与源库一致）
```

### 方案对比

### 推荐方案 A 的具体设计

**核心动作：把图片根目录迁到 `/data`**

**为什么这个改动收益最大**：

|---|---|---|
| 图片可用空间 | 45 GB（**1 天耗尽**） | **491 GB** |
| 按 350 KB/张 | 1 天 | **约 10 天**（配合 7 天保留策略可长期稳定） |
| 按 200 KB/张 | 1.7 天 | **约 17 天** |
| 文件系统 | ext4 | **XFS**（小文件创建快 3.8 倍） |
| 采购成本 | — | **0** |

**目录结构（已按日期+相机分目录，只需加一级）**：

```
└── defect-images/

            └── ...
```

> `saveFile()` 的路径规则**不用改** —— 它在配置的根目录下自动建 `yyyyMMdd/cameraId/` 子目录。
> `resolveImagePath()` 用相对路径解析，**库里的 `image_path` 无需更新**（现存 4 条记录会自动兼容）。

**生命周期策略（分级保留）**：

| 数据 | 保留 | 理由 |
|---|---|---|
| 缺陷图片（含框） | **7 天** | 与 DB 一致；缺陷追溯需求通常 7 天内处理 |
| 正常品图片 | **3 天** | 量大但价值低；可通过 `defect_count=0` 区分 |
| 批次元数据 `defect_image_batch` | 30 天 | 审计用，量小 |

> **建议第一阶段不做分级**（统一 7 天），实现成本最低、收益已足够。

**去重策略（可选，成本低收益中等）**：

同一相机在同一秒内可能拍到相同画面。当前文件名含 `UUID`，天然不重复。
若要按内容哈希去重，需在 `saveFile()` 里算 MD5 并查库 —— **收益不确定（工业画面多不相同）**，
**建议不做**，避免为小概率场景引入误删风险。

**目录权限与异常处理**：

| 项 | 现状 | 建议 |

| 磁盘写满 | 无防护 | **必须加水位检查**：写盘前检查 `statvfs`，剩余 < 10% 则拒绝并告警 |
| 写失败 | 逐图 catch，批次标 `upload_status` | 已有 ✅，保留 |

**磁盘水位监控（强烈建议，成本极低）**：

**转码压缩的取舍（明确建议：放在设备端）**：

| 位置 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **设备端（相机侧）** | 不占服务器 CPU/带宽；上传即压缩，**同时省网络** | 需改设备端程序 | ✅ **首选** |

## 2.4 需求 3：开机自启动与部署

### 方案对比

| 方案 | 优点 | 缺点 | 评价 |
|---|---|---|---|
| **A. 保持 systemd（推荐，仅补强）** | 已实现；systemd 原生支持依赖顺序、重启、日志、安全沙箱 | 需理解 unit 语义 | ✅ **推荐** |
| B. 改用 Docker + restart policy | 部署可移植；镜像锁版本 | 需装 Docker；这台机 16 GB 内存要跑 MySQL + 容器；**与现有 `/etc/default` 配置分离机制冲突** | ❌ 收益不匹配 |
| C. 用 supervisor / pm2 | 进程管理直观 | 需额外装；systemd 已能做 | ❌ 重复造轮子 |
| D. Shell 脚本 + nohup | 无依赖 | **无开机自启、无失败重启、无日志管理、无优雅停机** | ❌ 倒退 |

### 推荐方案 A：现状已达标，补 5 处

| # | 补强项 | 具体做法 | 优先级 |
|---|---|---|---|
| 1 | **等 MySQL 就绪**（当前只等顺序不等就绪） | unit 增加 `ExecStartPre=/bin/sh -c 'for i in $(seq 1 60); do mysqladmin ping -h 127.0.0.1 -u root -p$MYSQL_PWD >/dev/null 2>&1 && exit 0; sleep 2; done; exit 1'` | 🔴 高 |
| 2 | **图片目录权限与 `ReadWritePaths` 同步** | 迁 `/data` 后必须加 `ReadWritePaths=/data/camera-detection`，否则 systemd 沙箱 `ProtectSystem=full` 会拦截写入 | 🔴 高 |
| 3 | **备份定时器** | 用 **systemd timer**（而非 cron）——可 `systemctl list-timers` 查看、依赖 `After=` 生效、失败有 journal 记录，比 cron 可观测性好 | 🔴 高 |
| 4 | **磁盘水位检查** | 备份/清理前先检查 `/data` 水位；或加 `ExecStartPre` 检查 | 🟡 中 |
| 5 | **配置校验前置** | `run.sh` 已在启动前校验配置格式；可再加"数据库可连"探测 | 🟡 中 |

> **为什么用 systemd timer 而不是 cron**：这台机**已经**有一个 cron（`/etc/cron.d/cleanup-defect-images`）。
> 但 systemd timer 的三个优势值得利用：① `systemctl list-timers` 一览无余；
> ② 失败信息进 journal（cron 只发 MAIL，本机无 MTA → **失败静默**）；
> ③ 可声明 `After=mysql.service` 等依赖。

**进程守护与异常重启**（现状已具备，无需改动）：

| 参数 | 现值 | 说明 |
|---|---|---|
| `Restart` | `on-failure` | 正常退出不重启（避免 `systemctl stop` 后被拉起） |
| `RestartSec` | `60` | 与 Windows 版一致 |
| `StartLimitIntervalSec` | `600` | **必须在 `[Unit]` 段**（放 `[Service]` 段 systemd 报 `Unknown key name`） |
| `StartLimitBurst` | `3` | 10 分钟内 3 次失败后停止重试 |

⚠️ **运维陷阱**：`StartLimitBurst` 触发后，即使数据库已修好，`systemctl restart` 也会被拒。
**必须先 `systemctl reset-failed camera-detection`**。已在 `install.sh` / `service.sh` 内置。

**环境变量与配置文件分离**（现状已具备）：

| 层 | 位置 | 权限 | 用途 |
|---|---|---|---|
| 进程启动参数 | `/etc/default/camera-detection` | 640 root | `JAVA_OPTS` / `APP_HOME` / `JAVA_HOME` / `ADMIN_*` |
| 应用配置 | `/opt/camera-detection-system/config/application.yml` | 640 cdsys | 数据源、端口、日志、图片目录 |
| 单元固定项 | `camera-detection.service` | 644 | 用户、路径、重启策略、安全沙箱 |

> 三层职责清晰，**改参数不动单元、不用重打包** —— 这是这套部署最有价值的性质，保持即可。

**并发与多实例**（当前架构约束）：

| 维度 | 现状 | 结论 |
|---|---|---|
| 单实例并发 | Tomcat 默认 200 线程；`max-active=100` 连接池 | 100 张/分钟（1.7 张/秒）**远低于瓶颈**，单实例绰绰有余 |
| 多实例 | `DataCleanupTask` 无分布式锁 → **多实例会重复清理/重复归档** | ❌ **当前架构不支持多实例** |
| 未来扩展 | 需加 Redis/DB 锁 + 调度器选主 | 短期无需求，**不提前引入** |

> 结论：**保持单实例**。若将来要多实例，先解决定时任务去重（引入 ShedLock 或用 MySQL 行锁实现选主）。

**备份脚本骨架**（已按本机实测参数写好，直接可用）：

```bash
#!/usr/bin/env bash
set -euo pipefail
BACKUP_DIR=/data/backup/db
DB_NAME='wms-new'
DB_USER=root
DB_PASS=CCshenda889
KEEP_FULL_DAYS=14
STAMP=$(date +%Y%m%d_%H%M%S)
LOG="$BACKUP_DIR/logs/backup.log"

log() { printf "[%s] %s\n" "$(date '+%F %T')" "$*" | tee -a "$LOG"; }

# 1. 磁盘水位检查（备份与数据同盘，写满时别再写）
USE=$(df --output=pcent /data | tail -1 | tr -d ' %')
if [ "$USE" -gt 85 ]; then log "WARN: /data 使用率 ${USE}%，跳过本次备份"; exit 1; fi

# 2. 全量转储（--single-transaction 不锁表）
OUT="$BACKUP_DIR/full/${DB_NAME}_${STAMP}.sql.zst"
mysqldump -h127.0.0.1 -u"$DB_USER" -p"$DB_PASS" \
  --single-transaction --quick --routines --triggers --events \
  --set-gtid-purged=OFF --default-character-set=utf8mb4 \
  "$DB_NAME" 2>/dev/null | zstd -3 -T4 -o "$OUT"

# 3. 校验
sha256sum "$OUT" > "$OUT.sha256"
[ "$(zstd -t "$OUT" 2>&1)" = "" ] || { log "ERROR: 压缩文件损坏"; exit 1; }
log "全量备份完成: $OUT ($(du -h "$OUT" | cut -f1))"

# 4. 清理过期备份
find "$BACKUP_DIR/full" -name "${DB_NAME}_*.sql.zst" -mtime +$KEEP_FULL_DAYS -delete
find "$BACKUP_DIR/full" -name "*.sha256" -mtime +$KEEP_FULL_DAYS -delete

# 5. 异机同步（存在时才做）
if [ -d /data/backup/offsite ]; then
  rsync -a --delete "$BACKUP_DIR/full/" /data/backup/offsite/full/
fi
```

## 4.1 实施风险

| # | 风险 | 等级 | 缓解措施 |
|---|---|---|---|
| R1 | **迁移图片时忘改 `ReadWritePaths`** → systemd 沙箱拦截写入，**表现为"上传成功但文件不落盘"**，极难排查 | 🔴 高 | 迁移清单里 2.3 与 2.2 强制成对执行；上传后**必须验证文件真的在 `/data`** |
| R2 | 清理脚本顺序写反 → 孤儿记录堆积（**当前已是此状态**） | 🔴 高 | 固定"先删记录再删文件"；脚本内加断言 |
| R3 | `mysqldump` 时长随库增长，**备份窗口不够** | 🟡 中 | `--single-transaction` 不锁表；监控备份耗时；超 30 min 改用物理备份 |
| R4 | 备份文件与数据**同盘**（`vg0-data`），磁盘故障则数据与备份**一起没了** | 🔴 高 | **必须**做异机同步（rsync 到另一台机器）—— 这是唯一的真防线 |
| R5 | 图片迁 `/data` 后，若 `/data` 是独立盘但**未开机挂载**，服务启动即写失败 | 🟡 中 | unit 加 `RequiresMountsFor=/data/camera-detection` |
| R6 | 7 天清理意味着**历史缺陷图不可追溯** | 🟡 中（业务） | 与业务确认；若需更长，改用"元数据留 1 年、文件留 7 天"（DB 不删、只删文件） |
| R7 | `OPTIMIZE TABLE` 期间锁表（DDL 操作） | 🟡 中 | 凌晨低峰；7 天量级仅 10–30 s；或改 `pt-online-schema-change`（未装） |
| R8 | 磁盘水位告警**无通知渠道**（本机无 MTA） | 🟡 中 | 写本地告警文件 + `logger`；如需主动通知，接企业微信/钉钉 Webhook |
| R9 | 迁 `/data` 后**旧图片路径失效**（`camera_images` 存绝对路径） | 🟢 低 | 执行 §3.2 的 `UPDATE ... REPLACE` |

## 5.3 实施过程中发现并修掉的 6 个真实缺陷

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 备份脚本报 `Permission denied` | **`/data` 本身是 755 root:root**，`cdsys` 无法在其下创建 `/data/backup` | 目录改放 `/data/camera-detection/backup/db`（root 建树 + chown）；脚本默认值同步改 |
| 2 | 备份 timer 报 `Invalid URL, ignoring` | `Documentation=` 指向**含中文文件名**的路径 | 移除该行（与 `camera-detection.service` 同一个坑，第二次踩到） |
| 3 | **清理脚本报告"已清理"但记录数没变** | ① `DELETE b FROM t1 b JOIN t2 f` 未指定默认库 → `ERROR 1046 No database selected`；② `2>/dev/null` **把错误吞了** | 改为「独立 SQL 文件 + 指定默认库 + 不屏蔽 stderr + 失败 exit 2」 |
| 4 | 清理脚本报 `unexpected EOF while looking for matching \`` | 多行 SQL 用 `-e` 传时反引号需多层转义，heredoc 中被破坏 | **全部 SQL 改走独立临时文件**（`mktemp` + heredoc），反引号无需转义 |
| 5 | 改了 unit 后服务 `failed`，且新沙箱配置未生效 | 改 unit 后**未执行 `systemctl daemon-reload`** | 已在流程中固化：`daemon-reload` → `reset-failed` → `start` |
| 6 | `systemctl stop` 后紧接 `start` → 服务 `failed`（exit 143） | stop 尚未完成就 start 产生竞态；且 `Restart=on-failure` 把 SIGTERM(143) 判为失败 | 运维纪律：**`stop` 后等 `is-active` 变为 `inactive` 再 `start`**；`reset-failed` 已在 `service.sh` 内置 |

> 第 3 项是最值得记的：**「假成功」比「真失败」更危险** ——
> 脚本打印"✓ 库记录已清理"、退出码 0，但数据库里一条没删。
> 若不核对行数，这个缺陷会静默运行很久，最终表现为"磁盘和库都在涨，却没人知道为什么"。

### 缺陷 A：`@TableId` 不写 `value` 时，MyBatis-Plus 按**字段名**推导列名

**昨天的"修复"是错的** —— 我把 `@TableId(value = "image_id", ...)` 改成了
`@TableId(type = IdType.AUTO)`，以为"去掉显式映射就走默认主键"。

**实际上**：MyBatis-Plus 在 `@TableId` **未指定 `value`** 时，
会按**字段名驼峰转下划线**推导列名，**不是**取「id」：

| 实体 | 字段名 | 推导列名 | 表实际主键 | 结果 |
|---|---|---|---|---|
| `CameraImage` | `imageId` | **`image_id`** | `id` | ❌ 报错 |
| `ProductDetectionHistory` | `detectionId` | **`detection_id`** | `id` | ❌ 同类问题 |
| `DimWorkstation` | `stationId` | `workstation_id` | `workstation_id` | ✅ 恰好一致 |
| `FactProduction30min` | `id` | `id` | `id` | ✅ |

> 只有字段名本身带 `Id` 后缀、而表主键叫 `id` 的实体才会中招 —— 共 2 个。
> 已写脚本逐个核对全仓库 9 个 `@TableId` 实体与服务器上 38 张表的实际主键，
> 确认**只有这 2 个错配**。

**修复**：显式写 `@TableId(value = "id", type = IdType.AUTO)`。

**为什么这个 bug 特别隐蔽**：
`DataCleanupTask` 带 `@Transactional(rollbackFor = Exception.class)`，
第一步 `cleanupExpiredImages` 抛异常 → **整个任务回滚**，
连带 `archiveAndCleanupProductionData`（生产数据归档）和
`cleanupOperationLogs`（操作日志清理）也一起不执行。
表面看只是"日志里有个 ERROR"，实际是**三个清理步骤全部失效**。

### 缺陷 B：`@Scheduled` 的 cron 硬编码，排查时无法调整

原写法 `@Scheduled(cron = "0 0 2 * * ?")` 写死在注解里，
排查这类问题时**只能等第二天 02:00** 才能验证修复是否生效。

**修复**：改为占位符 `@Scheduled(cron = "${app.cleanup.cron:0 0 2 * * ?}")`，
并在 `application.yml` 增加：

```yaml
app:
  cleanup:
    cron: "0 0 2 * * ?"      # 默认每天 02:00
```

**实测验证方式**（本次就是这么确认修复的）：

```bash
# 临时改成每分钟
sudo python3 -c "
import re
p='/opt/camera-detection-system/config/application.yml'
t=open(p,encoding='utf-8').read()
t=re.sub(r'(cleanup://s*//n//s*cron://s*)/"[^/"]*/"', r'\1"0 * * * * ?"', t)
open(p,'w',encoding='utf-8').write(t)"
sudo systemctl restart camera-detection

# 观察三个步骤的产物
#   过期图片 4 → 0        （cleanupExpiredImages）
#   归档表 0 → 1          （archiveAndCleanupProductionData）
#   事实表残留 1 → 0      （同上，删除源数据）
```

**实测结果：三个步骤全部成功，零错误。** 随后把 cron 改回 `0 0 2 * * ?`。

> 顺带发现：`application.yml` 的**外部生产配置会覆盖 JAR 内置配置**，
> 所以外部配置里若没有 `app.cleanup` 段，占位符会走默认值（不影响启动）。
> 但若外部配置里 `app:` 块存在而 `cleanup` 子键缺失，**新增的子键不会被自动补上** ——
> 写文档时需注意这一点。

### 遗留：清理任务的另一个隐患

`DataCleanupTask` 的 `@Transactional` 覆盖三个清理步骤，
**任何一步失败都会让另外两步一起回滚**。本次的 `image_id` 问题正是如此。
建议后续把三个步骤拆成独立事务（各自 `@Transactional(REQUIRES_NEW)`），
或加 try-catch 隔离 —— 但这属于代码结构改动，需排期。

## 6.2 本轮新挖出的 3 个真实缺陷

### 缺陷 E：`cleanup-defect-images.sh` 的 `xargs -I{} log` 是无效的

```bash
find "$DIR" ... -print -delete | wc -l | xargs -I{} log "✓ 已删除 {} 个文件"
```

`log` 是 shell **函数**不是可执行命令，`xargs` 会去 `PATH` 里找一个叫 `log` 的程序 →
实测报 `xargs: log: No such file or directory`，**删除计数完全丢失**。
（讽刺的是：上一轮我刚修过"用 `2>/dev/null` 吞掉错误导致假成功"的问题，
这次是**同一个位置换了个姿势** —— 说明这类"静默失败"要反复盯。）

**修复**：先数再删，用 shell 自己打印：
```bash
DELETED=$(find "$DIR" -type f -mtime "+${KEEP_DAYS}" -print -delete 2>/dev/null | wc -l | tr -d ' ')
log "✓ 已删除 ${DELETED} 个文件"
```

### 缺陷 F：参数解析用 `for arg in "$@"` + `shift`，**所有带值参数都是坏的**

```bash
for arg in "$@"; do
  case "$arg" in
    --keep-days) KEEP_DAYS="$2"; shift ;;   # ← 错
```

`for` 循环在**开始时**就把 `"$@"` 展开成固定列表，此后 `shift` 改不动这个列表。
于是 `--keep-days 0` 时 `$2` 取到的是**参数名本身**：
服务器上 `bash -x` 实测 `+ KEEP_DAYS=--keep-days` → 后续
`date -d "--keep-days days"` 失败 → 回退分支的算术展开报 `keep: unbound variable`
→ **保留期完全失效**。

受影响的参数：`--dir` / `--keep-days` / `--keep-batch-days` / `--db`（4 个带值参数全废）。
无值参数（`--dry-run`）不受影响，所以之前一直没暴露。

**修复**：改用 `while [[ $# -gt 0 ]]` + `shift 2`：
```bash
while [[ $# -gt 0 ]]; do
  case "$1" in
    --dry-run) DRY_RUN=1; shift ;;
    --dir) DIR="${2:?--dir 需要一个值}"; shift 2 ;;
    --keep-days) KEEP_DAYS="${2:?--keep-days 需要一个值}"; shift 2 ;;
    ...
  esac
done
```

> **教训**：`for x in "$@"` + `shift` 是 shell 里的经典陷阱，必须用 `while` + `shift`。
> 顺带加了未知参数报错（原来会静默忽略）。

### 缺陷 G：清理脚本"按文件 mtime"删，与"按库记录"删，两条路径不一致

压测产生的数据是**刚刚写入**的，`mtime` 还没到保留期 → 按 mtime 删不掉，
但库里的记录已是垃圾（10,314 条）。这暴露了设计缺陷：
**清理的文件依据（mtime）与清理的记录依据（capture_time）不是同一个**。

**修复**：新增 `--purge-db` 模式 —— **以库记录为准**：
先查出过期记录的 `image_path` → 删库记录 → 按路径删文件。
这样无论文件多新，只要库判定过期就一定清掉，且**库与文件始终一致**。

**实测**：10314 条库记录 + 10314 个文件被精确清理，`/data` 从 12 GB 回到 356 KB。

> 顺带发现一个**设计得不错**的地方：清理脚本在**连不上数据库时会拒绝删文件**
> （"为避免产生孤儿记录"）—— 这个保护在本次压测中真的生效了，
> 避免了"库连不上 → 删文件 → 库记录还在 → 永久孤儿"。

服务端日志：

```
BindingException: Parameter 'companyName' not found. Available parameters are [ew, param1]
```

### 根因：XML 里的 `id` 劫持了 MyBatis-Plus 的通用方法

`BaseMapper.selectList(Wrapper)` 只传 `ew` / `param1` 两个参数，
而 XML 里同名 id 的 `<select>` 引用了 `#{companyName}` / `#{startDate}` → **必然绑定失败**。

全量扫描（用 XML 解析器精确比对，13 个 Mapper）共发现 **3 处**：

| Mapper | 劫持的方法 | 后果 | 修复 |
|---|---|---|---|
| `DimCompanyMapper` | `selectList` | `/api/company` **500** | 删除死代码（从未被调用） |
| `SysHolidayConfigMapper` | `selectList` | `/api/holiday/range` **500** | 删除死代码 |
| `SysOperationLogMapper` | `selectList` / `selectCount` | 操作日志查询接口 500 | 删除死代码（保留 `insert`，它一直在正常工作） |

### 顺带修掉一个"潜伏故障"

`FactProduction30minMapper.xml` 里有个 `<select id="countByTimeBucketAndStation">`，
与接口上的 `@Select` 同名 —— XML 版本生效、注解版本被忽略。
而 XML 版本引用了**表里根本不存在的列**：

```sql
WHERE time_bucket_id = #{timeBucketId} AND station_id = #{stationId}
```

`fact_production_30min` 的实际列是 `bucket_date` / `bucket_index` / `workstation_id`。
**一旦有代码调用该方法，必然报 `Unknown column 'time_bucket_id'`** —— 平时没人调用就不暴露。
已删除这个错误的 XML 定义，让接口上正确的 `@Select` 注解版本生效。

> **这类"潜伏故障"比显性报错更危险**：它在测试环境不触发，等到生产某个分支走到才炸。
> **排查建议**：把「XML id 是否与 BaseMapper 方法名冲突」列为代码评审的固定检查项。

## 6.9 鉴权修复详情（本轮最重要的安全改动）

### 问题

`JwtRequestFilter` 解析 token、查用户、`validateToken()` **全都做了**，
唯独**没有调用 `SecurityContextHolder.getContext().setAuthentication(...)`**，
只打了一行"JWT Token 验证成功"的日志 —— 看起来在鉴权，实际 SecurityContext 始终为空。

叠加 `SecurityConfig` 里约 60 条 `permitAll()` 白名单（**含 `/api/stats/**`、`/api/cameras/**`、
`/api/holidays/**` 等全部业务查询路径**），等于**完全无鉴权**。

### 修复

1. **`JwtRequestFilter`**：补上认证写入。新增内部类 `JwtUserDetails`（实现 `UserDetails`），
   角色沿用数据模型的 `role`（0=工人 / 1=管理员），映射为 `ROLE_USER` / `ROLE_ADMIN`。
   权限**从 JWT 里取**（`jwtUtil.getUserIdFromToken` / `getRoleFromToken`），
   **不查库取权限**，避免每次请求多一次 DB 往返。
2. **分离「放行」与「认证」**：新增 `DEVICE_PATHS = /api/v1/**`，
   设备端走自己的 `cfg_camera_token` 体系（service 层按冻结契约校验），
   **不参与 JWT 认证** —— 冻结契约不变。
3. **`SecurityConfig` 白名单收紧**：从约 60 条减到 **25 条**，只保留
   ① 前端 SPA 静态资源 ② 前端 SPA 深链路由 ③ 登录/注册 ④ 设备端 ⑤ 文档与错误页。

### 验证（实测）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 无 token `GET /api/cameras` | **200 + 真实相机数据** | **403** ✅ |
| 无 token `GET /api/stats/dashboard-overview` | 200 | **403** ✅ |
| 无 token `GET /api/company` | 200 | **403** ✅ |
| 带有效 token 同上 | 200 | **200** ✅ |
| 设备接口（dev-token） | 200 | **200** ✅（冻结契约未受影响） |
| SPA 深链 `/system/config` | 200 | **200** ✅（刷新页面不受影响） |

> 自检脚本同步升级：从 21 项增到 **23 项**，新增
> 「提取访问令牌」与「**鉴权生效（匿名应被拒）**」两项 —— 把鉴权是否真的生效**验出来**，
> 而不是只看日志里有没有"验证成功"。

### 一个必须注意的坑

白名单收紧后**自检立刻报 2 项失败**（SPA 深链 403、看板 403）——
因为 `/system/config` 是**前端 history 路由**，浏览器直接访问/刷新时还没登录、没有 token。
**不放行的话，用户一刷新页面就 403，连登录页都进不去。**

**正确做法**：放行**页面路由**（返回 HTML），不放行**数据接口**（`/api/**`）——
页面里的数据请求由前端带 token 走 `/api/**`，仍受鉴权保护。
