sudo bash scripts/migrate-to-main-app.sh --apply             # 执行

## 五、配置与密钥

唯一权威文件：`/etc/default/camera-detection`（`640 root:root`），由 systemd `EnvironmentFile` 注入，
7 个脚本 `source` 它。关键键：

```bash
BASE=/main/app            INSTALL_DIR=/main/app/dist      WORK_DIR=/main/app
APP_HOME=/main/app        DATA_BASE=/main/app/data        LOG_BASE=/main/app/logs
IMAGES_SRC=/main/app/data/images/defect-images            IMAGE_TRASH=.../images/.cleanup-trash
MYSQL_DATA_DIR=/main/app/data/mysql                       OFFSITE_BASE=/var/backups/camera-detection
JAVA_OPTS="-Xms512m -Xmx1024m"   JAVA_HOME=...            MYSQL_PASSWORD=...   JWT_SECRET=...
BACKUP_DIR=/main/app/data/backup/db   OFFSITE_DIR=/var/backups/camera-detection/db
```

三个覆盖点（优先级从高到低）：

1. `/etc/default/camera-detection`
2. `/main/app/dist/config/application.yml`（Spring 外部配置，按 key 合并）
3. JAR 内 `BOOT-INF/classes/application.yml`（兜底默认）

> 外部配置是「按 key 合并」：文件里没写的键走 JAR 内默认值。
> 查「实际生效值」先看外部文件，取不到再 `unzip -p app.jar BOOT-INF/classes/application.yml`。

## 六、图片路径规则

```
/main/app/data/images/defect-images/{yyyyMMdd}/{camera_code}/{HHmmssSSS}_{uuid8}.{ext}
```

- **`defect-images` 这一级不能改名**：`DefectImageServiceImpl` 的白名单按 `"/defect-images/"` 过滤，
  改名后所有读图请求 403。
- `{camera_code}` 是相机唯一标识（不是名称，现场有重名）。
- `.cleanup-trash` 必须与图片**同一文件系统**，清理才能用「先 `mv` 再 `rm -rf`」保证原子性。
- 改路径须同步 systemd `ReadWritePaths`。

| 类型 | 位置 | 保留 | 说明 |

## 十、数据库

- 库名 `wms-new`（**带连字符，SQL 里必须加反引号**，否则被解析成「wms 减 new」）。
- datadir `/main/app/data/mysql`，由 `zz-camera-detection.cnf` 指定；
  迁移后必须断言 `SELECT @@datadir` 生效。
- binlog 在 datadir 内，`log_bin=ON` / `ROW`；MySQL 侧 `binlog_expire_logs_seconds=2592000`（30 天）。
- 全新库建库：`/main/app/dist/scripts/init-database.sh`，按 01→05 顺序（缺 05 会导致清理保护集为空）。

漏配表现为「上传返回成功但文件不落盘」，极难排查。

## 十二、挂载与启动安全（本布局最关键的一条）

```ini
# /etc/fstab —— 用 UUID，绝不加 nofail
UUID=xxxx-xxxx  /main  ext4  defaults  0 2
```
```ini
# camera-detection.service
RequiresMountsFor=/main
```

原因：`/main` 若没挂上，它只是系统盘上的普通空目录，程序与数据会静默写进系统盘；
盘修好后一挂载就被"盖住"，表现为「数据全丢」且没有任何报错。
因此 **fstab 不加 `nofail` + unit 加 `RequiresMountsFor`**，让盘挂不上时服务直接启动失败。
`verify.sh` 第 3a 节会检查这两条。

## 十三、改路径联动清单（改一个路径必须同步 5 处）

1. `/etc/default/camera-detection` 的变量（`BASE`/`DATA_BASE`/`LOG_BASE`/`IMAGES_SRC`…）
2. `installer/templates/application.yml` 的 `defect-image.upload.dir`（**必须保留 `defect-images` 段名**）

4. `/etc/cron.d/*` 里传给脚本的 `DIR=` / `IMG_ROOT=` / `TRASH=` / `LOG=` 与脚本路径

## 十五、老机迁移实操记录（2026-11-11，10.2.77.72）

现场机（Ubuntu 24.04.5）第一次按本布局搬完。新机迁移直接照这节执行，数字是同型号机器的实测参照。

### 15.1 迁移前后真实数字

| 项 | 迁移前 | 迁移后 |
|---|---|---|
| 数据盘挂载点 | `/data`（xfs，`defaults,noatime`） | `/main`（同一块 500G 盘，UUID 不变，**选项原样保留**） |

| MySQL datadir | `/var/lib/mysql` **3.9G**（`/var` LV） | `/main/app/data/mysql`（跨盘 rsync ≈ 90 秒） |
| 日志 / 上传 | `/var/lib/camera-detection-system` 6.5M | `/main/app/logs`、`/main/app/data/uploads` |
| 系统盘 | `/` 6.0G、`/var` 5.6G | `/` **4.2G**、`/var` 5.6G（旧 datadir 留着回滚） |

TEST 相机每小时清理，总数随时变，**行数 ≈ 文件数**才是健康信号。库数据量 `information_schema` 合计 **49.9MB**（`wms@002dnew` 目录 165MB，差额是 InnoDB 页与 undo）。

### 15.2 执行顺序

```bash
# 1) 上传发布包并解压（迁移脚本要从这里取新脚本/新 unit）
python3 docs/scripts/upload_jar_b64.py dist-release/linux/camera-detection-system-1.0.0.tar.gz /home/lims/
sudo tar -xzf /home/lims/camera-detection-system-1.0.0.tar.gz -C /tmp

# 2) 先 dry-run 两次（零写操作），确认计划与基线
sudo bash /tmp/camera-detection-system/scripts/migrate-to-main-app.sh
sudo bash /tmp/camera-detection-system/scripts/migrate-to-main-app.sh

# 3) 执行；中途失败可**直接重跑**（脚本支持断点续跑，M2/M4 已完成会自动跳过）
sudo bash /tmp/camera-detection-system/scripts/migrate-to-main-app.sh --apply

# 4) 回滚（数据搬回 + 挂载点还原 + /etc/default 还原）
sudo bash /tmp/camera-detection-system/scripts/migrate-to-main-app.sh --rollback --apply
```

停机时长实测：正常路径 3~5 分钟（3.9G 库跨盘拷贝是大头）。本次因两个 bug 中断过一次，停机合计约 6 分钟。

### 15.3 这次踩到的六个坑（都已修进脚本）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `--apply` 停在「M2 挂载点切换」，只吐 `EXIT=1`，无任何报错 | `fuser -m /data \| head -8` → head 提前关管道 → 上游 SIGPIPE → `pipefail` 判整条流水线失败 → `set -e` 静默退出 | 用 `awk 'NR<=8'` 读完全部输入；同时加 `trap ... ERR` 报出「第几行、哪条命令、返回码」 |
| 2 | `Failed to set datadir ... OS errno 13`，看着像 AppArmor | `/main/app/data` 从旧 `/data/camera-detection`（750 cdsys）继承权限，**mysql 用户连目录都进不去** | M4 里 `chmod 755 $BASE $DATA_BASE`（datadir 自身仍 700 mysql）。AppArmor 只是第二道门 |
| 3 | 迁移后一切正常，**下次重启** MySQL 才起不来 | M3 的 `chown -R cdsys:cdsys $BASE` 把 `data/mysql` 也改成了 cdsys | 改成按用途逐个 `chown`，结构性跳过 datadir；末尾再单独 `chown mysql:mysql` |
| 4 | 防线三回归从「退出码 4」变成「退出码 0」，**并且真删了数据** | 迁移把 `MAX_SINGLE_DELETE=50000` 写进 `/etc/default`；清理脚本 `source` 该文件时**覆盖了调用方显式传入的 `MAX_SINGLE_DELETE=2`** | 脚本记住外部值，`source` 之后再盖回去（`BACKUP_DIR` 同理，见 `restore-database.sh`） |
| 5 | 图片盘写入变多（迁移后"变慢"） | 重建 fstab 条目时只写 `defaults`，丢了现场的 `noatime` | M2 从原 fstab 行解析 options 与 fsck 位，原样带走 |
| 6 | `/tmp/.../migrate-to-main-app.sh: line 25: set: pipefail: invalid option name` | 用 Python 改写脚本时按文本模式写回，**整份变成 CRLF** | 改写脚本一律 `newline=''` 或二进制读写；提交前跑一次 `grep -rlU $'\r' installer/` |

另外两个小坑：`[[ -d /etc/os-release ]]`（是文件不是目录）；`/main` 里留有装系统时的空骨架 `/main/app/camera`（0 文件），必须先 `mv` 到 `/root/pre-migrate-main-<日期>` 留档——`/main` 成为挂载点后盘内原内容会被遮住。

### 15.4 迁移后仍保留的东西（回滚窗口）

| 保留项 | 位置 | 何时可删 |
|---|---|---|
| 旧 datadir | `/var/lib/mysql`（3.9G） | 确认新版稳定运行 1~2 周后 |
| 旧程序目录 | `/opt/camera-detection-system.migrated-<时间戳>`（318M） | 同上 |
| 旧工作目录 | `/var/lib/camera-detection-system.migrated-<时间戳>`（6.5M） | 同上 |
| fstab / 配置备份 | `/etc/fstab.pre-migrate-*`、`/etc/default/camera-detection.pre-migrate-*` | 建议永久保留最近一份 |

三个旧路径现在是 symlink（`/opt/camera-detection-system` → `dist`、`/var/lib/camera-detection-system` → `/main/app`、`/data/camera-detection` → `/main/app/data`），**数据库里历史 `image_path` 靠它兜底**，不要拆。
