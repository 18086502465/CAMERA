## 1. 发版链待拍板项（#1~#5）

### 1.1 #1 去掉 `123456` 口令兜底 —— 推荐执行

**问题澄清**

兜底实际有 **2 处**，台账此前只记了 1 处且行号漂移：

| 位置 | 当前行为 | 现场真口令来源 |
|---|---|---|
| `installer/linux/scripts/verify.sh:42` | `ADMIN_PASSWORD="${VERIFY_PASSWORD:-${ADMIN_PASSWORD:-123456}}"` | `source /etc/default/camera-detection` 的 `ADMIN_PASSWORD` 键（该文件 640） |
| `installer/linux/scripts/deploy.sh:714` | `APP_PASSWORD="123456"`，从 `DEFAULT_CFG` 读 `ADMIN_PASSWORD` 失败才兜底 | 同上 |

**为什么现在做是安全的**：全仓检索确认 **cron / systemd / CI 都没有调用 verify.sh 的地方**，受影响的只有人工裸跑命令。也就是说去掉兜底不会打断任何自动化链路，只让"忘记传口令"从"看似通过（其实用错口令）"变成"明确失败"。

**方案对比**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 保留兜底，只加强提示 | 不动脚本，验收单勾选确认 | 零改动 | 弱口令语义仍在；现场改密后不自知 |
| **B 强制显式传参（推荐）** | verify.sh 无口令直接 die；deploy.sh 的 `--app-password` 改必填 | 消除弱口令兜底；失败即显性 | 需同步改 6 处文档命令 |

**推荐执行步骤**

1. `verify.sh`：把 `:42` 改为 `${VERIFY_PASSWORD:-${ADMIN_PASSWORD:-}}`，为空时 `die "必须显式传 VERIFY_PASSWORD 或 ADMIN_PASSWORD"`。
2. `deploy.sh`：把 `--app-password` 从可选改必填，`:714` 兜底改为 `die`。
3. 文档同步：`README.md:111`、`CODEBUDDY.md:74`、`docs/配置项清单.md:214`、`docs/踩坑速查.md:198-199`、`docs/交付件体系与端到端交付流程.md:135-138`、`install.sh:696`、`init-database.sh:140` 全部改显式传参形式。
4. 验收单（`templates/06`）增加勾选项「自检口令已显式传入，未使用弱口令兜底」。

**责任/风险控制**：DEV 执行，PO 批准。风险是现场改过口令但 `/etc/default` 未同步 → 自检登录失败；探测方式是先 `sudo cat /etc/default/camera-detection | grep ADMIN_PASSWORD` 确认存在；应对是先跑 `reset-password.sh` 同步。

### 1.2 #2 static 同步"两套"收敛 —— 推荐不做收敛

**问题澄清**：实际是 **3 套**，而且策略不同，台账建议的"用 Python 版替换构建脚本内嵌版"是错误方向：

| 实现 | 时机 | 策略 |
|---|---|---|
| `installer/linux/build-release.sh:97-235` | 构建主路径（npm build 后、mvn package 前） | 保留最近 3 版 + current，物理淘汰更旧 chunk |
| `docs/scripts/sync_static_keep_legacy.py` | 人工按需同步 | **只补不删**，从不淘汰 |
| `frontend/scripts/sync-static.mjs`（postbuild） | 每次 `npm run build` 自动跑 | **仅 static 为空时首次填充**，非空立即退出 |

后两套的存在意义是：**避免新 clone 直接 `mvn package` 打出白屏 JAR**（C）以及**人工同步不破坏历史 chunk 版本链**（B）。CI 更是绕开全部三套（`ci.yml:98,247-252` 自己 `rm -rf static` 后复制）。

**为什么不能简单收敛**：直接换成 Python 版会让 `KEEP_STATIC_VERSIONS=3` 淘汰失效 → `static/assets` 与 JAR 持续膨胀；两版 `.versions` 的版本号来源不同（A 用上一版入口 hash，B 用本次入口 hash）→ 混用会误标历史版本，触发旧标签页 chunk 404。这正是 2026-11-04「旧页面点不动」事故的翻版。

**推荐**：不改代码，把 M-5 从"待收敛"改为「**三套职责已明确，构建脚本是唯一发版入口**」，在三处文件头各加一行职责注释，并把这条写进 `踩坑速查.md`。风险归零。

### 1.5 #5 verify.sh 写库副作用 L-1 —— 推荐执行

**问题澄清**：verify.sh 有 4 处写库 POST：心跳（`:771`，更新真实相机的 `camera_status` + 插入 `fact_camera_heartbeat`）、两次批量上报（`:777/:784`，写 `fact_inspection_batch` / `fact_camera_status_current` / `fact_inspection_mapping_exception`）、登录（`:555`，写审计日志）。清理段（`:830-834`）只按 `batch_id LIKE 'VERIFY%'` 删 3 张表，**心跳与状态表污染不清**——真实相机的 `last_heartbeat_at`、计数、`product_name` 被改写且无还原。

**方案对比**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 维持现状 + 验收后人工核对 | 不改脚本 | 零改动 | 污染真实数据，长期累积 |
| **B 专用测试相机 + 全前缀清理（推荐）** | 造 `ZZTEST-VERIFY` 相机（TEST 类型，已在每小时清理保护集外），所有写库请求用它的 code；清理按该前缀删全表 | 不碰真实相机；与现有 TEST 清理链一致 | 需确认测试相机在保护集外且能被清理 |
| C 改为只读端点探测 | 去掉心跳/上报写库检查 | 零污染 | 失去"上报链路真通"的验证能力 |

**推荐**：B。若现场当前没有可用的 TEST 相机，退而求其次用 C（把上报链路检查改为只读探测 + 提示人工验证）。**责任人** QA/DEV，**验收**是跑完 verify 后 `SELECT` 确认无 `ZZTEST-VERIFY*` 残留、真实相机 `last_heartbeat_at` 未变。

## 2. LIC-09 密钥迁移（#6，唯一 high）—— 推荐执行，单独窗口

### 问题澄清

现场存量授权（`VALID`、到期 2029-11-12、`maxCameras=200`、机器码 `05144C536FC17D9E`）**确为 jar 内置默认密钥自签的试点授权**，不是商务交付授权。本地无 `.lic`/`ledger.csv` 快照，结论来自 `docs/archive/服务器授权使用流程与交付规划-20261121.md:30,91,94` 与 `templates/10:26-28` 的记载；`/etc/default` 与配置模板均未写 `LICENSE_SECRET`。

内置默认密钥在 `LicenseSigner.java:37-42`（`cds-lic` + `-2026-zlp` + salt 推导），Python 签发工具 `issue_license.py:45-47,56-59` 逐字节一致。切 `LICENSE_SECRET` 后，`LicenseSigner.resolveSecret()`（`:65-67`）优先用配置 → 旧授权立刻验签失败。

### 为什么顺序错会"新旧双失"

服务器同一时刻只认一把密钥。旧 lic 用默认密钥签、新 lic 用新密钥签。若**先切密钥再上传新 lic**，或上传失败，则旧 lic 变 `INVALID`、新 lic 没装成 → 授权状态 `INVALID`，产线授权失效。五步序的第②步是**刻意负向验证**（服务器仍用旧密钥时上传新 lic，预期失败且原授权仍 `VALID`），用来证明"错密钥不会覆盖原文件"——跳过它就失去了安全网。

### 推荐的五步执行序（不可调换）

| 步 | 动作 | 成功判据 | 失败应对 |
|---|---|---|---|
| ① | 用新密钥按机器码 `05144C536FC17D9E` 签发新 lic（到期不晚于 2029-11-12），`inspect` 自检 | 载荷 v2、字段与合同一致 | 停止，重新签发 |
| ② | 服务器仍用旧密钥时上传新 lic → **预期验签失败** | 原授权仍 `VALID`（负向验证通过） | 若原授权变 INVALID，立即恢复 `.bak`，终止迁移 |
| ③ | 写 `LICENSE_SECRET` 到 `/etc/default/camera-detection`，`systemctl restart` | 服务 active，日志显示新密钥指纹 | 撤销环境变量 + 重启 + 恢复原 lic |
| ④ | 再上传新 lic → `POST /api/license/reload` | `/api/license` 为 `VALID` 且是新单号 | 同③回滚 |
| ⑤ | 清理旧 lic 备份，保留 1 份 `.bak-*` | 备份目录只剩 1 份 | — |

### 执行条件与窗口

- **需要停机**：仅第③步一次重启。`camera-detection.service:37` `TimeoutStopSec=45`、`:35` 优雅停机 30s、`run.sh:105-120` DB 探测最多 120s（正常首秒成功）、JVM 启动 + `@PostConstruct` 加载授权约 15-40s。**建议预留 5-10 分钟窗口**，真正业务不可用仅重启那几十秒。
- **批准人**：客户/项目负责人（不是执行人自己），与 S8 推送授权同规格。
- **回滚点**：`/etc/default` 的 `LICENSE_SECRET` 行 + 旧 lic 的 `.bak-*`；⑤之前不得删备份。
- **验证命令**：`systemctl is-active camera-detection`；`journalctl -u camera-detection -n 100 --no-pager | grep '授权状态\|授权文件已加载'`；`curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8091/api/license | jq '{status,licenseId,expireAt}'`；迁移完成后跑 `sudo ./verify.sh --delivery`。

## 3. LIC-12 到期告警（#7）—— 推荐执行

### 问题澄清

5. 测试：`LicenseAlertListenerTest` + `LogNoiseReductionTest` 增 OPS 成员断言。

文案要求：title `"授权已到期："+expireAt`（<200），正文前 500 字放关键结论（Repository 截 2000）。ArchUnit 合规：system 域只发事件，不直接调 analytics 的 Repository。

## 4. 业务/前端待拍板项（#8~#11）

### 4.2 #9 排行 LIMIT 20 —— 推荐放开到 30/全量

现场 37 种缺陷类型被截掉 17 种，是**实际数据损失**。相机 36 台（18 有数据）勉强够。热力和班次对比已在快聚合路径放开全量（R-1/R-2 终态），排行仍硬截断。

**推荐**：
- 快聚合路径删 `DefectImageSummaryFastAggregator.java:517/553/590` 三处 `subList` 截断（主路径，现场 99% 命中，几十行数据无性能问题）。
- SQL 回退路径把 6 处 `LIMIT 20` 改 30（保留防御性上限）。

### 4.4 #11 element-plus 按需引入 —— 推荐暂缓；若做走自动插件
