# 图像记录链路一致性分析与修复报告

日期：2026-06-18

## 1. 链路梳理

相机缺陷图片链路如下：

1. 相机调用 `POST /api/v1/defect-images/upload`，以 `multipart/form-data` 上传 `files` 和 `metadata`。
2. 后端 `DefectImageController.upload` 合并 `files/file` 字段并校验单批数量。
3. `DefectImageServiceImpl.upload` 解析 metadata，按 `metadata.images[].fileName` 与 multipart 原始文件名匹配。
4. 每张图片先写入磁盘目录：`defect-image.upload.dir`。
5. 图片解析成功后写入：
   - `defect_image_batch`
   - `defect_image_file`
   - `defect_image_box`
   - 兼容表 `camera_images`
6. 图像记录页面原先调用 `/api/v1/defect-images/recent?limit=200`，前端再按相机分组展示。

## 2. 发现的问题

### 问题 A：页面只取全局最近 200 张，导致单相机展示数量小于数据库/文件夹数量

现场数据中，杭州上料相机实际已有 629 张数据库记录，但旧页面只从全局最近 200 张里再按相机分组，因此某台相机历史数会被截断。

验证结果：

```json
{
  "summary": 629,
  "historyTotal": 629,
  "historyRows": 10,
  "globalRecentLimit200ForCamera": 200
}
```

### 问题 B：文件先落盘、后写数据库，失败场景可能留下孤儿文件

旧逻辑中，`saveFile()` 先 `Files.copy()`，之后才做图片内容解析与数据库写入。若图片内容解析失败、数据库插入失败或缺陷框写入失败，物理文件可能已经存在，但 `defect_image_file` 未写入或被回滚，造成“文件夹数量 > 页面/数据库数量”。

当前运行目录诊断：

```json
{
  "fileCount": 1171,
  "dbCount": 1164,
  "orphanFileCount": 7,
  "missingFileCount": 0
}
```

说明：现有 7 个孤儿文件是历史失败流程遗留；本次修复会阻止后续继续产生。

### 问题 C：metadata 与 multipart 文件未强制一一对应

旧逻辑用文件名 Map 匹配，未强制校验：

- multipart 多传文件但 metadata 未声明；
- metadata 声明文件但 multipart 未上传；
- 文件名大小写不一致；
- 重复文件名被 Map 覆盖。

这会导致相机端认为“上传了 N 张”，但服务端只处理部分文件。

## 3. 修复内容

### 后端修复

修改文件：

- `fact-product/src/main/java/com/wms/controller/DefectImageController.java`
- `fact-product/src/main/java/com/wms/service/IDefectImageService.java`
- `fact-product/src/main/java/com/wms/service/impl/DefectImageServiceImpl.java`

新增接口：

- `GET /api/v1/defect-images/camera-summaries`
  - 按相机聚合图片总数、严重度统计、最近 5 张图片。
- `GET /api/v1/defect-images/history`
  - 单相机图片历史分页查询。

一致性保护：

- 强制校验 multipart 文件与 `metadata.images[]` 一一对应。
- 文件名匹配改为大小写不敏感。
- 拒绝重复文件名。
- 图片解析失败时立即删除已落盘文件。
- 数据库写入失败时清理 `defect_image_file`、`defect_image_box` 和已落盘文件。
- 查询时修正 `camera_status` join，避免配置重复导致图片记录被 join 放大。

### 前端修复

修改文件：

- `frontend/src/api/camera.js`
- `frontend/src/components/CameraImageRecords.vue`

优化点：

- 图像记录页不再依赖全局最近 200 张。
- 页面首屏按相机展示聚合总数和最近 5 张图片。
- 展开单个相机后，走后端分页查询真实历史总数。
- 分页总数使用数据库真实 count。

### 运维诊断脚本

新增：

- `scripts/defect-image-consistency-check.mjs`

用法：


如需把历史孤儿文件移动到隔离目录，确认后可执行：

## 5. 结论

本次不一致的核心原因有两个：

1. 页面展示层取数模型错误：只取全局最近 200 张再前端分组，无法代表每台相机真实历史数量。
2. 上传落库链路缺少文件系统与数据库的一致性补偿，失败时可能留下历史孤儿文件。

已完成链路修复、页面分页模型优化和失败清理保护。后续新上传数据应保持“成功文件数 = `defect_image_file` 记录数 = 页面可分页总数”。历史 7 个孤儿文件建议通过新增诊断脚本确认后隔离。
