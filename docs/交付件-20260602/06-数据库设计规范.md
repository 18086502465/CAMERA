# 数据库设计规范

## 1. 数据库概况

| 项 | 值 |
|---|---|
| 数据库 | MySQL 8.0 |
| 库名 | `wms-new` |
| 字符集 | 建议 `utf8mb4` |
| 初始化脚本 | `D:\45344\0004-软件源码\wms-new-20260531-new.sql` |
| 发布包 SQL | `dist-release\CameraDetectionSystem\sql\wms-new.sql` |

## 2. 表命名规范

| 前缀 | 含义 | 示例 |
|---|---|---|
| `dim_` | 维度表/基础配置 | `dim_factory`、`dim_workstation` |
| `fact_` | 事实表/统计事实 | `fact_production_30min`、`fact_anomaly_alert` |
| `sys_` | 系统表 | `sys_user`、`sys_operation_log` |
| `defect_image_` | 缺陷图片上传链路 | `defect_image_batch`、`defect_image_file`、`defect_image_box` |
| `camera_` | 相机状态或图片兼容表 | `camera_status`、`camera_images` |

## 3. 字段命名规范

- 使用小写下划线：`camera_code`、`create_time`。
- 主键建议：`表语义_id` 或 `id`。
- 创建/更新时间：`create_time`、`update_time`。
- 逻辑删除：`is_deleted`，`0=正常`、`1=删除`。
- 状态字段：明确枚举值并在接口文档中说明。
- 金额/比例/资源指标使用 `decimal`，避免浮点误差。

## 4. 核心表分类

### 4.1 组织与配置维表

| 表 | 说明 | 核心字段 |
|---|---|---|
| `dim_company` | 公司/集团 | `company_id`、`company_name`、`company_code` |
| `dim_factory` | 工厂 | `factory_id`、`company_id`、`factory_name`、`factory_code` |
| `dim_production_line` | 产线 | `line_id`、`factory_id`、`line_name`、`line_code` |
| `dim_workstation` | 工位 | `workstation_id`、`line_id`、`station_name`、`station_code` |
| `camera_status` | 相机配置与状态 | `id`、`camera_name`、`camera_code`、`line_id`、`workstation_id`、状态/资源字段 |

层级关系：

```text
company -> factory -> production_line -> workstation -> camera_status
```

说明：当前 `camera_status` 同时承载“相机基础配置”和“实时状态”，后续建议拆分为 `dim_camera` + `camera_status_snapshot`。

### 4.2 生产与检测事实表

| 表 | 说明 | 核心字段 |
|---|---|---|
| `product_detection_history` | 检测历史明细 | `detection_id`、`line_id`、`workstation_id`、`brand_id`、`result`、`defect_*` |
| `fact_production_30min` | 30 分钟生产聚合 | `line_id`、`workstation_id`、`brand_id`、`shift_id`、`bucket_date`、`bucket_index`、`total_count`、`ok_count`、`ng_count`、`yield_rate` |
| `fact_production_info` | 日级生产信息 | `production_date`、`total_count`、`ok_count`、`ng_count`、`yield_rate` |
| `fact_production_30min_archive` | 30 分钟归档 | 与事实表类似，增加 `archive_time` |

### 4.3 缺陷图片链路表

| 表 | 说明 | 核心字段 |
|---|---|---|
| `defect_image_batch` | 图片上传批次 | `batch_id`、`batch_no`、`camera_id`、`camera_name`、`metadata_json` |
| `defect_image_file` | 图片文件记录 | `image_id`、`batch_id`、`file_name`、`image_path`、`image_url`、`defect_count` |
| `defect_image_box` | 单张图片缺陷框 | `box_id`、`image_id`、`defect_type`、`severity`、`x/y/width/height/area` |
| `camera_images` | 旧图像兼容表 | `camera_name`、`image_path`、`image_url`、`capture_time` |

关系：

```text
defect_image_batch 1 -> N defect_image_file 1 -> N defect_image_box
```

## 5. 关键业务规则

### 5.1 相机唯一性

- 推荐唯一键：`camera_code/deviceId`。
- `camera_name` 只作为展示名。
- 当前系统部分兼容以 `camera_name` 匹配，后续应收敛到 `camera_code`。

### 5.2 相机与工位

- 一个工位允许多台相机。
- 相机归属由系统配置维护，设备上报不能修改归属。

### 5.3 缺陷严重度

接口使用：`HIGH`、`MEDIUM`、`LOW`。  
数据库同时保存：

- `severity`：字符串枚举。
- `severity_level`：数字映射，`HIGH=3`、`MEDIUM=2`、`LOW=1`。

### 5.4 时间口径

- 心跳时间：`last_heartbeat_at`。
- 图片上传时间：`last_upload_at`、`defect_image_file.upload_time`。
- 图片拍摄时间：`capture_time`。
- 统计时间：`bucket_date` + `bucket_index`。

## 6. 索引规范

建议索引：

| 表 | 建议索引 | 用途 |
|---|---|---|
| `camera_status` | `camera_code`、`line_id,workstation_id` | 相机状态和筛选。 |
| `defect_image_file` | `camera_id,upload_time`、`batch_id` | 最近图片、批次查询。 |
| `defect_image_box` | `image_id`、`severity` | 图片弹窗、严重度统计。 |
| `product_detection_history` | `detection_time`、`line_id,workstation_id`、`brand_id` | 缺陷统计和明细查询。 |
| `fact_production_30min` | `bucket_date,bucket_index`、`line_id,workstation_id` | 产线和良率趋势。 |
| `sys_operation_log` | `operation_time`、`user_id`、`operation_type` | 日志查询。 |

## 7. 数据清理规范

| 数据 | 默认保留 | 处理方式 |
|---|---:|---|
| 缺陷图片文件 | 30 天 | 删除文件与图片记录，必要时保留统计摘要。 |
| 缺陷框 metadata | 90 天 | 归档或摘要保留。 |
| 检测历史明细 | 90 天 | 归档至历史表。 |
| 30 分钟事实 | 1 年 | 保留。 |
| 操作日志 | 180 天 | 清理。 |

## 8. 迁移与发布规范

- 所有 DDL 必须可重复执行或有版本脚本。
- 新增字段必须设置默认值或允许空，避免历史数据迁移失败。
- 不允许在业务代码中依赖本地绝对路径，路径通过配置注入。
- 发布前必须备份数据库。

## 9. 当前数据库改进建议

| 优先级 | 建议 |
|---|---|
| P0 | 明确 `camera_status.camera_code` 唯一约束，避免同设备重复。 |
| P0 | 增加配置删除依赖约束，避免误删工厂/产线/工位导致孤儿数据。 |
| P1 | 拆分相机基础配置表和实时状态表。 |
| P1 | 为图片与检测历史增加归档表和定时清理配置表。 |
| P2 | 建立数据库版本迁移机制，如 Flyway/Liquibase。 |
