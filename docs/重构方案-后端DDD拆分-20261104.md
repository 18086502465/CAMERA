# 后端 DDD 拆分重构方案

> 版本：V1.0（待确认）｜日期：2026-11-04
> 硬约束：**拆分后功能与现有行为完全不变**（接口路径、请求/响应、权限、定时任务行为均不变）

---

## 一、现状诊断（实测数据）

| 维度 | 现状 | 问题 |
|---|---|---|
| 规模 | 131 个 Java 文件 / 15,605 行；19 个 Controller 共 6,279 行 | 单体平铺，按技术分层而非业务分层 |
| JDBC 直连 | **9 个 Controller 直连 JdbcTemplate（135 处）** | SQL 散在 HTTP 层，无法复用与单测 |
| 巨型类 | `LineAnalyticsController` **1,511 行 / 23 端点 / 67 段 SQL / 58 处 JDBC**；`StatsController` 886 行；`ConfigImportController` 556 行；`DefectImageServiceImpl` **1,606 行 / 24 处 JDBC**；`CameraStatusServiceImpl` 416 行 | 上帝类，多业务混在一起 |
| DDL 散布 | 3 个文件内嵌 `CREATE TABLE`（LineAnalytics / SystemSettings / DefectImageServiceImpl） | 表结构管理失控 |
| 裸返回 | 47 个方法返回裸 `Map<String,Object>` | 契约不明确 |
| 全局异常 | **无 @ControllerAdvice** | 异常处理分散 |
| 已有先例 | `repository/{analytics,log,stats}` 3 个 Repository（412 行），`OperationLogRepository` 注释明确"Controller 只负责 HTTP，SQL 收敛到 Repository" | **重构方向已被验证**，照此推广 |
| 行为基线 | 单测 19/19、verify.sh 28/28、浏览器回归 5 套脚本 | 具备渐进式重构的护栏 |

**结论**：代码量中等（1.5 万行），已有 Repository 先例与完整验证基线，适合**渐进式 strangler 重构**，不做 big-bang。

## 二、目标架构：6 个业务域 + 1 个共享内核

### 2.1 模块划分（Maven 单模块内按包划分，保留单 JAR 部署形态）

```
com.wms
├── shared/                       ★ 共享内核（不依赖任何业务域）
│   ├── common/                   ResultVO、PageVO、常量、异常体系（BizException 等）
│   ├── web/                      @ControllerAdvice 全局异常处理、通用参数解析
│   ├── config/                   MybatisPlusConfig、JdbcTemplate、DefectImageUploadLimitConfig
│   └── util/                     ExcelUtils、ShiftCalculator、CodeGenerator
│
├── iam/                          ★ 身份与访问域（认证、用户、审计）
│   ├── api/                      AuthController、SysUserController、SysOperationLogController
│   ├── app/                      AuthService、SysUserService、OperationLogService
│   ├── domain/                   用户/角色模型、JWT 契约（JwtUtil、JwtRequestFilter）
│   └── infra/                    SysUserMapper、OperationLogRepository、SecurityConfig
│
├── masterdata/                   ★ 主数据域（组织与基础档案）
│   ├── api/                      DimFactory / DimProductionLine / DimWorkstation /
│   │                             DimCompany / DimProductBrand / SysHolidayConfig /
│   │                             CascadeController（级联树）
│   ├── app/                      各主数据 Service、级联组装
│   ├── domain/

├── device/                       ★ 设备域（相机档案与运行状态）
│   ├── api/                      CameraStatusHeartbeatController、CameraImageController、
│   │                             ServerMetricsController
│   ├── app/                      CameraStatusAppService、ServerMetricsService
│   ├── domain/                   心跳/状态模型、code-first 匹配规则
│   └── infra/                    CameraStatusMapper、CameraImageMapper
│
├── defect/                       ★ 缺陷检测域（现场主通道）
│   ├── api/                      DefectImageController
│   ├── app/                      DefectImageAppService（拆分上传/查询/历史三个应用服务）
│   ├── domain/                   批次/文件/框模型、相机匹配规则
│   └── infra/                    DefectImageRepository（JDBC 收敛到这里）、配置映射
│
├── inspection/                   ★ 检测批次域（冻结契约通道，基本停用）
│   ├── api/                      ProductDetectionHistoryController、BatchUpload 入口

│   ├── api/                      LineAnalyticsController（瘦身后仅 HTTP 壳）、
│   │                             StatsController、CameraDashboardController
│   ├── app/                      LineTrendAppService / DefectParetoAppService /
│   │                             StationRankingAppService / DashboardAppService /
│   │                             StatsAppService（把 1,511 行按报表主题拆开）
│   ├── domain/                   报表口径模型（班次、良率、聚合窗口）
│   └── infra/                    LineAnalyticsRepository（扩充）、StatsQueryRepository、
│                                 聚合 ensure* 建表收敛到 SchemaInitializer
│
```

> 命名说明：`api` = HTTP 层；`app` = 应用服务（编排、事务边界）；`domain` = 领域模型与规则；`infra` = 持久化（Mapper/Repository/JDBC）。

### 2.2 域边界一览（谁管什么）

| 域 | 核心职责 | 明确不管 |
|---|---|---|
| iam | 登录、JWT、用户、操作日志 | 业务权限点分散在各域 Controller 的 @PreAuthorize |
| masterdata | 工厂/产线/工位/公司/品牌/假期档案、级联树 | 相机归属校验（device 域做） |
| device | 相机档案归属、心跳、状态快照、服务器指标 | 图片与缺陷业务 |
| defect | 图片上传三表、历史查询、相机匹配 | 心跳 |
| inspection | batch-upload 冻结契约、product_detection_history | 现场主通道（defect 域） |
| analytics | 所有报表/看板/聚合（agg_*、fact_production_30min） | 明细写入（defect/inspection 域写） |
| system | 系统设置、配置导入导出、保留策略 | 业务数据 |

### 2.3 依赖规则（三条铁律）

1. **自上而下单向依赖**：`api → app → domain → infra`；同域内禁止反向。
2. **跨域只走 app 层接口**：例如 analytics 需要"相机显示名"时，注入 `device` 域的
   `CameraDirectory`（接口，由 device 域实现），**禁止**直接注入对方 Mapper/Repository/Entity。
3. **shared 不依赖任何业务域**；业务域之间禁止循环依赖。
   （用 ArchUnit 固化这三条，防止未来回退 —— 待确认项 C6）

### 2.4 跨域协作机制

**接口协作**（查询类，同步）：
- `CameraDirectory`（device 域提供）：按 code 批量取相机档案/显示名/产线归属
  → analytics、defect、masterdata 共用，替代各自 JOIN dim_camera

**事件协作**（状态变更类，异步解耦，用 Spring `ApplicationEvent`，**不引入 MQ**）：
| 事件 | 发布方 | 消费方 |
|---|---|---|
| `CameraHeartbeatReceivedEvent` | device | analytics（心跳计数口径刷新） |
| `DefectImagesUploadedEvent` | defect | analytics（30 分钟聚合、看板缓存失效） |
| `ConfigChangedEvent` | system | device / defect（配置热生效，如保留策略） |

> 事件监听器必须幂等且异常不阻断主流程（try-catch + 日志），与现有行为一致
> （现状本来就是顺带更新，无跨表事务）。

## 四、实施步骤（渐进式，每步可验证可回滚）

> 每步完成 = 代码提交（等你授权）+ 部署验证（mvn test 19/19 → 部署 → verify.sh 28/28 → 浏览器回归 5 套）。
> 任何一步行为 diff 即停，回滚该步。

| 阶段 | 内容 | 规模 | 风险 |
|---|---|---|---|
| **P0 基线固化** | ① 生成接口快照：对全部 ~60 个端点录制请求/响应 JSON（改造前），改造后逐个 diff；② 确认 19 个单测覆盖点，补 3~5 个关键契约测试（登录、心跳、图片上传、camera-summaries） | 0.5 天 | 低 |
| **P1 抽共享内核** | 建立 shared/ 包；移动 ResultVO/工具类/配置类；新增全局异常（行为保持模式）；纯移动不改逻辑 | 0.5 天 | 低 |
| **P2 按域搬包** | 建 6 域包结构，把现有类按 2.1 归位（先搬家不改逻辑），IAM/masterdata/system 先行；每域一个 commit | 1 天 | 低-中 |
| **P3 JDBC 收敛**（分 4 批） | 把 9 个 Controller 的内联 SQL 下沉到各域 Repository（照 OperationLogRepository 模式）：<br>批次① Dim*、Cascade（19 处，简单）<br>批次② SystemSettings、FinalConfig、ConfigImport（49 处）<br>批次③ CameraDashboard、Stats（9 处 + Repository 已有）<br>批次④ **LineAnalytics**（58 处，1,511 行 → 拆 5 个 AppService + 扩充 Repository，每拆一个端点验证一个） | 2~3 天 | 中-高（批次④） |
| **P4 解耦与事件** | 抽 `CameraDirectory` 接口替换跨域 JOIN；心跳/上传/配置变更事件化；DefectImageServiceImpl（1,606 行）拆为 3 个 AppService | 1 天 | 中 |
| **P5 DDL 收敛** | 3 个文件的 ensure* 建表统一到 `SchemaInitializer`（保持 INFORMATION_SCHEMA 判断与"必须自调"语义不变），加启动日志 | 0.5 天 | 中 |
| **P6 文档重建** | 见下节 | 1 天 | 低 |

总计约 **6.5~7.5 个工作日**。P2 之后每个阶段结束都可独立交付（旧包结构删除前先保留一个 deprecated 转发层？—— 不需要：Java 包移动不影响 HTTP 契约，直接删干净）。

### 行为不变的三个保障手段

1. **P0 接口快照 diff**：请求参数、响应 JSON 结构与值（动态时间字段除外）、HTTP 状态码逐项比对；
2. **SQL 原样搬运**：P3 阶段 SQL 文本不做任何"顺手优化"（包括参数拼接方式），只做物理位置迁移；
3. **权限矩阵不变**：SecurityConfig 白名单与 @PreAuthorize 逐一登记成表，重构后照表核对。
