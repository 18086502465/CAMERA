## 2. 日志体系

### 2.1 三处日志，别搞混

| 位置 | 内容 | 谁写的 | 轮转 |
|---|---|---|---|
| `journalctl -u camera-detection` | JVM 的 stdout/stderr | systemd 收集 | journald（已限 500M/30 天） |
| `/var/lib/camera-detection-system/logs/camera-detection-system.log` | 业务日志（同一份内容） | 应用 `logging.file.name` | logrotate（30 天，`copytruncate`） |
| 数据库 `sys_operation_log` 表 | **操作审计**（谁在什么时候调了哪个接口） | 应用 AOP 切面 | 应用定时任务清 180 天前的 |

> **注意**：前两者内容基本重复（同一份日志既进 stdout 也进文件）。
> 排查时看 journald 即可，文件主要用于历史留存与离线分析。

### 2.2 常用日志命令

```bash
# 实时跟踪
journalctl -u camera-detection -f

# 只看最近 1 小时
journalctl -u camera-detection --since "-1h"

# 只看错误
journalctl -u camera-detection -p err --since "-1h"

# 按时间倒序看最后 200 行
journalctl -u camera-detection -n 200 --no-pager | tail -50

# 某次启动失败的原因
journalctl -u camera-detection --since "10:00" --until "10:05" --no-pager

# 业务日志文件
tail -f /var/lib/camera-detection-system/logs/camera-detection-system.log
grep -i "ERROR" /var/lib/camera-detection-system/logs/camera-detection-system.log | tail -20
```

### 2.3 ⚠️ 已修复的日志膨胀问题（务必了解）

**现象**：journald 几小时内涨到 **243 MB**，业务日志文件 15 分钟涨 150 KB。
**根因**：JAR 内置的开发版 `application.yml` 里带了两条开发期设置，而**外部生产配置没有覆盖它们**：

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl   # ← 每条 SQL 打到 stdout
logging:
  level:
    com.wms.mapper: DEBUG                                  # ← mapper 级别 DEBUG
```

两个坑叠加：
1. 外部配置**省略**某项时，JAR 内部配置的该项**依然生效**（配置是按 key 合并，不是按文件整体替换）。
2. logback 取**最具体**的 logger 级别 —— `com.wms.mapper` 比 `com.wms` 更具体，
   所以只写 `com.wms: INFO` **压不住** `com.wms.mapper: DEBUG`。

**修复**（已写入 `installer/templates/application.yml`，服务器已生效）：

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.slf4j.Slf4jImpl   # 改走 logback，由级别控制
logging:
  level:
    com.wms.mapper: INFO                                  # 必须显式覆盖更具体的 logger
```

**实测效果**：同样打 20 次业务请求
- 修复前：journald 新增 **19666 行**（其中 2835 条是 SQL 打印）
- 修复后：journald 新增 **40 行**，SQL 打印 **0 行**

> **推广提醒**：以后新增任何部署配置项，只要 JAR 内置的 `application.yml` 里同名 key 有值，
> 就必须在外���配置里**显式覆盖**，否则开发期设置会漏到生产。

### 2.4 日志轮转配置

**业务日志**（已安装 `/etc/logrotate.d/camera-detection`）：

```
/var/lib/camera-detection-system/logs/*.log {
    daily
    rotate 30
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
    su cdsys cdsys
}
```

> 用 `copytruncate` 而不是 `create`：应用持有日志文件句柄，不 truncate 的话空间不会释放。

**journald**（已写入 `/etc/systemd/journald.conf`）：

```ini
[Journal]
SystemMaxUse=500M
MaxRetentionSec=30day
```

改完需 `systemctl restart systemd-journald`，并 `journalctl --vacuum-size=200M` 立刻回收。

### 2.5 日志里的"噪音"别误判

启动时必然出现这 4 条 ERROR（**已知无害**）：

```
ERROR ... c.b.m.core.MybatisConfiguration : mapper[com.wms.mapper.FactProduction30minMapper.countByTimeBucketAndStation] is ignored, because it exists, maybe from xml file
ERROR ... c.b.m.core.MybatisConfiguration : mapper[com.wms.mapper.SysHolidayConfigMapper.selectByDate] is ignored, ...
ERROR ... c.b.m.core.MybatisConfiguration : mapper[com.wms.mapper.SysUserMapper.findByFactoryId] is ignored, ...
ERROR ... c.b.m.core.MybatisConfiguration : mapper[com.wms.mapper.SysUserMapper.findByUsername] is ignored, ...
```

**原因**：MyBatis-Plus 优先级是 **XML > `@Select` 注解**，同名方法两处都定义时 XML 生效、注解被忽略。
**影响**：功能正常，但其中 `countByTimeBucketAndStation` 的 XML 版引用了**任何建表脚本里都不存在的 `time_bucket_id` 列**，
一旦被调用就会报 `Unknown column 'time_bucket_id'` —— 属潜伏故障，需要改代码才能根治。

判断日志里是不是真错误，用这个过滤器：

```bash
journalctl -u camera-detection --no-pager | grep "ERROR" | grep -v "MybatisConfiguration" | grep -v "Preparing:"
```

输出为空 = 没有真实运行时错误。

## 3. 图片存储

> ⚠️ **2026-10-26 架构评审后已改造**：图片从 `/var/lib/camera-detection-system/data/uploads/`
> 迁到 **`/data/camera-detection/images/defect-images/`**（500 GB XFS）。
> 原因见 §3.3 的容量测算 —— 原 `/var` 49 GB 在目标负载下**约 1 天就写满**。

### 3.1 实际路径与机制

```
/data/camera-detection/images/defect-images/
└── 20261026/                    ← 日期
    └── CAM-001/                 ← 相机
        └── 203000000_adc28391.png
```

- **配置项**：`application.yml` 的 `defect-image.upload.dir`
- **落盘规则**：`saveFile()`（`DefectImageServiceImpl`）自动建 `yyyyMMdd/<cameraId>/` 子目录
- **命名**：`HHmmssSSS_<uuid8>.<ext>` —— 毫秒时间戳 + 随机后缀，天然不重名

**关键性质（迁移与排查都依赖它）**：

| 字段 | 存什么 | 影响 |
|---|---|---|
| `image_url` | **相对路径** `/api/v1/defect-images/file/20261026/CAM-001/xxx.png` | 前端只用它，**改根目录不影响前端** |
| `defect_image_file.image_path` | **绝对路径**（`saved.absolutePath`） | 仅作兜底反查用；**旧记录会失真但不影响回读** |
| `camera_images.image_path` | **绝对路径**（兼容表） | `DataCleanupTask` 用它删文件 → **改根目录必须 UPDATE 修正** |

回读逻辑（`resolveImagePath()`）第一步就是 `root.resolve(decoded)`，
用 URL 里的相对路径直接命中新根目录 —— 所以**换根目录后旧图片仍能正常显示**。

> ⚠️ **两个必做的配套动作**（漏一个就有坑）：
> 1. 改 `defect-image.upload.dir` 后，**同步改 systemd 的 `ReadWritePaths`**，
>    否则 `ProtectSystem=full` 会拦截写入 —— 表现为「上传返回 200 但文件不落盘」，极难排查。
> 2. 改根目录后，执行一次路径修正：
>    ```sql
>    UPDATE camera_images SET image_path = REPLACE(image_path,
>      '/var/lib/camera-detection-system/data/uploads', '/data/camera-detection/images');
>    ```

### 3.2 单批上传限制

| 限制 | 值 | 超出时的表现 |
|---|---|---|
| 单批图片数 | ≤ 100 | HTTP **413**（按 `X-Image-Count` 头提前拒绝） |
| 单文件大小 | ≤ 10 MB | 400 |
| 整批请求 | ≤ 1024 MB | 400 |

> **走 nginx 时**：`client_max_body_size` 必须配到 `1024m`，
> 否则 nginx 默认 1MB 会把图片拦成 413，表现成"设备上报失败"而不是应用报错。

### 3.3 容量测算（按目标负载）

目标场景：**20 相机 × 5 张/分钟 = 144,000 张/天**。

单张图片体积**高度依赖产线画面**，实测区间跨 70 倍：

| 类型 | 体积 |
|---|---|
| 渐变"产品照" 1920×1080 PNG | **88 KB** |
| 实测上传 800×600 PNG | 1,407 KB |
| 随机噪声 1920×1080 PNG（最坏） | **6,078 KB** |

按 350 KB/张（对工业相机 JPEG 是保守估计）：

| 分区 | 容量 | 日增 | 够用 |
|---|---|---|---|
| ~~`/var`（改造前）~~ | 45 GB | **48 GB/天** | **约 1 天** ⚠️ |
| **`/data`（改造后）** | **491 GB** | 48 GB/天 | **约 10 天**（配合 7 天保留期可长期稳定） |

> **上线首日必须用真实图片复核单张均寸** —— 若实际是 6 MB 的噪声图，日增会到 835 GB，
> 那就必须做设备端转码压缩（见 §3.5）。

**数据库侧对比**（说明为什么瓶颈在磁盘而非数据库）：
`defect_image_file` 单行（数据+索引）实测 **630 字节** → 100 万行仅 **0.6 GB**。

监控命令：

```bash
# 容量与 inode 一起看（海量小文件 inode 消耗快）
df -hT /data
df -i /data

# 总量
du -sh /data/camera-detection/images

# 按天看增长
du -sh /data/camera-detection/images/defect-images/*/ | sort -k2

# 文件数
find /data/camera-detection/images -type f | wc -l
```

### 3.4 保留策略与清理机制

> ⚠️ **2026-10-27 修复**：应用内的 `DataCleanupTask`（02:00）曾因
> `Unknown column 'image_id'` 整体失败 —— 它带 `@Transactional`，
> 第一步抛异常会让**三个清理步骤全部回滚**（图片清理、生产数据归档、操作日志清理）。
> 根因是 MyBatis-Plus 的 `@TableId` 未显式写 `value` 时会按**字段名**推导列名。
> 已修复（`@TableId(value = "id", ...)`）并实测通过。

| 数据 | 保留 | 由谁清理 |
|---|---|---|
| `defect_image_file` / `_box` | **7 天** | `cleanup-defect-images.sh`（cron 03:30） |
| `defect_image_batch` | 30 天 | 同上 |
| `camera_images`（兼容表） | 7 / 30 天 | 同上 + 应用内 `DataCleanupTask`（02:00） |
| `fact_production_30min` | 3 个月 | 应用内 `DataCleanupTask`（归档到 `fact_production_30min_archive`） |
| `sys_operation_log` | 6 个月 | 应用内 `DataCleanupTask` |
| `agg_*` / `fact_inspection_*` | 永久 | 不清理（看板数据源，量小） |

**⚠️ 清理顺序必须是「先删库记录、再删磁盘文件」**：

反过来（先删文件）会让库中记录仍指向已删除的文件 → 前端显示破图，
且 `resolveImagePath()` 返回 null，**记录永不复收**。
先删记录再删文件则天然幂等 —— 文件删失败下次会跳过。

> **必须知道的坑（已修复，但要知道原理）**：
> `sys_data_retention_policy` 表存了 5 条策略，但**代码从不读它** ——
> 真正的清理是 `DataCleanupTask` 里硬编码的三条。新版缺陷图片表
> `defect_image_file` 及其磁盘文件**原本没有任何定时任务清理**，
> 这就是 2026-10-26 补上 `cleanup-defect-images.sh` 的原因。

**清理任务的执行时间可配置**（排查时很有用）：

```yaml
# /opt/camera-detection-system/config/application.yml
app:
  cleanup:
    cron: "0 0 2 * * ?"     # 默认每天 02:00
```

改完 `systemctl restart camera-detection` 生效。
排查时可临时改成每分钟 `"0 * * * * ?"` 快速验证清理链路，**验证完记得改回**：

```bash
# 观察三个步骤的产物
mysql -h127.0.0.1 -u root -N -e "
  SELECT CONCAT('  过期图片=',COUNT(*)) FROM \`wms-new\`.\`camera_images\`
    WHERE capture_time <= DATE_SUB(NOW(), INTERVAL 30 DAY);
  SELECT CONCAT('  归档表=',COUNT(*)) FROM \`wms-new\`.\`fact_production_30min_archive\`;
  SELECT CONCAT('  事实表残留=',COUNT(*)) FROM \`wms-new\`.\`fact_production_30min\`;"
```

> ⚠️ **外部配置覆盖内置配置的坑**：`application.yml` 的外部生产配置会覆盖 JAR 内置配置。
> 若外部配置里 `app:` 块存在而缺 `cleanup` 子键，**新增的子键不会被自动补上** ——
> 升级后若发现清理任务没按预期时间跑，先检查这个键是否存在。

手工执行与查看：

```bash
# 预演（不实际删除）
sudo MYSQL_PASSWORD='...' DIR=/data/camera-detection/images/defect-images \
  bash /usr/local/bin/cleanup-defect-images.sh --dry-run

# 实际执行
sudo MYSQL_PASSWORD='...' DIR=/data/camera-detection/images/defect-images \
  bash /usr/local/bin/cleanup-defect-images.sh

# 定时任务日志
tail -20 /var/log/camera-detection-cleanup.log
```

## 4. 常见故障速查

### 4.1 服务类

| 现象 | 原因 | 处理 |
|---|---|---|
| `systemctl status` 显示 `activating` 一直不变 | 应用启动时连不上库，反复崩溃 | 看 `journalctl -u camera-detection -n 50`；先建库再启动 |
| `status=127/n/a` | `run.sh` 找不到 java 或配置格式错 | `cat /etc/default/camera-detection`；`/etc/default/` 里的值**必须加引号**（`JAVA_OPTS="-Xms512m -Xmx1024m"`） |
| `Start request repeated too quickly` | 连续失败 3 次触发 systemd 限流，**此时 restart 会被直接拒绝** | `systemctl reset-failed camera-detection && systemctl restart camera-detection` |
| 内存溢出 / 容器被杀 | 堆配置过大或磁盘满导致 GC 风暴 | `free -m`、`df -h /var`；调小 `/etc/default/camera-detection` 的 `JAVA_OPTS` |
| 端口 8091 被占 | 其他进程 | `ss -tlnp \| grep 8091` |
| 开机不自启 | `enable` 没做 | `systemctl enable camera-detection`；`systemctl is-enabled camera-detection` 应返回 `enabled` |

### 4.2 数据库类

| 现象 | 原因 | 处理 |
|---|---|---|
| `Unknown database 'wms-new'` | 库没建 | `sudo MYSQL_PASSWORD=... /opt/camera-detection-system/scripts/init-database.sh` |
| `Access denied for user 'root'@'localhost'` | 口令错；或该机 root 是 `auth_socket`（不认密码） | 查 `SELECT user,host,plugin FROM mysql.user;`；本机是 `mysql_native_password`，直接用密码 |
| `Public Key Retrieval is not allowed` | 账号是 `caching_sha2_password` 但 JDBC URL 缺参数 | 用 `application.yml` 里含 `allowPublicKeyRetrieval=true&useSSL=false` 的 URL |
| `Unknown column 'brand_id'` | 建库脚本没跑全 | 重跑 `04_align_entity_columns.sql` |
| `Table 'dim_camera' doesn't exist` | 用了旧的 `wms-new.sql` 建库 | 用 `sql/` 下 4 段脚本重跑 |
| `Unknown column 'image_id'` | 用了修复前的 JAR | 换新 JAR（`CameraImage` 主键映射已改） |
| 表被清空 | 跑了 `02_final_schema_p0.sql` | **该脚本会 DROP 并重建 21 张表**，生产库只能跑增量 DDL |

### 4.3 接口类

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面 403 | 路径不在白名单 | 查 `SecurityConfig` |
| 节假日/用户/公司页 404 | 前端复数 ↔ 后端单数（`/api/holidays` vs `/api/holiday`） | 统一 URL 后同步白名单 |
| 登录总是"用户名或密码错误" | `sys_user.password_hash` 为 NULL | 跑 `04` 脚本（已含哈希搬运语句） |
| 批量上报 422 `UNMAPPED` | `sourceCode` 与映射表不一致（**大小写敏感**） | 查 `cfg_camera_defect_mapping.source_code`，有效值形如 `p0`、`p1` |
| 批量上报 500 | `dim_camera` 缺该相机 | 补 `dim_camera` 记录 |
| 批量上报报 schemaVersion 错 | **只接受 `"2.0"`**（DTO 注释写的 `1.0` 是错的） | 改请求体 |
| 图片传了不显示 | 文件名与 metadata 不符 / 映射缺失 / 目录权限 | 查 `data/uploads` 属主是否 `cdsys` |
| 设备上报 413（走 nginx） | nginx `client_max_body_size` 默认 1MB | 调大到 `1024m` |
| 看板 500 | `fact_production_30min` 缺列 | 跑 `04` 脚本 |

### 4.4 磁盘类

| 现象 | 原因 | 处理 |
|---|---|---|
| `/var` 持续上涨 | 缺陷图片不被清理 | 见 §3.4、§3.5 |
| journald 涨到几十 GB | SQL 打印未关 | 见 §2.3（已修） |

## 6. 备份与恢复

> ⚠️ **2026-10-26 架构评审后已重建**：原先是"手工执行的 mysqldump 脚本"，
> 现在是 **systemd timer 每日自动全量备份 + sha256 校验 + 恢复演练流程**。
> 改造前**服务器上完全没有备份**。

### 6.1 自动备份（已上线）

| 项 | 值 |
|---|---|
| 触发 | **systemd timer**，每日 **01:00**（`Persistent=true`，关机错过会补跑） |
| 方式 | `mysqldump --single-transaction --quick --routines --triggers --events` + `zstd -3` |
| 位置 | `/data/camera-detection/backup/db/full/wms-new_<时间戳>.sql.zst` |
| 保留 | 14 份（`KEEP_FULL_DAYS=14`），过期自动删除 |
| 校验 | 每个文件配 `.sha256` 伴随文件 |
| 增量 | 依赖 MySQL binlog（**已开启，ROW 格式，保留 30 天**），可用 `mysqlbinlog` 做时间点恢复 |
| 异机同步 | `OFFSITE_DIR` 指向的目录（⚠️ **当前仍是同一物理盘，需改为另一台机器**） |

**为什么选 01:00**：早于应用内 `DataCleanupTask`（02:00 清理）——
备份的是**清理前的完整状态**；也早于图片清理（03:30），且避开夜班交接。

**`--single-transaction` 的意义**：对 InnoDB 取一致性快照且**不锁表**，
业务无感知。备份窗口只是磁盘占用时间，不是停机时间。

运维命令：

```bash
# 看定时器
sudo systemctl list-timers camera-detection-backup.timer

# 手动触发一次
sudo systemctl start camera-detection-backup.service
sudo systemctl show camera-detection-backup.service -p Result --value   # 应为 success

# 看日志
sudo journalctl -u camera-detection-backup.service -n 30

# 看产物 + 校验
ls -la /data/camera-detection/backup/db/full/
cd /data/camera-detection/backup/db/full && sudo sha256sum -c *.sha256

# 备份脚本日志
tail -20 /data/camera-detection/backup/db/logs/backup.log
```

> **口令来源**：`/etc/default/camera-detection` 的 `MYSQL_PASSWORD`（640 root）。
> `install.sh` 装时从 `application.yml` 的 `datasource.password` 自动提取 ——
> **改数据库口令只需改 `application.yml` 一处**，备份与清理脚本自动跟随。
> unit 文件里**不写口令**（unit 是全局可读的）。

### 6.2 恢复演练（**务必每月做一次**）

> 未验证的备份等于没有备份。以下流程**不碰生产库**。

> ⚠️ **先确认 root 的认证插件** —— 两种情况写法完全不同（2026-10-31 实测踩过）：
>
> ```bash
> mysql -h127.0.0.1 -uroot -p'口令' -N -e \
>   "SELECT user,host,plugin FROM mysql.user WHERE user='root';"
> ```
>
> | plugin | 现象 | 正确写法 |
> |---|---|---|
> | `auth_socket` | Ubuntu 默认。只认 OS 身份，**不认口令** | `sudo mysql ...`（socket 免密），**不能加 `-h127.0.0.1`** |
> | `mysql_native_password` | 改过之后就是这种（如本机 10.2.77.72） | **必须带 `-h127.0.0.1` + 口令**，socket 免密会失败 |
>
> **判别方法**：不带口令执行 `sudo mysql -e "SELECT 1"` ——
> 成功 = `auth_socket`；报 `Access denied ... (using password: NO)` = `mysql_native_password`。
>
> **最稳的写法**（两种插件都适用，统一走 TCP + 环境变量口令）：
>
> ```bash
> export MYSQL_PWD='你的数据库口令'
> mysql -h127.0.0.1 -uroot -e "SELECT 1"     # 先验证能连上
> ```
>
> ⚠️ `sudo` **不继承** `MYSQL_PWD`；若要在 `sudo bash -c '...'` 里用口令，
> 必须写成 `sudo MYSQL_PWD='xxx' bash -c '...'`。

```bash
# 1. 建临时库
export MYSQL_PWD='你的数据库口令'
mysql -h127.0.0.1 -uroot -e "DROP DATABASE IF EXISTS cds_restore_test; \
                               CREATE DATABASE cds_restore_test DEFAULT CHARSET utf8mb4;"

# 2. 回灌（zstd 解压后直接管道给 mysql，字节流不乱码）
zstd -dc /data/camera-detection/backup/db/full/*.sql.zst \
  | mysql -h127.0.0.1 -uroot cds_restore_test

# 3. 校验四件事
sudo mysql -h127.0.0.1 -u root -N -e "
  SELECT CONCAT('  表数=',COUNT(*),' (应为 39)') FROM information_schema.tables
    WHERE table_schema='cds_restore_test';
  SELECT CONCAT('  索引数=',COUNT(DISTINCT index_name),' (应为 7)')
    FROM information_schema.statistics
    WHERE table_schema='cds_restore_test' AND table_name='defect_image_file';
  SELECT CONCAT('  中文=',product_name) FROM cds_restore_test.dim_product LIMIT 1;
  SELECT CONCAT('  映射=',COUNT(*),' 条 (应为 120)')
    FROM cds_restore_test.cfg_camera_defect_mapping;"

# 4. 清理
sudo mysql -e "DROP DATABASE IF EXISTS cds_restore_test;"
```

**2026-10-26 实际演练结果**：39 表、索引 7 个、`产品A` / `杭州工厂` / `产线缺陷在线AI检测系统`
中文完好、`cfg_camera_defect_mapping` 120 条 —— **全部通过**。

## 8.6 2026-10-31 服务器实测发现并已修掉的 3 个缺陷

> 这三个都是**在服务器上跑出来才发现**的 —— 代码走查看不出来。
> 完整复现步骤见 `docs/服务器运行与问题排查手册.md` 同名章节与评审报告。

### 缺陷 1（最严重）：匿名可注册管理员账号

`/api/auth/register` 在 `SecurityConfig` 白名单里（匿名可调），
而 `AuthController.register()` **直接采用请求传入的 role**：

```java
user.setRole(request.getRole() != null ? request.getRole() : 0);   // ← 致命
```

**实测链路**（2026-10-31 已复现并修复）：

```
匿名 POST /api/auth/register  {"username":"evil","password":"...","role":1}
  → HTTP 200「注册成功」
  → 库里真的写入 role=1（管理员）
  → 用该账号登录拿到 token
  → /api/user、/api/v1/system/settings、/api/logs/operation 全部 200
```

**修复**：角色由服务端决定，**永远为普通用户（0）**，请求里传什么都不采信。
管理员账号只能由已登录的管理员在「系统设置 → 用户管理」里创建。

> **建议后续**（需业务确认）：生产环境应把 `/api/auth/register` 从白名单移除、
> 关闭自助注册 —— 前端注册页保留但接口不开放，工人账号一律由管理员建。

### 缺陷 2：登录接口 `password` 字段缺失 → HTTP 500

`BCryptPasswordEncoder.matches(null, hash)` 抛
`IllegalArgumentException: rawPassword cannot be null`，
被 Spring 兜成 **500 + 默认错误页** —— 既不像业务失败、也在日志里刷整段堆栈。

**修复**：入参判空（null / 空串 → 直接返回「用户名或密码错误」）；
同时修掉 `isDisabled` 为 `Integer` 时 `== 1` 的**自动拆箱 NPE** 隐患。

修复后实测三种入参：

| 请求体 | 修复前 | 修复后 |
|---|---|---|
| `{"username":"admin"}`（无 password） | **HTTP 500 + 默认错误页** | HTTP 200 + 「用户名或密码错误」 |
| `{"username":"admin","password":""}` | 200 + 提示 | 200 + 提示（不变） |
| `{"username":"admin","password":"admin123"}` | 200 + 成功 | 200 + 成功（不变） |

### 缺陷 3：清理脚本「图片目录不存在」时跳过库记录清理

`cleanup-defect-images.sh` 原本在第 69 行 `exit 0`，
而库记录统计在第 126 行、删除在第 207 行 ——
**目录一旦不存在（首次部署未上传过图片、或目录被清掉），

### 缺陷 4（★ P0）：匿名可读写生产库 —— `/api/v1/**` 白名单过宽

#### 根因

上一版为了让设备端接口免鉴权，把**整个 `/api/v1/**`** 放进了白名单：

```java
// ❌ 修复前
.antMatchers(
    "/api/v1/**",          // ← 致命
    "/api/camera/heartbeat",
    ...
).permitAll()
```

但 `/api/v1/**` 下面**不只有设备端点**，还混着一大批管理端点：

| 路径 | 功能 | 匿名可做什么 |
|---|---|---|
| `/api/v1/system/settings` | 系统设置 | GET 读、**PUT 改** |
| `/api/v1/config/products` | 产品配置 | GET 读、**POST/PUT/DELETE 写** |
| `/api/v1/config/defect-types` | 缺陷类型 | GET 读、**POST/PUT/DELETE 写** |
| `/api/v1/config/camera-defect-mappings` | 缺陷映射 | GET 读、**写** |
| `/api/v1/config/mapping-exceptions` | 映射异常 | GET 读、**PUT 关闭异常** |
| `/api/v1/analytics/**` | 看板与部件 | GET 读、**写** |

同时 `JwtRequestFilter` 的 `DEVICE_PATHS` 也是 `/api/v1/**`，
导致该前缀下**所有请求都不做 JWT 认证**。

#### 实测复现（2026-10-31，服务器 10.2.77.72，真实改生产库）

```
① 匿名 PUT /api/v1/system/settings
   body: {"settings":[{"settingKey":"alert.cpuWarning","settingValue":"77"}]}
   → HTTP 200「系统设置已保存」
   → 查库：alert.cpuWarning 从 90 变成 77      ← ★ 匿名真的改了生产库

② 匿名 POST /api/v1/config/products
   body: {"productCode":"PROBE_001","productName":"匿名插入"}
   → HTTP 200「创建成功」
   → 查库：dim_product 从 2 条变成 3 条        ← ★ 匿名真的插了数据

③ 匿名 GET /api/v1/config/products、/defect-types、/camera-defect-mappings
   → 全部 HTTP 200                              ← ★ 配置数据完全泄露
```

**危害**：**只要能访问到 8091 端口，不需要任何凭据**，
就能改告警阈值、增删产品与缺陷类型、改缺陷映射、关掉异常单、读写看板。
这比 §8.6 缺陷 1（匿名注册管理员）更严重 —— 那个至少要先注册一个账号。

#### 修复

白名单改为**精确到方法与路径**，只放行冻结契约的 3 个设备端点 + 图片静态读取：

```java
// ✅ 修复后
.antMatchers(HttpMethod.POST,
    "/api/v1/camera/status/heartbeat",           // 冻结契约
    "/api/v1/camera/inspection/batch-upload",     // 冻结契约
    "/api/v1/defect-images/upload"                // 冻结契约
).permitAll()
.antMatchers(HttpMethod.GET,
    "/api/v1/defect-images/file/**",              // 图片静态读取
    "/api/v1/camera/image/**"
).permitAll()
```

> ⚠️ **图片静态读取必须保持放行**：前端 `<img :src="...">` 标签
> **不会带 Authorization 头**（浏览器只在 XHR/fetch 里才带）。
> 一旦要求 token，前端所有缺陷图片都会裂图。
> 这类路径用的是不可猜测的名字（日期/相机/毫秒时间戳+uuid8），暴露面可接受。

`JwtRequestFilter.DEVICE_PATHS` 同步收窄为同样 3 个精确路径。

### 缺陷 5（★ P0）：无角色鉴权 —— 普通用户可删管理员

#### 根因

`JwtRequestFilter` 早已把角色放进 Spring Security 的权限集合：

```java
// JwtRequestFilter.java —— role==1 → ROLE_ADMIN，role==0 → ROLE_USER
list.add(new SimpleGrantedAuthority(role != null && role == 1 ? "ROLE_ADMIN" : "ROLE_USER"));
```

但 `SecurityConfig` **从来没用过它** —— 只有 `authenticated()`，没有 `hasRole()`。
全仓库也没有 `@EnableGlobalMethodSecurity` / `@PreAuthorize` / `@Secured`。

**前端做菜单隐藏（`Layout.vue` 的 `isAdmin`），但那只是界面隐藏，不是权限控制。**

#### 实测复现（2026-10-31）

```
① 匿名 POST /api/auth/register  {"username":"probe_worker_01",...}
   → 200「注册成功」，角色被固定为 0（这部分上一轮已修）
② 用该账号登录拿到 token（role=0）
③ GET  /api/user              → 200（读到全部用户）
④ GET  /api/logs/operation    → 200（读到全部操作日志）
⑤ DELETE /api/user/3          → 200「删除成功」
⑥ 查库：admin 账号被删除，只剩探针账号   ← ★ ★
```

> 事后已从备份恢复 admin（`user_id=3`，口令 `admin123`，实测可登录）。

#### 修复（路径级 + 方法级双保险）

**第一步：路径级**（`SecurityConfig`）—— 原则是**读开放给所有登录用户，写只给管理员**：

```java
// 纯管理，全段 ADMIN
.antMatchers("/api/user/**", "/api/logs/operation/**").hasRole("ADMIN")

// 写操作 ADMIN
.antMatchers(HttpMethod.POST, "/api/v1/config/**", "/api/v1/analytics/**",

.antMatchers(HttpMethod.PUT,   ...).hasRole("ADMIN")
.antMatchers(HttpMethod.DELETE, ..., "/api/detection-history/clean-history").hasRole("ADMIN")

// 其余只读端点：登录即可（现场工人也要看看板、缺陷记录）
.antMatchers("/api/stats/**", "/api/cameras/**", "/api/v1/defect-images/recent", ...)
        .authenticated()
```

**第二步：方法级**（防将来新增路径漏配）：

```java
@Configuration
@EnableGlobalMethodSecurity(prePostEnabled = true)   // 开启方法级鉴权
```

并在 8 个高危 Controller 的写方法上加 `@PreAuthorize("hasRole('ADMIN')")`：
`SysUserController`、`SystemSettingsController`、`FinalConfigController`、
`ConfigImportController`（整类）、`DimCompanyController`、

### 缺陷 6（P1）：`/etc/default/camera-detection` 重复叠加 4 份

实测现场该文件 **103 行**，同样的「备份相关」段落出现了 **4 次**
（第 22、47、72、97 行）。

**根因**：`install.sh` 第 4 节用 `cat >` 写主体、第 8c 节用 `cat >>` 追加备份参数，
而第 8c 节的 `sed -i` **只删掉了 4 个变量行，没删注释行**：

```bash
sed -i '/^MYSQL_PASSWORD=/d; /^BACKUP_DIR=/d; ...'   # ← 注释行 "# ---- 备份相关 ----" 残留
cat >> /etc/default/camera-detection <<EOF
...
EOF
```

**重复执行 install.sh 就会一段段叠加。**

**后果**：
- 最后一行的 `ADMIN_PASSWORD` 才是生效值，前面的重复段全是垃圾
- 排查时容易看错段、改错位置
- `run.sh` 会 source 整个文件，重复的 `MYSQL_PASSWORD=` 赋值虽然值相同不出错，
  但**一旦某次值不同，生效的是最后一段**，极易误判

**修复**：
1. 第 4 节改为**整份文件一次性重写**（`mktemp` + `mv`，原子替换）
2. 第 8c 节追加前**先剥离整个备份段**（含注释行），并折叠多余空行
3. 权限从 `chmod 0644` 改为 **`chmod 640`** —— 之前第 4 节写的是 0644，
   而文件里有数据库口令与管理员口令，**0644 意味着任何本地用户都能读到**；
   第 8c 节才改回 640，安装中途失败就会短暂暴露

**实测**：模拟重复执行 3 次，文件稳定在 31 行、内容一致（不再增长）。

### 缺陷 8（P2）：自检检查的是"用不到的目录"，真正的落盘目录从未被检查

**根因**：`run.sh` 每次启动都执行：

```bash
mkdir -p "${WORK_DIR}/logs" \
         "${WORK_DIR}/data/uploads/images" \
         "${WORK_DIR}/data/uploads/defect-images" 2>/dev/null || true
```

而 `verify.sh` 检查的也是这条路径。但**缺陷图片实际落盘在
`/data/camera-detection/images/defect-images/`**（配置项 `defect-image.upload.dir`），
`run.sh` 里硬编码的这条是**迁移前的遗留**，应用根本不用。

**危害**：自检永远显示"目录存在且可写"，
**真正在用的 `/data/.../defect-images` 从未被检查** ——
它一旦不存在（比如误删、换机漏建），图片上传会"返回成功但不落盘"，

1. `run.sh` 不再创建遗留路径
2. `verify.sh` 改为**从 `config/application.yml` 解析实际落盘目录**再检查：

```bash
DEFECT_IMAGE_DIR="$(sed -n 's/^[[:space:]]*dir:[[:space:]]*\(.*\)$/\1/p' \
  "${INSTALL_DIR}/config/application.yml" | grep -E '^/' | head -1)"
```

目录不存在时报「图片上传会『成功但不落盘』」。

**修复后实测**：真实图片（200×150 PNG，63 KB）端到端上传成功，

（`{yyyyMMdd}/{cameraId}/{HHmmssSSS}_{uuid8}.{ext}`）全部正确。

### 缺陷 9（★ P1）：每分钟 4 次重复 DDL —— 慢查询日志被自己的建表语句淹没

#### 现象

MySQL 慢查询日志 `/var/log/mysql/slow.log` 里，**近期慢查询全是同一条建表语句**：

```
# Time: 2026-11-01T20:16:24.300856Z
# Query_time: 7.411144  Lock_time: 0.000003
CREATE TABLE IF NOT EXISTS analytics_aggregation_schedule (...);
```

#### 根因

`LineAnalyticsController` 的 3 个 `ensure*` 方法**每次被调用都执行一遍 DDL**，
而它们被 `@Scheduled(fixedDelay = 60000)` 每分钟调一次 → **每天 5760 次无谓 DDL**。

#### 危害

- **元数据锁（MDL）阻塞**：DDL 期间该表上所有查询排队，实测单次最慢 **7.4 秒**
- DDL 不可回滚、不能与事务共存，是 InnoDB 最重的操作
- 慢查询日志被自己的 DDL 淹没，**真实业务慢查根本找不到**

#### 修复

三个 `ensure*` 各加 `AtomicBoolean` 守卫，DDL 只在进程内首次调用时执行一次：

```java
private final AtomicBoolean scheduleTableEnsured = new AtomicBoolean(false);

private void ensureAggregationScheduleTable() {
    if (!scheduleTableEnsured.compareAndSet(false, true)) {
        return;   // ★ 已建过，直接跳过
    }
    try {
        jdbcTemplate.execute("CREATE TABLE IF NOT EXISTS ...");
        ...
    } catch (Exception e) {
        scheduleTableEnsured.set(false);   // ★ 失败必须复位
        throw e;
    }
}
```

> ⚠️ **失败复位是关键**：否则第一次建表失败（比如 MySQL 短暂不可用），
> 标志位永久停在 `true`，应用再也不会建表 —— 那才是真故障。
> 用 `compareAndSet` 而非 `get()+set()`，多线程下也只建一次。

#### 修复后实测

```
部署 → 100 秒（覆盖 1+ 个定时周期）→ 手动再调一次接口
  GET /api/v1/analytics/aggregation/schedule -> 200
  慢查询日志中该 DDL 的条数：部署前 5 → 部署后仍是 5   ← 不再增长 ✅
```

> 修复前：每分钟 +4 条。

### 缺陷 10（★ P2）：自检脚本每次运行都往生产库写脏数据

#### 现象

`fact_inspection_mapping_exception` 表里出现 `batch_id = VERIFY-UNMAPPED` 的记录。

#### 根因

`verify.sh` 验证"未映射编码应返回 422"时会发一条**真实上报**，
服务端如实写库：
`fact_inspection_mapping_exception` +1、`fact_inspection_batch` +1、
`fact_inspection_defect_count` +1。

而这些表**没有任何定时清理任务**（`sys_data_retention_policy` 只是元数据，代码从不读它），
自检跑得越多，垃圾越多。

**实测证据**：跑一次自检，异常表 3 → 4 条、批次 1 → 2 条（只增不减）。

#### 危害

- **污染业务数据**：假异常会出现在"映射异常统计"里，
  让现场误以为设备真有映射问题
- 验收时看库里有 UNMAPPED 记录，分不清是测试造的还是设备真报的

#### 修复

`verify.sh` 末尾新增第 8 节，自检后**立刻清掉自己造的数据**：

```bash
DELETE FROM fact_inspection_mapping_exception WHERE batch_id LIKE 'VERIFY%';
DELETE FROM fact_inspection_batch                WHERE batch_id LIKE 'VERIFY%';
DELETE FROM fact_inspection_defect_count         WHERE batch_id LIKE 'VERIFY%';
```

- 口令从 `/etc/default/camera-detection` 读（640 root）
- 清理前后各查一次条数，**清理不彻底则自检判失败**
- 只匹配 `VERIFY%` 前缀 —— 真实设备的 batch_id 不会是这个前缀

#### 修复后实测

```
[8] 清理自检数据
  通过  清理自检数据       已清理 异常 4 条 / 批次 1 条
  通过 26 项，失败 0 项

执行后：异常表 0 条 / VERIFY 批次 0 条   ← 自检不再留痕 ✅
```

> 自检项数从 25 增到 **26**。

## 附录 C：磁盘写满故障树（2026-10-26 新增）

> 触发条件：`/data` 按 350 KB/张、144000 张/天 约 **10 天**写满；
> `/var`（含 MySQL datadir）若图片仍在 `/var` 则约 **1 天**写满。

### C.1 症状对照

| 症状 | 最可能原因 | 立即动作 |
|---|---|---|
| 页面 200 但**上传图片失败** | 图片分区写满 | `df -h /data` |
| 上传返回 **200 但文件不落盘** | systemd `ReadWritePaths` 未放行该路径 | `systemctl show camera-detection -p ReadWritePaths` |
| 上传返回 **500 / 数据库错误** | `/var` 写满（MySQL datadir 在 `/var/lib/mysql`） | `df -h /var` |
| 磁盘 100% 但 `du` 查不到大文件 | **inode 耗尽**（海量小文件） | `df -i /data` |
| 应用日志暴涨 | journald 未限容 | `journalctl --disk-usage` |

### C.2 排查步骤

```bash
# 1. 容量与 inode 一起看
df -hT /var /data
df -i /var /data

# 2. 谁在占
du -sh /data/camera-detection/* 2>/dev/null
du -sh /var/lib/mysql 2>/dev/null
du -sh /var/lib/camera-detection-system/logs 2>/dev/null

# 3. 图片文件数（144000 张/天 → inode 消耗快）
find /data/camera-detection/images -type f 2>/dev/null | wc -l

# 4. 看告警记录
tail -20 /var/log/camera-detection-disk-alert.log 2>/dev/null
```

### C.3 应急处置

```bash
# 1. 立即释放：手动跑一次清理（缩短保留期）
sudo MYSQL_PASSWORD='...' DIR=/data/camera-detection/images/defect-images   KEEP_DAYS=2 bash /usr/local/bin/cleanup-defect-images.sh

# 2. 紧急清 journald
sudo journalctl --vacuum-size=200M

# 3. 若 /var 满：先停应用，再清 MySQL 临时文件
sudo systemctl stop camera-detection
sudo rm -f /var/lib/mysql/mysql-bin.*        # binlog（注意：会丢失增量恢复点）
sudo systemctl start camera-detection

# 4. 确认应用能连库
sudo systemctl reset-failed camera-detection && sudo systemctl start camera-detection
```
