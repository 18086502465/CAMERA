## 二、逐项说明

### H-1　报表读路径不再写库（PERF-02）

**改造前**（每次查询都执行）

```java
if (daily) {
    aggregationRepository.ensureDailyAggregationTables();
    rebuildQualityDaily(start, end, factoryId, lineId);   // DELETE 全范围 + INSERT … SELECT
    rebuildDefectDaily(start, end, factoryId, lineId);    // 同上
    aggregationRepository.purgeOrphanAggregationRows();   // 4 张表全表 DELETE + LEFT JOIN
}
```

前端 30s 轮询 → 每 30s 一次全范围重建；多用户并发时「DELETE 已提交、INSERT 未完成」的窗口里
别人查到的是空数据；binlog/redo 写放大、锁等待反向拖慢上传主链路。

**改造后**

- 查询侧：`ensureDailyAggregationTables()`（INFORMATION_SCHEMA 幂等查询，不执行 DDL）+ 只读水位判断；
- 写入侧①：`@Scheduled(fixedDelay=300_000, initialDelay=90_000) refreshRecentDailyAggregation()`
  刷新「今天 / 昨天 / 前天」窗口（口径与 3 天阈值对齐），单线程执行器 + `recentRefreshInFlight` 防重入，
  **不写任务表**（5 分钟一条会把任务表变成日志，淹没手工任务）；
- 写入侧②：查询发现水位落后时 `requestAsyncAggregation()` 异步补齐，**10 分钟节流**，
  不阻塞本次请求；
- 孤儿行清理：从「每次查询」移到刷新任务内，**1 小时节流**（产线删除是低频人工操作）；
- 重建的 DELETE + INSERT 放进**同一事务**（`rebuildDailyAtomically`），
  配合 InnoDB MVCC，并发查询不会再看到「今天被删了还没插回来」的空窗。

**响应新增字段**（仅 `dataSource=AGGREGATION` 分支）：`aggregationWatermark`、`aggregationStale`，
并在 `aggregationMessage` 里如实说明「本次结果仅含已物化部分」。

**已知边界**：`aggregationWatermark` 为 `null`（日聚合表从未物化）时**不自动补齐** ——
现场设备走图片通道、`agg_quality_30m` 本身是空表，补齐只会产出 0 行并刷一堆无意义任务；
这种情形交给 5 分钟刷新任务自动接上，历史区间用 `POST /api/v1/analytics/aggregation/daily/run` 显式补齐。

### H-2　`/line-summary` 短缓存（PERF-03）

- 新增 `TtlCache<K,V>`：`ConcurrentHashMap` + 每项过期时间戳，容量满时先清过期再放弃写入（**有界**，不会变内存泄漏）；
- 缓存键 = 起始/结束时间（精确到秒）+ 工厂/产线/工位/相机/产品/班次/缺陷类型/严重度；
- TTL 60s、容量 64 条：30s 轮询可命中一半以上，最坏内存 ≈ 数 MB；
- **只读约定**：缓存值是响应 Map，取用方只经 Jackson 序列化，没有任何调用方原地修改；
- 为什么不上 Caffeine / Spring Cache：现场离线部署，少一个三方依赖少一条发版链。

### H-3　上传事务瘦身（PERF-04）

`DefectImageServiceImpl.upload`：

| 改造前 | 改造后 |
|---|---|
| 方法级 `@Transactional` 包住整批（≤100 张） | 无方法级事务 |
| 事务内：`Files.copy` 落盘、`ImageIO.read` 解码、逐张 INSERT | 落盘/解码在事务外；每张图的「图片行+缺陷框+兼容表」为一个独立短事务（`persistImageRows`） |

行为等价性：原实现逐张 `try/catch` 并把失败记进 `results`，**从不因单张失败回滚整批** ——
所谓「整批事务」从未提供整批原子性，只是把文件 IO 白白关进事务里。
改用编程式 `TransactionTemplate` 而非给私有方法加注解，是因为**同类内部调用不走 Spring 代理**，
注解会静默失效。

`ConfigImportController.importConfig`：Excel 解析（`WorkbookFactory.create` + 逐行解析校验）
移到事务外，解析产物 `ParsedRow` 列表进事务落库。错误语义保持：单行失败仍 catch 后
计入 `failedRows` 并追加「第 N 行：xxx」，不回滚其他行。

**未改**：`InspectionUploadServiceImpl`（冻结契约 `batch-upload`）—— 该通道入参是纯 JSON
（无 multipart、无磁盘 IO、无解码），事务本身就是纯 DB 操作，不构成 H-3 所指的问题；
改动它反而扩大冻结契约的回归面。

### H-4　告警去重与恢复（SEC-NEW-05）

策略（键 = `camera_code|alert_type`）：

| 情形 | 动作 |
|---|---|
| 条件首次成立 | 插 1 条告警 |
| 30 分钟窗口内重复 | 只累加抑制计数，**不写库** |
| 超过 30 分钟仍持续 | 续报 1 条（消息带「已持续 X 分钟，期间抑制 N 条」），并把上一条置 `resolved_by=SUPERSEDED` —— 保证同一时刻同一 key **只有 1 条未恢复** |
| 条件消失并稳定 2 分钟 | 置 `is_resolved=1, resolved_by=AUTO_RECOVER`（抗抖动） |

- 状态放进程内：`fact_anomaly_alert` **没有 camera_code 列**，无法在库侧按相机去重，
  用 message 文本匹配不可接受；重启后首条心跳会新开一条、旧的留未恢复，属可接受的降级；
- 跨域仍走事件：`CameraAlertEvent` 增加 `resolved` 标记与 `alertId`（同步监听器回填 / 恢复事件由发布方给出），
  device 域**不直接写** analytics 域的 Repository（ArchUnit 规则保持通过）；
- 恢复关闭用 UPDATE 而不是插一条「已恢复」假行，历史可追溯且不污染告警列表。

### H-5　错误码族与 HTTP 状态对齐（QUAL-02）

- `ApiErrorCode`：`400xx` 参数 / `401xx` 凭据 / `409xx` 冲突 / `422xx` 设备上报 / `429xx` 限流 / `500xx` 内部；
- `ResultVO` 增加 `errorCode` 字段与 `of(ApiErrorCode…)` 工厂；
- `ApiStatusAdvice`（`ResponseBodyAdvice`）在一处把 code 映射成 HTTP 状态；
- **兼容硬保证**：只有枚举里登记过的 code 才改状态。存量 93 处 `ResultVO.fail(...)` 用的
  500/422 **未登记** → 仍返回原状态，前端 `code !== 200` 的分支全部照旧；
- 设备上报通道（`/api/v1/defect-images/upload`）**刻意不改 code 数值**（固件可能按 body.code
  判定重试），只补 `errorCode` 字符串；
- 前端只需确认一件事：`/api/auth/login` 失败现在是 HTTP 401 —— `request.js` 的 401 分支
  在登录页 `redirectToLogin()` 会直接 return（`pathname === '/login'`），因此不会误跳，
  `Login.vue` 仍按 `e.response.data.message` 展示原文。

## 五、残留与建议

1. **告警恢复依赖后续心跳**：相机彻底下线（不再发心跳）时，未恢复告警会一直挂着。
   建议下一步加「心跳超时扫描」定时任务（`last_heartbeat_at < now-10min` → 自动置 OFFLINE 并关闭故障告警）。
2. **缓存一致性**：60s 内新上传的图片不会出现在报表里（可接受）。若要「传完即见」，可在
   上传成功后 `summaryCache.clear()` —— 需把缓存抽成 Spring Bean（当前是 Controller 内字段）。
3. **错误码只迁了两族**：其余 88 处仍是 `code=500`。建议按模块分批（用户管理 → 主数据 → 报表），
   每批只改 `ResultVO.fail` → `ResultVO.of`，由 `ApiStatusAdvice` 自动对齐状态。
4. **中优先级未动**：M-1 授权护栏（含 `/api/user/login` 第二登录端点无限速）、M-2 其余组件单测、
   M-3 空控制器与死规则、M-4 死视图、M-5 仓库瘦身、M-6 索引失效 —— 按 v3 报告节奏推进。
5. **本地未提交**：本轮与第 2 周改动均在工作区（未 commit / 未 push），等确认后再提交。
