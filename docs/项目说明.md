# 第一部分　项目功能项

## 1. 项目定位与目标

### 1.1 定位

面向**离散制造产线**的在线 AI 缺陷检测系统。工业相机在产线运行过程中持续上报状态与检测数据，系统在服务端完成**接收 → 校验 → 映射 → 聚合 → 展示**的完整链路，把相机侧的原始检测记录转化为产线管理层可直接消费的良率、缺陷分布与异常告警。

系统的核心使用者有三类，各自对应一组功能：

| 角色 | 使用入口 | 核心诉求 |
|---|---|---|
| 产线操作员 | `views/camera/CameraStatusView.vue`、`views/Dashboard.vue` | 实时看相机是否在线、当班产量与良率 |
| 质量工程师 | `views/stats/*`、`views/defect/GalleryView.vue` | 缺陷类型分布、趋势、图库回溯 |
| 系统管理员 | `views/system/ConfigView.vue`、`views/user/UserList.vue` | 维护组织/产品/缺陷分类/映射关系 |

### 1.2 目标

1. **打通设备侧数据入口** —— 冻结 3 个设备端 HTTP 接口（心跳、批量上报、缺陷图片上传），形成稳定的设备接入协议。
2. **建立统一的数据模型** —— 以「工厂 → 产线 → 工位 → 相机」为组织维度，以「品牌/产品 + 缺陷类型」为业务维度，把设备原始数据落到规范的维度表与事实表。
3. **提供可分析的聚合** —— 数据入库时同步写入 30 分钟粒度的质量聚合表（`agg_quality_30m`、`agg_defect_type_30m`），看板查询不必扫明细。
4. **交付可独立运行的系统** —— 单个 Spring Boot 可执行 JAR 内含前端静态资源，配套 systemd 单元与建库脚本，可在无外网的产线内网服务器上一键部署。

### 1.3 明确的非目标

- 不做图像识别算法本身。系统接收的是相机端**已完成的检测结果**（缺陷类型 + 位置 + 面积），不解析图片内容做推理。
- 不做设备端 SDK。本项目只定义设备与服务端之间的 HTTP 契约。
- 不做多租户。当前是单组织（公司/工厂/产线）的部署模型。

### 3.2 对外 HTTP 接口

统一响应封装 `ResultVO<T>`（`com.wms.vo.ResultVO`），字段 `{code, message, data}`，`code=200` 成功、`500` 业务失败、`422` 参数/业务校验失败。
设备侧接口（`/api/v1/**`）HTTP 状态码与 body `code` 同步；页面侧接口一律 HTTP 200，靠 body `code` 表达成败。

#### 3.2.1 设备侧冻结接口（协议见 `docs/api/接口冻结契约-v1.0-20260616.md`）

| # | 端点 | Controller | 输入 | 输出 |
|---|---|---|---|---|
| 1 | `POST /api/v1/camera/status/heartbeat` | `CameraStatusHeartbeatController` | Header `Authorization: Bearer <device-token>`、`X-Device-Id`；body `CameraStatusHeartbeatDTO`（相机名/编号/时间戳/状态/计数/CPU/内存/温度） | `ResultVO<CameraHeartbeatResponseDTO>`；写 `fact_camera_heartbeat`、`fact_camera_status_current`、同步 `camera_status` 兼容表 |
| 2 | `POST /api/v1/camera/inspection/batch-upload` | `BatchUploadController` | 同上 Header；body `InspectionBatchUploadRequest`（`schemaVersion` 必须 `"2.0"`、`batchId`、`cameraCode`、`productName`、`reportTime`、`counterMode`、`timeRange`、`summary`、`defects[]`） | `ResultVO<InspectionBatchUploadResponse>`；落 `fact_inspection_batch` / `_defect_count` / `_mapping_exception`，并 upsert `agg_quality_30m`、`agg_defect_type_30m`、`fact_camera_status_current` |
| 3 | `POST /api/v1/defect-images/upload` | `DefectImageController` | `multipart/form-data`：`files`（图片数组）+ `metadata`（JSON，含 `cameraId`/`cameraName`/`uploadTime`/`images[]`） | `ResultVO<DefectImageUploadResultDTO>`；图片落盘到 `defect-image.upload.dir`，写 `defect_image_batch` / `_file` / `_box` 与兼容表 `camera_images` |

**批量上报的错误码**（`InspectionUploadServiceImpl.fail422`）：

`TOKEN_REQUIRED`、`DEVICE_ID_REQUIRED`、`INVALID_BODY`、`INVALID_SCHEMA_VERSION`、`BATCH_ID_REQUIRED`、`CAMERA_CODE_REQUIRED`、`CAMERA_NOT_FOUND`、`PRODUCT_NOT_FOUND`、`COUNT_MISMATCH`、`INVALID_DEFECT_COUNT`、`UNMAPPED`

**图片上传的边界**：单批 ≤ 100 张（`defect-image.max-batch-images`）、单文件 ≤ 10 MB、整批 ≤ 1024 MB；超量返回 HTTP **413**（`DefectImageUploadLimitConfig` 按 `X-Image-Count` 头提前拒绝）。

**图片读取**：`GET /api/v1/defect-images/file/**` —— 按 `defect-image.upload.dir` + URL 相对路径解析（不依赖数据库里的绝对路径），因此换机器只需拷贝图片目录即可显示。

### 3.5 核心业务流程

#### 流程 A：设备批量上报（最核心）

```
相机/上位机
  │ POST /api/v1/camera/inspection/batch-upload
  │ Header: Authorization: Bearer <token>, X-Device-Id, X-Batch-Id
  ▼
BatchUploadController.batchUpload
  ▼
InspectionUploadServiceImpl.upload   @Transactional(rollbackFor=Exception, noRollbackFor=InspectionUploadException)
  │
  ├─ 1. validateBasic      → schemaVersion=="2.0"、batchId、cameraCode、reportTime、counterMode、summary 计数自洽
  ├─ 2. validateToken      → 查 cfg_camera_token 比对 SHA-256/明文
  ├─ 3. findCamera         → dim_camera 按 cameraCode / deviceId 定位
  ├─ 4. findProduct        → dim_product 按 productName 定位
  ├─ 5. 幂等检查            → queryExistingBatchId(batchId) 命中则直接返回 duplicate:true
  ├─ 6. 逐缺陷 findMapping → cfg_camera_defect_mapping 查 sourceCode→defect_type
  │        未命中 → fail422(UNMAPPED) + 记 fact_inspection_mapping_exception
  ├─ 7. insertBatch        → fact_inspection_batch
  ├─ 8. insertDefectCount → fact_inspection_defect_count
  ├─ 9. 聚合 upsert        → agg_quality_30m / agg_defect_type_30m（按 30 分钟桶）
  ├─ 10. upsertCurrentStatus → fact_camera_status_current
  ├─ 11. syncLegacyCameraStatus → camera_status 兼容表
  └─ 12. 返回 accepted:true / mappedDefectCount / duplicate 标记
```

**设计要点**：
- **幂等**：`batchId` 唯一，重复上报返回 `duplicate:true` 而非重复写入。
- **部分失败不整体回滚**：`noRollbackFor = InspectionUploadException.class` —— 某个缺陷编码未映射时，记录异常表并返回 422，但已成功落库的部分保留。
- **班次归属**：`resolveShiftId` 用 `ShiftCalculator`（白班 08:00-20:00，晚班 20:00-08:00 跨天）按 `reportTime` 判定。
- **时间桶**：`floorToBucket` 把时间向下取整到 30 分钟粒度，与 `dim_time_bucket_30min` 对齐。

#### 流程 B：缺陷图片上传

```
POST /api/v1/defect-images/upload  (multipart)
  │
  ├─ DefectImageUploadLimitConfig 过滤器：按 X-Image-Count 头判超量 → 413（不进入业务逻辑）
  ├─ 解析 metadata JSON → 校验 cameraId / images[] 与 files 一一对应
  ├─ saveFile：按 日期/相机/时间戳_随机8位.ext 落盘，Files.createDirectories + copy
  ├─ ImageIO 读宽高；PNG/JPG 解析失败 → 报「图片内容解析失败」
  ├─ insertImageFile   → defect_image_file
  ├─ insertDefectBoxes → defect_image_box
  └─ insertLegacyCameraImage → camera_images（兼容表，异常只 WARN 不阻断）
```

#### 流程 C：看板查询

```
前端 views/stats/*.vue
  │ api/stats.js、api/analytics.js（axios baseURL='/api'）
  ▼
StatsController / LineAnalyticsController
  ▼
repository/stats/StatsQueryRepository、repository/analytics/LineAnalyticsRepository
  │  JdbcTemplate 手写 SQL，直接查 agg_* 聚合表
  ▼
ResultVO<List<Map>> → ECharts 渲染
```

**设计要点**：看板**不扫明细表**，只读 `agg_quality_30m` / `agg_defect_type_30m` / `agg_defect_type_day` 等聚合表，响应时间与数据量解耦。

#### 流程 D：操作审计（横切）

```
任意 controller 公开方法
  ▼
OperationLogAspect  @Around("execution(* com.wms.controller..*(..))")
  ├─ 从方法名前缀推导 operationType：login→LOGIN、save/create/add→CREATE、update/edit→UPDATE、
  │   delete/remove→DELETE、export→EXPORT、其他→QUERY
  ├─ 从类名推导 moduleName
  ├─ 记录 user_id / user_name / request_method / request_uri / request_params / ip / 执行耗时 / 结果
  └─ 写 sys_operation_log（自捕获异常，不影响业务）
```
跳过 `/api/logs/operation` 自身，避免自记录。

#### 流程 E：定时任务

| 任务 | 时机 | 行为 |
|---|---|---|
| `InitTimeBucketRunner`（`CommandLineRunner`） | 应用启动 | 预生成 `dim_time_bucket_30min` 时间桶 |
| `DataCleanupTask` | 每天 02:00 | 清理 `camera_images`（30 天，删文件+删记录）、`fact_production_30min` 归档 3 个月、`sys_operation_log` 清理 6 个月 |
| `SystemSettingsController.init` / `CameraStatusServiceImpl.initSchema` / `DefectImageServiceImpl.init` | 启动（`@PostConstruct`） | 运行时自建 9 张表并补列 |

## 6. 核心模块实现思路与数据流

### 6.1 数据访问：三种风格并存（迁移中）

| 风格 | 位置 | 模式 | 适用 |
|---|---|---|---|
| MyBatis-Plus Mapper | `mapper/` + `resources/mapper/*.xml` | `BaseMapper<T>`、`LambdaQueryWrapper`、实体返回、逻辑删除 | 简单 CRUD（维度表、用户） |
| JdbcTemplate Repository | `repository/{analytics,stats,log}/` | 手写 SQL，返回 `Map<String,Object>`，手写 `is_deleted=0`、手写 `LIMIT ? OFFSET ?` | 复杂统计查询 |
| Controller/Service 内直连 | 8 个 controller + 3 个 service | `JdbcTemplate` 裸 SQL | 遗留代码（`LineAnalyticsController` 1072 行、`StatsController` 886 行最密集） |

**取舍**：`repository/` 是**目标层**。新增统计查询放 repository 而非 controller。已知的两种 Map key 命名不一致需注意：`LineAnalyticsRepository` 别名成 camelCase（`product_id AS productId`），`StatsQueryRepository` 返回原始 snake_case（`total_count`、`bucket_date`）。

### 6.2 设备接入层

`InspectionUploadServiceImpl`（`service/impl/inspection/`）是设备数据落地的唯一入口。核心方法：

| 方法 | 职责 |
|---|---|
| `validateBasic` | 协议级校验（`schemaVersion` 必须 `"2.0"`） |
| `validateToken` | 设备 Token 校验（`cfg_camera_token`，支持明文或 SHA-256） |
| `findCamera` / `findProduct` | 按业务键定位维度 |
| `findMapping` | `sourceCode` → 缺陷类型（**大小写敏感**） |
| `queryExistingBatchId` | 幂等检查 |
| `insertBatch` / `insertDefectCount` | 事实表落库 |
| `upsertQualityAgg` / `upsertDefectAgg` | 30 分钟粒度聚合 upsert |
| `upsertCurrentStatus` / `syncLegacyCameraStatus` | 当前状态快照 + 兼容表同步 |
| `recordException` | 映射失败留痕 |
| `resolveShiftId` | 按 `reportTime` 定班次（`ShiftCalculator`） |
| `floorToBucket` | 时间向下取整到 30 分钟桶 |

### 6.3 设备鉴权

**不依赖 Spring Security**：`SecurityConfig` 的 `permitAll()` 白名单放行设备路径，**设备 Token 在 service 层校验**（`validateToken`）。这样设备端无需携带 JWT。

页面侧用 JWT：`JwtUtil.generateToken(username, userId, role)` 签发，`JwtRequestFilter` 解析。

### 6.4 前端数据流

```
views/*.vue
  │ 调用 api/*.js 导出的函数
  ▼
utils/request.js (axios)
  ├─ baseURL: '/api'      ← 因此 api 模块里的 url 不带 /api 前缀
  ├─ timeout: 15000
  ├─ 请求拦截：getToken() → Header Authorization: Bearer <token>（过期则不附加）
  └─ 响应拦截：拆 {code,message,data}，code!=200 → ElMessage 报错
  ▼
Pinia stores/user.js：login() 保存 token + user；isAdmin getter 判 role===1
  ▼
router/index.js beforeEach：未登录 → /login；meta.requiresAdmin 不满足 → 回首页
```

### 6.5 页面模式：view + composable

`views/camera/CameraStatusView.vue` + `views/camera/useCameraStatusTable.js` —— 把表格状态、筛选、分页、加载抽到组合式函数，组件只做渲染。

### 6.6 SPA 路由兜底

`SpaFallbackController` 映射 `/{path:[^\\.]*}` 与 `/**/{path:[^\\.]*}`，命中时 `forward:/index.html`；但对 `/api/`、`/v3/api-docs`、`/swagger-ui`、`/actuator`、`/assets/`、`/error` 返回 404 —— 保证 API 与静态资源不被兜底吞掉。

## 7. 关键设计与取舍

| # | 设计 | 取舍与理由 |
|---|---|---|
| 1 | **3 个设备接口冻结** | 改 URL/Header/字段名/错误码都需先升协议版本。牺牲灵活性换取设备端固件稳定。代价：DTO 注释与契约测试里 `schemaVersion` 写成 `1.0` 是错的（实测只接受 `"2.0"`） |
| 2 | **设备鉴权在 service 层** | 避免为设备端引入 JWT 依赖。代价：`SecurityConfig` 白名单、`JwtRequestFilter.PUBLIC_PATHS` 与 service 层校验三处分散，易漏 |
| 3 | **数据入库时同步写聚合表** | 看板只读 `agg_*`，查询不扫明细。代价：写放大（一次上报写 6 张表）；聚合与明细存在短暂不一致窗口 |
| 4 | **`noRollbackFor = InspectionUploadException`** | 单个缺陷编码未映射不丢弃整批数据。代价：一次上报可能部分成功，调用方需读 `accepted`/`failureMessages` |
| 5 | **`batchId` 幂等** | 设备网络重试不产生重复数据。代价：需设备端保证 `batchId` 全局唯一 |
| 6 | **`sourceCode` 大小写敏感** | 严格映射，避免"看起来一样"的编码误映射。代价：设备端升级时映射表需同步维护（当前 120 条） |
| 7 | **前端产物打进 JAR** | 单文件交付，部署只需一个 jar。代价：无法独立灰度前端；改前端必须重新打 jar |
| 8 | **图片按相对路径解析** | `image_url` 存相对路径、`image_path` 存绝对路径；读取优先相对路径。收益：换机器拷目录即可显示。代价：`image_path` 里的旧绝对路径失效，`DataCleanupTask` 按它删文件会漏删（迁移场景需用 cron 兜底） |
| 9 | **两套 `camera_images` / `defect_image_file`** | `camera_images` 是兼容旧链路的表，承载 30 天清理任务；`defect_image_file` 是新版主表。代价：双写、概念重复；已知 `defect_image_file` 无定时清理，靠 cron 兜底 |
| 10 | **`sys_data_retention_policy` 只作元数据** | 保留策略以配置形式呈现便于运维查看与修改。**代价：代码不读它**，实际清理是 `DataCleanupTask` 里硬编码的三条 —— 改表不改代码不生效。已在排查手册中显式说明 |
| 11 | **运行期参数集中在 `/etc/default/camera-detection`** | 改端口/堆/路径不用重打包、不用改 systemd unit。代价：需要理解"参数在两处"（unit + env 文件） |
| 12 | **生产配置必须覆盖 JAR 内置的开发期设置** | JAR 里打包的是开发版 `application.yml`；外部配置省略的 key 仍取内部值（按 key 合并），且 logback 取最具体 logger。代价：新增配置项时必须逐个确认内部同名 key，否则开发期设置漏到生产（如 `log-impl: StdOutImpl` 导致 journald 几小时涨到 243 MB） |
| 13 | **建库用 4 段脚本而非单一 dump** | 单一 Navicat 导出（`wms-new.sql`）缺 15 张 P0 表，设备上报会 500。代价：4 段有顺序依赖，`02` 会 DROP 重建 21 张表，生产升级只能跑增量 DDL |
| 14 | **`04_align_entity_columns.sql` 用 UPDATE 搬运哈希** | `sys_user` 建表用 `password` 列、实体映射 `password_hash`；先 ADD 再 DROP 会把种子哈希丢掉，导致"全新库登录永远提示密码错误"。修复：DROP 前 `UPDATE ... SET password_hash = password` |
| 15 | **Linux 用 systemd + 启动器脚本，不用 C# 包装器** | Windows 版 `CameraDetectionService.exe` 依赖 .NET，Linux 不可用。改为 `run.sh` 承担同等职责（定位 java、拼 `-Dapp.home`、`exec` JVM） |

## 10. 已知限制

### 10.1 P0（上线前必须处理）

| # | 问题 | 证据 |

| 1 | **后端鉴权实际不生效** —— `utils/JwtRequestFilter` 第 83–89 行解析 token、查用户、`validateToken()` 全部做了，**唯独没有调用 `SecurityContextHolder.getContext().setAuthentication(...)`**，只打了一行「JWT Token 验证成功」日志。SecurityContext 始终为空，Spring Security 的 `anyRequest().authenticated()` 因此永不生效。叠加 `SecurityConfig` 约 65 条 `permitAll()` 白名单（含 `/api/cameras/**`）与 `JwtRequestFilter` 自己的 10 条 `PUBLIC_PATHS`（含 `/api/v1/**`、`/api/cameras/**`），实测**无 token 访问 `/api/cameras` 返回真实相机数据** | 运行时实测 + 源码逐行核对 |

### 10.3 协议与数据限制

| 项 | 限制 |
|---|---|
