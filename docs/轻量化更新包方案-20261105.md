# 轻量化更新包方案（分层发版）

> 版本：V1.0（待确认）· 日期：2026-11-05
> 目标：日常更新传输量 **53.5MB → ~5MB**（-90%），升级流程一条命令不变

---

## 一、现状与体积账

当前每次发版打全量包 53.5MB（tar.gz），内部构成：

| 内容 | 体积 | 更新频率 |
|---|---|---|
| 依赖库（Spring Boot fat jar 的 `BOOT-INF/lib/`，87 个 jar） | **56.7 MB** | **几乎不变**（升级依赖才变） |
| 自研后端类（`BOOT-INF/classes/` 除 static 外） | 1.1 MB | 每次后端变更 |
| 前端产物（`classes/static/`） | 5.5 MB | 每次前端变更 |
| 运维脚本（scripts/ 10 个） | ~120 KB | 极低频 |
| 建库 SQL（四段） | ~80 KB | 极低频 |
| systemd unit + 配置模板 | ~20 KB | 极低频 |
| docs（随包文档） | ~200 KB | 低频 |

**结论：95% 的传输是重复的依赖库。** 每次更新的真实增量只有 ~6.6MB。

## 二、目标分层模型

```
┌─ 基础层（"镜像"，一次安装，极低频变更）──────────────┐
│ 目录骨架 / 运维脚本 10 个 / systemd unit /          │
│ 四段建库 SQL / 配置模板 / install.sh        ~1 MB   │
├─ 依赖层（随首次部署落盘，之后不动）──────────────────┤
│ BOOT-INF/lib/（87 个依赖 jar）             ~57 MB   │
│  → 留在服务器现有 fat jar 内，不重复传输             │
├─ 应用层（每次更新替换）────────────────────────────┤
│ 自研 classes（1.1MB）+ 前端 static（5.5MB）         │
│  → 打成 update.zip                      ~4-5 MB    │
└────────────────────────────────────────────────────┘
```

**"镜像"= 服务器上已安装的 fat jar（lib 层）+ `/opt/camera-detection-system/` 基础目录**；
每次更新只传应用层 zip，在服务器端**合成**进现有 fat jar。

## 三、技术方案：增量合成（推荐）

### 3.1 原理

沿用项目已验证的 **Python zipfile 增量写 JAR** 技术（`recover_legacy_chunks.py` 同原理，
已实机验证不破坏 `Main-Class: JarLauncher` / `Start-Class` / `classpath.idx`）：

```
update.zip
├── manifest.json         # 版本、构建时间、libSha256、classesSha256、变更说明
└── BOOT-INF/classes/**   # 自研类 + 前端 static 全集（整体替换，无残留）
```

服务器端合成：读现有 fat jar → **跳过全部 `BOOT-INF/classes/` 条目** → 写入 update.zip 的
classes 全集 → 其余（lib/、MANIFEST、根条目）原样保留 → 输出合成 JAR → 校验 → 原子替换。

**为什么整段替换 classes 而不是逐文件合并**：类移动/删除（如 P2 搬包）场景下逐文件合并会
残留旧类导致 classpath 冲突；整段替换天然无残留。classes 段全量也只有 ~7MB，无性能问题。

### 3.2 一致性保障（何时必须回退全量）

- update 包 manifest 带构建时 `libSha256`（依赖清单哈希）；
  deploy 时与服务器现有 JAR 的 lib 清单比对 —— **不一致（依赖升级/新增）→ 自动回退全量 fat jar 部署**，
  并在输出中明确提示"依赖已变更，本次走全量"。
- 合成后校验：JAR 完整性（0 重复条目、MANIFEST 完好）→ 启动健康检查（已有）→ verify.sh（已有）。
- deploy_jar.sh 已有的 **备份 + 失败自动回滚** 机制对增量模式同样生效 —— 合成失败自动还原上一版。

### 3.3 发版产物形态（build-release.sh 改造后）

```
dist-release/linux/
├── base/                                  # 基础层包（低频重建）
│   └── camera-detection-base-<ver>.tar.gz     (~1 MB：scripts+systemd+sql+config+install.sh)
├── update/                                # 更新层包（每次发版）
│   └── update-<yyyyMMdd-HHmm>.zip             (~4-5 MB：classes 全集 + manifest.json)
└── camera-detection-system-1.0.0.tar.gz   # 全量包（保留，用于首次安装/依赖变更兜底）
```

### 3.4 升级流程（日常）

```bash
# 本地：构建后产 update 包（一条命令）
bash installer/linux/build-release.sh --update-only

# 上传 + 升级（deploy_jar.sh 自动识别 zip=增量 / jar=全量）
scp dist-release/linux/update/update-*.zip lims@10.2.77.72:/tmp/
ssh lims@10.2.77.72 "SUDO_PASSWORD='***' bash /tmp/deploy_jar.sh /tmp/update-*.zip"
```

脚本/SQL 有变更时：重打 base 包上传解包（或按 manifest 提示逐个 scp）。
前端 chunk 历史保留机制不受影响（recover/prune 脚本操作的就是合成后 JAR 内的 assets）。

## 四、各内容归属总表

| 内容 | 归属层 | 分发方式 |
|---|---|---|
| 依赖库 87 jar | 依赖层（fat jar 内） | 首次随全量包；变更时自动回退全量 |
| 自研后端类 | 应用层 | **update.zip 每次传** |
| 前端 assets | 应用层 | **update.zip 每次传** |
| 运维脚本 10 个 | 基础层 | base 包（低频）或 manifest 变更提示单独 scp |
| systemd unit | 基础层 | base 包 |
| 建库 SQL | 基础层 | base 包（表结构变更时执行对应迁移） |
| 配置模板 application.yml | 基础层 | base 包（占位符版，真实值在 /etc/default） |
| /etc/default 密钥 | 服务器本地 | **永不进包** |
| 图片数据 / 数据库数据 | 服务器本地 | **永不进包** |

## 六、明确不做 / 暂缓

- **Docker 容器镜像**：当前无容器运行环境，引入 Docker 会推翻 systemd 部署形态，收益不成比例。
  本方案的"基础层"已等价于镜像分层思想；将来若上 Docker，分层模型可平移。
- **PropertiesLauncher / thin jar**（把 lib 真正拆出 fat jar 外部目录）：改变启动机制，
  风险大于收益；增量合成方案不动启动方式。
- **前端完全独立部署**（nginx 托管 assets）：当前无 nginx，且单 JAR 形态是优点，不拆。
