## 一、问题诊断

### 1.1 FAILED 报错（截图问题 1）

截图报错原文：

```
FAILED - PreparedStatementCallback; bad SQL grammar [DELETE FROM agg_quality_day
WHERE date_bucket BETWEEN ? AND ?]; nested exception is
java.sql.SQLSyntaxErrorException: Table 'wms-new.agg_quality_day' doesn't exist
```

**根因链（三层）**

| 层级 | 问题 | 说明 |
|---|---|---|
| 表不存在 | `agg_quality_day` / `agg_defect_type_day` 在生产库从未建成 | 这两张表**不在 `sql/deploy/` 脚本里**，只靠 controller 运行时 DDL |
| 入口漏调 | `submitDailyAggregation()` 有 3 个入口，只有 2 个在调它之前调了 `ensureDailyAggregationTables()` | **定时任务 `runScheduledDailyAggregationIfNeeded` 那条路径直接就进去了** → DELETE 不存在的表 → 任务记 FAILED |
| 判断机制 | `ensure*` 用**进程内 `AtomicBoolean` 标志位**判断是否已建表 | 标志位只反映「本进程建过」。一旦建表失败或表被人工删除，**永远不会重建** —— 标志位方案是 2026-10-31 为修「每分钟产生 4 条 DDL」引入的，副作用在此暴露 |

### 1.2 默认产线统计 KPI 全 0（截图问题 3）

**根因：现场上报通道与统计读取的是两套完全不同的表。**

| 通道 | 写入表 | 现场是否在用 |
|---|---|---|
| `defect-images/upload`（设备真正在用的） | `defect_image_batch` / `defect_image_file` / `defect_image_box` | ✅ 在用（44083 张） |
| `batch-upload`（冻结契约通道） | `fact_inspection_*` + `agg_quality_30m` / `agg_defect_type_30m` | ❌ 现场基本不用 |

统计页只读 `agg_*`，而现场数据全在 `defect_image_*` → **KPI 必然全 0**。

服务器实测佐证（修复前）：

```
agg_quality_30m   仅 5 行，其中 4 行 factory_id=1（已删除的杭州工厂残留）
defect_image_file 1355 行，全部 2026-11-02，camera_id=DA9200622 / DA8119487
```

### 1.3 良率口径不可计算

图片通道**只上传缺陷图，没有良品样本** —— 良率在当前数据源下**根本算不出来**。
若照原样显示 `0.00%`，会让厂长误判产线全线报废。

## 二、修复方案

### 2.1 FAILED 修复（两处）

**① 补齐建表调用**（`LineAnalyticsController.submitDailyAggregation`）

```java
private Map<String, Object> submitDailyAggregation(...) {
    // ★ 必须先确保两张日聚合表存在。
    //   之前只有 runDailyAggregation / retryAggregationJob 两条入口做了 ensure，
    //   而 @Scheduled 定时任务走的 submitDailyAggregation 直接就 DELETE，
    //   线上实测报 "Table 'wms-new.agg_quality_day' doesn't exist" → 任务 FAILED。
    ensureDailyAggregationTables();
    ensureAggregationJobTable();
    ...
}
```

**② 判断依据从标志位改为实际存在性**

```java
private boolean tableExists(String tableName) {
    Integer count = jdbcTemplate.queryForObject(
        "SELECT COUNT(1) FROM INFORMATION_SCHEMA.TABLES WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = ?",
        Integer.class, tableName);
    return count != null && count > 0;
}
```

三个 `ensure*` 方法统一改为「表在就跳过 DDL，不在才建」：
- 不再产生每分钟 4 条 DDL（原问题仍在修复中）
- 表被人为删除或首次建表失败时**能自愈**

`INFORMATION_SCHEMA` 是内存字典查询（毫秒级），不构成性能负担。

### 2.2 KPI 全 0 修复 —— 数据源兜底

`buildSummary` 在聚合表无数据时，自动回落到缺陷图片事实表：

```java
if (longVal(kpi.get("totalCount")) == 0 && longVal(kpi.get("defectCount")) == 0) {
    Map<String, Object> fallback = buildDefectImageSummary(start, end, ...);
    if (longVal(map(fallback.get("kpi")).get("totalCount")) > 0) {
        data.putAll(fallback);
        data.put("dataSource", "DEFECT_IMAGE");
        data.put("dataSourceMessage", "当前范围聚合表无数据，已自动切换到缺陷图片事实表统计。");
    }
}
```

响应新增两个字段：

| 字段 | 取值 | 含义 |
|---|---|---|
| `dataSource` | `AGGREGATION` / `DEFECT_IMAGE` | 本次统计实际用的数据源 |
| `dataSourceMessage` | 文本 | 中文说明，前端直接展示 |

**兜底口径与聚合表不同**（前端必须区分，否则误导）：

| 指标 | 聚合表口径 | 兜底口径（图片事实表） |
|---|---|---|
| 检测总数 `totalCount` | 批次累计检测量 | **缺陷图片张数** |
| 缺陷数 `defectCount` | 映射后缺陷计数 | **缺陷框总数** |
| OK 数 `okCount` | 良品数 | **0（无良品样本）** |
| NG 数 `ngCount` | 异常数 | 缺陷图片数 |
| 良率 `yieldRate` | OK/总数 | **null（不可计算）** |

关联注意：`defect_image_file.camera_id` 存的是**相机编号**（`DA9200622`）而非 `dim_camera.camera_id`，
必须 `JOIN dim_camera c ON c.camera_code = f.camera_id` 才能拿到工厂/产线/工位维度。

### 2.3 良率呈现（用户已确认方案）

### 2.4 工厂厂长默认看板（用户已确认主线）

**主线：质量总览 → 缺陷帕累托 → 责任工位定位 → 严重度构成 → 缺陷趋势**

选这条线而非「良率+产量」的原因：良率在当前数据源下算不出来，硬推良率是 0% 误导；
而厂长真正的决策链是「质量好不好 → 主要矛盾是什么 → 谁的工位 → 多严重 → 趋势如何」，
帕累托与责任工位正好对应「主要矛盾」和「责任人」两个动作。

默认看板更名为「**工厂质量看板（厂长视角）**」，6 个组件：

| # | 组件名称 | metric | 类型 | 布局 |
|---|---|---|---|---|
| 1 | 质量总览（厂长视角） | `plantOverview` | KPI | 12×1 |
| 2 | 缺陷类型帕累托（累计占比） | `defectPareto` | BAR | 8×3 |
| 3 | 缺陷严重度构成 | `severityDistribution` | STACK_BAR | 4×3 |
| 4 | 责任工位定位（缺陷数） | `stationRanking` | BAR | 6×3 |
| 5 | 责任相机定位（缺陷数） | `cameraRanking` | BAR | 6×3 |
| 6 | 缺陷发生趋势 | `defectTrend` | LINE | 12×3 |

**后端新增 4 个指标**：

- `plantOverview`：检测总量 / 缺陷总数 / 高危缺陷数 / 高危占比 / 单图缺陷数 / 受影响工位数 / 涉及相机数 / 首要缺陷及其占比 / 良率可得性

配套：`exportTable` 支持 4 个新指标的 Excel 导出；元数据 `widgetTypes` 新增
`PLANT_OVERVIEW` / `PARETO` / `SEVERITY` 三种图表类型；前端 `metricOptions` 与
`widgetPresets` 同步扩充。

**旧看板升级**：`upgradeLegacyDefaultDashboard()` 把「默认产线统计看板」重命名并按新蓝图重建组件。
**保护措施**：仅当该看板的组件**全部是内置默认件**时才升级；用户若自行加过组件则跳过，不覆盖用户配置。

## 五、遗留事项

1. **临平二期两台相机仍无缺陷映射、无设备令牌**
   （`cfg_camera_defect_mapping` = 0 条，`cfg_camera_token` = 0 条）。
   令牌查询为空时当前直接放行 —— **任意 Token 都可上报**，投产前必须配置独立令牌。
2. **`sourceCode=p0` 尚无映射关系** —— 设备端上报 `p0` 会返回 422 `UNMAPPED`。
3. **良率/产量维度暂不可用** —— 需设备端补齐良品样本上报，才能启用「产量达成 + 良率趋势 + 损失评估」主线。
   当前默认看板的 `quality` / `trend` 指标仍在，等聚合表有数据后自动生效。
4. **`cfg_camera_defect_mapping` 为空导致缺陷类型只有中文名**（污点/接头/胶污），
   与 `dim_defect_type` 的标准编码（P0_INNER_GLUE_SMALL 等）**未关联**，
   帕累托图与缺陷类型筛选按中文名工作。补齐映射后即可与标准缺陷字典打通。
5. **异机备份、设备端 JPEG** —— 已按决定本期不做。
6. **Windows 版已停止维护** —— 不再同步修改。
7. **Git 未提交** —— 按用户新约定，本次改动未 `commit`/`push`，等明确指示。
