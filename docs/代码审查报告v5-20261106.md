## 1 P1（上线前必修）— 未提交改动自身的缺陷

### NEW-01　日聚合「失败即当日断档」，且故障被静默吞掉
**证据**：`LineAnalyticsController:804-808`
```java
Map<String,Object> job = submitDailyAggregation(...);   // 只是 submit，异步
aggregationRepository.updateLastRun(today, jobId);      // ★ 立刻写「今天跑过了」
} catch (Exception ignored) { }                          // ★ 连 error 都不记
```
`updateAggregationJob`（`:1006-1013`）同样 `catch (Exception ignored)`。

**影响**：H-1 已经把「查询时同步重建」这条自愈通道拆掉了，日聚合现在**只有**这一个触发点（外加 5 分钟近期窗口刷新，但它只管近 3 天）。异步任务一旦失败（锁等待超时、磁盘慢、表结构漂移），`lastRunDate` 已写成今天 → **当天不会再重试**，`analytics_aggregation_job` 若也写失败，连 FAILED 状态都没有。运维唯一的线索是页面上那句「聚合落后」，而它不会自愈。

**改法**：① `updateLastRun` 移到 `updateAggregationJob(status=SUCCESS)` 成功分支里；失败时把 `lastRunDate` 置空让下一分钟重试。② 两处 `catch (Exception ignored)` 至少 `log.error`，并让 `updateAggregationJob` 的失败单独打日志（它是失败现场的唯一记录者）。

### NEW-02　登录/注册限速可被一个 HTTP 头绕过
**证据**：`AuthController:188-195`
```java
String xff = request.getHeader("X-Forwarded-For");
if (xff != null && !xff.isEmpty()) { return 首段; }   // 无任何可信代理判断
return request.getRemoteAddr();
```
**影响**：`installer/linux/` 全链路没有 nginx，Spring Boot 直接在 8091 上serve 静态页与 API（`install.sh:25`、`health 127.0.0.1:8091`）。即**没有代理，XFF 完全由客户端控制** → 攻击者每次请求换一个伪造 XFF，`limitKey` 就换一个槽位，5 次锁定永远触发不到。v3 花 116 行写的 `LoginRateLimiter` 目前是装饰品。
**改法**：默认只用 `getRemoteAddr()`；确实要上代理时，用配置项（如 `app.security.trusted-proxies`）声明可信网段，只有 `remoteAddr` 命中才采信 XFF。

### NEW-03　401 语义把登录页的回跳目标污染了
**证据链**（三处，缺一不可）：
- `ApiErrorCode:47` `AUTH_INVALID_CREDENTIALS → HttpStatus.UNAUTHORIZED`
- `AuthController:51` 登录失败返回该码 → `ApiStatusAdvice` 把状态改成 **401**
- `request.js:56-63` 拦截器对**任何** 401 无条件执行 `clearToken()` + `saveLoginContext(currentPath())` + `redirectToLogin()`

**实际发生的事**（已逐段验证，不是猜测）：
1. 在 `/login` 输错密码 → 后端 401 → 拦截器写入登录上下文。`currentPath()` 是 `/login`，但 `isSafeRedirect('/login')===false`（`auth-redirect.js:132`），于是 `saveLoginContext` **回退成 `DEFAULT_LANDING='/camera-status'`**（`auth-redirect.js:80`）；
2. `redirectToLogin` 发现已在登录页 → 直接 return（`auth-redirect.js:217`），所以**不会**跳转、也不会弹「登录状态已失效」——这点比 v4 担心的要好；
3. `Login.vue:98` 照常显示「用户名或密码错误」✓；
4. 用户改对密码 → `takeLoginContext()` 返回 `/camera-status` → **原本想去 `/line-analytics`，却被送到相机状态页**。

**影响**：不是登录死循环，但「先输错一次密码」会稳定丢掉回跳目标；同时匿名端点的 401 还在做无意义的清 token / 写 sessionStorage。
**改法**：语义上 401 应只表示「无有效会话」。凭据错误改 400（`PARAM_INVALID` 族或新增 `AUTH_BAD_CREDENTIALS(400xx)`），401 只留给 `AUTH_TOKEN_INVALID`；拦截器再加一条 `/auth/login|/auth/register` 前缀跳过，双保险。

## 5 已决策不做：设备上报 token 校验

按指示不再作为待办。只记录残余风险与**不需要改代码**的缓解手段，供发版时勾选：

**残余风险**（两条上报通道均匿名可调，`SecurityConfig` 精确白名单内）
- 匿名可写 `defect_image_*` 与磁盘 → 统计数字可被任意污染，且无法追溯来源；
- `max-request-size: 1024MB` + 500G 磁盘 → 单点可打满盘，磁盘满会连带影响归档、备份与数据库写入。

**零代码缓解**（运维层，30 分钟内可做完）
1. `application.yml` 把 `max-request-size` / `max-file-size` 从 1024MB 降到现场真实单批上限（100 张 × 6MB ≈ 600MB，建议 256MB）；
2. 防火墙只放行产线网段访问 8091（匿名端点因此等价于「内网可信」）；
3. 磁盘水位与「单日上传量突增」接入现有告警（`ServerMetricsServiceImpl` 已有磁盘指标，加阈值即可）。
