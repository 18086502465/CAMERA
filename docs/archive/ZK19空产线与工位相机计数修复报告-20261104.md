# ZK19 空产线与工位相机计数修复报告

**日期**：2026-11-04
**服务器**：10.2.77.72（Hik-Vision，Ubuntu 24.04.5 LTS）
**触发**：用户反馈「ZK19 下面两个相机；产品正面胶污检测工位的数据为什么为空？数据有问题，手动修复。」

---

## 一、结论先行：根因与表象不一致

用户看到的事实是：

| 观察 | 实际情况 |
|---|---|
| ZK19 产线徽标显示「2」 | 这个 2 是**工位数**，不是相机数 —— 徽标数字未标注单位，导致误读 |
| 点「产品正面胶污检测」工位，右侧「暂无数据」 | **确实为空，且是正确结果** —— ZK19 从未绑定过任何真实相机 |

**核心结论**：ZK19（`line_id=4`）是一条**从未接入任何设备的空产线**，与同工厂同名的 ZK23 产线**工位编码和名称完全重复**（CV-1 产品正面胶污检测 / CV-2 产品背面胶污检测）。现场在跑的两台真实相机绑在 ZK23 的工位 23/24 上。ZK19 之所以显示 2，是因为它有 2 个工位，而**不是**有 2 台相机。

## 二、事实认定过程

### 2.1 数据库现状（修复前）

```
dim_production_line:  id=4 ZK19 (factory_id=3 杭州临平一期工厂, is_deleted=0)
dim_workstation:      id=21 CV-1 产品正面胶污检测 (line_id=4)
                      id=22 CV-2 产品背面胶污检测 (line_id=4)
```

`/api/cameras?page=1&size=999` 返回 16 台，`workstationId` 分布为
`{7:1, 8:1, ..., 20:1, 23:1, 24:1}` —— **不含 21/22**。
`/api/cameras?stationId=21` → `total=0`。

### 2.2 三条独立证据链

**证据一：11-04 01:01 完整备份逐表核对**

`/data/camera-detection/backup/db/full/wms-new_20261104_010154.sql.zst`（60MB 解压后）中：

- `dim_camera` 仅 16 行（id 9~24），`workstation_id` 为 7~20 与 23、24 —— **无 21/22**
- `camera_status` 仅 16 行（id 9~24）—— **无 21/22**
- 即：ZK19 建立以来的**全部历史中，从未有过一台真实相机**

**证据二：所有事实表/聚合表/看板中 ZK19 的数据量均为 0**

```
fact_production_30min / fact_production_info / fact_inspection_defect_count
fact_inspection_batch / fact_anomaly_alert / product_detection_history
camera_images / agg_quality_30m / agg_quality_day / agg_defect_type_30m
agg_defect_type_day / analytics_aggregation_job / analytics_aggregation_schedule
                                    → 对 line_id=4 或 workstation_id IN (21,22) 的行数全部为 0
cfg_analytics_dashboard / cfg_analytics_widget 的 layout_json / metric_json / filter_json
                                    → 无任何 ZK19 / lineId=4 引用
```

**证据三：操作日志溯源**

- ZK19 产线创建于 `2026-11-03 10:30:30`（`POST /api/lines`）
- 两个工位创建于 `10:31:19` / `10:31:32`（`POST /api/workstations`）
- **此后 ZK19 再无任何相机创建/绑定操作**
- 现场两台真实相机 `DA8119489` / `DA4733319` 创建于 `2026-11-03 14:59:08` / `14:59:28`，
  绑定目标是 **ZK23 的工位 23/24**，且持续心跳、上传图片（今日图片数 349 / 140）

### 2.3 为什么会出现这条空产线

`2026-11-03` 上午的重建序列：

```
10:30:12  POST /api/factories    → 创建「杭州临平一期工厂」(id=3)
10:30:30  POST /api/lines        → 创建 ZK19 (id=4)
10:31:19  POST /api/workstations → 工位 21 (CV-1 产品正面胶污检测)
10:31:32  POST /api/workstations → 工位 22 (CV-2 产品背面胶污检测)
10:33:39  POST /api/lines        → 创建 ZK23 (id=5)     ← 3 分钟后又建了一条同结构产线
10:34:33  POST /api/workstations → 工位 23 (CV-1 产品正面胶污检测)
10:34:52  POST /api/workstations → 工位 24 (CV-2 产品背面胶污检测)
14:59:08  POST /api/cameras      → DA8119489 → 工位 23（ZK23）
14:59:28  POST /api/cameras      → DA4733319 → 工位 24（ZK23）
```

即：ZK19 与 ZK23 是**同一工位结构的重复建立**，相机最终全部绑定到了 ZK23，ZK19 遗留为空壳。

### 2.4 附带发现：11-04 排查遗留的测试垃圾

`dim_camera` id=28 (`aaaaab`)、id=29 (`CCCC1`) 与 `camera_status` id=28、29 是上一轮排查删除按钮时创建的测试相机，
已逻辑删除（`is_deleted=1` / `is_active=0`）但物理行仍在，且占用 ZK19 工位 21 的绑定位。

## 三、修复动作

### 3.1 数据修复（服务器，已执行）

脚本：`docs/scripts/fix_zk19_data.sh`（含回滚 SQL 生成）

```sql
-- 1) 物理清理测试残留（确认无图片/心跳/映射/令牌关联后执行）
DELETE FROM cfg_camera_defect_mapping WHERE camera_id IN (28,29) OR camera_code IN ('aaaaab','CCCC1');
DELETE FROM cfg_camera_token          WHERE camera_id IN (28,29) OR camera_code IN ('aaaaab','CCCC1');
DELETE FROM dim_camera                WHERE camera_id IN (28,29) AND camera_code IN ('aaaaab','CCCC1');
DELETE FROM camera_status             WHERE id      IN (28,29) AND camera_code IN ('aaaaab','CCCC1');

-- 2) 逻辑删除 ZK19 及其 2 个空工位（工位先下线）
UPDATE dim_workstation     SET is_deleted=1, is_enabled=0, update_time=NOW() WHERE workstation_id IN (21,22);
UPDATE dim_production_line SET is_deleted=1, is_enabled=0, update_time=NOW() WHERE line_id=4;
```

**为什么用逻辑删除**：可随时恢复，回滚 SQL 已生成并存档。
**为什么工位先删**：避免产线仍处于可见状态但已无有效工位。

### 3.2 代码修复一：工位「相机数」口径对齐绑定真源

**问题**：配置页「工位 → 相机数」按 `camera_status`（**设备上报的状态快照**）统计，
而相机与工位的**绑定关系真实来源是 `dim_camera`**（`is_deleted=0`）。
后果是：刚绑定好、尚未上报心跳的相机不计数，页面显示的「相机数」与实际配置不符。

**修复**：

- 后端 `CascadeController`：`/api/cascade/all` 在每个工位节点下发 `cameraCount`，
  由**单条 GROUP BY** 统计 `dim_camera`（无 N+1），统计异常时退化为空 Map，不影响级联数据返回
- 前端 `ConfigView.vue`：`cameraCountByStation` 优先使用后端下发的绑定数，
  后端未提供时（老接口）才退化为 `camera_status` 统计

### 3.3 代码修复二：树徽标数字标注单位（消除误读根源）

**问题**：工厂 / 产线 / 工位三层节点的徽标都是**裸数字**，但含义完全不同
（产线数 / 工位数 / 相机数）。现场把「ZK19 徽标 = 2（2 个工位）」误读为「下面有 2 个相机」，
这正是本次问题的**认知根源**。

**修复**：徽标统一显示为 `2厂` / `1线` / `14位` / `1机`，并加 `title` 完整说明
（如「该产线下共 2 个工位」）。

### 3.4 附带修复：前端产物陈旧 chunk 清理

`npx vite build --emptyOutDir false` 会把上一次的 chunk 残留在 `dist/assets`（78 个 vs 干净构建 49 个），
打进 JAR 多占约 1.5MB 且可能造成静态资源混乱。
本次先清空 `dist/assets` 再构建，并逐文件比对同步到 `fact-product/src/main/resources/static/`。

## 五、遗留风险（本次未处理，需知晓）

### 5.1 `camera_status.camera_name` 存在重名 —— 心跳可能串号

```
CV1_Cam1  →  id=9  (DA8119487, ZK54, 工位7)
CV1_Cam1  →  id=23 (DA8119489, ZK23, 工位23)
CV2_Cam1  →  id=10 (DA9200622, ZK54, 工位8)
CV2_Cam1  →  id=24 (DA4733319, ZK23, 工位24)
```

`CameraStatusServiceImpl.saveCameraStatus` 的匹配顺序是
**先按 `camera_name` 匹配 → 找不到再按 `camera_code` 兜底**。
重名时 `selectOne(... LIMIT 1)` 会命中错误行。

**当前实测**：连续 5 次采样（每 2 秒），id 9 与 id 23 各自的 `product_name` 与计数**仍独立更新**
（id 9 是「棉芯与内装正面污点检测」、id 23 是「拉美小蓝M码」），暂未发生串号。
但这是**结构性隐患**，现场一旦新增同名相机即可能触发。

**建议**：将匹配顺序改为**先 `camera_code`（有唯一索引 `uk_camera_code`）后 `camera_name`**。

### 5.2 映射表与令牌表为空

`cfg_camera_defect_mapping` 与 `cfg_camera_token` 当前均为 **0 行**。
设备走 `defect-images/upload` 通道不受影响（现场 4 万+ 张图片正常入库），
但若后续启用 `batch-upload` 冻结契约通道，需先重建映射数据。
