# 项目结构与部署链路深度评审（2026-11-12）

> 性质：一次性评审 + 优化方案（过程产物，执行完毕后归档）。本报告**只出清单与方案，未删除/移动任何文件**。
> 范围：①部署流程（步骤/环境配置/依赖管理）②部署包构建与组织 ③交付文档完整性 ④本地文件清理与规整。
> 证据口径：全部来自当日实测（git ls-files / du / diff / 脚本源码），非回忆。

---

## 核心结论（先看这段）

1. **部署链路本身是健康的**：`build-release.sh`（唯一打包入口）→ `deploy.sh`（新机一键）→ `deploy_jar.sh`（增量/全量+自动回滚）→ `verify.sh`（38/40 项自检）职责清晰、有断点续跑与回滚能力。主要问题不在链路，在**周边的"脏"**。
2. **最大的结构性风险是脚本双份**：`jar_manifest.py`、`prune_legacy_chunks.py`、`recover_legacy_chunks.py` 在 `docs/scripts/` 与 `installer/linux/scripts/` 各存一份（当前逐字节一致）。这正是本仓库历史上"副本漂移、测的是旧版"事故的同款模式，只是没有机制防它再漂。
3. **本地已积累约 140MB 纯垃圾**：`.workbuddy/tmp/upd-test/`（64MB 增量包测试残留）、`dist-release/linux/parts/`（59MB base64 分片残留）、3 份历史 update zip、`frontend/dist.bak-*`、6 个 vite 临时 mjs。全部可安全删除。
4. **105 个文件未提交**（License 全套 + 三版前端 chunk），单次变更跨后端/前端/文档/脚本四个层面，颗粒度已到必须拆分提交的程度。
5. 交付文档体系（9 份现行规范 + scripts/README + archive）**结构是全项目最好的部分**，问题只剩数字漂移（135/139 端点、7/9 份）与口径分散。

## 一、现状分析

### 1.1 部署流程现状

```
构建机（Windows Git Bash / Linux）
  installer/linux/build-release.sh ──┬─ 全量：前端构建→同步 static→mvn test→打包→stage→tar.gz（54MB）
                                     └─ --update-only：只含 BOOT-INF/classes/**（3MB zip）
          │ 上传（≤10MB stdin 直传 / >10MB base64 分块 upload_jar_b64.py）
          ▼
服务器 10.2.77.72（Ubuntu 24.04，统一布局 /main/app）
  新机：deploy.sh（宿主机前置：JDK8 探测/apt 安装/MySQL 调优/断点续跑 --skip-apt）
        → install.sh（目录树/unit/白名单口令注入）
  升级：deploy_jar.sh（*.zip 增量：依赖指纹校验→classes 整段替换；*.jar 全量）
        流程：备份→停服→原子替换→健康检查→失败自动回滚；保留最近 3 份 .bak
  验收：verify.sh（root+双口令，40 项）+ docs/scripts/verify_*_browser.cjs（浏览器回归）
```

**步骤完整性：好。** 健康检查、回滚、备份保留策略、增量依赖指纹校验都在。

**环境配置：好，但真源分散。** 生产配置真源是 `/etc/default/camera-detection`（systemd EnvironmentFile 注入）；仓库内 `application.yml` 有**两份**（`fact-product/src/main/resources/` 与 `installer/templates/`），实测当前除 BOM/注释外**逐行一致**——一致靠人工纪律，无守卫。

**依赖管理：可复现性中上。**

## 三、优化方案（按优先级，附落地步骤）

### P0 —— 立即执行（防事故，0.5 天）

**P0-1 脚本去重（对应 P1）**：删 `docs/scripts/` 里三份副本，installer 为唯一真源。
```bash
git rm docs/scripts/jar_manifest.py docs/scripts/prune_legacy_chunks.py docs/scripts/recover_legacy_chunks.py
# 引用方改指 installer 路径：grep -rn "docs/scripts/jar_manifest" 全仓替换
# docs/scripts/README.md 对应条目删除
```
**P0-2 提交 License 变更（对应 P2）**：按层拆 4 个提交（后端协议+服务 / 接口+闸门+配额 / 前端页面 / 文档+脚本+verify），每个提交前跑对应门禁。**需你显式授权后执行。**

**P0-3 废弃脚本出库（对应 P6）**：
```bash
git rm docs/scripts/sync_static.py docs/scripts/verify-legacy-nav.cjs \
       "docs/scripts/验证脚本-403拦截器行为.cjs" "docs/scripts/验证脚本-P0修复回归.cjs"
```
删除前把 4 个脚本归档到 `docs/archive/scripts-retired/`（保留历史可追溯）。

### P1 —— 本周（提效，0.5 天）

**P1-1 临时产物清扫 + 构建前自动清理（对应 P9）**：
- 一次性手工清（见第四章清单 C1–C7，约 140MB）；
- `build-release.sh` 开头加两行：`rm -rf dist-release/linux/parts` 与 `find dist-release/linux/update -name 'update-*.zip' -mtime +7 -delete`（只清 7 天前）。

**P1-2 孤儿跟踪修正（对应 P5）**：`git rm --cached dist-release/linux/README.md`，内容并入 `docs/部署与运维手册.md` §4（发布包说明）。

**P1-3 npm 口径统一（对应 P8）**：`build-release.sh:37` 的 `npm install` 改为 `npm ci`（与 CI 一致；代价是必须先有 lock，本项目有）。

### P2 —— 本月（结构治理，1–2 天）

**P2-1 配置单源化（对应 P4）**：`installer/templates/application.yml` 定为唯一真源，构建时复制进 jar：
- build-release.sh 打包前 `cp installer/templates/application.yml fact-product/src/main/resources/`；
- 加守卫：diff 两文件不一致即构建失败（比"复制"更显式，推荐守卫方案）；
- 同步给 check_doc_links 同目录加一条校验。

**P2-2 前端产物入库策略定案（对应 P3，二选一）**：
- **方案 A（推荐）：产物出库**。`git rm -r --cached fact-product/src/main/resources/static/assets/`，加 ignore；发布包靠 build-release 生成。代价：旧页面兼容（保留 3 版 chunk）依赖构建机本地状态——需把"保留版本数"从 `.versions` 机制改为显式清单文件入库。
- 方案 B：全量跟踪（含 .versions 与所有历史 chunk）。代价：每次发版几百个文件 diff，.git 继续膨胀。
- ⚠ 此项影响"部署后旧页面失效"防线，**执行前必须过一轮浏览器回归**，建议单独排期。

**P2-3 脚本改名（对应 P7）**：`cleanup-zk54-incremental.sh` → `cleanup-test-cameras.sh`，同步改 3 处：installer、发布包 stage、服务器 crontab（`15 * * * *` 行）+ `服务器文件布局.md` 的计划任务表。

**P2-4 文档数字自校准（对应 P10）**：根 README 与 docs/README 的"现行 N 份"改为"以 docs/README.md 为准"不带数字；`gen_api_doc.py` 生成后回写端点数到 docs/README（脚本尾部加 5 行）。

### P3 —— 长期（登记）

- P3-1 `.git` BFG 瘦身（421MB → 预期 <80MB），需协调全员重新 clone（对应 P11）。
- P3-2 deploy.sh 依赖清单集中化：把 JDK8/MySQL/Python3/磁盘要求的"宿主机前置"写成 `docs/部署与运维手册.md` 的一张表（当前散在脚本注释里）。
