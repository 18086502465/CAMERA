# 相机类型隔离方案：区分真实相机与测试相机

> 日期：2026-11-05
> 目标：让「无效图片 + 对应数据库记录」的定时清理**只作用于测试相机**，

> 现场：杭州临平二期，16 台相机，其中 2 台真实（ZK23 两台），其余 14 台为测试。

## 一、现状（改造前的事实基线）

### 1.1 定时清理任务

| 项 | 值 |
|---|---|
| 脚本 | `docs/scripts/cleanup_zk54_incremental.sh` → 服务器 `/usr/local/bin/cleanup_zk54_incremental.sh`（md5 一致 `606af9b1…`） |
| 调度 | **root crontab**：`15 * * * * MYSQL_PASSWORD=… /usr/local/bin/cleanup_zk54_incremental.sh`（每小时 :15） |
| 日志 | `/data/camera-detection/backup/cleanup_zk54.log` |
| 白名单 | **脚本内硬编码** `KEEP="'DA8119489','DA4733319'"` |

清理口径（**白名单排除制**，不是按类型）：

```
DELETE b FROM defect_image_box b JOIN defect_image_file f … WHERE f.camera_id NOT IN ($KEEP)
DELETE   FROM defect_image_file      WHERE camera_id NOT IN ($KEEP)
DELETE   FROM defect_image_batch     WHERE camera_id NOT IN ($KEEP)
DELETE   FROM camera_images          WHERE image_path NOT LIKE '%/DA8119489/%' AND … NOT LIKE '%/DA4733319/%'
磁盘：find $IMG_ROOT -mindepth 2 -maxdepth 2 -type d ! -name 'DA8119489' ! -name 'DA4733319' → rm -rf
```

执行顺序：**先删库 → 再删磁盘**（铁律）。
幂等性：靠 `NOT IN (KEEP)`，重复执行第二次删 0 条。

**实测运行日志**（2026-11-05）：

```

15:15 box=8100  file=8100  batch=81  camera_images=8100  diskDirs=1 remain_file=3009

21:15 box=0     file=0     batch=0   camera_images=0     diskDirs=0 remain_file=3042
```

16:15 起 `file=0` → 测试相机已停止上报。当前 `defect_image_file` 3042 行**全部**属于两台真实相机
（`DA8119489` 1717 行、`DA4733319` 1325 行），磁盘 270MB 也只有这两个相机目录。

### 1.2 相机数据模型

| 表 | 归属域 | 作用 | 实体类 | camera_code |
|---|---|---|---|---|
| `camera_status` | device | 运行状态快照（旧页面兼容） | `CameraStatus`（device.domain.model） | `uk_camera_code` 唯一 |
| `dim_camera` | masterdata | 相机维度表（档案，相机↔工位绑定真源） | **无实体**，纯 SQL | `uk_camera_code` 唯一 |

**关键关联**：`defect_image_file.camera_id` 存的是 **camera_code**（设备编号，如 `DA8119489`），
不是数字主键。磁盘目录结构 `/data/camera-detection/images/defect-images/{yyyyMMdd}/{cameraCode}/{HHmmssSSS}_{uuid8}.{ext}`
—— 第二层目录名也是 camera_code。因此**按 camera_code 就能同时定位库记录与磁盘文件**。

```

```

### 1.4 现有问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | 真实相机名单**硬编码在脚本里** | 加一台真实相机必须改脚本 + 重跑，改漏即误删 |
| 2 | 白名单是"排除制"而非"按类型" | 相机属性无表达，清理范围只能靠排除名单 |
| 3 | 真实相机若被误标/漏标，无任何第二道防线 | 单点失误 = 真实数据被删 |
| 4 | SQL 失败被 `|| true` 吞掉 | 清理失败**静默**，运维无感知 |
| 5 | 无并发锁 | 上轮未跑完下一轮已启动，可能并发删同一批 |
| 6 | 无异常告警落库 | 只写文本日志，系统内看不到 |
| 7 | 新建相机无类型概念 | 无法表达"这台是测试机" |

## 二、字段与表结构设计

### 2.1 选型：`camera_type` 而非 `is_real`

| 维度 | `is_real TINYINT` | **`camera_type VARCHAR(20)`** ✅ |
|---|---|---|
| 取值 | 0/1 | `REAL` / `TEST` |
| 扩展性 | 加第三种类型要改列语义 | 加枚举即可（如后续 `TRIAL`/`MAINTENANCE`） |
| 可读性 | 需查文档才知道 1 是啥 | SQL 里直接可读：`WHERE camera_type='TEST'` |
| 清理脚本友好度 | `camera_type NOT IN ('REAL')` | 同左，且语义自解释 |

**结论：采用 `camera_type VARCHAR(20) NOT NULL DEFAULT 'TEST'`。**

### 2.2 取值枚举与默认值

| 值 | 含义 | 清理任务行为 |
|---|---|---|
| `REAL` | 真实产线相机 | **数据一律不参与清理**（库记录 + 磁盘文件都保留） |
| `TEST` | 测试/调试相机 | 参与清理（无效图片 + 对应库记录） |

**默认值 = `TEST`**，理由：
- 现场现状是"仅 2 台真实、其余 14 台测试"，默认 `TEST` 与现状一致，**存量迁移 = 只改 2 行**，
  风险面最小；
- 若默认 `REAL`，则存量 14 台测试相机初始都是 `REAL`，必须逐行 UPDATE 成 `TEST` ——
  漏一行 = 该测试相机的数据永久不清理（磁盘持续涨），比误删更隐蔽；
- 新建相机时用户在界面显式选择，**默认值只是兜底**，不依赖它。

> ⚠️ 取舍点见文末 §7.1（默认值方向的取舍）。

### 2.3 加列位置：两张表都加

| 表 | 新增列 | 说明 |
|---|---|---|
| `camera_status` | `camera_type VARCHAR(20) NOT NULL DEFAULT 'TEST' COMMENT '相机类型：REAL=真实产线相机（不参与清理），TEST=测试相机（参与清理）'` | 运行状态快照 |
| `dim_camera` | 同上 | 相机档案（维度表） |

**为什么两张表都加**：`camera_status` 是运行态、`dim_camera` 是档案态，二者是本系统既有的
"双表一致"模式（`is_active` / `is_deleted` / `is_enabled` 已经在两表各存一份，
删除时也是两表一起逻辑删除）。沿用同一模式，避免引入第三种数据归属口径。

**权威源约定**：**`dim_camera` 为准**（相机↔工位绑定的真源就在这里，见项目长期记录）。
`camera_status` 是冗余副本，用于列表查询免 JOIN。两表在
`CameraDashboardController.create/update` 的同一个事务里一起写，保证一致。

### 2.4 清理任务的判据（关键设计）

清理脚本需要回答："相机 X 是真实还是测试？"

```sql
-- 判据：dim_camera 档案为准
SELECT camera_code FROM dim_camera
 WHERE camera_type = 'REAL' AND is_deleted = 0
```

**为什么不用 `camera_id NOT IN (...)` 排除制**：
排除制需要"列出所有真实相机"，新增真实相机必须改脚本；按类型判定则
"标记即生效"，脚本永不需要改 —— 这正是本次改造的核心价值。

**孤儿数据处理**：`defect_image_file.camera_id` 里可能存在**不在 `dim_camera` 中**的
camera_code（历史遗留、相机已删但图片还在）。这些**一律按 TEST 处理**（清理掉），
理由：它们不属于任何已登记的真实相机，留着只是垃圾。判据写成"排除所有 REAL"即可自然覆盖：

```sql
-- 只删非 REAL 的（等价于：TEST 的 + 孤儿的）
WHERE camera_id NOT IN (SELECT camera_code FROM dim_camera WHERE camera_type='REAL' AND is_deleted=0)
```

但为了可读性与防误伤，脚本实际采用**两段式**（见 §4.3）。

## 三、存量数据回填

### 3.1 回填目标

| camera_code | camera_name | 目标 camera_type |
|---|---|---|
| `DA8119489` | CV1_Cam1 | **REAL** |
| `DA4733319` | CV2_Cam1 | **REAL** |
| 其余 14 台 | — | TEST |

### 3.2 回填方式：**迁移脚本 + 应用启动兜底**（双保险）

#### (a) 迁移脚本 `sql/deploy/05_camera_type_migration.sql`

幂等、可重复执行：

```sql
-- ① 加列（幂等：MySQL 8.0 不支持 ADD COLUMN IF NOT EXISTS，用 information_schema 判断）
--    camera_status
SET @s = (SELECT IF(COUNT(*)=0, 'ALTER TABLE `camera_status` ADD COLUMN `camera_type` VARCHAR(20) NOT NULL DEFAULT ''TEST'' COMMENT ''相机类型：REAL=真实产线相机（不参与清理），TEST=测试相机（参与清理）''', 'SELECT 1')
          FROM information_schema.COLUMNS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='camera_status' AND COLUMN_NAME='camera_type');
PREPARE st FROM @s; EXECUTE st; DEALLOCATE PREPARE st;

-- ② 回填：先全部置 TEST（这一步同时修正"默认 TEST 但历史行可能是 NULL"的情况）
UPDATE `camera_status` SET `camera_type`='TEST' WHERE `camera_type` IS NULL OR `camera_type` NOT IN ('REAL','TEST');
UPDATE `dim_camera`   SET `camera_type`='TEST' WHERE `camera_type` IS NULL OR `camera_type` NOT IN ('REAL','TEST');

-- ③ 标记两台真实相机为 REAL
UPDATE `camera_status` SET `camera_type`='REAL' WHERE `camera_code` IN ('DA8119489','DA4733319');
UPDATE `dim_camera`   SET `camera_type`='REAL' WHERE `camera_code` IN ('DA8119489','DA4733319');

-- ④ 校验（只读，人工核对）
SELECT camera_code, camera_name, camera_type FROM camera_status ORDER BY camera_type, camera_code;
```

**为什么不用 `UPDATE … WHERE camera_code NOT IN (两台)`**：
那种写法在两台真实相机尚未写入某张表时会把该表全部标成 TEST（虽然结果一样），
但语义不清晰、且一旦真实相机 code 变更要改两处。分三步（先 TEST 再 REAL）语义更明确，
且第 ③ 步是**幂等覆盖** —— 重复执行永远得到同一结果。

#### (b) 应用启动兜底：`ensureColumn` 机制

项目已有运行时补列机制（`CameraStatusServiceImpl.ensureCameraStatusColumns()`，
`@PostConstruct` 触发，用 INFORMATION_SCHEMA 判断列是否存在）。
在其后追加一行即可：

```java
ensureColumn("camera_type", "ALTER TABLE camera_status ADD COLUMN camera_type VARCHAR(20) NOT NULL DEFAULT 'TEST' COMMENT '相机类型：REAL=真实产线相机（不参与清理），TEST=测试相机（参与清理）'");
```

`dim_camera` 的补列同理（`CameraDirectoryRepository` 加 `ensureDimCameraColumn`）。

**双保险的意义**：
- 只跑了迁移脚本没重启应用 → 正常
- 只部署了新 JAR 没跑迁移脚本 → 应用启动时自动补列，**不会因为缺列而启动失败**
  （这是关键：`NOT NULL` 列若不存在，`cameraStatusMapper.insert` 会抛
  `Unknown column 'camera_type'`）

> ⚠️ 但自动补列只能补**列**，不能补**数据**。若迁移脚本没跑，
> 两台真实相机会是 `TEST` → **有被清理的风险**。因此脚本必须有 §5.1 的第二道防线。

### 3.3 存量迁移的执行顺序

```
1. 停止清理任务（避免迁移过程中被误判）
   root crontab -e 注释掉 cleanup_zk54_incremental.sh 那行（或 mv 脚本为 .bak）
2. 执行 05_camera_type_migration.sql
3. 核对 SELECT 输出：REAL 恰好 2 台，TEST 14 台
4. 部署新 JAR（应用启动自动补列兜底）
5. 用新版脚本 dry-run 验证清理范围
6. 恢复清理任务调度
```

## 四、清理任务改造

### 4.1 现状执行逻辑（改造前）

```
cron 15 * * * *  →  cleanup_zk54_incremental.sh（root）
  ├─ SQL() 封装：mysql -uroot -p"$MP" -N -B -D 'wms-new' -e "..."
  ├─ N1..N4：先 COUNT 后 DELETE（box→file→batch→camera_images），每步 || true 吞错
  ├─ 磁盘：find 出所有非白名单相机目录 → rm -rf；再删空的日期目录
  ├─ log() 追加一行到 cleanup_zk54.log
  └─ 阈值守护：单次 file 删除 > 10 万 → WARN
```

涉及数据表：

| 表 | 清理条件（改造前） |
|---|---|
| `defect_image_box` | JOIN file，`f.camera_id NOT IN (KEEP)` |
| `defect_image_file` | `camera_id NOT IN (KEEP)` |
| `defect_image_batch` | `camera_id NOT IN (KEEP)` |
| `camera_images` | `image_path NOT LIKE '%/DA8119489/%' AND NOT LIKE '%/DA4733319/%'` |

涉及文件路径：`/data/camera-detection/images/defect-images/{yyyyMMdd}/{cameraCode}/**`
（第二层目录名 = camera_code，与 `defect_image_file.camera_id` 同源）。

### 4.2 改造后的执行逻辑

```
cron 15 * * * *  →  cleanup_zk54_incremental.sh（root）
  ├─ flock 独占锁（防并发重入）
  ├─ 读取 REAL 相机名单（权威源 dim_camera，兜底 camera_status）
  │    ├─ 名单为空 → 判定为"标记异常"，直接中止本轮 + 告警（§5.1 防线二）
  │    └─ 同时取两表并集（任一表标记 REAL 即受保护，§5.1 防线一）
  ├─ 读取「物理保护名单」PROTECTED_CODES（环境变量，运维可临时加码）
  ├─ 统计待删量，超过阈值 → 中止本轮 + 告警（§5.1 防线三）
  ├─ 删库：box → file → batch → camera_images（先库后文件，铁律不变）
  │    └─ 每步检查 SQL 返回码，失败记 ERROR 并计数，**不再 || true 吞错**
  ├─ 删磁盘：仅删除 camera_code 不在保护集合内的相机目录
  ├─ 清理后自检：REAL 相机的图片数/文件数是否变化（应恒为 0 变化）
  └─ 写日志（分级 INFO/WARN/ERROR）+ 异常写 fact_anomaly_alert 落库
```

### 4.3 按相机维度隔离清理范围（核心）

**保护集合（Protected Set）** = 下列三者取并集：

```bash
# ① 档案权威：dim_camera 中标记为 REAL 的相机
REAL_FROM_DIM=$(mysql … "SELECT camera_code FROM dim_camera WHERE camera_type='REAL' AND is_deleted=0")
# ② 冗余副本：camera_status 中标记为 REAL 的相机（任一表标记即保护 —— 双保险）
REAL_FROM_STATUS=$(mysql … "SELECT camera_code FROM camera_status WHERE camera_type='REAL' AND is_active=1")
# ③ 运维硬保护：环境变量（临时加码，不改代码）
PROTECTED="${PROTECTED_CODES:-}"
```

**清理范围** = 保护集合之外的一切：

```sql
-- defect_image_box
DELETE b FROM defect_image_box b JOIN defect_image_file f ON f.image_id=b.image_id
 WHERE f.camera_id NOT IN (<保护集合>);
-- defect_image_file / defect_image_batch 同理
-- camera_images（旧兼容表只有路径，用 LIKE 匹配目录名）
DELETE FROM camera_images WHERE image_path NOT LIKE '%/DA8119489/%' AND image_path NOT LIKE '%/DA4733319/%';
```

磁盘同理：`find` 出的相机目录名若不在保护集合 → `rm -rf`。

> **关键点**：保护集合用 **OR/并集** 语义 —— 只要**任一**来源把它标成 REAL，
> 它就不受清理。这让"单表漏更新"不会导致误删。

### 4.5 改造前后对照

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 真实相机判定 | 脚本内硬编码常量 | 数据库字段 `camera_type='REAL'` |

| 双表不一致时 | 无保护 | 任一表标 REAL 即保护 |
| 真实名单为空 | 照常清理（= 全删） | **中止本轮 + 告警** |
| 单轮删除过大 | WARN 后继续 | **中止本轮 + 告警** |
| SQL 失败 | `\|\| true` 吞掉 | 记 ERROR、计数、退出码非 0、告警落库 |
| 并发 | 无保护 | flock 独占 |
| 孤儿数据 | 清理 | 清理（不变） |

## 五、边界情况处理

### 5.1 真实相机被误标为测试相机的保护（三道防线）

| 防线 | 机制 | 触发后果 |
|---|---|---|
| **一：双表 OR 保护** | 保护集合 = dim_camera 的 REAL ∪ camera_status 的 REAL ∪ PROTECTED_CODES | 单表漏更新 → 不误删 |
| **二：名单为空即中止** | 查出的 REAL 集合为 0 → 认为"标记被整体误改" → **中止本轮清理** + 写告警 | 立即发现，不会全删 |
| **三：单轮删除量熔断** | 待删 file 行数 > `MAX_SINGLE_DELETE`（默认 50000）→ 中止 + 告警 | 误标 1 台真实相机时，若其数据量不大则防线一已挡住；若批量误标则被熔断 |
| **附加：清理后自检** | 清理后复查 REAL 相机的 `defect_image_file` 行数与磁盘目录数，与清理前对比 | 出现减少即告警（事后检测） |

> 防线二、三需要脚本在**删除前**先统计。这会让脚本多一次 COUNT 查询，
> 但 3042 行量级下耗时可忽略（<50ms），值得。

**误标后的修复路径**：
```sql
UPDATE dim_camera   SET camera_type='REAL' WHERE camera_code='XXX';
UPDATE camera_status SET camera_type='REAL' WHERE camera_code='XXX';
```
下一轮清理自动跳过该相机（无需改脚本、无需重启）。

### 5.2 幂等性与中途失败

| 场景 | 行为 | 保证 |
|---|---|---|
| 重复执行 | 第二次 `DELETE` 影响 0 行，`rm -rf` 无匹配目录 | **天然幂等**（判据是"类型"，不是"是否处理过"） |
| 上一轮未跑完 | `flock -n` 拿不到锁 → 立即退出，记 INFO | 不并发；下一轮自然补齐 |
| 删库成功、删磁盘失败 | 库记录已删，磁盘文件残留 | 下轮 `find` 仍能匹配到目录 → 补删（顺序保持"先库后文件"，失败方向安全） |
| 删磁盘成功、库删除失败 | 不可能发生（顺序是库先） | — |
| 中途 SQL 失败 | 记 ERROR + 失败计数，**继续下一步**，退出码非 0 | 下一轮重试；已删的不重复 |
| 部分相机目录删不掉（权限） | `rm -rf` 返回非 0 → 记 ERROR | 下一轮重试；日志可查 |

**幂等性的根本保证**：判据用的是「相机类型」而非「处理状态标记」，
所以「删过」和「没删过」的相机在下一轮看来是一样的 → 重复执行无副作用。

**顺序铁律保留**：**先删库、后删文件**。
理由：若先删文件后删库失败，库里就留下"有记录无文件"的坏数据（页面显示裂图）；
先删库后删文件失败，最坏只是留下"无记录的文件"（孤儿文件，下轮自动清）。

## 七、需要你确认的取舍

### 7.1 默认值方向（**最重要**）

| 选项 | 含义 | 后果 |
|---|---|---|
| **A. 默认 `TEST`**（本方案推荐） | 新建相机不选类型 → 视为测试相机 | 与现场现状一致（14:2），存量迁移只改 2 行；风险：**误建的真实相机若忘了选"真实"，其数据会被清理** |
| B. 默认 `REAL` | 新建相机不选类型 → 视为真实相机 | 存量 16 台初始全是 REAL，需逐行改 14 台为 TEST，**漏一行 = 该测试相机数据永不清理**（磁盘涨，隐蔽）；好处：真实相机绝不因"忘了选"被误删 |

选 A 还是 B，取决于**现场新建相机的实际习惯**：
若现场主要在调试新相机（数据可丢）→ A 更省事；
若现场经常新建真实产线相机 → B 更安全。

**我倾向 A**，因为：① 清理任务只对**明确标记为 TEST** 的相机生效，
而新建时界面有下拉选择，正常操作不会漏；② 漏标 B 的后果（数据不清理）
可以用磁盘水位告警发现，而漏标 A 的后果（数据被删）无法恢复。

### 7.2 真实相机白名单的维护方式

- **A. 只靠数据库字段**（本方案推荐）：界面/DB 改即生效，脚本永不改
- B. 数据库字段 + 环境变量 `PROTECTED_CODES` 兜底（本方案已实现为防线一的一部分）
- C. 保留脚本内 `KEEP` 常量作为第三层：需要改脚本，改漏风险高

本方案已实现 A + B。是否还需要 C（即保留脚本内的两台硬编码）？
建议**不保留** —— 保留会造成"改了 DB 但脚本仍按旧名单"的行为差异，反而更危险。

## 八、实施过程中的一个致命坑（已修复，必读）

### 8.1 现象

保护集合从字符串 `"DA4733319,DA8119489"` 拆成 bash 数组时，**只剩 1 个元素**，
少的那台恰好是真实相机 —— 若上线，保护集合少一台 → 该相机数据会被误删。

### 8.2 根因

```bash
# ❌ 有 bug 的写法
printf '%s' "$PROTECTED" | tr ',' '\n' | sed '/^[[:space:]]*$/d'
```

`printf '%s'` **不追加换行符** → `tr` 转换后**最后一行没有 `\n`** →
`while IFS= read -r c` 读到最后一行时 read 返回非零（没读到分隔符）→
**循环体不执行 → 最后一个元素被静默丢弃**。

而丢掉的恰恰是排在最后的那台真实相机。

### 8.3 修法

```bash
# ✅ 用 here-string（等价于 printf '%s\n'，末尾恒有换行）
tr ',' '\n' <<< "$PROTECTED" | sed '/^[[:space:]]*$/d'
```

### 8.4 为什么值得单列

这类 bug **没有任何报错**：脚本正常退出、日志正常、清理"成功"，
只是保护集合少了一台 —— 直到真实相机的数据消失才会被发现，而那时**无法恢复**。

因此补了两个回归工具：

| 工具 | 作用 |
|---|---|
| `docs/scripts/test_cleanup_protect_set.sh` | 从**真实脚本**里抽取保护集合代码段跑 6 个场景（两表各标/单表标/运维加码/全误标/3 台），**测的就是线上跑的那段逻辑** |
| `docs/scripts/verify_camera_type_guards.sh` | 实机验证三道防线 + 正向清理（造 ZZTEST 数据 → 验证被清 → 验证真实相机分毫不动） |

> 通用教训：**凡是 `while read` 消费管道/字符串的地方，最后一行有没有换行符
> 必须显式确认**。`$(...)` 命令替换会吃掉尾部换行，是最容易踩的入口。
