```
              │                ▲                │                 │
              ▼                │                │                 ▼

                                                    │
                                    备份脚本读水位 → >85% 直接跳过备份
```

**三条硬依赖**：

1. **磁盘水位 ↔ 备份互斥**：`backup-database.sh:84-90` 在水位 >85% 时 `exit 1`，即「磁盘越满越不备份」。备份与数据同盘，这个设计在磁盘满时**同时失去备份能力和写入能力**。
2. **保留期口径 ↔ 跨进程约定**：磁盘脚本的 `KEEP_DAYS=730`（cron 传入）必须等于 `app.archive.images.retain-days`（默认 730）。两个值分别存在于 cron 文件与 `application.yml`，**没有编译期或运行期校验**，改一个忘另一个就裂图。
3. **zk54 保护集 ↔ `camera_type` 字段**：保护集 = `dim_camera` ∪ `camera_status` 的 REAL 并集 ∪ `PROTECTED_CODES`。若两表同时被误改为 TEST，防线一失效，只能靠防线二（保护集为空即中止）。现场 11-05 21:39 就触发过防线二。

## 3 实测发现（v1 未覆盖，或需修正 v1 结论）

### D1 备份**真的可用**（v1 的最大空白已补齐）

把最新备份 `wms-new_20261107_010415.sql.zst` 导入临时库：

| 指标 | 结果 |
|---|---|
| 导入耗时 | **15.5 秒** |
| 表数 | **41 / 41**（与 `information_schema` 一致） |
| `defect_image_file` | 3326（当时值） |
| `camera_images` | 3326 |
| `dim_camera` | 16 |
| `sys_operation_log` | 113202 |

**结论**：43MB 的库、41 张表，mysqldump + zstd 的产物**完整可还原**。备份方案本身不需要换（不需要 xtrabackup）。

> 顺带纠正一处既有记忆错误：库里 `SUM(data_length+index_length)` = **43.0 MB**，不是此前记录的 2.6GB。43MB 的量级下 mysqldump 每天 1~15 秒完成，任何「引入物理备份工具」的建议都不成立。

### D2 binlog **实际上是开启的**——但从不备份（推翻 v1 结论）

| 项 | 实测值 |
|---|---|
| `log_bin` | **ON** |
| `binlog_format` | **ROW** |
| 文件数 / 总量 | 35 个（`binlog.000001`~`000035`），**约 2.2 GB** |
| 单个最大 | `binlog.000024` 127 MB |
| `backup/db/binlog/` 目录 | **空**（`backup-database.sh:79` 只 `mkdir -p`，此后从不写入） |

**这意味着**：

- v1 说「无 binlog、RPO=24h」是**错的**——MySQL 一直在记录行级变更，技术上具备分钟级恢复能力；
- 但 binlog 与数据**同盘**且**从未被备份**。盘坏 = 数据与 binlog 一起没，实际 RPO 仍是 24 小时。

**⚠ 本节的第二处更正（2026-11-07 执行 P0-3 时实测）**：原文写「binlog 没有任何清理策略」
也是错的。实际 `binlog_expire_logs_seconds = 2592000`（**30 天**），`max_binlog_size = 100MB`，
所以文件按「满 100MB 或满 30 天」滚动 —— 最早的文件是 10-23，与 30 天窗口吻合。
真实问题只剩「从不备份」，不含「无限增长」。执行时因此**没有去改过期设置**：
30 天是有价值的历史回溯窗口（D5 那类事故依赖它），改小等于主动销毁证据；
副本侧改为按 14 天保留（与 `KEEP_FULL_DAYS` 对齐 —— 比最早全量还旧的 binlog 没有可回放的基线）。

**这是本次最需要纠正的认知偏差**：不是「没有能力」，是「有能力但没接上」。

### D3 「异机备份」是同盘硬链接级镜像（md5 实证）

```
db/full       32 个文件（16 zst + 16 sha256），8.2M
offsite/full  32 个文件，8.2M
md5(wms-new_20261107_010415.sql.zst) 两份完全相同：5045de363a06075d85703332f05b906e
```

两者都在 `/data/camera-detection/backup/` 下，同一块 `/dev/mapper/vg0-data`。

更危险的是同步方式：`backup-database.sh:149` `rsync -a --delete "$FULL_DIR/" "${OFFSITE_DIR}/full/"`。**`--delete` 使副本不具备独立性**——若 `db/full` 被误清空（脚本 bug、误操作、磁盘错误），下一次 rsync 会把 offsite 一起清空。

### D4 告警通道被 `LIMIT 20` 截断——P0-2 的修复在现网规模下可能失效

`FactAnomalyAlertController:28` 只有 `LIMIT 20`，按 `create_time DESC`，无级别排序、无类型过滤。

现场实测：

| 项 | 值 |
|---|---|
| 未恢复告警总数 | **84** |
| `TEMPERATURE_HIGH` / WARNING | 78（时间跨度 11-06 10:11 ~ 16:47） |
| `CLEANUP_FAILED` / HIGH | 6（11-05 三条 + 11-06 17:15/18:15/19:15 三条） |
| 前端可见 | **最新 20 条**，其余 **64 条（76%）永远不可见** |

**后果**：
- 我刚加的 `BACKUP_FAILED` 是低频告警，插入时会短暂排进前 20，但随着后续高频相机的 `TEMPERATURE_HIGH` 涌入会**沉底消失**；
- 更要紧的是**现在就有 6 条 `CLEANUP_FAILED`（HIGH 级）已经沉底**——其中 3 条是 11-05 的「保护集为空 / 待删超阈值」双重防线触发，性质严重，但页面看不到；
- 告警无自动收敛（无过期、无自动 resolve），**只增不减**，任何告警最终都会沉到第 21 位。

**所以 P0-2 只修了「写」，没修「读」**。这是本轮最重要的修复缺口。

### D5 11 万条审计日志批量消失，且**无法追溯**（本次最重要发现）

| 时点 | `sys_operation_log` | `log_id` 范围 | `operation_time` |
|---|---|---|---|
| 11-07 01:04（备份） | **113202** | 304933 ~ 418134 | 11-05 14:01 ~ 11-06 23:52 |
| 11-07 09:10（现场） | **32** | 418273 ~ 418304 | 11-07 09:03 ~ 09:10 |

**已确认的事实**：

1. 删除**确实发生过**：`information_schema` 显示该表 `data_length=12.52MB`、**`data_free=33.00MB`**——33MB 是「已删未回收」的空洞，与 11 万行约 34MB 的量级完全吻合；
2. 删除**不是 `DataCleanupTask` 干的**：02:00 的 `cleanupOperationLogs(now.minusMonths(6))` 只删 `<= 2026-05-07` 的行，而这 11 万条全是 11-05/11-06 的；
3. 删除**没有进入 binlog**：`mysqlbinlog` 解析 `binlog.000035`（覆盖 00:00–09:07）全文，**没有任何 `### DELETE FROM` 事件**，也没有对 `wms-new` 的 `TRUNCATE`/`DROP`（仅有的 2 次 `DROP TABLE sys_operation_log` 时间戳为 09:06:12 / 09:06:51，是我自己的恢复演练，作用在 `ZZTEST_restore`）；
4. **没有任何外部客户端痕迹**：`performance_schema.host_cache` 为空，`PROCESSLIST` 只有应用连接池（`Sleep 3421s`，对应 08:14 启动）；
5. 中间段 `log_id` 418135~418272（138 条，约 08:14 部署后 `verify.sh` 产生的）也一起消失。

**唯一自洽的解释**：执行删除的会话设置了 `SET sql_log_bin=0`（或 `SESSION SQL_LOG_BIN=0`），因此语句不进入 binlog。这类设置常见于数据导入/恢复工具、部分图形客户端（如某些「清空表」动作）。

**这个发现的价值不在于「谁删的」，而在于**：

> 一套宣称「有 binlog」的系统，在 8 小时内丢失 11 万条审计记录，而**现有手段无法定位原因**——因为 binlog 没有备份、没有异地留存、没有基础审计表。**这不是运维事故，这是可观测性设计的缺口。**

**必须采取的应对**（见 §5 P0-3）：不猜测，而是把「能查出来」变成可交付能力——binlog 定期备份 + `binlog_expire_logs_seconds` 显式设置 + 关键表变更审计。

### D6 02:00 的清理任务**没有任何日志输出**

`journalctl --since 01:55 --until 02:10` 只有每 5 分钟的 `日聚合近期窗口刷新完成`，**没有一行清理相关日志**。

原因是旧版 `DataCleanupTask` 全程无日志（`@Transactional` 静默方法 + 无 `log.info`）。这也解释了为什么「11 万条消失」的时间点无法从应用日志定位——**任务执行了也不会留痕**。

P0-3 已补：三步各一条 `log.info`（删除行数）+ 失败 `log.error`。**这是 D5 类问题未来可定位的前提**。

### D7 备份链路内部口径不一致：口令传递

| 位置 | 方式 | 进程列表可见 |
|---|---|---|
| `alert()`（P0-2 新增） | `MYSQL_PWD="$DB_PASS" mysql ...` | 否 |
| `mysqldump`（原有） | `mysqldump -p"$DB_PASS"` | **是**（`ps aux` 在备份的 1~15 秒窗口内可见） |

同一条链路两种写法。备份每天 01:00 跑，任何本地用户在那个窗口 `ps` 一次就能拿到数据库 root 口令。

## 5 优化方案

### P0 —— 本周（做完这 4 项，备份链路才算真的闭环）

#### P0-1 修告警读取端：让 HIGH 级不被淹没

**问题**：D4/H5。写入端刚修好，读取端仍按时间截断。

**改法**（二选一，建议 a+b 同时）：

- a) 排序改为**级别优先**：`ORDER BY FIELD(alert_level,'HIGH','MEDIUM','LOW'), create_time DESC`（一行改动，`FactAnomalyAlertController:27`）；
- b) 运维类告警（`BACKUP_FAILED` / `CLEANUP_FAILED` / 磁盘水位）走独立查询或前端独立区块，不与相机业务告警抢窗口。

**同时**：给 `TEMPERATURE_HIGH` 加自动收敛——同 `(line_id, workstation_id, alert_type)` 已有未恢复记录时只更新 `update_time`，不再新插。现场 78 条同类型告警就是缺这个去重。

#### P0-3 binlog 纳入备份 + 显式过期策略

**问题**：D2/H6。这是本次定性最高、最容易被忽视的一项。

**改法**：
1. `backup-database.sh` 在 dump 成功后，把 `binlog.index` 之后新增的 binlog 文件 `cp` 到 `${BACKUP_DIR}/binlog/`（该目录已存在，只是从没写过东西）；
2. ~~`my.cnf` 显式设置 `binlog_expire_logs_seconds = 604800`（7 天）~~ → **执行时撤销**：实测现场已是 **2592000（30 天）**，并非无策略；30 天是有价值的历史回溯窗口，改小等于销毁证据。副本侧改为 `BINLOG_KEEP_DAYS=14`（与 `KEEP_FULL_DAYS` 对齐）；
3. 保留 14 天 binlog 副本，与 14 天全量备份配合，把 RPO 从 24h 压到「最后一次 binlog 备份」的粒度。

**实现要点（踩过的坑，别再踩）**：
- 取文件用 `mysqlbinlog --read-from-remote-server --raw`，走协议即可，**不需要读 `/var/lib/mysql`**（该目录 750 mysql:mysql，脚本以 cdsys 运行读不了；为读 binlog 给 cdsys 加 mysql 组会动 MySQL 安全基线）。
- `--result-file` 必须给**目录且结尾带斜杠**。给完整文件名时 mysqlbinlog 会把原始名再接一遍：`--result-file=/x/binlog.000001` → 产物叫 `binlog.000001binlog.000001`，而且**不报错**（实测踩过）。
- 只复制「dump 起点文件及更新」的增量；正在写的那个 binlog 每晚大小都变，会重复复制，副本是「当晚那一刻的前缀」，回放到该时刻仍然有效。

**风险提示**：binlog 备份后与全量备份**必须在同一位置**（`/data` 之外的第二块盘或异机），否则同盘无意义。

**验证**：`ls backup/db/binlog/` 应出现文件；`mysqlbinlog --start-datetime` 能从副本还原出某个时间点的变更。
