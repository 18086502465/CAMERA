## 一、总体判断

工程质量底座继续向好：v1/v2 的 10 项修复全部在位且经服务器实测验证；归档任务（事务模板、DDL 外置、跨月拆分、滞后自检）是全仓工程质量最高的模块之一；RBAC 路径规则经完整交叉比对**实际覆盖完整**（v2 报告怀疑的 factories/lines 缺口排除）。

本轮主要结论：**性能债成为下一个主要风险面**——PERF-02/03/04 三项都集中在报表与上传两条主链路上，当前 7.9 万行数据量下表现尚可，但没有任何一项随数据量线性可控；其次是第 2 周新增的安全组件缺直接单测（自审发现）。

## 二、高优先级（两周内）

### H-1　PERF-02　报表查询触发日聚合全范围重建（读路径写库）

| 项 | 内容 |
|---|---|
| 证据 | `LineAnalyticsController.java:137-142`：`shouldUseDailyAggregation()` 命中即 `ensureDailyAggregationTables()` + `rebuildQualityDaily()` + `rebuildDefectDaily()`，内部为 DELETE+INSERT 全范围重建 |
| 问题 | 每次报表查询都重建聚合表。前端 30s 轮询 = 每 30s 一次全范围 DELETE+INSERT；多用户并发查询互相覆盖中间态，binlog/磁盘写放大，聚合数据在重建窗口内不一致 |
| 改进 | 聚合重建只留在 `@Scheduled` 定时任务与显式管理端点；查询一律只读物化表，数据新鲜度由任务频率保证（如 5 分钟）。查询侧加"聚合表水位"判断，落后才提示而非重建 |

### H-2　PERF-03　`/line-summary` 单请求 69 次 Repository 调用且无缓存

| 项 | 内容 |
|---|---|
| 证据 | `LineAnalyticsController.java` 全文 `Repository.` 调用 69 处；无任何缓存层（v2 已确认） |
| 问题 | 一次页面请求 = 数十次独立聚合 SQL；数据翻 5 倍后 P95 必然超标，且放大 H-1 的重建频率 |
| 改进 | ① 短期：Caffeine 60s 短缓存（键=工厂+产线+日期窗），30s 轮询天然命中同一键；② 中期：把 8 条独立聚合并成 1~2 条 GROUP BY SQL |

### H-3　PERF-04　上传事务包住文件 IO 与图像解码

| 项 | 内容 |
|---|---|
| 证据 | `DefectImageServiceImpl.java:91`、`InspectionUploadServiceImpl.java:44`、`ConfigImportController.java:118` 均 `@Transactional` 覆盖整批处理（含磁盘写入、ImageIO 解码、POI 解析） |
| 问题 | 100 图批次占用数据库连接数秒；解码慢时拖垮连接池（200 上限 > MySQL 默认 151，问题会传导） |
| 改进 | 解析/校验/落盘移出事务 → 纯 DB 写入收敛为短事务（参考归档任务的 `transactionTemplate` 分批写法） |

### H-4　SEC-NEW-05　设备告警无去重节流

| 项 | 内容 |
|---|---|
| 证据 | `CameraStatusServiceImpl.java:209-244`：每次心跳（5s）独立做 4 类阈值判定并 `insertAnomalyAlert`，无任何去重 |
| 问题 | 相机持续故障时 1.7 万条/天/台 CRITICAL 告警——告警表失真、运维麻木（告警疲劳本身就是安全事故温床）。当前 67 行是侥幸（未发生过长故障） |
| 改进 | 同（camera_code, alert_type）在窗口期（建议 30min）内只插首条 + `resolved_at` 恢复条目；恢复检测复用现有心跳状态 |

### H-5　QUAL-02　93 处业务失败返回 HTTP 200 + code=500

| 项 | 内容 |
|---|---|
| 证据 | `ResultVO.error/fail` 全仓 93 处，HTTP 状态恒 200；与 QUAL-01 新增的 400/500 体系并存后，同一系统存在两套错误语义 |
| 问题 | 监控/网关无法按 HTTP 状态分类告警；前端只能字符串匹配 message；新 `GlobalExceptionHandler` 的 400 与业务 code=500 口径分裂 |
| 改进 | 定义错误码族（40xxx 参数 / 401xx 凭据 / 422xx 设备校验），HTTP 状态对齐。可渐进：先改登录与上传两族（高频且有监控价值），存量 93 处分批迁 |

### M-1　ARCH-01　授权护栏三层不齐（漂移温床）

| 项 | 内容 |
|---|---|
| 证据 | ① `LineAnalyticsController` 12 个写端点 0 个 `@PreAuthorize`，仅靠 `/api/v1/analytics/**` 路径规则；② `CameraDashboardController`、`DimFactoryController` 的 POST/PUT 同样裸奔靠路径规则；③ `SysUserController.java:117` 存在第二登录端点 `POST /api/user/login`——重复实现登录逻辑、**无限速**，当前因 `/api/user/**` 是 ADMIN 段而不可滥用，但该规则一旦放宽即成洞 |
