| 作者 | 司南（产品）× 工程落地同步撰写 |

## 一、背景与目标

**背景**：系统现有 30+ 统计指标、自定义看板与 Excel 导出，但三个结构性缺口使厂长实际用不上：
①数据不会自己送达（要人登录点开）；②只看不闭环（异常无责任人）；③看板数字存在
「看似有、实际无」（severity 全 HIGH、TEST 相机混入、良品率不可算）。

**本期范围**：先解决「按天掌握产线结论」——新增**产线统计日报** Tab，每天一份快照、按天查询、
可导出。异常闭环（R-02）与目标基线（R-03）不在本期。

**已拍板口径**：
- H1：缺陷率分母 = **检测图片数**（非检测件数；产量数据源未接入前唯一可算口径）
- D1：「每天一个数据」= 列表页每天一行（厂级汇总），点详情展开每产线一行
- D2：缺陷率单位 = **每千张（‰）**
- D3：本期不加目标值列
- D4：本期只做 Tab + 导出；推送通道（企微/邮件）待验证内容后再接

**成功指标**：
- 打开 Tab 3 秒内看到「昨天」整页（快照查询，P95 < 500ms）
- 报表与现场手工盘点偏差 < 5%（上线前用 2026-11-16 实测数据对数：1230 张 / 38 框）
- 厂长连续 2 周主动查看（送达验证后统计）

## 二、名词与口径定义

| 术语 | 定义 |
|---|---|
| 检测图片数 | 当日 `defect_image_file` 中 REAL 相机上报的图片张数（缺陷率分母） |
| 缺陷框数 | `SUM(defect_image_file.defect_count)`（分子；现场恒每图 1 框） |
| 缺陷率(‰) | 缺陷框数 ÷ 检测图片数 × 1000；**分母为 0 时为 NULL，绝不显示 0** |
| REAL 相机 | `dim_camera.camera_type='REAL' AND is_deleted=0`；TEST 与未登记相机不进日报 |
| 快照行 | 每天 00:05 物化前一天的行（`fact_daily_line_report`，幂等覆盖） |
| 实时行 | 当天不入库，查询时实时计算，响应带 `dataSource=REALTIME` |
| 样本下限 | 当日检测图片数 ≥100 才参与「最差相机」排名与环比参考（`sampleInsufficient` 标记） |
| snapshot_version | 口径版本号；改口径只影响新版本之后的日期，历史快照数字不变 |

## 三、需求范围

**包含**：日报快照表与生成任务、日报列表（区间查询+环比）、单日详情（KPI 卡+产线分解+TOP3
缺陷类型+最差相机）、Excel 导出、管理员补算、`DAILY_REPORT_FAILED` 运维告警、口径页脚。
**不包含（本期不做）**：良品率/产量/OEE、推送通道、目标值与达成率、异常闭环、产品维筛选
（图片通道无产品列，显式不支持）。

## 四、方案对比与选型

| 方案 | 思路 | 结论 |
|---|---|---|
| A 实时聚合 | 不落表，查询时按天 GROUP BY | 否决：31 天外要 UNION 归档月表；改口径后历史全变；「当日在册相机数」等快照信息算不出 |
| **B 日终物化快照** | `fact_daily_line_report`，00:05 物化昨天，当天实时算 | **采纳**：历史口径稳定、查询快、不受归档影响、补算幂等留痕 |
| C 塞进现有看板 | LineAnalyticsView 加预设 | 否决：形态是图表不是「每天一行可查」，导不出整份日报 |

## 五、用户角色与场景

| 角色 | 场景 |
|---|---|
| 厂长 | 早会前打开日报 Tab 看昨天整页；按周翻历史对比 |
| 产线主管 | 点开某天详情，看本产线缺陷率与最差相机，安排改善 |
| 管理员 | 任务失败告警后手动补算；导出 Excel 汇报 |
| 系统 | 每天 00:05 自动物化前一天；失败落 `DAILY_REPORT_FAILED`（OPS 类告警，成功自动恢复） |

## 六、功能需求

| 编号 | 需求 | 业务规则 | 验收标准（GWT） |
|---|---|---|---|
| FR-01 | 日报列表 | 默认近 30 天含今天；历史读快照、今天实时；start>end 拒绝 | Given 区间含昨天，When 打开 Tab，Then 每天一行且 3 秒内渲染 |
| FR-02 | 缺陷率口径 | ‰=框数/图片数×1000；分母 0 → NULL 显示「无数据」 | Given 某日 detectCount=0，Then defectRateKilo=null 且前端显示「无数据」 |
| FR-03 | 环比 | 与前一天同 scope 缺陷率比较，%；任一侧缺失 → null 显示「—」 | Given 前日 25.0‰、当日 30.9‰，Then 显示 ↑23.6% 红色 |
| FR-04 | 单日详情 | 厂级行+产线行拆分；TOP3 缺陷类型（按框数）；最差相机（样本≥100） | Given 当日样本 620 张的相机，Then 显示其缺陷率；样本 50 张 → 「样本不足，未排名」 |
| FR-05 | 相机健康 | 每行含在线相机 x/y（当日有上报算在线）与当日温度告警数 | Given 2 台 REAL 1 台未上报，Then 1/2 |
| FR-06 | 导出 | 区间内快照行+今天实时行一起导出；列含日期/产线/指标/数据源 | Given 7 天区间，Then 导出 8 行（7 快照+1 实时）×12 列 |
| FR-07 | 补算 | 仅 ADMIN；幂等覆盖（DELETE+INSERT 同事务）；失败提示已落告警 | Given 某日无快照，When ADMIN 补算，Then 行出现且 unique key 不冲突 |
| FR-08 | 生成任务 | 每日 00:05 物化昨天；失败落 `DAILY_REPORT_FAILED` HIGH（OPS 前排），成功自动恢复 | Given DB 故障一次，Then 告警出现；恢复后重跑成功 → 告警 is_resolved=1 |
| FR-09 | 口径披露 | 页脚固定显示：公式/相机范围/排名样本/数据源 | 打开详情页即见，无需展开 |

## 七、非功能需求

- 列表查询 P95 < 500ms（快照表唯一键查询，无大表扫描）
- 生成任务单日耗时 < 30s（现场日增 ~1.5k 张）
- 快照表保留：随库备份策略，不参与 31 天归档（单行 <1KB，10 年 <400 万行可接受）
- 兼容性：不改动既有统计端点，旧页面零影响

## 八、数据设计

表 `fact_daily_line_report`（DDL 见 `sql/deploy/07_daily_report.sql`，SchemaInitializer 启动期幂等建表）：
`uk_report_date_line(report_date, line_id)`；`line_id=0` 为厂级汇总行；产线名/快照版本随行固化。

端点（`/api/v1/analytics/daily-reports`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 列表：`startDate/endDate/lineId` |
| GET | `/{date}` | 详情：厂级+产线分解，`missing=true` 表示无快照 |
| POST | `/{date}/regenerate` | 补算（ADMIN） |
| GET | `/export` | Excel 导出 |

配置项：`app.daily-report.cron`（默认 `0 5 0 * * ?`）。

## 九、异常处理清单

| 场景 | 行为 |
|---|---|
| 生成任务失败 | 落 `DAILY_REPORT_FAILED` HIGH 运维告警（已同步 `OPS_ALERT_TYPES` 前排）；成功后自动恢复 |
| 历史日无快照 | 详情返回 `missing=true` + 提示可补算；列表该日无行（不是 0 行数据） |
| 当天无任何上报 | `detectCount=0` → 缺陷率 NULL「无数据」；环比「—」 |
| 产线改名/删除 | 历史行 `line_name` 为生成时快照，不受影响 |
| 重跑/并发 | DELETE+INSERT 同事务 + 唯一键兜底，幂等 |

## 十二、口径修正记录（2026-11-17 现场实测后增补）

对数验收时发现：**图片口径缺陷率恒为 1000‰**——图片通道只上报缺陷图（每张必带缺陷框），
分母 ≡ 分子，该指标无区分度。同时发现 `camera_status` 心跳带**真实累计检测计数**
（`total_count/ok_count/ng_count`，现场实测如 DA6560418 total=169504 / ng=311）。

**修正**：缺陷率改双口径——
- **主口径（计数）**：缺陷率(‰) = NG计数日增 ÷ 检测总数日增 × 1000；日增 = 当日 00:05
  固化的累计和 − 前一日累计和。自第二份快照起可用；首日或计数器被重置（差分为负）显示「待积累」。
- **辅口径（图片）**：保留缺陷图片数列（通道真实上传量），不再作为缺陷率展示。

连带调整：相机排名由「缺陷率最高」改为「缺陷框数最多 + 占比」（相机级图片口径缺陷率恒 1000‰
无区分度）；表增列 `insp_total_cum/ok_total_cum/ng_total_cum`（`ensureColumns` 幂等补列）；
快照固化计数时不过滤 `is_active`（已删相机计数器冻结，排除会让累计和下跌）。

**验收数据更新**：2026-11-16 厂级 REAL 口径实测：缺陷图片 1688 张（ZK06 1072 / ZK22 355 /
ZK09 139 / ZK23 108 / ZK65 14），5 条产线、在册 REAL 相机 18 台、16 台当日有上报、温度告警 31 条；
计数口径自 2026-11-18 首次差分起出数。

## 十三、交互重构 v2（2026-11-17 晚，用户反馈「不是我想要的」后重做）

### 13.1 反馈与判断

用户两点诉求：产线统计**默认进「工厂质量看板」**；日报要 **最上面选产线 → 点本月日期 → 看当天各维度**。

判断：两个页面的问题同源——**都要求用户先配置/先读表，才看到结论**。所以只改入口与信息层级，不动口径
（REAL 过滤、无数据不显示 0、样本下限、计数主口径全部保留）。

### 13.2 产线统计（`/line-analytics`）

| 位置 | 改前 | 改后 |
|---|---|---|
| 首屏 | 模板下拉 + 6 筛选 + 5 管理按钮，先配后看 | **进页即渲染内置「工厂质量看板（默认）」**（代码常量，不可编辑/删除，不随上次选择漂移） |
| 内容顺序 | 由模板决定 | 固定结论优先：工厂总览 → 缺陷量趋势（按产线）→ 产线缺陷排行 + 责任相机 → 帕累托 + 时段热力 → 缺陷日历 |
| 工具栏 | 5 个按钮平铺 | 收进「看板设置 ▾」（新建/编辑/复制/另存为/大屏/删除 + 记住上次看板） |
| 筛选 | 5 个下拉常驻占一整行 | 默认只露「时间范围 + 高级筛选 ▾」；产线来自顶部级联，收起时显示「当前按哪条产线看」 |
| 两侧栏 | 组件库 + 配置面板常驻 | 内置看板下隐藏，画布占满；用户模板不受影响 |
| 日聚合运维卡 | 挡在 KPI 与图表之间 | 移到页面底部 |

「记住上次看板」开关**默认关**（每次进入先看默认看板，保证可预期）；开启后才记住上次选择。

### 13.3 统计日报（`/daily-report`）——从「表格 + 详情」改为三段式

| 段 | 内容 | 交互 |
|---|---|---|
| ① 产线 | 胶囊 Tab：全厂 / 各 REAL 产线（`listRealLines`） | 点击即换，记住上次选择（localStorage）；顶部布局级联变化时跟随 |
| ② 月历 | 当月 7×N 网格，每格 = 日期 + 缺陷框数 + 缺陷率 | 点格选中；`←/→` 切日、`Home` 回今天；四态：有数据（底色分档）/ 无数据 / 无快照 / 未来（虚线） |
| ③ 当日 | 4 张 KPI（检测日增 / 缺陷日增 / 缺陷率‰ / 在线相机）+ 四宫格（缺陷类型 TOP5 · 相机 TOP5 · 24 小时分布 · 当日异常）+ 口径页脚 | 换日期只刷这一段，月历不动 |

**色阶**：按当月「有数据日」的缺陷框数分位（P50/P75/P90）分 4 档，不写死阈值——现场缺陷量跨月波动大，
固定阈值会让某个月全红或全浅。

**月历格主值为什么是「缺陷框数」而不是缺陷率**：缺陷率依赖心跳累计值的日终快照差分，补算历史日期时
当前计数已含之后上传（拍下来必错），所以补算一律不拍计数（`generateFor(date, stampCounters)`）；
图片通道又每张必带缺陷框（图片口径恒 1000‰）。结论：**历史日只给缺陷量，缺陷率从第二份日终快照起才有**，
格上第二行显示「率待积累」而不是编个数字。

**0 上传小时**：夜间 20:00–08:00 本来不排产，全算会天天报「13 小时无上传」→ 只把白天 08:00–20:00
的 0 上传当异常线索，夜间段合并成一句「夜间未排产」。

**当日异常的口径**：「0 上传」可能停线/断网，也可能只是没排产 —— 页面明确写「只能当线索，不当结论」。

### 13.4 新增端点

| 端点 | 说明 |
|---|---|
| `GET /daily-reports/calendar?month=&lineId=` | 月历：全月每天一格（含未来/无数据/无快照状态），一次取全月（多取一天做计数差分基线），返回 `lines` 供胶囊 Tab |
| `GET /daily-reports/{date}/breakdown?lineId=` | 单日维度：汇总取快照/实时，明细（类型 TOP5、相机 TOP10、24 小时、白天 0 上传）从图片事实表算；超 31 天归档后 `detailsAvailable=false` → 页面显示「明细已归档（仅保留汇总）」 |

`summary.worstDate/bestDate` **只在已完成的历史日里评**：今天还在涨，拿它当「最差」会让厂长每天早上
看到「今天最差」，随后又自我修正，没有决策价值。
