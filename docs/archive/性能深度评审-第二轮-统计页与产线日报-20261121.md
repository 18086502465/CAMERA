## 2. 新发现（首轮未覆盖）

### 2.1 ★ 前端重复并发请求击穿缓存（本轮主因）

**统计页**（首屏，11 个 API，累计 3955ms）：

| 相对时刻 | 时长 | URL | 判定 |
|---:|---:|---|---|
| +1677ms | **1012ms** | `line-summary?...&dim=line` | 穿透 |
| +1678ms | **1080ms** | `line-summary?...&dim=line`（**完全相同**） | 穿透（并发重复） |
| +2852ms | 967ms | `line-summary?...`（global） | 穿透 |
| +3965ms | 79ms | `line-summary?...&dim=line` | 命中 |
| +3965ms | 132ms | `line-summary?...&dim=line` | 命中 |

- 5 次 `line-summary` 中 **4 次是同一个 `dim=line` URL**；前两次同时发出、同时穿透。
- 每次穿透 = 69 次 Repository 聚合 SQL → 首屏约 **3 × 69 ≈ 207 次**。
- 二次刷新仍发出同样 5 次（全部命中 68–122ms），说明**重复是确定性的代码路径，不是偶发竞态**。

**调用链根因**：

- `onMounted` 先 `await loadDashboard()`，该函数内部已 `await loadWidgetData()`；
- 紧接着 `await loadData()`，其内部**又** `await loadWidgetData(seq)`；
- 内置看板多个 widget 的 `widgetParams(w)` 生成**相同参数**（同为 `dim=line`，无独立 filterJson）→ `Promise.all` 里多个同 URL 并发。
- 注意：`loadDashboard()` 另有 6 处调用点（`loadDashboardById` / `refreshDashboard` / `saveDashboard` / `removeDashboard` 等）**不跟随 `loadData()`**，因此不能简单删掉其内部调用，需在 API 层去重。

**日报页**（首屏，8 个 API）：

| 相对时刻 | 时长 | URL | 判定 |
|---:|---:|---|---|
| +1639ms | **1127ms** | `daily-reports/2026-11-21/breakdown` | 穿透 |
| +1640ms | **1169ms** | 同上（**完全相同**） | 穿透（并发重复） |
| +891ms | 732ms | `daily-reports/calendar?month=2026-11` | 穿透 |
| +890ms | 366ms | `defect-images/filter-options` | 无缓存 |

- 调用链：`loadAll()` → `loadCalendar()` → `ensureSelection()` → `loadBreakdown()`（**未 await**）→ 返回后 `loadAll()` 又 `await loadBreakdown()`。

**后端放大机制**：`TtlCache.get()` 只做「查 map → 判过期 → 返回 null」，**没有 single-flight**。多个同 key 请求同时到达时全部 miss，各自重算。前端去重是成本最低的止血点。

### 2.2 ★ 静态资源未压缩且每次刷新全量重下

| 资源 | 传输大小 | 首次耗时 | 刷新耗时 |
|---|---:|---:|---:|
| `index-CAgzr4Su.js` | **1832 KB** | 948ms | 918ms |
| `index-Bb6yjXMn.js`（第二块 vendor） | **1012 KB** | 481ms | 463ms |
| `index-BSatY7oR.css` | **351 KB** | 948ms | 725ms |
| 其余 12 个小 chunk | ~140 KB | — | — |
| **合计** | **≈3.3 MB / 每次导航** | — | — |

- 响应头实测：`Content-Length: 1875306`、`Vary: Origin`，**无 `Content-Encoding`** → 带 `Accept-Encoding: gzip` 请求仍回 1.8MB 原文（`server.compression` 未配置）。
- `Cache-Control: no-cache, no-store, max-age=0, must-revalidate`（Spring Security 默认）→ 刷新时 `transferSize` 仍是 1832KB，**浏览器完全没复用**。
- 这解释了二次刷新 API 已全部命中（累计 1.17s）但 FCP 仍 1.68s：时间花在下载 + 解析 3.3MB。
- 产物带内容哈希且 `build-release.sh` 保留历史 chunk，**给 `/assets/**` 加 immutable 长缓存是安全的**。

### 2.3 ★ 前端长任务（ECharts 渲染）

| 页面 | 首次长任务 | 刷新长任务 |
|---|---|---|
| 统计页 | 5 个 / 696ms（最长 299ms），canvas=6 | 10 个 / 824ms |
| 日报页 | 6 个 / 423ms，canvas=0 | 4 个 / 212ms |

- 统计页内置看板 6 个 ECharts 实例同时 `renderAllCharts()`，主线程连续阻塞。
- 即使后端缓存全命中，这部分时间无法避免 —— 属于**前端固有成本**，需要单独处理。

### 2.4 `filter-options` 每次 350–780ms 且无缓存

- 实测连续三次：**0.49s / 0.64s / 0.78s**（无缓存，且在 DB 争用时波动明显）。
- SQL：`defect_image_box b JOIN defect_image_file f` + `COUNT(DISTINCT b.image_id)` + `GROUP BY`，另有分辨率选项同样全表扫描。
- 统计页和日报页**都调用**它，是首屏固定成本。下拉候选来自实际上报数据，分钟级变化，适合短缓存。

### 2.5 后台热路径负载（首轮 P1-1 之外的残留）

25 秒窗口差分采样：

| 操作 | 当前增速 | 说明 |
|---|---:|---|
| `INFORMATION_SCHEMA.COLUMNS` 检查 | **0 / 25s** | P1-1 已确认生效；累计 315.9 万次全部是部署前产生 |
| `UPDATE camera_status`（全字段） | **120 / 25s ≈ 4.8/s** | 心跳主流程，每次 5.24ms，产生 binlog |

| `sys_system_setting` 查询 | **306 / 25s ≈ 12.2/s** | `checkAndAlert()` → `getDecimalSetting()` 每次心跳读阈值，无本地缓存，累计 84.8 万次 |

- 这些不直接阻塞页面（DB 连接仅 7、buffer pool 4G），但在首屏 200 次聚合 SQL 同时涌入时会放大排队。
- java RSS 4.5GB（接近 `-Xmx3986m` + 堆外）、进程 CPU 均值 48%，仍非瓶颈信号。

## 3. 根因归纳

| 编号 | 根因 | 性质 |
|---|---|---|
| R6 | 前端两处确定性重复调用 + 多个 widget 同参数 → 同 URL 并发 → `TtlCache` 无 single-flight → 缓存击穿 | 代码缺陷（可零风险修） |
| R7 | 静态资源 3.3MB、无 gzip、no-store → 每次导航重下 | 部署配置缺失 |
| R8 | 6 个 ECharts 实例同步渲染 → 主线程长任务 0.7–0.8s | 前端渲染设计 |

| R10 | 心跳每次读系统设置阈值（12.2/s）；全字段 UPDATE 4.8/s | 后台背景负载 |

## 4. 第二批优化方案（按收益 / 风险排序）

| 级别 | 措施 | 预期收益 | 风险 | 改动范围 |
|---|---|---|---|---|
| **P0-1** | `frontend/src/api/analytics.js` 给 `getLineAnalyticsSummary` 与 `getDailyReportBreakdown` 加 **in-flight Promise 去重**：key = url + 稳定序列化 params，同 key 并发复用同一 Promise，`finally` 清理。**不删页面调用**，兼容 `loadDashboard()` 的 6 处独立调用点。 | 统计页 line-summary **5→2** 次、日报 breakdown **2→1** 次；首屏省 **1.1–2.1s** | **极低**（不改口径、不改后端） | 1 个 JS |

| **P1-1** | `TtlCache` 增加 single-flight（同 key 只放一个线程计算，其余等待结果）。作为后端兜底，防其它页面/轮询并发穿透。 | 消除所有并发穿透场景 | **中**（共享类，影响全部缓存使用方，需全量测试） | `TtlCache.java` |
| **P1-2** | 心跳阈值 `getDecimalSetting()` 结果本地缓存（配置变更时失效），消除 12.2/s 的设置查询。 | 减少 105 万次/天查询 | 低–中（需处理配置热更新） | `CameraStatusServiceImpl` |
| **P1-3** | ECharts 渲染：6 个实例改为分批渲染 / `requestAnimationFrame` 错峰；热力图 422 格窗口内降采样。 | 长任务 824ms → **<300ms** | 中（需视觉回归） | `LineAnalyticsView.vue` |
| **P2** | 物化汇总表（5/15 分钟粒度，按 line/camera/defectType/shift 预聚合）+ 合并 69 次 SQL 为少量多维度查询。 | 单条 100–190ms → <5ms | 高（口径、刷新任务、对账、存储需立项） | 独立项目 |

**明确不做（已有实测结论，勿重复尝试）**：

1. `FORCE INDEX (idx_defect_file_capture_time)` —— 首轮 317ms > 默认 200ms。
2. 扩 JVM 堆 / MySQL buffer pool —— 资源空闲，RSS 4.5G 是 `-Xmx` + 堆外的正常占用。
3. 改统计口径换取速度 —— 「图片事实表优先 / 无数据≠0 / 截断上报 / 列表与导出口径一致」是铁律。
4. 开 `slow_query_log` 长期记录 —— 需改生产配置，本轮只读。

**与预期的两点偏差（如实记录）**：

1. 统计页请求数是 **5→3** 而非 5→2。`loadDashboard()` 内部的 `loadWidgetData()` 与随后 `loadData()` 的调用是**串行**的，两次同 URL 请求不在同一飞行窗口，in-flight 去重只能合并同一轮里的多个 widget（4→1）；跨轮重复靠后端已有缓存命中（实测 68ms）。若需压到 2 次，须改页面调用结构，风险高于本批收益，暂不做。
2. 入口 chunk 刷新 `transferSize=0`，但第二个 vendor chunk `index-Bb6yjXMn.js` 刷新仍传 335KB（gzip 后，原 1MB）。响应头已确认 immutable，原因未完全定位（疑似动态 import 的缓存分区），不影响 FCP 达标，留作后续观察。
