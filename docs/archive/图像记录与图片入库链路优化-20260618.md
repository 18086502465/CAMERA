# 图像记录与缺陷图片入库展示链路优化报告

日期：2026-06-18  
范围：`/api/v1/defect-images/upload`、图像记录页、相机状态页最近图像跳转、缺陷图片数据库入库与查询链路。

## 1. 本次优化结果

### 1.1 图像记录页不再受“最近 200 张”限制

- 图像记录页首屏改为按相机聚合查询：`GET /api/v1/defect-images/camera-summaries?latestLimit=5`。
- 单个相机展开后使用数据库分页：`GET /api/v1/defect-images/history?page=1&size=10&cameraId=...`。
- 页面展示总数来自 `defect_image_file` 的 `COUNT(1)`，不再依赖全局最近 N 条图片。
- 兼容接口 `/api/v1/defect-images/recent` 默认上限从 200 提升到 1000，服务层最大保护值为 5000；正式页面不再依赖该接口做全量图像记录展示。

### 1.2 相机状态页增加“图像记录”跳转

- 相机状态页“最近图像”列新增 `图像记录` 按钮。
- 点击后跳转到：`/stats/images?cameraId=<相机编号>&cameraName=<相机名称>`。
- 图像记录页读取路由参数后自动按相机过滤，只展示对应相机对象，并在顶部展示当前筛选提示。
- 若有 `cameraId`，后端查询优先按相机编号聚合，避免历史 `cameraName` 变化导致漏图。

### 1.3 缺陷图片入库链路优化

- `defect_image_batch` 新增并维护：
  - `declared_image_count`：metadata 声明图片数
  - `success_count`：成功入库图片数
  - `fail_count`：失败图片数
  - `upload_status`：`PROCESSING / SUCCESS / PARTIAL_FAILED / FAILED`
  - `error_summary`：失败摘要
- 上传文件与 `metadata.images[].fileName` 改为一一对应校验：缺失、额外、重复均返回 422，且不落盘、不入库图片记录。
- 单图处理失败时会清理已保存文件和已写入的图片/缺陷框记录，批次保留失败状态，便于现场追踪。
- 查询聚合逻辑改为以 `camera_id` 优先聚合，避免同一相机历史上报名称变化造成页面拆成多个相机对象。
- 新增/补齐查询索引：
  - `defect_image_file(camera_id, create_time, image_id)`
  - `defect_image_file(camera_name, create_time, image_id)`
  - `defect_image_file(capture_time, image_id)`
  - `defect_image_box(defect_type)`
  - `defect_image_box(severity, image_id)`
  - `defect_image_batch(upload_status, upload_time)`

## 2. 数据库入库方案评估

当前三表模型适合现场追溯与页面查询：

```text
defect_image_batch  上传批次，记录一次接口调用及整体状态
defect_image_file   图片文件，一张图片一条记录
defect_image_box    缺陷框，一张图片可关联多个缺陷对象
```

结论：方案合理，建议继续保留三表结构。关键优化点已补齐：批次状态、成功/失败数量、错误摘要、相机编号聚合和查询索引。

需要持续关注：

1. 设备重试幂等：当前同一批次重复上传会生成新批次和新文件，后续可增加 `requestId` 或设备侧批次号唯一约束。
2. 历史孤儿文件：当前诊断存在 7 个历史孤儿文件，均为本次优化前产生；本次测试未新增孤儿文件。
3. 大批量查询：页面已改为分页，避免一次性拉取全部图片；后续如图片超过百万级，可继续按月分区或冷热归档。

## 6. 验收结论

本次围绕“上传图片数量、数据库记录、页面展示数量不一致”的链路问题进行了修复和回归：

- 正常上传：文件、批次、图片记录、缺陷框、页面聚合均一致。
- 异常上传：文件名不匹配直接 422；损坏图片保留失败批次、不新增图片记录、不留下新孤儿文件。
- 图像记录页：通过相机聚合 + 展开分页，不再被最近 200 张限制。
- 相机状态页：可从最近图像直接跳转到对应相机的图像记录页面。

结论：本次 P0 链路修复通过，可进入现场回归。
