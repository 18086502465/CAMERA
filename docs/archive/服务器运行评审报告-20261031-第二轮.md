## 2. 本轮实测发现并已修掉的 4 个缺陷

### 2.1 ★ P0：匿名可读写生产库 —— `/api/v1/**` 白名单过宽

#### 根因

为让设备端接口免鉴权，上一版把**整个 `/api/v1/**`** 放进白名单：

```java
// ❌ 修复前
.antMatchers("/api/v1/**", ...).permitAll()
```

但 `/api/v1/**` 下面混着**管理端点**：`/api/v1/system/settings`、`/api/v1/config/**`、
`/api/v1/analytics/**`。同时 `JwtRequestFilter.DEVICE_PATHS` 也是 `/api/v1/**`，
导致该前缀下所有请求**都不做 JWT 认证**。

#### 实测复现（真实改了生产库）

```
① 匿名 PUT /api/v1/system/settings
   {"settings":[{"settingKey":"alert.cpuWarning","settingValue":"77"}]}
   → HTTP 200「系统设置已保存」
   → 查库：alert.cpuWarning 从 90 变成 77        ← ★ 匿名真的改了库

② 匿名 POST /api/v1/config/products
   {"productCode":"PROBE_001","productName":"匿名插入"}
   → HTTP 200「创建成功」
   → 查库：dim_product 从 2 条变成 3 条          ← ★ 匿名真的插了数据

③ 匿名 GET /api/v1/config/products / defect-types / camera-defect-mappings
   → 全部 HTTP 200                                ← ★ 配置数据完全泄露
```

**危害**：**只要能访问到 8091 端口，不需要任何凭据**，
就能改告警阈值、增删产品与缺陷类型、改缺陷映射、关掉异常单、读写看板。

#### 修复

白名单精确到**方法与路径**，只保留冻结契约的 3 个设备端点 + 图片静态读取：

```java
.antMatchers(HttpMethod.POST,
    "/api/v1/camera/status/heartbeat",        // 冻结契约
    "/api/v1/camera/inspection/batch-upload",  // 冻结契约
    "/api/v1/defect-images/upload"             // 冻结契约
).permitAll()
.antMatchers(HttpMethod.GET,
    "/api/v1/defect-images/file/**",           // 图片静态读取
    "/api/v1/camera/image/**"
).permitAll()
```

> ⚠️ **图片静态读取必须放行**：前端 `<img :src="...">` **不带 Authorization 头**
> （浏览器只在 XHR/fetch 里带）。要求 token 会让所有缺陷图片裂图。

#### 修复后实测

| 请求 | 修复前 | 修复后 |
|---|---|---|
| 匿名 GET `/api/v1/system/settings` | **200** | **403** |
| 匿名 PUT `/api/v1/system/settings` | **200**（真改库） | **403** |
| 匿名 POST `/api/v1/config/products` | **200**（真插数据） | **403** |
| 匿名 GET `/api/v1/config/products` | **200** | **403** |
| 设备端 batch-upload（正确 token） | 200 | **200** ✅ 契约未受影响 |

### 2.2 ★ P0：无角色鉴权 —— 普通用户可删管理员

#### 根因

`JwtRequestFilter` 早已构造好 `ROLE_ADMIN` / `ROLE_USER` 权限，
但 `SecurityConfig` **从来没用过**（只有 `authenticated()`，没有 `hasRole()`），
全仓库也没有 `@EnableGlobalMethodSecurity` / `@PreAuthorize`。
前端菜单隐藏（`Layout.vue` 的 `isAdmin`）**只是界面隐藏，不是权限控制**。

#### 实测复现

```
① 匿名注册 probe_worker_01 → 200，角色固定为 0（上一轮已修）
② 该账号登录拿 token（role=0）
③ GET  /api/user            → 200（读到全部用户）
④ GET  /api/logs/operation  → 200（读到全部操作日志）
⑤ DELETE /api/user/3        → 200「删除成功」
⑥ 查库：admin 被删除，只剩探针账号            ← ★ ★
```

> **事后已从备份恢复 admin**（`user_id=3`，`admin123`，实测可登录）。

#### 修复（路径级 + 方法级双保险）

**路径级**：原则是**读开放给所有登录用户，写只给管理员** ——
工人账号仍要看看板、缺陷记录、统计，不能一刀切。

```java
// 纯管理，全段 ADMIN
.antMatchers("/api/user/**", "/api/logs/operation/**").hasRole("ADMIN")

// 写操作 ADMIN（POST / PUT / DELETE 三组）
.antMatchers(HttpMethod.POST, "/api/v1/config/**", "/api/v1/analytics/**",
             "/api/v1/system/**", "/api/cameras/**", ...).hasRole("ADMIN")
...
// 只读端点：登录即可
.antMatchers("/api/stats/**", "/api/cameras/**", "/api/v1/defect-images/recent", ...)
        .authenticated()
```

**方法级**：`@EnableGlobalMethodSecurity(prePostEnabled = true)`，
8 个高危 Controller 的写方法加 `@PreAuthorize("hasRole('ADMIN')")`
（`SysUserController`、`SystemSettingsController`、`FinalConfigController`、
`ConfigImportController` 整类、`DimCompanyController`、`DimWorkstationController`、
`DimProductionLineController`、`SysHolidayConfigController`）。

### 2.3 P1：`/etc/default/camera-detection` 重复叠加 4 份、口令文件曾 0644

实测该文件 **103 行**，「备份相关」段落出现 **4 次**（第 22、47、72、97 行）。

**根因**：`install.sh` 第 4 节 `cat >` 写主体、第 8c 节 `cat >>` 追加备份参数，
而 `sed -i` **只删 4 个变量行、没删注释行** → 重复执行就一段段叠加。

**修复**：
1. 第 4 节改为整份文件**一次性重写**（`mktemp` + `mv` 原子替换）
2. 第 8c 节追加前**先剥离整个备份段**（含注释行）+ 折叠多余空行
3. 权限 `0644` → **`640`**：文件里有数据库口令与管理员口令，
   0644 意味着**任何本地用户都能读到**；之前第 8c 节才改回 640，
   **安装中途失败就会短暂暴露**

**实测**：模拟重复执行 3 次，文件稳定在 31 行、内容一致（不再增长）。

### 2.4 P2：Mapper 注解与 XML 重复 → 每次启动刷 4 条 ERROR/WARN

详见 §1.1。已修（`SysUserMapper` 只留 XML；`SysOperationLogMapper.xml` 删掉
与 `BaseMapper.insert` 撞名的 `<insert>`，交给 MP 原生）。

### 2.5 P2：自检脚本检查的是"用不到的目录"，遗留目录每次重启被重建

追查 `/var/lib/camera-detection-system/data/uploads/defect-images`
（迁移前遗留、应用根本不用的空目录）在每次服务重启后都会重新出现的原因：

**根因**：`run.sh` 里的自愈建目录：

```bash
# ❌ 修复前
mkdir -p "${WORK_DIR}/logs" \
         "${WORK_DIR}/data/uploads/images" \
         "${WORK_DIR}/data/uploads/defect-images" 2>/dev/null || true
```

而**缺陷图片实际落盘在 `/data/camera-detection/images/defect-images/`**
（配置项 `defect-image.upload.dir`）——
`run.sh` 里硬编码的这条路径是**迁移前的遗留**，应用根本不用。

**为什么危险**：自检脚本 `verify.sh` 检查的也是这条遗留路径，
所以它**永远显示"存在且可写"**，
而真正在用的 `/data/.../defect-images` **根本没被检查** ——
一旦它不存在，图片上传会"返回成功但不落盘"，而自检全绿、无人察觉。

**修复**：
1. `run.sh` 不再创建遗留路径
2. `verify.sh` 改为**从 `config/application.yml` 解析实际落盘目录**再检查，
   目录不存在时报「图片上传会『成功但不落盘』」

**端到端验证**（真实图片上传实测）：

```
POST /api/v1/defect-images/upload（metadata + 真实 PNG，200x150，63KB）
  → HTTP 200「缺陷图片上传成功」
  → 落盘：/data/camera-detection/images/defect-images/20261031/CAM-001/100000000_c050b2c9.png ✅
  → 库中 image_path 与 image_url 均正确
  → 目录结构：{根}/{yyyyMMdd}/{cameraId}/{HHmmssSSS}_{uuid8}.{ext} ✅
```

> 这是**服务器上第一次跑通完整的图片上传链路**（此前 `defect_image_file` 恒为 0）。
> 测试数据已全部清理（库记录 + 磁盘文件 + 空目录）。

## 9. 结论

**运行质量是好的**：服务零重启、备份连续 9 次成功且实测可恢复、
慢查询日志干净、内存用 12%、磁盘用 2%、日志治理到位。

**但本轮实测又挖出 4 个此前所有轮次都没发现的缺陷**，其中 2 个是 P0：

1. **匿名可读写生产库** —— 只要能访问 8091 端口，无需任何凭据就能改配置
2. **普通用户可删管理员** —— 前端菜单隐藏被误当成了权限控制

**这两次的根因是同一类错误**：**用「路径前缀」代替「端点语义」做权限判断**。
`/api/v1/**` 一放行，混在下面的管理端点就全部裸奔；
`authenticated()` 一写，`ROLE_ADMIN` 就永远用不上。

> **给后续的硬规则**：
> ① 白名单必须**精确到方法与路径**，禁止任何 `/**` 兜底放行；
> ② 新增管理端点时，**必须同时改三处**：`SecurityConfig` 路径规则、
>    Controller 的 `@PreAuthorize`、`verify.sh` 的安全回归项；
> ③ 前端菜单隐藏**永远不等于**权限控制。

**两件事必须说清楚**：

1. **它还是空转的** —— 一帧产线图片都没有。所有"接了产线才会暴露"的问题
   （高并发上传、图片清理真实行为、库表增长）**都还没被验证**。

2. **安全项不可能靠读代码发现**。连续两轮实测各挖出 3–4 个 P0/P1，
   而上一轮的报告曾写"安全项已修复完"。**唯一可靠的做法是把安全断言写成
   可执行的检查项**（本轮已把 2 项写进 `verify.sh`，每日自动跑）。

**下一步优先级**：
① 接产线前做真实图片联调 → ② 关闭公开注册 + 建专用 MySQL 账号
→ ③ 改管理员口令 → ④ systemd 加资源上限。
