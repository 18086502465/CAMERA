# 全项目评审清单与优化方案（2026-11-12）

扫描范围：`fact-product/`（后端）、`frontend/src/`（前端）、`installer/linux/`（部署）、`docs/` + CI + 构建链。
方法：三路只读扫描 + 关键结论逐条回读源码复核（6 条最高影响项全部核实，其中 2 条为本次提交引入）。

> 本文件是一次性评审记录，数字与结论以 2026-11-12 的代码状态为准。

---

## 一、整体评估

**综合 6.0 / 10（B-）：能跑、有人踩过坑并留下了痕迹，但"改完没删干净"和"文档与实现脱节"是两个系统性病灶。**

| 维度 | 评分 | 判断依据 |
|---|---|---|
| 后端代码质量 | 6.5 | 七域 DDD 分层已成型、Repository 收敛彻底，注释沉淀了大量真实故障；但 P3~P5 只做了"搬"没做"删"，同段 SQL 在 Service 与 Repository 双份，已修的 bug 在另一条路径复发 |
| 后端安全 | 5.0 | 主通道有完整鉴权链路，但 3 个 `permitAll` 设备端点里 2 个的 token 校验是空壳，与 `SecurityConfig` 注释的声称直接矛盾 |
| 前端 | 6.0 | 12 个在线页面的接口路径已与后端对齐（历史 `/users` 类断裂未复发）；风险已从"路径错"转为"失败静默"——接口挂了界面照样显示 0 |
| 部署易用性 | 7.0 | 主干脚本严谨度高于同类项目（空库保护、`MYSQL_PWD`、备份产物非空校验、清理三道防线、`set -Eeuo pipefail`）；但 `init-database.sh` 是全项目唯一"跑一次就毁库"的入口 |
| 文档正确性 | 5.5 | 体系与守卫都在，但统一布局改造后有 10 处以上路径/数字未同步，且 3 处错误会直接误导现场操作 |
| CI 与构建链 | 5.0 | 4 个 job 都是真实执行而非空跑，但**发布链完全未被 CI 覆盖**——打包缺陷只能到服务器上才暴露 |

**一句话结论**：这套系统的风险不在"功能不对"，而在"错了不报错"。三处最典型：接口失败显示 0、token 不校验但注释说校验了、发布包缺文件但脚本报成功。
