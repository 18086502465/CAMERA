## 二、本轮新发现并修复的缺陷（8 项）

### 🔴 D-1【P0】导出与列表口径分裂（**上一轮修复未覆盖到的姊妹端点**）

| 项 | 内容 |
|---|---|
| **现象** | 同一区间，**列表 19 行 / 导出 114 行**（每天 6 行：厂级 + 5 条产线）。导出把厂级与产线行混在一起 → 拿去做 SUM **翻倍 2.00×**；且违反 PRD RPT-18「7 天区间 → 8 行」的验收口径（实测 42 行） |
| **复现** | `GET /daily-reports?startDate=2026-11-01&endDate=2026-11-19` → 19 行；<br>`GET /daily-reports/export?startDate=2026-11-01&endDate=2026-11-19` → 114 行 |
| **影响范围** | 日报 Excel 导出全部内容；任何基于导出的二次统计 |
| **根因** | 上一轮把 `list()` 端点改成「lineId 为 null → 只返回厂级行」，但 `export()` 端点的快照部分（`listRange` 调用，`:493`）**没同步过滤** |
| **修复** | 导出端点与 `list()` **完全同口径**：`lineId` 为 null → 只导厂级行；传了 → 只导该产线行 |
| **验证** | 4 组区间全部 **列表 == 导出**：19/19、11/11、20/20、1/1；产线列取值恒 `['全厂']` ✅ |

### 🟠 D-3【P1】明细「合计」其实是 TOP10 截断，与汇总值矛盾

| 项 | 内容 |
|---|---|
| **现象** | `detailDetectCount` 名为「明细合计」，实为 **TOP10 之和**。实测 2026-11-19：`kpi.detectCount=19812` vs `detailDetectCount=16455`（**差 3357 张 / 16.9%**）；当日 **16 台**相机有数据但只返回 10 台，**无任何截断标记** |
| **影响** | 页面上一边显示「检测图片数 19812」，下方相机明细条形图合计却 16455 → **肉眼可见矛盾**；字段名让人误以为是当日总量 |
| **根因** | `DailyReportRepository` 相机明细 SQL `LIMIT 10`，`detailDetectCount` 仅对已取回的 10 台求和 |
| **修复** | 新增 `detailDetectCountTotal`（全量）、`detailCameraTotal`（有数据相机台数）、`detailTruncated`（是否截断）；前端相机维度卡显示「已列 10/16 台（明细上限截断）」+ 缺陷类型卡补「全量 19812 张 / 16 台相机有上传」脚注 |
| **验证** | ✅ `19812 / 16455(TOP10) / Total=19812 / 相机=16 / 截断=True` |

### 🟡 D-4【P2】实时日计数列为 null 但**无原因说明**

| 项 | 内容 |
|---|---|
| **现象** | 实时日 `inspDelta`/`ngDelta`/`counterRateKilo` 为 null，响应里**没有任何说明** → 页面显示「待积累」，用户以为「这天没数据」 |
| **根因** | null 是**设计如此**（PRD RPT-05：首日/基线不可信 → NULL），实时日缺「次日 00:05 日终快照」作差分基线。但**没说** |
| **修复** | `putCounterUnavailable` 统一回传 `counterPendingReason`（区分「实时日待日终基线」与「首日无基线/计数器重置」）；前端 KPI 卡副标题显示该原因 |
| **验证** | ✅ `reason=实时日：需等次日 00:05 日终快照作为差分基线，今日至今的率待积累` |

### 🟡 D-5【P2】无快照日在列表端点返回 0 行且**无任何标记**

| 项 | 内容 |
|---|---|
| **现象** | 查 `2026-10-10~10-12` → `rows=0`，响应顶层只有 `{caliber, rows}` → 调用方**无法区分**「这天无数据」/「这天没快照」/「区间超出快照范围」三种完全不同的语义 |
| **修复** | 新增 `missingSnapshotDates`（缺失日期列表）+ `missingSnapshotMessage`（可读说明 + 「可用管理员补算生成」），**不伪造 0 行数据** |
| **验证** | ✅ `rows=0  missingSnapshotDates=['2026-10-10','2026-10-11','2026-10-12']` |

### 🟡 D-7【P2】老日期 `offlineCameras=18` —— 「当日无数据」被当成「18 台相机离线」

| 项 | 内容 |
|---|---|
| **现象** | `GET /daily-reports/2026-10-19/breakdown` → `offlineCameras=18`（全厂相机数）。真相是「这天有快照、但**一台相机都没上报**」——心跳无记录 ≠ 设备离线，页面却显示「18 台相机离线」，会被误读成设备故障 |
| **修复** | ① 无快照时 `offlineCameras=null` + 「无快照，无法判断相机在线状态」；② 有快照时措辞改为「N 台当日未上报（心跳无记录，非设备离线）」 |
| **验证** | ✅ `2026-10-19 offlineCameras=18 msg=18 台当日未上报（心跳无记录，非设备离线）` |

### 🟡 D-8【P3】未来日语义不统一，且导致列表/导出**再次分裂**

| 项 | 内容 |
|---|---|
| **现象** | ① `/{date}` 与 `/{date}/breakdown` 查未来日 → HTTP 200 + body.code=500（HTTP 说成功、业务码说失败），且**无 `isFuture` 标记**；② 列表端点把 **11-21~11-30 这 10 个未来日**也算成「实时行」返回（`detectCount=0`）→ **列表 30 行 vs 导出 20 行**，两个端点再次分裂 |
| **修复** | ① 未来日统一为 HTTP 400 + 可读消息；② 列表实时段**只算到今天为止**，未来日不返回行 |
| **验证** | ✅ 未来日两端点均 400；未来月列表返回 **0 行**；`11-01~11-30` 列表 20 == 导出 20 |

### 🟢 D-9【P3】导出 `start>end` → HTTP 400 **空 body**

| 项 | 内容 |
|---|---|
| **现象** | 导出端点返回 `ResponseEntity.badRequest().build()` → **body 为空** → 前端 `errorMessage(e)` 走 `e.response?.data?.message` 拿不到 → 只显示「未知错误」。同时列表端点对同一事实返回 200 + code=500 → **同一语义两种结论** |
| **修复** | 两者统一为 **HTTP 400 + 结构化 body**（`{code,message,data}`）；前端 `errorMessage` 支持 **Blob 错误体**（`responseType:'blob'` 时错误体也是 blob）→ 能取出可读消息 |
| **验证** | ✅ 导出与列表均 `HTTP 400 {"code":500,...,"message":"参数错误: 开始日期不能晚于结束日期"}`；前端导出失败能显示具体原因 |

### 🔴 R-1 / R-2【必须】热力图与班次对比**静默截断**，无任何提示

| 项 | R-1 热力图 | R-2 班次对比 |
|---|---|---|
| **现象** | SQL `LIMIT 360`，而「小时(24) × 缺陷类型」完整组合数现场实测 **422** → **静默丢 62 格（14.7%）**；30 天窗口丢 272 格 / 1777 框；且 `defectCount=1` 处有 66 行并列 → **丢哪些不保证稳定** | SQL `LIMIT 12`，现场实测 **37~40 种**缺陷类型 → **静默丢 25~28 种（67.6%）**；被截类型合计 10706 个缺陷框（KPI 的 13.9%） |
| **危害** | 班次对比是「**对比**场景」—— 缺 2/3 的类型，对比结论直接失真；热力图会让「高发时段」判断偏一边 |
| **修复** | 两条轻量 `COUNT(DISTINCT)` 查询取真实总量，回传 `hourlyHeatmapTotalCombos`/`hourlyHeatmapTruncated`/`hourlyHeatmapTruncatedCount` 与 `shiftCompareTotalTypes`/`shiftCompareTruncated`/`shiftCompareTruncatedCount`；前端图表卡加**黄色告警条**说明「已显示前 N 个（另有 M 个未显示）」。**不改 LIMIT**（避免极端筛选下查询量不可控） |
| **验证** | ✅ `热力图 259/259 截断=False`（当前时间窗未超限）、`班次对比 12/40 截断=True 丢=28` |

### 🟡 R-4【建议】`lineIds`/`workstationIds` 超 50 **静默截断**

| 项 | 内容 |
|---|---|
| **现象** | 传 80 个产线 → 实际只按**前 50 个**筛选，**无任何提示**（「静默吞掉筛选是最伤信任的失败模式」，PRD 原文）。已构造决定性用例：第 51 个（产线 9）被丢弃 |
| **修复** | 超 50 → **明确报错**（HTTP 400 +「多选 ID 数量超过上限 50 个（实际 80 个），请检查是否误传了完整 ID 列表」）。现场只有 6 条产线 / 6 个工位，传超 50 几乎必然是调用方 bug。非法 token 仍按既定语义忽略，但已在 `ignoredFilterNotes` 中披露 |
| **验证** | ✅ 80 个 → HTTP 400；50 个 → HTTP 200 |

### 🟡 R-6【建议】无数据产线的良率显示 **0.00%**（违反「无数据 ≠ 0」铁律）

| 项 | 内容 |
|---|---|
| **现象** | 切到今天没有上报的产线（如 ZK23 / lineId=5）→ 聚合通道 `total=0` → `yieldRate=0.0` → 前端 `percent(0)` → 显示「**良率 0.00%**」。用户会读成「这条线今天良率为 0、全是废品」，而真相是「这条线**今天没有上报**，无法计算良率」。图片通道已按「无数据 ≠ 0」处理，**聚合通道漏了** |
| **修复** | 聚合分支 `total==0` → `yieldRate=null` + `ngRate=null` + `yieldRateAvailable=false` + `noDataReason`；前端 5 处良率渲染点统一在 `yieldRateAvailable===false` 时显示「—」+ 原因 |
| **验证** | ✅ 接口 `yieldRate=null, yieldRateAvailable=false, noDataReason=当前筛选范围内没有检测记录…`；浏览器实测 ZK23 页面显示「良率 **—** / 当前筛选范围内没有检测记录（该范围可能未上报），良率无法计算」 |

## 四、核实为「设计如此 / 非缺陷」（避免误判）

| 项 | 结论 |
|---|---|
| `lineId` 与 `lineIds` 同时传且不一致 | **取并集**（`lineId=9&lineIds=10,11` → 17198），与 PRD STAT-05 一致 |
| `lineId=9`（ZK65）返回 0 | **数据实况**：11-20 凌晨 ZK65 一张图未上传（库直查：当日仅 line 3/11/12 有图）→ 走聚合表兜底 |
| `lineId=5`（ZK23）返回 0 | 同上，ZK23 已停产 |
| 缓存 key 覆盖度 | **逐一审阅 + 17 组黑盒验证，14 个参数全部入键**，无漏参、无数据串号 |
| 并发 10 次 | 10/10 完全一致，无 5xx；连发 20 次 max=167ms |
| SQL 注入 | ID 类参数 Spring 层拒绝；`defectType` 参数化，`' OR '1'='1` 返回 0（不是全量） |
| 跨产线工位/相机筛选冲突 | **正确**：全部返回**空集**，无报错、无越界数据 |
| 产线统计页不读 URL query | **无缺陷**：无任何页面用带参跳转（已 grep 确认），页面筛选来自布局级联 |
| `HTTP 400 + body.code=500` | **项目既有约定**（`ResultVO.fail` 固定 code=500），前端按 HTTP 状态码判断并读 `message` → 不改 |

| **导出 xlsx 字节级不稳定** | POI 在 `docProps/core.xml` 写生成时间戳 → 同参数连发 5 次 sha256 不同（**业务数据逐单元格完全一致**），仅影响文件级校验 |
| **`/dashboards/default` 是会写库的 GET** | 且返回的看板与前端内置常量 `BUILTIN_DASHBOARD` 不是同一套 7 个 widget → 需统一真源 |
