## 三、优化方案（按优先级排序）

### R1（P1，问题 2）：冻结契约下沉到 Service 层 —— **本轮最高收益**

现有 `BatchUploadControllerTest` 保护的是 HTTP 包装（且用无效 `schemaVersion="1.0"` 也能过），契约真身在校验逻辑里：

1. 新建 `InspectionUploadServiceTest`（mock `InspectionUploadRepository` + `CameraDirectoryRepository`），逐条断言 20 个 `fail422` 分支的错误码与 HTTP 语义：`TOKEN_REQUIRED`、`DEVICE_ID_REQUIRED`、`INVALID_SCHEMA_VERSION`、`BATCH_ID_REQUIRED`、`UNSUPPORTED_COUNTER_MODE`、`SUMMARY_REQUIRED`、`TIME_RANGE_REQUIRED`、`COUNT_MISMATCH`（两处）、`INVALID_DEFECT_COUNT`、`PRODUCT_NOT_FOUND`、`UNMAPPED`、`TOKEN_NOT_CONFIGURED`、`TOKEN_INVALID`、`CAMERA_NOT_FOUND`；
2. 补 DTO 字段级契约断言：`InspectionBatchUploadRequest` 的字段名集合固定（字段被删改即红）——这是"冻结契约"最直接的表达；
3. 修正现有 `BatchUploadControllerTest` 的 `schemaVersion("1.0")` → `"2.0"`（用无效数据测成功路径会误导读者）。

**成本**：1 天。**验证**：`mvn test` 新增 15± 用例全绿；负向——临时删一个 DTO 字段应使契约测试红。

### R2（P1，问题 3）：上传主链路测试

`masterdata` 的 `camera_type` 核心已由 `CameraTypeContractTest` 覆盖（6+ 用例，REAL/TEST 双表），无需重复。真实空白是 **`DefectImageServiceImpl.upload`**：

1. metadata 与文件名集合不一致 → `FILE_NAME_MISMATCH`（含大小写不敏感比较）；
2. 非法扩展名（svg）/ 超限（>100 张）→ 对应错误码；
3. 部分成功语义：单图失败不影响其余图落盘，响应 `success=false` 但 `code=200`；
4. 未建档相机：图片落盘但 `defect_image_file.camera_id` 存 camera_code（这是历史踩坑点，值得钉住）。

**成本**：1 天。

### R3（P1，问题 4）：前端 ESLint 接入（渐进式）—— **已落地**

1. `npm i -D eslint eslint-plugin-vue`，flat config，规则集从 `vue3-essential` 起步（只抓错误级，不抓风格）；
2. `package.json` 加 `lint`；CI 前端 job 在 build 前跑 `npm run lint`；
3. **不做** `--max-warnings 0`（存量代码会瞬间爆红），首轮只求错误级清零。

**成本**：半天。**风险**：规则过严会假红——参考 CI 假红教训，先本地全量跑一遍再上 CI。

> **落地记录（2026-11-13）**
> - ESLint **降到 9.x**（`9.39.5`）而不是最新 10：ESLint 10 要求 Node ≥20.19，而 CI 的 `node-version: '18'` 会解析到 18.20.x，只有 ESLint 9 的 `engines: ^18.18.0` 覆盖得到。为 lint 而抬构建环境是本末倒置。
> - 实测扫描 **83 个文件、0 告警**；负向验证植入 `v-for` 缺 key → `vue/require-v-for-key` 报错、rc=1，撤销后 rc=0。
> - 关闭 `vue/multi-word-component-names`：本仓库页面按业务命名（Home/Cameras/Login），改名收益为零且破坏路由引用。

### R4（P2，问题 5）：Controller 裸 Map → DTO（按需渐进）—— **约定已写入，重构按需**

不做一次性替换（406 处，风险大于收益）。策略：**改哪个接口就顺手 DTO 化哪个**，新增接口一律 DTO（写入 CODEBUDDY 约定）。优先级排序：前端有表单依赖的 17 个 Controller 中的写接口。

> **落地记录（2026-11-13）**：约定已写入 `CODEBUDDY.md`「Controller 出口不许是裸 `Map<String,Object>`」条目，含"字段名必须与前端现有取值逐字一致"的约束（否则等于静默改契约）。存量 17 个按"改哪个动哪个"摊销。

### R5（P2，问题 6）：色值收敛 —— **已落地，但原方案前提有误，已改道**

1. ~~建 `frontend/src/styles/tokens.scss`~~ → **本项目没有 sass 依赖，也没有任何 `.scss` 文件**，全站是纯 CSS + SFC scoped 样式。按原方案会为一个配色重构引入构建期依赖，不划算，改用 **CSS 自定义属性**。
2. 先收敛**语义色**（成功/警告/危险/主色）；3. 不追求一次清零。

> **落地记录（2026-11-13），含两处原判断修正**
>
> **① `global.css` 从未被任何文件 import —— 整份 470 行是死文件。**
> 全仓无 `global.css` 引用，`index.html` 只引 `/src/main.js`。也就是说其中的
> `.el-button/.el-card/.el-table` 覆盖、状态标签、空状态、响应式、工具类规则
> **生产环境一次都没生效过**，页面外观完全由各组件 scoped 样式决定；Element Plus
> 一直用它自己的默认主题。这也解释了"为什么每个页面都得手写颜色"。
> → 处理：**不整份引入**（会一次性激活 470 行从未生效的样式，属不可控外观变更），
> 只把令牌层抽成 `frontend/src/styles/tokens.css` 真正加载，`global.css` 保留原样
> 并在文件头标注"死文件 + 启用需逐屏回归"。
>
> **② 原报告"两套调色板"的说法不准确，实际是三套**：
> `global.css` 里写的 `#1677FF`（AntD 系，只在自身存在）｜页面手写的 `#2563eb`
> （Tailwind 系，组件样式块 **310 处**）｜Element 运行时默认的 `#409eff`。
> 经确认统一到 `#2563eb`：`tokens.css` 定义 25 个 `--color-*`，并**全量覆盖**
> `--el-color-primary/success/warning/danger` 及其 `light-3/5/7/8/9`、`dark-2`
> 色阶（色阶按 Element 的 `mix(white, base, N×10%)` 公式预算，只覆盖主色不覆盖
> 色阶会导致"主色变了、hover 底色还是旧蓝的淡色"）。
>
> **执行结果**：`<style>` 块内替换 **384 处 / 29 个文件**。三条安全边界：
> ①只动 `<style>`（`<script>` 里 79 处多为 ECharts 配置，画布不解析 `var()`，换进去图表直接变白）；
> ②只替换**令牌值与旧字面量逐字相等**的，因此这 384 处**零视觉变化**（唯一变化来自 Element 主题，即本次决策本身）；
> ③`#fff` 只在 `background`/`background-color` 上替换（其余是白字）。
>
> **验证**：`vite build` rc=0｜ESLint 0 告警｜`npm test` 1/1｜产物中 `--el-color-primary:#409eff`（偏移 1997）
> 被 `var(--color-primary)`（偏移 357834）覆盖，顺序正确｜浏览器实测登录页：
> `--color-primary` = `#2563eb`、主按钮 `background: rgb(37, 99, 235)`、全页 0 个"文字与背景同色"元素、无 `pageerror`。
>
> **遗留**：剩余 ~300 处长尾色（`#1a1a2e`/`#1f1f1f`/`#f56c6c` 等三方言不一的深色与 Element 旧色）未收敛——它们没有对应令牌，硬换就是改设计，按需摊销。
