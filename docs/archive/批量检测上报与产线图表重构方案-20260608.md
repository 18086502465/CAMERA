# 批量检测上报与产线统计图表重构方案

版本：v1.0  
日期：2026-06-08  
适用系统：产线缺陷在线AI检测系统  
关联接口：`POST /api/v1/camera/inspection/batch-upload`

---

## 1. 背景与当前实现问题

本方案基于当前前后端代码与数据库 SQL 现状重新设计。当前实现中，`/api/v1/camera/inspection/batch-upload` 仍使用旧版 `BatchUploadDTO`：

- 请求体包含 `deviceId / batchTime / recordCount / dataList[]`。
- `dataList` 中既有累计值、增量值，又有大量写死字段，如 `innerGlue13`、`frontWaistDefect3Plus` 等。
- 服务端当前写入 `product_detection_history`，且重复判断依赖 `detectionTime + defectCode`，其中 `defectCode` 兼容旧字段 `cameraName`，语义不清晰。
- 缺陷类型目前由 `dim_defect_type` 固定保存，前端仍有部分写死缺陷类型，无法适配现场相机统一上报 `p0 / p1 / p2` 后由后台动态映射的需求。
- 产线统计目前缺少真正可配置的统计图表工作台，不能满足按筛选条件动态新增、编辑、调整图表大小和布局的目标。

因此，本次需要从 **接口协议、缺陷映射配置、数据库保存与查询策略、产线统计图表工作台** 四个方面整体重构。

---

## 2. 重构目标

### 2.1 接口目标

`POST /api/v1/camera/inspection/batch-upload` 完全重构为新版协议：

1. 相机上报协议固定，不随现场缺陷名称变化。
2. 相机只上报统一来源编码，例如 `p0 / p1 / p2`、`a0 / a1` 或现场约定编码。
3. 后台通过系统配置把 `sourceCode` 精确映射为系统标准缺陷类型。
4. 映射必须 1 对 1；无法匹配、多匹配、停用映射都不能静默归类。
5. 支持批次幂等，避免重复上报造成统计翻倍。
6. 优先支持增量计数；累计计数作为兼容能力，必须有重置检测和差值计算。

### 2.2 配置目标

系统配置页增加或增强以下配置能力：

- 缺陷类型配置：维护系统标准缺陷类型。
- 相机缺陷映射：维护每台相机的上报编码与标准缺陷类型的 1 对 1 映射。
- 缺陷位置配置：维护前腰、后腰、内装、复合区等位置/区域。
- 严重等级配置：维护 HIGH/MEDIUM/LOW 或 1/2/3/4 的显示规则。

### 2.3 数据目标

- 原始上报明细可追溯。
- 统计查询不直接扫大明细表。
- 支持时间、工厂、产线、工位、相机、产品、班次、缺陷类型、缺陷位置、严重等级等多维筛选。
- 动态缺陷类型不通过数据库宽表字段承载，避免每次新增缺陷类型都改表。

### 2.4 图表目标

新增“产线统计”图表工作台：

- 顶部全局筛选条件统一控制所有图表。
- 每个图表可以从页面新增。
- 图表类型、指标、维度、分组、排序、TopN、时间粒度可配置。
- 图表大小和布局可拖拽调整。
- 支持保存多个看板方案，供工厂负责人、工艺负责人、质量负责人使用。

## 3. 新版批量检测上报协议

### 3.1 接口定义

```http
POST /api/v1/camera/inspection/batch-upload
Content-Type: application/json
Authorization: Bearer <device-token>
X-Device-Id: <deviceId>
X-Request-Id: <requestId>
```

### 3.2 请求体示例

```json
{
  "schemaVersion": "2.0",
  "batchId": "CAM-001-20260608-103000-0001",
  "deviceId": "DEV-001",
  "cameraCode": "CAM-001",
  "cameraName": "1号检测相机",
  "productName": "纸尿裤L码",
  "reportTime": "2026-06-08 10:30:00",
  "timeRange": {
    "startTime": "2026-06-08 10:29:00",
    "endTime": "2026-06-08 10:30:00"
  },
  "counterMode": "INCREMENTAL",
  "summary": {
    "totalCount": 1200,
    "okCount": 1160,
    "ngCount": 40
  },
  "defects": [
    {
      "sourceCode": "p0",
      "count": 12,
      "positionCode": "FRONT_WAIST",
      "severity": "HIGH"
    },
    {
      "sourceCode": "p1",
      "count": 28,
      "positionCode": "INNER_LAYER",
      "severity": "MEDIUM"
    }
  ],
  "extra": {
    "algorithmVersion": "ai-20260608.1",
    "clientIp": "192.168.1.20"
  }
}
```

### 3.3 字段说明

| 字段 | 类型 | 必填 | 说明 | 校验规则 |
|---|---|---:|---|---|
| `schemaVersion` | String | 是 | 协议版本 | 当前固定 `2.0` |
| `batchId` | String | 是 | 相机侧批次号 | 同一 `cameraCode + batchId` 幂等 |
| `deviceId` | String | 否 | 设备编号 | 优先取 Header `X-Device-Id`，Body 仅做交叉校验 |
| `cameraCode` | String | 是 | 相机编号 | 必须存在于系统相机配置 |
| `cameraName` | String | 否 | 相机展示名 | 仅用于日志和辅助排查，不更新配置关系 |
| `productName` | String | 否 | 当前产品 | 后台匹配产品/品牌表，未匹配保留原始名称并返回告警 |
| `reportTime` | String | 是 | 上报时间 | `yyyy-MM-dd HH:mm:ss` |
| `timeRange.startTime` | String | 是 | 统计开始时间 | 不晚于 `endTime` |
| `timeRange.endTime` | String | 是 | 统计结束时间 | 不早于 `startTime`，建议跨度 ≤ 5 分钟 |
| `counterMode` | String | 是 | 计数模式 | `INCREMENTAL` 推荐；`CUMULATIVE` 需差值计算 |
| `summary.totalCount` | Integer | 是 | 检测总数 | 非负；增量模式表示本批数量 |
| `summary.okCount` | Integer | 是 | OK 数 | 非负 |
| `summary.ngCount` | Integer | 是 | NG 数 | 非负；原则上等于 `defects[].count` 之和，允许配置容差 |
| `defects[].sourceCode` | String | 是 | 相机上报缺陷编码 | 如 `p0`、`p1`；按相机映射到标准缺陷类型 |
| `defects[].count` | Integer | 是 | 缺陷数量 | 非负；0 可上报但不落缺陷明细 |
| `defects[].positionCode` | String | 否 | 缺陷位置编码 | 未传时可使用映射默认位置 |
| `defects[].severity` | String | 否 | 严重度 | 未传时可使用映射默认严重度 |
| `extra` | Object | 否 | 扩展字段 | 只保存 JSON，不参与核心统计 |

### 3.4 计数口径

#### 推荐模式：`INCREMENTAL`

- `summary.totalCount / okCount / ngCount` 表示本批次新增数量。
- `defects[].count` 表示本批次该缺陷新增数量。
- 服务端直接累加到聚合表。
- 首期 P0 建议只开放此模式给正式设备使用。

#### 兼容模式：`CUMULATIVE`

- 字段表示设备启动以来累计值。
- 服务端需要读取同相机上一批累计值，计算增量。
- 如果出现累计值回退，判断为设备重启或计数器清零，本批按当前累计值入库并记录计数器重置事件。
- 如现场没有强需求，不建议首期启用。

```json
      }
    ]
```


### 3.6 关键校验规则

1. `Authorization` 必填，设备使用独立 Token。
2. `X-Device-Id` 必填，并与 `cameraCode` 绑定关系校验。
3. `cameraCode` 必须存在，且配置了工厂、产线、工位归属。
4. `batchId` 必填；同一 `cameraCode + batchId` 重复上报返回幂等成功，不重复入库。
5. `summary.totalCount = okCount + ngCount`，允许配置 `±0` 或 `±1` 容差。
6. `summary.ngCount` 与 `defects[].count` 之和应一致；不一致时返回 `422` 或按配置降级为告警。
7. 每个 `defects[].sourceCode` 必须在当前相机、生效时间内精确匹配到一个标准缺陷类型。
8. 不允许一个相机同一生效周期内把同一个 `sourceCode` 配到多个缺陷类型。
9. 不允许一个相机同一生效周期内把多个 `sourceCode` 配到同一个标准缺陷类型，除非开启“多编码同义归并”配置；本项目 P0 不开放。
10. `reportTime` 与服务器时间偏差超过配置阈值，例如 10 分钟，记录时间偏移告警。

## 4. 缺陷类型与 p0/p1 映射配置设计

### 4.1 配置对象

#### 标准缺陷类型

标准缺陷类型是系统内部用于统计、筛选、图表、报表的稳定编码，例如：

- `FRONT_DIRT_3_UP`：前腰腹异物污点（3mm²以上）
- `INNER_GLUE_1_3`：内装胶滴（1-3mm²）
- `COMPOSITE_JOINT`：复合区域接头

#### 相机上报编码

相机上报编码是现场算法或设备输出的编码，例如：

- `p0`
- `p1`
- `p2`
- `a0`
- `defect_001`

设备协议不关心业务缺陷名称，只稳定上报 `sourceCode` 和数量。

### 4.2 1 对 1 映射规则

映射粒度推荐为：

```text
工厂 + 产线 + 工位 + 相机 + sourceCode + 生效时间段 => 标准缺陷类型
```

P0 强制规则：

- 同一相机、同一生效时间段内，`sourceCode` 只能映射到 1 个标准缺陷类型。
- 同一相机、同一生效时间段内，1 个标准缺陷类型只能被 1 个 `sourceCode` 使用。
- 映射停用后，历史数据仍使用历史映射快照，不因配置变更而改变历史统计。
- 设备上报未配置编码时，不自动创建缺陷类型，不自动归入“其他”，必须返回明确错误或告警。

### 4.3 系统配置页面建议

在“系统配置”中新增/增强：

1. **缺陷类型配置**
   - 缺陷编码
   - 缺陷名称
   - 缺陷类别
   - 默认严重等级
   - 默认缺陷位置
   - 是否计入 NG
   - 排序

2. **相机缺陷映射**
   - 工厂 / 产线 / 工位 / 相机级联筛选
   - 相机上报编码 `sourceCode`
   - 映射标准缺陷类型
   - 默认缺陷位置
   - 默认严重等级
   - 生效开始时间 / 生效结束时间
   - 启用状态
   - 校验结果

3. **批量导入映射**
   - 支持 Excel/CSV 导入。
   - 导入前预检查：重复编码、重复缺陷、缺少相机、缺少缺陷类型、生效期冲突。
   - 支持“全量覆盖”和“增量追加”。
   - 全量覆盖必须二次确认，并提供影响数量。

## 5. 数据库保存与查询策略重构

### 5.1 总体原则

- **明细表负责追溯**：保存每次上报批次、相机汇总、缺陷计数、映射快照。
- **聚合表负责查询**：产线图表默认查 10 分钟/30 分钟/小时/日聚合表。
- **维度表负责配置**：缺陷类型、缺陷位置、相机映射、工厂产线工位产品班次均作为维度。
- **动态列不落表**：缺陷类型动态变化时，不新增宽表字段，查询时按 `defect_type_id` 分组或前端 pivot。

### 5.2 推荐新增表

#### 5.2.1 批次主表 `inspection_batch`

### 5.3 写入链路

```text
接收请求
  ↓
Header/Token/设备绑定校验
  ↓
批次幂等校验 cameraCode + batchId
  ↓
相机配置补齐 factory/line/workstation
  ↓
产品 productName 映射 productId，失败保留原始名称并返回告警明细
  ↓
sourceCode 映射标准缺陷类型；严格 1 对 1
  ↓
事务写入 inspection_batch + inspection_defect_count
  ↓
同步或异步刷新 30 分钟聚合表
  ↓
返回映射结果、告警、批次处理状态
```

### 5.4 查询策略

| 查询场景 | 推荐数据源 | 说明 |
|---|---|---|
| 当日趋势 | 10m/30m 聚合表 | 刷新快，适合看板 |
| 近 7 天趋势 | 30m/小时聚合表 | 控制点数 |
| 月度汇总 | 日聚合表 | 不扫明细 |
| 缺陷类型 TopN | `agg_defect_type_30m` | 按筛选条件 group by |
| 明细追溯 | `inspection_batch` + `inspection_defect_count` | 仅在点击钻取时查 |
| 图片追溯 | 现有 `defect_image_batch/file/box` | 与检测批次通过时间、相机、图片批次关联 |

### 5.5 性能要求

- 默认看板查询 24 小时内数据，接口响应目标 ≤ 1 秒。
- 近 7 天聚合查询响应目标 ≤ 3 秒。
- 明细查询必须分页，默认 10 条，可选 20/50/100。
- 大表建议按月归档或按 `report_time` 分区。
- 图表接口必须限制最大时间跨度，防止用户配置导致全表扫描。

## 6. 产线统计图表工作台设计

### 6.1 页面定位

新增主 Tab：**产线统计**。该页面不是固定报表，而是“可配置图表工作台”。工厂负责人可根据现场关注点，自行创建不同图表并保存布局。

### 6.2 页面结构

```text
顶部：全局筛选区
  时间范围 / 工厂 / 产线 / 工位 / 相机 / 产品 / 班次 / 缺陷类型 / 缺陷位置 / 严重度

左侧：图表组件库
  KPI卡 / 折线图 / 柱状图 / 堆叠柱图 / 环形图 / 排行榜 / 热力图 / 透视表 / 明细表

中间：图表画布
  可拖拽 / 可缩放 / 可复制 / 可删除 / 可保存布局

右侧：图表配置面板
  图表名称 / 图表类型 / 指标 / 维度 / 分组 / 排序 / TopN / 时间粒度 / 是否跟随全局筛选
```

### 6.3 全局筛选条件

| 筛选项 | 类型 | 说明 |
|---|---|---|
| 时间范围 | 日期时间范围 | 默认今天；支持最近 1 小时、今天、昨天、近 7 天、自定义 |
| 工厂 | 下拉 | 默认全部；支持杭州工厂等 |
| 产线 | 级联下拉 | 根据工厂筛选 |
| 工位 | 级联下拉 | 根据产线筛选 |
| 相机 | 级联下拉 | 根据工位筛选，支持一个工位多相机 |
| 产品 | 下拉/搜索 | 根据品牌/产品配置与上报原始名称生成 |
| 班次 | 下拉 | 白班、夜班或配置班次 |
| 缺陷类型 | 多选 | 来自系统配置，不写死 |
| 缺陷位置 | 多选 | 前腰、后腰、内装、复合区等 |
| 严重度 | 多选 | HIGH/MEDIUM/LOW 或配置值 |

### 6.4 图表类型

| 图表类型 | 适用问题 | 示例 |
|---|---|---|
| KPI 卡 | 当前总体水平 | 总检测数、OK数、NG数、良率、缺陷数 |
| 折线图 | 时间趋势 | 每 30 分钟 NG 数趋势、良率趋势 |
| 柱状图 | 横向对比 | 各产线 NG 数对比 |
| 堆叠柱图 | 构成对比 | 各产线按缺陷类型堆叠 |
| 环形图 | 构成占比 | 缺陷类型占比、严重度占比 |
| 排行榜 | TopN | 缺陷最多的工位 Top10、相机 Top10 |
| 热力图 | 时间与维度交叉 | 班次 × 小时 NG 热力、工位 × 缺陷类型热力 |
| 透视表 | 动态列报表 | 行=工位，列=缺陷类型，值=缺陷数 |
| 明细表 | 追溯 | 批次、相机、产品、缺陷映射明细 |

### 6.5 指标设计

基础指标：

- 检测总数：`sum(total_count)`
- OK 数：`sum(ok_count)`
- NG 数：`sum(ng_count)`
- 缺陷数：`sum(defect_count)`
- 良率：`sum(ok_count) / sum(total_count)`
- NG率：`sum(ng_count) / sum(total_count)`
- 缺陷率：`sum(defect_count) / sum(total_count)`

扩展指标：

- 高危缺陷数：`severity = HIGH`
- 指定缺陷类型数量：`defect_type_id in (...)`
- 指定位置缺陷数：`position_id in (...)`
- 产品维度 NG 数：按 `product_id/product_name` 统计
- 班次维度 NG 数：按 `shift_id` 统计

### 6.6 维度设计

| 维度 | 字段来源 | 使用场景 |
|---|---|---|
| 时间 | `time_bucket/report_time` | 趋势图、热力图 |
| 工厂 | `factory_id` | 多工厂对比 |
| 产线 | `line_id` | 产线负责人关注 |
| 工位 | `workstation_id` | 定位问题环节 |
| 相机 | `camera_code` | 定位设备/算法问题 |
| 产品 | `product_id/product_name` | 不同产品质量对比 |
| 班次 | `shift_id` | 白班/夜班差异分析 |
| 缺陷类型 | `defect_type_id` | 异常类型排行与构成 |
| 缺陷位置 | `position_id` | 工艺位置问题定位 |
| 严重度 | `severity` | 高危问题优先处理 |

### 6.7 图表新增/编辑交互

1. 点击“新增图表”。
2. 选择图表类型。
3. 输入图表名称。
4. 选择指标，可多选。
5. 选择维度，例如时间、产线、工位、缺陷类型。
6. 设置筛选继承：默认跟随全局筛选，也可配置图表独立筛选。
7. 设置排序、TopN、时间粒度、图例和数据标签。
8. 点击“预览”，系统实时生成 SQL 查询计划摘要与预览图。
9. 点击“保存”，图表加入画布。
10. 在画布中拖拽调整位置、拖动右下角调整大小。

### 6.8 动态透视表设计

透视表用于满足“根据配置的异常类型动态生成表格”的需求：

- 行维度：产线 / 工位 / 相机 / 产品 / 班次。
- 列维度：缺陷类型，来自 `dim_defect_type`。
- 值：缺陷数 / NG数 / 缺陷率。
- 当新增缺陷类型后，表格列自动出现。
- 缺陷类型停用后，默认隐藏，但历史查询可勾选“显示历史停用类型”。

示例：

| 工位 | 检测总数 | OK数 | NG数 | p0映射缺陷 | p1映射缺陷 | p2映射缺陷 | 良率 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 涂布工位 | 120000 | 118900 | 1100 | 420 | 510 | 170 | 99.08% |
| 复合工位 | 98000 | 96950 | 1050 | 300 | 620 | 130 | 98.93% |

前端表头显示标准缺陷名称，不显示 `p0/p1`；`p0/p1` 仅在配置和映射明细中展示。

## 11. 验收标准

### 11.1 接口验收

- 使用 `p0/p1` 上报时，能按配置映射到标准缺陷类型。
- 未配置 `sourceCode` 返回明确错误，不入库统计。
- 重复 `batchId` 不重复累计。
- `summary.ngCount` 与缺陷明细计数不一致时能明确提示。
- 上报后 30 分钟聚合表能正确累计。

### 11.2 配置验收

- 同一相机同一 `sourceCode` 不允许配置多个缺陷类型。
- 同一相机同一标准缺陷类型不允许绑定多个 `sourceCode`。
- 导入前可预检查冲突。
- 删除/停用映射有风险提示。
- 历史数据不因配置变化而改变显示。

### 11.3 图表验收

- 图表能跟随全局筛选刷新。
- 图表能新增、编辑、删除、拖拽、缩放、保存。
- 动态缺陷类型新增后，透视表列可自动变化。
- 查询 24 小时数据响应 ≤ 1 秒，近 7 天响应 ≤ 3 秒。
- 空状态、异常状态、加载状态完整。

## 12. 风险与建议

| 风险 | 影响 | 建议 |
|---|---|---|
| 现场相机编码不稳定 | 映射失败、统计不准 | 上线前冻结相机 `sourceCode` 字典 |
| 旧接口调用方未迁移 | 上报失败 | 提供 P0 临时兼容开关和迁移文档 |
| 缺陷类型频繁变更 | 历史统计口径混乱 | 保存映射快照，历史按当时映射展示 |
| 图表配置过于自由 | 可能产生慢查询 | 后端限制时间跨度、维度数量、TopN |
| 累计计数模式复杂 | 容易重复或漏计 | 首期只推荐增量模式 |

## 13. 推荐结论

本次重构的核心不是简单替换字段，而是建立一套稳定的“设备上报编码 → 系统标准缺陷 → 高效统计查询 → 可配置图表展示”的闭环。

推荐优先级：

1. 先完成新版 `batch-upload` 协议和 `p0/p1` 映射配置。
2. 再完成明细表与聚合表改造，保证数据口径正确。
3. 最后新增产线统计图表工作台，避免在旧数据结构上继续堆固定报表。
