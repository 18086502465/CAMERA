## 一、项目目标与核心模块

### 1.1 目标

让工业相机的缺陷检测数据**变成管理者能用的结论**。三个原始缺口（决定了当前功能边界）：

## 二、必须优化（4 项）

### M-01 ★ 统计核心查询的索引列错位 —— 每次多扫 12 倍行

**问题依据（生产库 EXPLAIN 实测）**

```sql
-- 统计接口的真实查询形态
SELECT COUNT(*) FROM defect_image_file f
  JOIN dim_camera c ON c.camera_code = f.camera_id
 WHERE c.camera_code = 'DA8119489' AND f.capture_time BETWEEN '2026-11-01' AND '2026-11-05';
```

| EXPLAIN | key | rows | filtered |
|---|---|---|---|
| `capture_time` 范围（**真实查询**） | `idx_defect_file_camera_id_time` | **3592** | **8.03%** |
| `create_time` 范围 | `idx_defect_file_camera_id_time` | 1362 | 100% |

现有索引是 `(camera_id, **create_time**, image_id)` —— 第二列是 `create_time`，
而统计接口过滤的是 **`capture_time`** → 索引只能定位到相机，**时间范围要回表逐行判断**
→ 扫 3592 行只命中 8%（**多扫 12 倍**）。

**影响范围**：产线统计全部 KPI/趋势/排行/透视、日报 breakdown、图像记录检索 ——
即现场最常用的查询全部走这条路径。当前 36 相机下影响有限；
**扩到 200 台 / 10 年数据**（项目设计目标）后，单次扫描行数放大到数十万级。

**预期收益**：核心统计查询从"扫 12 倍行"降到"精确范围扫描"，单次响应可降一个数量级。

**建议方向**：新增索引 `(camera_id, capture_time)`（**不要改**现有索引 ——
`create_time` 有其它查询在用，`listHistoryPage` 按它排序）。

### M-02 ★ 分页参数无上限保护，且前端 6 处按"全量"拉取

**问题依据**

- 前端 6 处硬编码拉全量：`CameraStatusView.vue:369`、`CameraImageRecords.vue:426`、
  `CameraDetail.vue:86`、`Dashboard.vue:245`、`ConfigView.vue:797`、`ConfigView.vue:802`
  → 全部 `getCameraList({ page: 1, size: 999 })`
- 后端 `CameraDashboardController.java:46`：`@RequestParam(defaultValue = "20") Integer size`
  → **直接透传给 MyBatis-Plus 分页，无上限校验**

**影响范围**：① 任何调用方传 `size=100000` 都会触发全表扫描 + 全表 `COUNT(*)`
（MyBatis-Plus 分页必带总数查询）+ 完整对象构建 → 内存放大与慢查询；
② 首页/Dashboard/配置页每次打开都按全量拉相机，随规模线性膨胀。

**预期收益**：把"误传大 size"的爆炸面封死；前端按需分页后首屏传输量与相机总数解耦。

**建议方向**：后端统一加 size 上限（如 `Math.min(size, 200)`）并对超限显式告警；
前端改为"默认分页 + 需要全量时用独立轻量端点（只取 id/名称/状态）"。

### M-03 ★ 设备图片上传通道**从未比对令牌**（已知缺口，至今未修）

**问题依据**

`docs/相机设备接口协议.md` §8.3 缺口 1 记录至今；代码侧 `SecurityConfig` 白名单放行
`/api/v1/defect-images/upload`，而该端点只校验 `Authorization` 以 `Bearer ` 开头，
**不比对 `cfg_camera_token`**（心跳与批量上报两个端点都比对了）。

**影响范围**：现场 **23,997 张缺陷图 / 24,209 个缺陷框全部走这条通道**。
任何能访问 8091 的人，带任意非空 Bearer 串 + 合法 `X-Device-Id`
即可写入图片与缺陷框 → **污染统计与良率口径**，且不留设备痕迹。

**预期收益**：把主通道纳入与心跳一致的鉴权口径；改动小（复用 `CameraTokenVerifier`）。

**建议方向**：`DefectImageController` 上传入口复用 `CameraTokenVerifier.verify(token, deviceId)`；
配套加回归用例；**修复前 8091 不得对外网暴露**（这条已在运维手册，需现场确认落实）。

### M-04 ★ 设备上传中途失败被静默丢弃，现场无感知

**问题依据（现场近 24h 日志实测）**

| 条数 | 内容 |
|---|---|
| **39** | `Failed to parse multipart servlet request` —— 上传中途断流 |
| **19** | `java.io.IOException: Broken pipe` —— 客户端主动断开 |
| 5 | Druid `CommunicationsException` —— 连接被丢弃 |
| 4 | Tomcat `ErrorPage` 异常 |

合计 **72 条 ERROR/24h**，且**没有一条转成告警**（`fact_anomaly_alert` 里没有对应类型）。

**影响范围**：失败的那张图**没有入库也没有告警**，设备端若未做重试则**永久丢失**；
现场无法知道"今天少了几张图"。昨天排查的 `DA8119489` 停报（25h 零上传）
与 ZK54 测试相机改传 200px 废图，**都是同一类设备端问题的不同表现**。

**预期收益**：把"上传失败"变成可观测信号，而不是埋在 journald 里等人翻日志。

**建议方向**：① 在上传 Controller 捕获解析异常时落一条告警（新增告警类型，需同步
`FactAnomalyAlertController.OPS_ALERT_TYPES`）；② 或加"上传失败率"指标；
③ 设备端侧：失败必须重试（协议已规定只重传失败项）。

## 三、建议优化（9 项）

### S-01 `camera_images` 与 `defect_image_file` 完全镜像 —— 10MB 纯冗余

**依据**：实测两表行数 23,387 / 23,997，`image_path` 100% 重叠（同批 jpg）。
`camera_images` 占 6.5MB + 3.6MB 索引；两表分别被 `DataCleanupTask`（30 天只删行）
与归档任务（31 天移月表）管理，**保留期还不一致** → 同一批图在两个表的可见期不同。

**影响**：存储冗余 ~10MB（当前库总量 40MB 级）；口径易混（查哪张表结论不同）。
**收益**：释放 ~25% 库空间；消除"该查哪张表"的歧义。
**方向**：明确 `camera_images` 的定位（兼容表）→ 要么下线、要么与主表同步保留期。

### S-02 `defect_image_file` 有 2 个 `camera_name` 前缀索引 —— 名字已不是身份标识

**依据**：`idx_defect_file_camera(camera_name, upload_time)`、
`idx_defect_file_camera_name_time(camera_name, create_time, image_id)`，
而现场 `camera_name` **跨产线重名**（ZK54 与 ZK23 都有 `CV1_Cam1`/`CV2_Cam1`）。
**影响**：① 索引 6.6MB 中相当部分浪费在这两处；② **按名字查会同时命中两台同名相机**
—— 这正是 11-05「筛选后比不筛选还多」类 bug 的温床。
**方向**：改用 `camera_id`（=camera_code）关联后下线这两个索引。

### S-03 操作日志表比业务主表还大

**依据**：`sys_operation_log` 50,192 行 / 7.5MB + 5.5MB 索引 = **13MB**，
超过 `defect_image_file`（10.5MB）；保留 6 个月，单条索引 3 个。
**影响**：库增长的主要来源；查询日志页会越来越慢。
**方向**：核对是否记录了请求体/大字段；缩减保留期或改定期归档。

### S-04 `defect_image_box` 索引是数据的 2 倍

**依据**：24,209 行 → 数据 3.3MB、**索引 6.4MB**（5 个索引）。
**方向**：随 S-02 一并评估索引必要性。

### S-05 统计维度从 `camera_status`（快照）取，而非 `dim_camera`（权威表）

**依据**：`DefectImageRepository.java:309/471/626/754` 四处均为
`LEFT JOIN camera_status cs ON cs.camera_code = ... ` 后再
`LEFT JOIN dim_workstation ws` / `LEFT JOIN dim_production_line pl`，且**未过滤 `is_deleted`**。
而项目铁律是"相机↔工位绑定的**权威表**是 `dim_camera`，`camera_status` 只是运行状态快照"。
实测：`camera_status` 与 `dim_camera` 的绑定**有 4 行不一致**（都是软删相机）。

**影响（实测结论要诚实）**：当前**没有造成统计污染** ——
4 台软删相机的图片量都是 0，且唯一软删产线 ZK19 没有相机指向它。
但这是"恰好没数据"，不是"逻辑上排除了"：**软删相机若有保留期内的历史图片，
统计会把它算进"未筛选产线"的总数**。
**方向**：统计路径改走 `dim_camera`（权威表）并显式 `is_deleted = 0`；
或至少补 `cs.is_active = 1` 过滤。

### S-06 同一段 SQL 在 5~7 处各写一遍

**依据**（实测片段重复度）：

| 片段 | 出现处数 |
|---|---|
| `JOIN defect_image_file f ON f.image_id = b.image_id` | **7** |
| `OR EXISTS (... defect_type LIKE ?)` | 5 |
| `LEFT JOIN dim_workstation ws ...` / `LEFT JOIN dim_production_line pl ...` | 各 5 |
| `LEFT JOIN dim_production_line l ON q.line_id = l.line_id` | 4（`AnalyticsAggregationRepository`） |

**影响**：改一处口径必然漏另一处 —— 这正是本次多条统计不一致 bug 的结构性成因。
**方向**：抽出共享的 SQL 片段常量/片段拼接器（仓库已有 `cameraStatusJoinSql()` 这种先例）。

### S-06.1 空 catch 让统计失败"看不出来"

**依据**：`StatsController.java:318` 与 `:348` 的 `catch (Exception ignored) {}` —
统计聚合（产线排名的良率排序、品牌统计）抛任何异常都被吞掉，
**该段结果直接缺失但接口照常返回 200**，页面看不出少了内容。
**影响**：现场"数字看着少一块"却无从判断是数据问题还是计算异常 —— 与本项目
一贯的"诚实降级"原则（`ignoredFilters`/`yieldRateAvailable`）不一致。
**方向**：至少记 WARN 并在响应里带"部分指标计算失败"的标记（对齐诚实降级口径）。

### S-07 冻结通道与孤立页面留下一批死代码

**依据**：前端 `api/defect.js:27` 定义了 `/detection-history/query`（打向恒 0 行的
`product_detection_history`）但**无任何调用方**；`api/stats.js` 的 15 个端点只被
4 个**无路由指向**的孤立页面使用（`stats/DefectTrend.vue`、`LineDashboard.vue`、
`ProductShiftYield.vue`、`StatsOverview.vue`）。
**影响**：读者误以为这些能力可用；改接口时要维护无人调用的代码。
**方向**：删除死代码，或把孤立页面接上路由/明确标注"暂未开放"。

### S-08 聚合通道实质废弃，但 UI 仍展示"日聚合运维卡"

**依据**：`agg_quality_30m` 实测**只剩 1 行**、`agg_quality_day` **0 行**
（现场不写该通道）。而产线统计页底部仍有"日聚合运维"卡片与
`/v1/analytics/aggregation/*` 6 个端点。
**影响**：用户看到"聚合任务 SUCCESS"却发现统计没变化 → 误判；
这正是 11-17 记录的"源表空却记 SUCCESS"问题，已改为记 SKIPPED，但**卡片本身仍在**。
**方向**：确认该通道是否彻底废弃；若是，隐藏卡片 + 标注"现场不写聚合表"。

### S-09 严重度全 HIGH → "高危占比"指标恒 100%，无区分度

**依据**：`defect_image_box` 24,209 行 severity 全为 `HIGH`；
服务端分级逻辑正确（`normalizeSeverity` 能识别 HIGH/严重/高、MEDIUM/中、其余 LOW）。
**影响**：`highCount/defectCount` 恒为 1.0，"高危缺陷"卡与严重度分布图**当前无信息量**；
日报的相机健康指标"当日温度告警数"同理依赖真实分级。
**方向**：这是**设备/算法侧**问题（上报即如此），服务端不能替它编；
需现场确认设备端严重度分级逻辑，或在页面对"全 HIGH"给出说明。

## 五、整体评审结论

### 5.1 总体判断：**架构与口径治理已到位，当前瓶颈在"数据访问效率"与"设备侧可靠性"**

三个正面结论：

1. **架构纪律执行得好** —— 七域分层 + ArchUnit 三条铁律 + 13 处跨域依赖冻结在 CI 守护；
   数据源优先级、相机 code-first、诚实降级（`ignoredFilters`/`yieldRateAvailable`）
   这类**口径纪律已固化成代码**，是本项目最有价值的资产。
2. **现场运行稳定** —— 服务 `active`、NRestarts=0、内存 2.67GB/16GB、
   `/main` 数据盘 17G/500G（4%），近 24h 无崩溃。
3. **数据治理分层合理** —— 31 天主表 → 月表 → 730 天，磁盘与库双生命周期，
   备份 + binlog + 跨盘副本齐备。

### 5.2 三个最需要决策的点

| # | 决策 | 为什么现在要定 |
|---|---|---|
| 1 | **是否立即修 M-01 索引** | 唯一"改一行 SQL 索引、收益一个数量级"的高杠杆项；且项目设计目标 200 台 / 10 年已写进硬件方案 |
| 2 | **设备端问题由谁负责** | M-04（72 条 ERROR/24h）+ S-09（severity 全 HIGH）**都是设备侧**；系统侧只能"看得见"（补告警），不能替设备修。需明确责任边界 |
| 3 | **冻结通道（`inspection`）与聚合通道是否彻底下线** | S-07/S-08：目前是"半废弃"状态 —— 代码在、UI 在、数据不在。留着会持续产生"功能不可用"的困惑 |

### 5.3 优先级建议

```
第 1 批（本周）：M-01 索引 + M-02 分页上限     ← 改动小、收益大、风险低
第 2 批（与设备端同步）：M-04 上传失败告警 + S-09 严重度说明
第 3 批（下个迭代）：M-03 上传鉴权（需协调现场设备）+ S-05 权威表口径 + S-01/S-02 存储与索引瘦身
第 4 批（排期）：S-06 SQL 复用 + S-07/S-08 死代码清理 + C 组技术债
```
