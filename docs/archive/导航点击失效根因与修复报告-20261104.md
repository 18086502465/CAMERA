**日期**：2026-11-04
**现象**：用户 Chrome 浏览器中点击顶部【图像记录】【系统配置】，**URL 完全不变、页面不刷新、也没有任何后端请求**
**服务器**：10.2.77.72（Hik-Vision，Ubuntu 24.04.5 LTS）

## 二、根因

### 2.1 完整因果链

```
Vite 产物的 chunk 文件名带**内容哈希**（index-XXXX.js / ImagesView-XXXX.js）
        │
        ▼ 每次构建，所有 chunk 名全部改变
新部署上线 → 服务器只剩新 chunk，旧 chunk 被替换掉
        │
        ▼
用户浏览器里那个**部署前就打开**的标签页
  └─ 内存中的路由表仍指向旧 chunk 名（ImagesView-3Im0_kdo.js）
        │
        ▼ 点击【图像记录】
动态 import 旧 chunk → 404
        │
        ▼
Vite 抛 "Failed to fetch dynamically imported module"
        │
        ▼
vue-router 的导航 Promise 被 reject → **导航静默中断**
        │
        ▼
★ URL 完全不变、页面不刷新、没有后端请求、按钮"点了没反应"
```

**为什么没有报错提示**：vue-router 4 把组件加载失败交给 `router.onError`，
若未注册该钩子，错误只出现在 Console 里，UI 上没有任何反馈。

### 2.2 为什么我的自动化测不出来

自动化脚本每次都是**新开页面**（`page.goto`），加载的是**当前** `index.html`，
引用当前 chunk 名，自然一切正常。只有**跨部署的旧标签页**才会触发。

现场场景恰好相反：产线人员长时间开着页面不刷新，部署后继续用 → 必然踩中。

### 2.3 这不是偶发，而是**每次部署必现**

只要现场有人的浏览器标签页跨越了一次部署，那个人点击任何**懒加载路由**
（图像记录 / 系统配置 / 产线统计 / 相机监控 / 服务器监控…）都会失效。

## 三、修复方案（三层防护）

### 层 1：前端版本守卫（主动检测 + 自愈）　`frontend/src/utils/resource-version.js`（新增）

| 能力 | 实现 |
|---|---|
| **主动检测** | 每 3 分钟 + 页面切回前台时，比对「当前页面加载的入口 chunk 哈希」与「服务器当前 `index.html` 的入口哈希」。不同 → 提示用户刷新 |
| **被动自愈** | 捕获全局 `error` / `unhandledrejection` + `router.onError`，识别 `Failed to fetch dynamically imported module` → **自动刷新页面**（sessionStorage 去重，防死循环） |
| **降级提示** | 已刷新过仍失败 → 明确提示"请手动强制刷新（Ctrl+F5）"，不再静默 |

检测原理无需改动构建流程：入口 chunk 名带内容哈希，页面里的 `<script src>` 就是它当时的版本，
拉一次服务器的 `index.html`（`cache: 'no-store'`）比对即可。

接入点：
- `frontend/src/main.js` → `startResourceVersionGuard()`
- `frontend/src/router/index.js` → `router.onError(...)`

### 层 2：构建时保留历史 chunk（治本）　`installer/linux/build-release.sh`

新构建的 chunk 与**上一版**的 chunk **共存于同一目录**（文件名带哈希，不会冲突），
旧页面的懒加载请求仍能命中 → **现场不必强制刷新页面**。

配套机制：
- `assets/.versions` 清单记录每个文件属于哪一版（`current` / 备份时间戳）
- `KEEP_STATIC_VERSIONS`（默认 3）控制保留版数，超出的自动淘汰
- 构建时**先清空 `dist/assets`** —— `vite build` 不清空输出目录，会把上次 chunk 一起留在 dist 里，
  导致 JAR 体积虚增、且"当前入口是哪个"无法判定

### 层 3：现场存量修复（把已失效的旧 chunk 找回来）

服务器上 11 个历史 JAR 备份共 1545 个静态文件（**去重后 452 个**），
用 `recover_legacy_chunks.py` 把它们合并回当前 JAR —— 用户报错的
`ImagesView-3Im0_kdo.js` 由此恢复（**404 → 200，20614 字节**）。

配套 `prune_legacy_chunks.py` 按 `.versions` 清单淘汰过旧版本。

## 六、踩坑记录（本次排查中遇到并修复）

| # | 坑 | 现象 | 教训 |
|---|---|---|---|
| 1 | **改注释不改变产物哈希** | 验证版本保留时哈希纹丝不动 | vite 的 chunk 哈希基于**输出内容**，注释被 tree-shake → 验证要用**改变行为**的改动 |
| 2 | **`vite build` 不清空 dist** | dist 里同时有新旧两个 `index-*.js` | 构建前必须清空，否则"当前入口是哪个"无法判定 |
| 3 | **版本标记顺序错误** | 先标历史再标 current → 历史文件全被标成 current，统计恒为 0 | 必须**先标 current（只针对本次 dist 的文件），再标历史** |
| 4 | **zipfile 重复条目** | 增量写 JAR 时既写了原 assets 又写了新 assets → `Duplicate name` 警告 | 增量写时**跳过所有 assets 条目**，统一在最后重写 |
| 5 | **`jar cf` 重打包会破坏 Spring Boot JAR** | 会丢 `Main-Class: JarLauncher` / `Start-Class` / `classpath.idx` | 必须用 **Python zipfile 增量写**，不重打包 |
| 6 | **StartLimit 限流** | 连续重启 3 次后 `Start request repeated too quickly`，服务起不来 | 重启前先 `systemctl reset-failed`（记忆里已记过，这次又踩到） |
| 7 | **恢复脚本与部署脚本的顺序冲突** | 部署中途改写 JAR → 部署脚本后续步骤失败 → 服务停在 stopped | 顺序必须是：**部署完成 → 恢复 chunk → 重启**；不能在部署流程中间动 JAR |
