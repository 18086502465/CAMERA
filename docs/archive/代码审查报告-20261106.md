## 一、总体结论

系统整体工程质量**高于同类现场项目**——有 DDD 分层、ArchUnit 架构守护、契约测试、增量发版与失败回滚、清理脚本多重防线，这些不是"写了文档"，是能在代码里对上的。

但存在**一处结构性失衡**：过去几个月的修复高度集中在"看得见的线上事故"（鉴权失效、统计翻倍、误删数据、旧页面卡死），而**请求路径上的基础开销、以及新增路径的鉴权覆盖**没有同步治理。结果是每修一个事故，就在热路径上多加一段同步逻辑，累积成现在的性能与安全债。

| 维度 | 评分 | 判断依据 |
|---|---|---|
| 架构设计 | 7 / 10 | 七域分层真实落地，ArchUnit 固化依赖；但 Controller 承载聚合逻辑、报表读路径写库 |
| 代码质量 | 6 / 10 | 注释密度极高且记录根因（罕见优点）；但 73 处 `catch (Exception)`、单方法 219 行、401 处裸 Map |
| 性能 | 5 / 10 | 无缓存层、无读写分离；最重的问题在**每一个请求**上都发生（见 PERF-01） |
| 安全 | 5 / 10 | 认证链路已正确；但文件上传白名单与 RBAC 路径存在实际缺口 |
| 可维护性 | 6 / 10 | 文档与脚本质量高；死代码与巨型类拉低分数 |
| 测试 | 5 / 10 | 100 个 `@Test`，但集中在契约与常量；Repository 层 SQL 无测试，这正是两次 SQL 事故的成因 |
| 部署运维 | 8 / 10 | 增量包、原子替换、回滚、自检脚本完备 |

## 二、P0 —— 本周必须处理

### SEC-01　SVG 上传导致存储型 XSS + 任意文件落盘

| 项 | 内容 |
|---|---|
| 证据 | `DefectImageServiceImpl.java:53` 扩展名白名单含 `svg`；`:936` 以 `image/svg+xml` 回写；`:490` 仅对 `jpg/jpeg/png/bmp/gif` 强制 `ImageIO` 解析；`DefectImageController.java:281` 的 `GET /file/**` 在 `SecurityConfig` 中 `permitAll` |
| 现象 | `.svg` 文件**跳过内容校验**（不在 `IMAGEIO_REQUIRED_EXTENSIONS`），任意内容原样落盘并以 `image/svg+xml` 同源返回 |
| 影响 | 攻击者（任一持有设备 token 的相机/内鬼）上传内嵌 `<script>` 的 SVG，诱导管理员点开图片链接 → 脚本在应用同源执行 → `localStorage.camera_token` 被读取外传（`utils/auth.js:8` token 存 localStorage）。**一次点击 = 管理员会话接管** |
| 修法 | ① 白名单删除 `svg`（设备端只产位图，无业务理由）；② 对所有落盘文件做 `ImageIO` 校验后按真实格式重写扩展名，不信任 `getOriginalFilename()`；③ `loadImage` 响应加 `X-Content-Type-Options: nosniff` 与 `Content-Disposition: inline; filename="..."`；④ 更彻底：图片走独立域名/独立端口提供，与主应用不同源 |
| 理由 | 这是当前唯一能"从设备通道打到管理员账号"的链路，且修复成本不到 20 行 |

### PERF-01　操作日志切面记录了所有 GET，包括每一个图片请求

| 项 | 内容 |
|---|---|
| 证据 | `OperationLogAspect.java:34` `@Around("execution(* com.wms.*.api..*(..))")`；`:149` `shouldSkipOperationLog` 只跳过 `/api/logs/operation` 与 `/api/v1/system/server/` |
| 现象 | `GET /api/v1/defect-images/file/**`（每张缩略图）、`/api/v1/defect-images/recent`（默认 1000 条）、所有看板轮询 GET，**每次请求同步写一行 `sys_operation_log`** |
| 量化 | 相机状态页 16 台相机 × 最新 5 张 = 80 个 `<img>`；每 30 秒轮询（`CameraStatusView.vue:437`）→ **9,600 行/小时/用户**。5 个用户在线 ≈ 4.8 万行/小时，占用 6 个月保留期（`DataCleanupTask`） |
| 影响 | ① 磁盘与表膨胀（与团队自己在 `:145` 记录过"服务器指标 5 秒轮询每天 1.7 万行"是同一类问题，**但只排除了那一个 URI**）；② 每个图片请求多一次 INSERT，吞吐与延迟双降；③ 真正的操作审计被淹没 |
| 修法 | ① 切点收窄到写操作：`execution(* com.wms.*.api..*(..)) && (@annotation(PostMapping) || @annotation(PutMapping) || @annotation(DeleteMapping))`；② 或改为只记录 `!GET` 且 URI 不在静态/文件前缀；③ 审计需求确实需要读日志时，走采样 + 异步队列，不要同步落库 |
| 理由 | 单点改动、收益最大：直接把热路径上的一次写库去掉 |

### SEC-02　RBAC 路径规则与实际映射错配，写接口只要求"登录"

| 项 | 内容 |
|---|---|
| 证据 | `SecurityConfig.java:217/233/249` 三组写规则写的都是 `/api/DimTimeBucket30min/**`；而 `DimTimeBucket30minController.java:23` 实际映射为 `@RequestMapping("/DimTimeBucket30min")`（**无 `/api` 前缀**），含 `@PostMapping` / `@PutMapping` / `@DeleteMapping`，且**无 `@PreAuthorize`**（全仓 38 处方法级鉴权未覆盖它） |
| 现象 | `POST /DimTimeBucket30min` 落到 `.anyRequest().authenticated()` → **任意 ROLE_USER（现场工人账号）可增删改时间桶主数据** |
| 影响 | 时间桶是统计口径的基础维度，被改写会让报表按错误粒度出数；且暴露了"安全规则靠手写字符串对齐 URL"这一系统性脆弱点 |
| 修法 | ① 该 Controller 迁到 `/api/v1/time-buckets`（与其余端点统一前缀）；② 每个写方法补 `@PreAuthorize("hasRole('ADMIN')")`；③ **根本治理**：`@PreAuthorize` 作为唯一授权真源，`SecurityConfig` 只保留认证入口与静态资源白名单，删掉这 60 余行手写路径规则；④ CI 加一条 ArchUnit/反射规则：所有 `@*Mapping` 必须落在 `/api/**` 下 |
| 理由 | 同一份路径在两个文件里各写一遍，必然漂移。这次漂移的是主数据写权限 |

## 三、P1 —— 两周内处理

### PERF-02　报表"读路径"触发聚合重算（DELETE + INSERT）

| 项 | 内容 |
|---|---|
| 证据 | `LineAnalyticsController.java:137-155`：范围 > 阈值时，每次查询都调 `rebuildQualityDaily` / `rebuildDefectDaily` / `purgeOrphanAggregationRows`；`AnalyticsAggregationRepository.java:303-326` 实现为 `DELETE FROM agg_quality_day ...` + `INSERT ... SELECT ... GROUP BY` |
| 影响 | ① 报表页 30 秒轮询（`StatsOverview.vue:339` 等 4 处）→ **每 30 秒一次全范围聚合重建**；② 并发用户互相锁表；③ 把只读接口变成写接口，备份/主从上会放大写放大 |
| 修法 | 拆分职责：查询只读聚合结果；重建由 `@Scheduled`（已有 `aggregation/jobs` 机制）或维护窗口触发；查询发现聚合缺失时**返回 `aggregationLevel=STALE` 提示**，而不是当场重建 |
| 理由 | 这是当前最典型的"为修一个数不对，把写操作塞进读路径"的技术债，随数据量线性恶化 |

### PERF-03　一次报表 = 8 次独立全表聚合，且无任何缓存

| 项 | 内容 |
|---|---|
| 证据 | `LineAnalyticsController.java:346-410`：KPI、趋势、缺陷排行、工位排行、相机排行、产品透视、严重度分布各自 `queryXxx`，共用同一 `WHERE` 但重复扫描 `defect_image_file` + `LEFT JOIN dim_camera` |
| 影响 | 单次 `/line-summary` 实际执行 8 条聚合；7.9 万行时约几十到几百毫秒，量级增长后线性恶化。叠加 30 秒轮询 × 并发用户 |
| 修法 | ① 一次 `GROUP BY` 出多维结果再用 Java 拆分（或用 `GROUPING SETS`）；② 引入 Caffeine 本地缓存，键 = 参数指纹，TTL 30~60 秒（报表本身允许 1 分钟延迟，前端已在轮询）；③ 中期引入预聚合表按 5 分钟窗口写入 |
| 理由 | 缓存命中率对这类"参数固定、多人同看"的页面接近 100%，是投入产出比最高的性能改造 |

### PERF-04　上传长事务包住文件 IO 与图像解码

| 项 | 内容 |
|---|---|
| 证据 | `DefectImageServiceImpl.java:89` `@Transactional` 覆盖整个 `upload()`；循环内 `Files.copy`（`:477`）、`ImageIO.read`（`:487`）、每图 3 次 INSERT（`:159-161`） |
| 影响 | 100 张图的批次可能占用数据库连接数秒；设备集中上报（换班/重启补传）时耗尽 Druid 连接池（`max-active: 200`），拖垮看板 |
| 修法 | 事务边界只包 DB 写入；文件落盘与解码在事务外完成，失败走补偿清理（现有 `cleanupFailedImage` 已具备该能力）；图片表插入改 `batchUpdate` 批量提交 |
| 理由 | 现场"设备重启后集中补传"是可预期的突发模式，这是最可能被打爆的点 |

### BUG-02　`/camera-summaries` 筛选发生在 `ROW_NUMBER` 之后（语义错误）

| 项 | 内容 |
|---|---|
| 证据 | `:555` `WHERE r.rn <= ?` 与随后的筛选条件同处外层 `WHERE` |
| 现象 | 先按全量数据选出"每相机最近 N 张"，再过滤严重度/时间 → 过滤后往往**少于 N 张甚至 0 张**，而正确语义是"满足条件的最近 N 张" |
| 修法 | 筛选条件下推到内层派生表（与 BUG-01 一并修） |
| 理由 | 静默少图比报错更难发现，属于数据正确性问题 |

### SEC-03　认证链路的三个缺口

| 缺口 | 证据 | 影响 | 修法 |
|---|---|---|---|
| 无登录限速 | `AuthController.java:41` 无任何频率控制 | 口令爆破；BCrypt 成本高，还可被打成 CPU DoS | 按 用户名+IP 计数，5 次/分钟失败即锁 5 分钟 |
| 开放注册无限速无审核 | `AuthController.java:85`，`SecurityConfig` 白名单 | 批量注册普通账号（虽已固定 role=0） | 关闭自助注册或加邀请码/管理员审批 |
| 禁用用户仍可用 24 小时 | `JwtRequestFilter.java:181` 只校验 token，不检查 `isDisabled` | 离职/异常账号处置不及时 | 过滤器加 `isDisabled` 判断，或在 JWT 加 `ver` 版本号并在禁用时自增 |

### SEC-04　CORS 通配 + 允许凭证

`SecurityConfig.java:379-382`：`setAllowedOriginPatterns("*")` + `setAllowCredentials(true)`。当前 token 在 Header 不在 Cookie，直接危害有限；但与 SEC-01 组合（同源脚本执行）后攻击面扩大。修法：改为部署域名白名单（`https://<现场域名>`），或干脆关闭 CORS（前后端同源部署，本就不需要）。

### QUAL-01　没有全局异常处理器，500 响应不符合统一契约

| 项 | 内容 |
|---|---|
| 证据 | 全仓无 `@ControllerAdvice` / `@ExceptionHandler`（grep 0 结果）；`ResultVO` 只在正常路径构造 |
| 影响 | 任何未捕获异常（如 `IllegalArgumentException`、SQL 错）返回 Spring 默认错误体 `{timestamp,status,error,path}`，前端读 `res.data.code` 得到 `undefined` → 页面只能显示"操作失败"，排查靠翻日志 |
| 修法 | 加 `GlobalExceptionHandler`：`IllegalArgumentException` → 400 + `ResultVO.fail`，`DataAccessException` → 500，`AccessDeniedException` 交给 Security；响应统一 `ResultVO` |
| 理由 | BUG-01 这类 SQL 错误现在会以"未知错误"呈现，正是缺这层导致的观测盲区 |

### QUAL-02　业务失败用 `code=500` + HTTP 200

`ResultVO.fail` 恒定 `code=500`（`ResultVO.java:47`），登录失败、参数校验失败都是 500。影响：监控/网关无法按 HTTP 状态分类；前端只能靠字符串匹配。修法：定义业务错误码（`40001` 参数、`40101` 凭据、`42201` 设备校验），HTTP 状态与之对齐。

### PERF-05　模糊搜索与列函数导致索引失效

| 项 | 内容 |
|---|---|
| 证据 | `DefectImageRepository.java:211-213`：`keyword` 同时 `LIKE '%kw%'` 8 个字段 + `EXISTS` 子查询；`:545` `WHERE COALESCE(NULLIF(f.camera_id,''), f.camera_name) IN (...)`；`:771` `WHERE COALESCE(capture_time, upload_time, create_time) >= ?` |
| 影响 | 关键词搜索必然全表扫；`COALESCE` 使 `idx_defect_file_capture_time` 与 `camera_id` 索引失效。主表 31 天热数据（当前数万行），随产线扩容线性恶化 |
| 修法 | ① 搜索改为 `camera_id = ?` 精确 + 只对 `file_name` 前缀匹配；需要全文时上 `FULLTEXT` + ngram 分词；② 为 `capture_time` 建**生成列** `capture_time_eff` 并索引，查询用该列；③ 相机键统一为 `camera_code`，老数据一次性回填后去掉 `COALESCE` |

### SEC-05　依赖停更与死依赖

| 项 | 内容 |
|---|---|
| 证据 | `pom.xml`：Spring Boot `2.7.15`（2.7 线已停止维护，末版 2.7.18）、Java 8（已 EOL）、`fastjson 1.2.83`、`druid 1.2.16`、`poi 5.2.4` |
| 关键 | **fastjson 全仓零引用**（`grep com.alibaba.fastjson` 无结果）—— 带着历史 CVE 的死依赖 |
| 修法 | 立即删 fastjson；Boot 升到 2.7.18（低风险，无需迁 jakarta）；中期评估 JDK 17 + Boot 3（需 `javax→jakarta` 全量替换，约 1~2 周）；接入 OWASP Dependency-Check 或 Trivy 进 CI |
| 理由 | 安全基线不能靠"没用到就没事"，依赖会被间接加载 |

### OPS-01　生产默认日志级别过高

`application.yml:55` `log-impl: StdOutImpl`（SQL 打到 stdout，进 journald）；`:93-95` `com.wms.mapper: DEBUG`。文档要求生产覆盖为 `Slf4jImpl` + `INFO`，但**默认值就是错的**——漏配一次就是全量 SQL 日志。修法：默认改为 `Slf4jImpl`/`INFO`，本地用 `application-dev.yml` 覆盖。

## 五、架构层面的三条结构性建议

**1. 把"授权"收敛到单一真源，删掉手写路径表。**
当前 `SecurityConfig` 有 60+ 行字符串路径规则，`JwtRequestFilter` 里还有两份 `PUBLIC_PATHS` / `DEVICE_PATHS` 需同步。三份清单、四个空控制器遗留的无效规则、SEC-02 的错配，都是同一个根因。做法：路径统一 `/api/v1/**`；授权只用 `@PreAuthorize`；`SecurityConfig` 只留"认证入口 + 静态资源 + 3 个设备端点"。

**2. 读路径只读，写路径异步。**
PERF-02（读时重建聚合）、PERF-01（读时写审计日志）、`ensureSchema`（读时查元数据）是同一个反模式的三次出现。建议立一条工程纪律并写进 `CODEBUDDY.md`：**HTTP 请求线程内禁止出现 DDL、聚合重建、批量写入**。

**3. 报表从"实时算"转向"预计算 + 缓存"。**
现场已从 3 千条走到 7.9 万条，图片通道还在按天增长。当前"每次查询 8 条聚合 + 30 秒轮询"的模式在数据量翻 5 倍后会直接不可用。短期加 Caffeine（改动小、当天见效），中期做 5 分钟粒度的预聚合表，让报表只读小表。

## 七、值得保留的做法（不要在重构中丢掉）

1. **根因写进注释**：`SecurityConfig` / `DefectImageServiceImpl` / 清理脚本里的"为什么这么写"是这类现场项目最稀缺的资产，重构时保留并搬运。
2. **ArchUnit freeze 模式**：12 处跨域存量只许清零不许新增，比"规则上线即全红"务实得多。
3. **增量发版 + 健康检查 + 自动回滚**：`jar_manifest.py` 的依赖指纹机制解决了"小改动必须传 61MB"的现实问题。
4. **清理脚本的三道防误删防线**（含 `while read` 丢末元素的修复）：这是用真实事故换来的，任何"简化"都是倒退。
5. **CI 三项静态检查**（明文口令 / CRLF / 假数据 TODO）：成本极低，拦的都是真实事故类型。
