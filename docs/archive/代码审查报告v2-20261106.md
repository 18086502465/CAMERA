## 二、新发现

### PERF-NEW-01（P0，本周）　设备心跳写审计日志——GET 修完后暴露的最大噪音源

| 项 | 内容 |
|---|---|
| 证据 | 服务器实测：11-05 全天 `sys_operation_log` 34,210 行，其中 `/api/v1/camera/status/heartbeat` **33,205 行（97%）**；11-06 至 11:36 已 48,504 行，心跳 **47,790（98.5%）**。GET 修复后（当日 GET 仅 588 条）心跳成为绝对主体 |
| 量级投影 | `nextInterval=5000ms`（`CameraStatusServiceImpl:296`）× 16 台相机 = 满载 **27.6 万行/天**；保留期 6 个月（`DataCleanupTask.cleanupOperationLogs`）→ **投影 ~5000 万行 / 12GB+**（当前表 19MB/8.2 万行，11-05 起算即已近翻倍） |
| 根因 | `OperationLogAspect` 现在只按 GET 跳过；心跳是 **POST**，且不在 URI 排除清单。这是同一反模式的**第三次出现**：server-metrics 轮询（17,280/天，11-02 修）、图片 GET（9,600/h，11-06 修）、心跳（27.6 万/天，未修） |
| 影响 | ①审计表被遥测淹没（登录、配置变更等真实审计事件占 <3%）；②每次心跳多一次 INSERT + 切面开销（5 秒 × 16 台常驻）；③6 个月保留期下容量线性膨胀 |
| 修法 | `shouldSkipOperationLog` 加一条：`uri.startsWith("/api/v1/camera/status/")` → true（心跳遥测已有 `camera_status` 快照 + `fact_anomaly_alert` 承接，审计表无增量价值）。**1 行改动 + 注释**，随下次发版部署 |
| 理由 | 与 PERF-01 同源；建议把"**遥测/轮询端点必须显式排除出审计日志**"写成与"审计只记写"并列的工程纪律，并在此方法 Javadoc 固化 |

### SEC-NEW-04（P2）　持续故障时告警表无去重节流

`CameraStatusServiceImpl.checkAndAlert`（:210-245）：相机上报 `cameraStatus=2` 时**每 5 秒插一条 CRITICAL** `CAMERA_FAULT`；CPU/内存/温度超阈值同理。当前未触发（表 67 行），但单台持续故障 = **1.7 万条/天/相机**，告警页会被同一事件刷屏。
修法：插入前查"同相机同类型同级别且未恢复的告警存在即跳过"（或 10 分钟节流窗口），恢复时写 resolved。当前量级不紧急，与告警页功能一起做。

### QUAL-NEW-03（P2）　注册口令零强度策略

`AuthController.register`（:101-113）：任意非空口令可注册（含 1 位口令）。开放注册（SEC-03 已列）+ 无强度校验 + 无频率限制三者叠加，弱口令批量存在成本极低。
修法：注册加最小长度 8 + 至少两类字符；与 SEC-03 的限速/审批一起做。

### QUAL-NEW-02（P2）　配置导入：POI 解析在事务内、行级错误被吞后整体提交

`ConfigImportController.importConfig:118` `@Transactional` 包住 Excel 解析 + 逐行 upsert：大文件解析（IO+POI）全程占连接；行级 catch-continue 语义 = "错误行跳过、其余提交"，与"事务整体回滚"直觉相悖（行为可接受但必须显式文档化，否则将来有人顺手加 rollbackFor 会变成整批失败）。
修法：解析放事务外（先全量读成行对象），事务只包批量 upsert；行为在 Javadoc 写明。
