## 1. SEC-01　SVG 存储型 XSS

### 1.1 现状与证据
- `DefectImageServiceImpl:53`：白名单 `IMAGE_EXTENSIONS` 含 `svg`；
- `:936`：`contentTypeByExtension("svg")` 返回 `image/svg+xml`；
- `:487-496`：`IMAGEIO_REQUIRED_EXTENSIONS` 不含 `svg` → 上传 SVG 时 `ImageIO.read` 返回 null 不报错，**文件内容零校验**直接落盘；
- `loadImage` 以同源 `image/svg+xml` 返回、匿名可读 → SVG 内嵌 `<script>` 在管理员浏览器执行，token 在 localStorage → 会话接管。

### 1.2 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 从白名单移除 `svg`，上传即拒 | 3 行改动，攻击面归零；产线相机只发 jpg/png，SVG 本无业务来源 | 存量 SVG 行仍可被读取（见 1.3 兜底） |
| B | 保留 SVG，落盘消毒（DOM 白名单过滤） | 功能不损失 | 需引入消毒库或手写解析，复杂度高；SVG 消毒历来是漏洞重灾区，不值得为无来源的格式承担 |
| C | 保留 SVG，读取时改 `Content-Disposition: attachment` + `Content-Type: application/octet-stream` | 不改上传逻辑 | 前端 `<img>` 标签无法渲染 attachment，图片页会碎；等于变相禁用 |

### 1.3 具体改动（方案 A）

| 文件:位置 | 改动 |
|---|---|
| `DefectImageServiceImpl.java:53` | `IMAGE_EXTENSIONS` 移除 `"svg"`，并加注释「SVG 可携带脚本，禁止进入图片通道；如未来确需，必须走消毒+attachment 双保险」 |
| `DefectImageServiceImpl.java:936` | 删除 `contentTypeByExtension` 的 svg 分支（防未来误加回），兜底 `application/octet-stream` |
| `DefectImageServiceImpl.java` loadImage 路径 | **存量兜底**：扩展名为 `svg` 的历史行改返回 `application/octet-stream` + `Content-Disposition: attachment`（不再以 `image/svg+xml` 同源渲染） |
| 上传拒绝提示 | 报错文案明确「不支持 SVG 格式」，避免现场误判为损坏图片 |

若 P0-0a 查出存量 > 0，追加子任务：一次性 `UPDATE` 或删除存量 SVG 行 + 对应磁盘文件（走既有"先删库后删磁盘"顺序铁律），清理前备份。

### 1.4 验证
1. 单测：上传伪造 `evil.svg`（内含 `<script>`）→ 断言 400 + 磁盘无文件；
2. 回归：jpg/png/bmp/gif/webp 各一张正常上传通过；
3. 若有存量：读取历史 SVG 行 → 响应头为 `application/octet-stream`，浏览器不执行。

### 1.5 风险与回滚
- 风险：现场某设备确实会推 SVG（概率极低，P0-0a 可证实）→ 若证实，转方案 C 并把"消毒"列入 P1；
- 回滚：单点 revert 白名单即可，无数据结构变更。

## 2. PERF-01　操作日志切面记录所有 GET（含每张图片请求）

### 2.1 现状与证据
- `OperationLogAspect.java:34`：切点 `execution(* com.wms.*.api..*(..))` 拦截**全部** Controller 方法；
- `:149-166`：`shouldSkipOperationLog` 只按 URI 排除 2 段（操作日志自身、服务器监控），**不区分 HTTP 方法**；
- 实测估算：相机状态页 80 张图 × 30s 轮询 ≈ **9,600 行/小时/用户** 进 `sys_operation_log`，淹没真实操作审计。

### 2.2 方案（单一，无需二选一）

**原则改为"只记写操作"**：`GET` 一律跳过，其余维持现有 URI 排除表。

前提核实（已完成）：全仓 `@GetMapping` 无删除/清理/导入类写语义端点——`ConfigImportController` 的 3 个 GET 是下载模板/导出，确属读操作。登录/注册是 POST，**继续记录**（安全审计需要失败登录记录，为 SEC-03 限速做数据基础）。

### 2.3 具体改动

| 文件:位置 | 改动 |
|---|---|
| `OperationLogAspect.java:149` `shouldSkipOperationLog` | 方法开头加：`if ("GET".equals(request.getMethod())) return true;` 并更新 Javadoc（把"为什么只记写"写成纪律，防止后人加回） |
| `OperationLogAspect.java:52` | `e.printStackTrace()` → `log.warn("操作日志写入失败", e)`（顺带修掉坏味道，1 行） |
| 排除表保留 | `/api/logs/operation`、`/api/v1/system/server/` 两条保留（POST 清空日志仍会被记，但那是低频管理动作，合理） |

**取舍说明**：为什么不反过来用"白名单只记 POST/PUT/DELETE 标注的端点"？——切面按 HTTP 方法过滤是数据驱动，不需要维护端点清单；反向白名单会重演 SecurityConfig 路径清单漂移的老问题（SEC-02 的根因就是清单漂移）。

### 2.4 验证
1. 上传一批图片 + 打开相机状态页 1 分钟 → `sys_operation_log` 无新增 GET 记录；
2. 执行一次"新增相机"（POST）→ 日志正常落库；
3. 登录失败一次 → 日志落库（`success=false`）；
4. 前端操作日志页仅显示写操作（如有 UI 按 type 过滤需同步确认）。

### 2.5 风险与回滚
- 风险：若将来出现"用 GET 完成的写操作"会被漏记 → 已用 2.3 的全仓扫描排除，且在 Javadoc 写明该前提；
- 存量数据：`sys_operation_log` 里的历史 GET 记录不清理（只停增），如需瘦身走 `DataCleanupTask` 的既有保留期机制；
- 回滚：删除一行方法判断即恢复原行为。

## 4. BUG-01 / BUG-02　`/camera-summaries` 筛选 SQL（合并修复）

### 4.1 现状与证据
`DefectImageRepository.java`（`listRecentImages`-型相机聚合查询）：
- 内层派生表别名 `f`（含 `ROW_NUMBER()` 窗口函数），外层别名 `r`；
- **外层 `WHERE` 引用了 `f.`**，共 4 处语法级错误：
  - `:563` severity 的 `EXISTS (... bs.image_id = f.image_id)`；
  - `:567` defectType 同上；
  - `:571/574` `COALESCE(f.capture_time, f.upload_time, f.create_time) >= ? / <= ?`；
  - **新发现（评审稿加重项）**：`:561` 调用的 `appendKeywordFilterRowLevel` 内部引用 `f.camera_id / f.file_name / ...`（`:224-225`）——keyword 筛选同样 1054，与前三处同根；
- 窗口函数阻断派生表合并 → `f` 在外层永不可见 → 任一筛选启用即 `Error 1054: Unknown column 'f.xxx' in 'where clause'` → 接口 500；
- 语义层（BUG-02）：原设计把筛选放在 `ROW_NUMBER` 之后，即使列名侥幸可见，也是"每相机最新图不满足筛选就整台消失"（静默少图），正确语义应为"每相机**满足筛选的最新一张**"。

### 4.2 方案：筛选条件下推内层（一步同时修语法 + 语义）

把整块行级筛选（keyword / severity / defectType / startTime / endTime）从外层 `WHERE r.rn <= ?` 之后，移到内层 `WHERE COALESCE(...) IN (...)` 内、`ROW_NUMBER` 计算之前。

**语义决策（需评审确认）**：下推后，某相机在筛选时间窗内无任何匹配图 → 该相机不出现在结果里。这与"相机聚合视图按时间看各相机最新命中"的语义一致（替代原设计"最新图不匹配则整台消失"），预期验收标准「带时间范围返回正确张数」即按此口径。

### 4.3 具体改动

`DefectImageRepository.java`：
1. 删除外层的 4 段筛选拼接（`:561-576`）；
2. 在内层 `WHERE COALESCE(NULLIF(f.camera_id,''), f.camera_name) IN (...)` 之后追加同样的筛选拼接（顺序：keyword → severity → defectType → startTime → endTime）；
3. **不复用** `appendKeywordFilterRowLevel` 的现有实现——方法注释声明它"用于内层"，恰好这次才是它第一次被放到正确位置；调用处保留，仅移动位置；
4. `startTime/endTime` 的 `COALESCE` 在内层执行，不影响外层 JOIN，性能不变差（反而筛选先行，窗口函数计算行数变少，是**顺带的小优化**）。

### 4.4 验证（静态修复必须配 SQL 级回归，防止再犯）
1. **新增 Repository 单测**（回应报告 TEST-01 的最小落地）：H2 MySQL 兼容模式（支持 `ROW_NUMBER()`）建 `defect_image_file` / `defect_image_box` / `camera_status` 三张最小表，覆盖 4 个断言：
   - 无筛选：每相机返回 rn=1 一张；
   - 仅时间窗：窗内最新一张、窗外相机不出现；
   - keyword：命中 file_name 与命中 defect_type 两个路径；
   - severity：EXISTS 路径命中。
2. 服务器实测（P0-0b 同一 curl，部署后复跑）：带时间范围返回正确张数；
3. 对比修复前后无筛选条件的结果集：必须完全一致（防止移动筛选引入回归）。

### 4.5 风险与回滚
- 风险：筛选下推改变"相机是否出现在结果中"的边界（见 4.2 语义决策），前端若有"相机列固定展示"的假设需确认——**图像记录页目前是"有图才显示"逻辑，无固定列**，已核对无冲突；
- 回滚：该查询为纯 SELECT，revert 即恢复。
