## 二、发现并修复的缺陷（11 项）

### 🔴 必须修（9 项）

| # | 现象 | 复现步骤 | 影响范围 | 修复内容 | 验证结果 |
|---|---|---|---|---|---|
| **B-1** | `defectTypeId` 筛选**完全失效且未上报**：传 `defectTypeId=1` / `99999` 与完全不筛**逐字节相同** | `GET /line-summary?defectTypeId=1` | 所有「缺陷类型 ID」筛选入口；外部按接口文档集成 100% 静默失效 | 如实上报 `ignoredFilters=["defectTypeId"]` + 说明「标准类型编码与现场中文类型不是同一套标识，无法直接匹配」（`buildDefectImageSummary` 原本连形参都没有） | ✅ `ignoredFilters=["defectTypeId"]`，消息可读 |
| **B-2** | `severity` 只作用于 3 个块（排行/透视/严重度分布），**KPI/趋势/工位相机排行/热力图/班次对比全不受约束**，且未上报 → 选「高危」后 KPI 纹丝不动 | `GET /line-summary?severity=MEDIUM` | 厂长的主力定位图表全部未受严重度约束 | 上报 `ignoredFilters=["severity(部分)"]` + 明确说明哪部分生效、哪部分不生效 | ✅ 正确上报 |
| **B-3** | 非法日期格式 → **HTTP 500**「系统异常」（7 种触发方式全 500） | `?startTime=not-a-date` / `2026/11/18` / `2026-11-18` | 所有时间筛选入口；5xx 可用性告警被污染 | `parseTime` 捕获 `DateTimeParseException` → 转 `IllegalArgumentException` → 400 | ✅ 7 种全部 400 + 可读消息 |
| **B-4** | 非数字 ID 参数 → **HTTP 500**；且 **GET 与 POST 状态码不一致**（GET 500 / POST 400） | `?cameraId=NOT_EXIST_CAM` | 第三方接入最常见手误收到 5xx | `GlobalExceptionHandler` 新增 `MethodArgumentTypeMismatchException` → 400 + 指明参数名与期望类型 | ✅ 400，指明 `参数 cameraId 类型不正确，期望 Long` |
| **B-5** | 不存在的日期被 **SMART 解析器静默纠正**到当月最后一天（`2026-11-31`→`11-30`、`2026-02-30`→`02-28`），**用户以为查 31 号、实际查 30 号** → 有数据的月份上**少算一天且毫无提示** | `?startTime=2026-11-31&endTime=2026-11-30` → 200（而 start>end 本该报 400，说明被改写过） | 所有按日期筛选的入口；数据静默少算 | `DT` 改 `ResolverStyle.STRICT`（年用 `uuuu`）+ 配合 B-3 转 400 | ✅ 400，不再静默纠正 |
| **B-6** | 聚合兜底分支**缺 3 个响应键**（`hourlyHeatmap`/`shiftCompare`/`shiftNames`），键数 25 vs 22 —— **恰好违背代码注释自己承诺的 P0-1 结构一致性** | `?lineId=9`（图片分支 25 键） vs `?lineId=5`（聚合分支 22 键） | 前端两个图表渲染成空图；**导出产出只有表头没有数据行的 Excel** | 聚合分支复用 `imageData` 已算好的 3 块（走到该分支的前提是「图片表无数据」，此时图片表热力图本就必为空 → 键集一致且语义正确，零新 SQL） | ✅ 两分支均 25 键，3 键齐全 |
| **B-7** | 不存在的班次 ID 被**静默忽略** → 返回**全量数据**（而 `lineId`/`cameraId` 传不存在值是返回空集，行为不一致） | `?shiftId=99999` → total=全量 | 用户以为在看某班次，实际看到全部班次 | `resolveShift` 查不到 → 抛 `IllegalArgumentException` → 400「班次不存在」；SQL 异常仍按原样吞（那是服务端故障，不该伪装成"班次不存在"） | ✅ 400；合法 `shiftId=1` 不受影响 |
| **P0-2**（日报） | **导出端点必然 500**：导出「本月」（含今天）→ 实时行漏了 `decorate` → 无 `reportDate` → `sort` 时 NPE。**前端导出按钮 100% 不可用** | `GET /daily-reports/export?startDate=2026-11-01&endDate=2026-11-30` | 日报导出功能完全不可用 | 实时行也走 `decorate`；`compareDateDesc` 补 null 防御 | ✅ HTTP 200、9053B、文件头 `PK`（合法 xlsx） |
| **P0-1**（日报） | 列表端点返回**厂级行 + 产线行并存**（每天 6 行）→ 下游 SUM **翻倍**；且快照部分返回 6 行、实时部分只返回 1 行，**同端点内行数不一致** | `GET /daily-reports?startDate=...` → 每天 6 行，`lineId` 混 0 与具体值 | PRD D1 定的口径是「每天一行（厂级汇总）」；任何 SUM 的下游报表都会翻倍 | 统一：`lineId` 为 null → 只返回厂级行；传了 → 只返回该产线行 | ✅ 10 天 × 每天 1 行、`lineId` 全为 0 |

## 三、核实为「设计如此 / 非缺陷」的项（避免误判）

| 项 | 结论 |
|---|---|
| 跨产线工位/相机筛选冲突 | **正确**：8 组冲突组合全部返回**空集**，无报错、无越界数据 |
| `lineIds`/`workstationIds` 多选 | **正确**：并集正确（`9,10` = 15328 = 14512+816）、非法 token 忽略、去重、超 50 截断 |
| `lineId=5`（ZK23）返回 0 | **数据实况**：ZK23 两台相机 11-16 停产 → 该产线今天无图；停产前查询正常返回 6426 张 |
| 图片通道 `okCount=0`/`yieldRate=null` | **设计如此**：只上报缺陷图、无良品样本（PRD 有说明） |
| `dailyCalendar` 固定 30 天窗口 | **设计如此**：日历用途是看节律与停线空档 |
| `severity` 小写值 | **正确归一化**为 HIGH |
| `HTTP 400 + body.code=500` | **项目既有约定**（`ResultVO.fail` 固定 code=500），前端按 HTTP 状态码判断并读 `message` → 不改 |
| 列表端点不支持分页 | 设计如此（返回全量聚合块），建议在接口文档标注「不支持分页」 |
| `metadata` 产线集合 vs 逐产线求和 | **一致**（[3,5,9,10,11,12] 求和 = 基线） |

## 五、测试脚本自身的两处缺陷（已修，避免误报）

| 脚本 | 问题 | 修法 |
|---|---|---|
| `verify_daily_report_browser.cjs` | ① 切产线后**固定 sleep 4s** 就读 KPI → 接口慢时读到**切换前的旧值** → 误判「lineId 没透传」<br>② 点**最早**的有数据格（11-03）—— 那天**只有 ZK23 在上传**，全厂与 ZK23 的在线相机/检测数/缺陷数**全部相同** → 断言必然失败 | ① 改为**轮询**等待值变化；② 改为**多指标任一变化**即算透传，并点**最近**的有数据格 |
| `verify_line_multi_browser.cjs` | 硬编码「ZK09 当日 ~311 张」→ 现场数据随时间增长（当日已 1741 张）→ 断言必然假红 | 改为测**用例本意**（竞态守卫）：先测稳定单选 ZK09 的值 → 快速切 2 轮 → 断言两者**相等**，无硬编码数字 |
| `verify_stats_modules_full.cjs`（新增） | 首次编写时误判 6 项失败（时序不足、字段名取错、`ResultVO<?>` 结构差异、折叠菜单影响） | 全部为脚本自身问题：改朴素轮询、兼容两种 KPI 结构、metadata 取 `positions`、导航检查不受折叠影响 |

## 七、仍需后续排期（未在本轮修）

| 项 | 原因 |
|---|---|
| `defectTypeId` 真正生效 | 需先做「标准类型编码（P0_*）→ 现场中文类型名」的映射表（现场 15 个标准类型与实际上报类型**完全不相交**） |
| `severity` 作用于 KPI/趋势/排行 | 需改 Repository 的 6 处查询 SQL（当前只有 3 个块带 `sevWhere`） |
| `hourlyHeatmap` LIMIT 360 截断（静默丢 37/397 格） | 需改分页策略并在响应里回传 `truncated` / `totalCombos` |
| `shiftCompare` LIMIT 12 截断（合计比 KPI 少 2660） | 同上；班次对比是「对比」场景，截断破坏完整性 |
| `breakdown` 支持工位/相机/缺陷类型筛选 | 需改 `DailyReportRepository.computeBreakdownDetails` 的 SQL |
| 列表端点 P95 774ms（PRD 目标 500ms） | 需加索引或缓存 |
| `factory`/`position` 维度拆分 | 需三处同步（`resolveDimSplit` / `DIM_NAME` / `wizardDimOptions`） |
