# 备份与清理链路评审与优化方案（2026-11-07）

> 范围：数据库备份、缺陷图片归档与磁盘清理、测试相机清理、磁盘水位巡检、兼容表与聚合数据清理。
> 方法：逐脚本 / 逐任务读源码取证据，不改口径、不引入新框架；方案全部可落地。

---

## 0. 核心结论

1. **时间轴设计良好**：01:00 备份 → 02:00 通用清理 → 02:30 图片归档 → 03:30 磁盘清理，错峰且"备份先于清理"的顺序正确；测试相机清理每小时独立运行、三道防线完备。**主干不需要重构。**
2. **最危险的不是缺流程，而是流程之间口径打架**：`install.sh` 写入的磁盘清理 cron 是 **KEEP_DAYS=7**，而图片归档月表按 **730 天**保留 —— 一旦用安装脚本重装/新装，会出现"库里有记录、磁盘没文件"的大面积裂图，直接击穿「库里有记录就必须有文件」的核心不变量。
3. **备份是"静默单点"**：备份失败/跳过只进 journal，不写 `fact_anomaly_alert`（清理脚本会写，备份不写）——本项目最典型的故障形态恰是"服务活着、业务全错、无人知晓"，备份停摆数月不会有人发现。
4. **`DataCleanupTask` 是链路里可靠性最弱的 Java 环节**：三步清理绑在一个事务里，且"先删磁盘文件、后删库记录"，异常回滚后文件无法恢复。

## 1. 全景：每日时间轴

```
01:00  systemd timer   backup-database.sh        数据库全量备份（mysqldump+zstd，保 14 天）
02:00  Spring @Scheduled DataCleanupTask      camera_images(30d) + 30min聚合归档(3mo) + 操作日志(6mo)
02:30  Spring @Scheduled DefectImageArchiveTask  defect_image_* >31天 → 月表；月表 >730天 DROP
每小时:15  cron  cleanup-zk54-incremental.sh   TEST相机数据清理（库+磁盘，三道防线）
每小时≤1次 随5min刷新  purgeOrphanAggregationRows  孤儿聚合行清理（节流）
05min  Spring refreshRecentDailyAggregation    近3天日聚合刷新（数据新鲜度，非清理）
*/30   cron  check-disk-usage.sh               / /var /data 水位巡检
03:30  cron  cleanup-defect-images.sh          磁盘日期目录整删（730天）+ camera_images(30d)
每5s   Spring ServerMetrics                    磁盘/CPU 指标采样（前端展示用）
```

## 3. 依赖关系与耦合点

1. **口径耦合（最重要）**：磁盘文件保留天数（C2 `KEEP_DAYS`）↔ 月表保留天数（C1 `app.archive.images.retain-days`）必须同为 730，否则「库里有记录必须有文件」不成立。目前两者靠**约定**对齐，没有任何校验；install.sh 甚至把它配成了 7。
2. **配置源耦合**：B1/C2/C3 的口令与参数都应来自 `/etc/default/camera-detection`（640 root:root）。C3 已改造为脚本自读；**C2 的 cron 行仍把 MYSQL_PASSWORD 明文写进全局可读的 cron 文件**。
3. **重复写者**：`camera_images` 表有**三个**清理方（C4 每日 02:00、C2 每日 03:30、C3 每小时）。口径都是 30 天，暂无冲突，但改任何一处口径都要同步三处。
4. **顺序依赖**：01:00 备份 → 02:00/02:30/03:30 清理，保证"备份的是清理前的完整状态"。C1 与 C2 按同一 730 天口径分别管库和盘，互不感知。
5. **水位依赖链**：C6 只告警不动作；C7 让备份在 /data >85% 时自弃；C2/C3 删除是唯一的水位下降手段 —— 磁盘告警后的实际处置完全依赖人工。

## 4. 风险清单

### High

| # | 风险 | 证据 | 后果 |
|---|---|---|---|
| H1 | install.sh 写入的 cron `KEEP_DAYS=7`，与脚本默认/月表归档的 730 天矛盾 | install.sh:428,430（"保留 7 天"）vs cleanup-defect-images.sh:15-17,55 | 用安装脚本重装/新装后，7 天前的图片文件被删，而月表保留 730 天 → 大面积裂图；历史数据"看起来在库里、点开没图" |
| H2 | 明文 MYSQL_PASSWORD 写入 `/etc/cron.d/cleanup-defect-images`（全局可读） | install.sh:428 | 违反本项目"口令不入 cron"铁律（8a-2 节为 C3 专门修过，C2 漏网）；本地任意用户可读库口令 |

### 不建议做的事

- **不重排时间轴**：01:00→02:00→02:30→03:30 的错峰与"先备份后清理"顺序是正确设计，不要为"合并脚本"破坏。
- **不给 cleanup-zk54 再加功能**：它的三道防线、flock、幂等、自检是全链路最完善的，改动风险大于收益。
- **不引入专业备份工具（xtrabackup 等）**：2.6GB 库 + 每日全量 60s 的体量，mysqldump 完全够用；引入新组件的运维成本不划算。等库到 50GB 量级再评估。
