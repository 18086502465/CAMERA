## 0. 一页纸结论

| 问 | 答 |
|---|---|
| 服务器抗不住了吗？ | **不是**。load 0.13（8 核）、java RSS 1.53G/15G、`/main` 用 4%、MySQL buffer pool 4G 且 Threads_connected=7。资源全线空闲。 |
| 慢在哪？ | **后端一次统计汇总要跑 69 次 SQL**，其中 10+ 次是 100–190ms 的 6 万行 JOIN+分组；独立图表再各跑一整轮。日报是 6 个接口累计 ~1.4s。 |
| 为什么缓存没救住？ | 缓存 key 含 `endTime` **精确到秒**，而前端默认 `endTime = 当前秒` → 每次进页面 key 都不同，**60 秒 TTL 形同虚设**。实测不同秒请求 0.62/0.71/0.65/0.69s，同 key 命中 0.03–0.12s。 |
| 有没有隐藏负载？ | 有：心跳每次 `saveCameraStatus()` 都做 **9 次 INFORMATION_SCHEMA 列检查**，12.7 小时累计 **298 万次**；`camera_status` 全字段 UPDATE 22.4 万次 × 5.2ms。与页面争抢 DB 连接/CPU。 |
| 加索引能解决吗？ | **不能**。EXPLAIN 实测：近 7 天范围优化器选全表扫描（正确），`FORCE INDEX` 后反而 317ms > 200ms（回表 6 万次）。瓶颈是行数×JOIN×分组，不是索引缺失。 |
| 先做什么？ | **P0-1 缓存键归一化到分钟 + 首屏预热**、**P0-2 日报两个端点加 30s 短缓存**、**P1-1 心跳元数据检查改为启动一次**。预计首屏 0.7s→0.1s，改近 7 天 3.6s→0.1s。 |

## 3. 根因分析

### R1 ★ 缓存键秒级精度 → 刷新必然穿透（主因）

- 后端 `LineAnalyticsController.summaryCacheKey()` 把 `start`/`end` 用 `DT`（秒级）格式化进 key；TTL 60s、最大 64 条。
- 前端 `defaultRange()` 的 `endTime = formatDate(now)` **精确到秒**，每次进页面都变。
- 结果：同一用户刷新页面 = 新 key = 3 个请求各自重跑 69 次 SQL；TTL 只救住在页面内 30s 轮询（此时 `timeRange` 不变）。
- 证据：不同秒 endTime 四次均 0.62–0.71s；固定 key 二次 0.03–0.12s。

### R2 ★ 一次汇总 69 次 SQL，独立 widget 再各跑整轮

- 源码注释明示「一次 `/line-summary` 要打 69 次 Repository 聚合查询」。
- 内置看板 7 个 widget 中，`defectTrend(dim=line)`、`defectRanking(dim=line)` 因带拆分维走**独立请求**（`loadWidgetData` → `Promise.all`），每个独立请求又跑完整 69 次。
- 首屏共 **3 × 69 ≈ 207 次**聚合查询；其中 10+ 次是 100–190ms 的重查询。
- 这类重查询大多重复扫描同一批 6 万行图片，只是 GROUP BY 维度不同。

### R3 单条重 SQL 的固有成本：6 万行 JOIN + filesort

- `defect_image_file` 只有 6.7 万行，但每条重 SQL 都做：时间过滤 → `LEFT JOIN dim_camera`（61,068 次索引查找）→ `GROUP BY DATE_FORMAT/HOUR/defect_type` → `filesort` → `LIMIT`。
- `COUNT(DISTINCT ...)`、`COUNT(DISTINCT b.image_id)` 额外建临时表。
- `FORCE INDEX` 实测更慢（317ms vs 200ms），已排除索引方案。

### R4 心跳热路径抢占 DB（间接但持续）

- `CameraStatusServiceImpl.saveCameraStatus()` **每次心跳**调用 `ensureCameraStatusColumns()`，内含 **9 次** `INFORMATION_SCHEMA.COLUMNS` 检查（8 列 + 1 个 dim_camera 列）。
- 现场心跳频率约 7 次/秒 → 约 65 次元数据查询/秒 → 12.7 小时 298 万次。
- 同时 `camera_status` 每次心跳全字段 UPDATE（22.4 万次 × 5.2ms），产生 binlog 与行锁开销。
- `@PostConstruct initSchema()` 已在启动时做过同样的 9 次检查，**运行期重复属于冗余**。

### R5 日报没有缓存，6 个接口累计

- 日报首屏依次请求 `cascade/all`、`cameras/options`、`defect-images/filter-options`、`metadata`、`calendar`、`breakdown`，实测累计约 **1.4s**（串行口径）。
- `calendar` / `breakdown` 都是 0.39–0.46s 且**无缓存**；这两端点是日终物化 + 当天实时差分，短缓存语义安全。

## 4. 优化方案（按优先级）

| 级别 | 措施 | 预期收益 | 风险 | 改动范围 |
|---|---|---|---|---|
| **P0-1** | `summaryCacheKey` 的 `endTime` **向下取整到分钟**（`truncatedTo(TimeUnit.MINUTES)`）；前端 `formatDate` 同步去掉秒。TTL 60s 语义不变，最多多 60s 延迟，与现有缓存承诺一致。 | 刷新/首屏命中缓存：**3.6s/4.0s → 0.1s** | 极低（仅缓存键） | `LineAnalyticsController.java` + `LineAnalyticsView.vue` |
| **P0-2** | 后台定时预热默认看板三个 key（今天全厂 global / dim=line / dim=defectType），每 30–60s 一次；前端首屏直接命中。 | 首次打开不再穿透 | 低（后台只读） | `LineAnalyticsController` 现有 `@Scheduled` 链 |
| **P0-3** | 日报 `calendar`（按 month+lineId）与 `breakdown`（按 date+lineId+明细筛选）加 **30s TtlCache**（复用现有 `TtlCache` 实现，不引新依赖）。 | 日报 0.8s → 0.05s | 低（实时段最多延迟 30s） | `DailyReportController.java` |
| **P1-1** | `saveCameraStatus()` 去掉运行期 `ensureCameraStatusColumns()`，只保留 `@PostConstruct` 启动自检；保留 Repository 层 `ensure*` 幂等语义不删。 | 减少 298 万次/12.7h 元数据查询 | 低（现场单实例，DDL 已存在；多实例部署需评估） | `CameraStatusServiceImpl.java` |
| **P1-2** | 心跳 `camera_status` 改为**按变化字段更新**或降频写快照（心跳历史已有独立节流表）。 | 减少 22 万次全字段 UPDATE + binlog | 中（需保持 `product_name` 等快照语义） | `CameraStatusServiceImpl` + Repository |
| **P1-3** | 两个独立 widget 共用一次后端响应：后端对 `dim=line` 同时返回趋势+排行所需数据，或前端对 global 响应**本地按产线拆分**画趋势与排行。 | 首屏请求 3 → 1，SQL 207 → 69 | 中（口径必须逐项对齐） | 前后端联合 |
| **P2-1** | 建统计专用**物化汇总表**（5/15 分钟粒度，按 line/camera/defectType/shift 预聚合），统计页读汇总表；图片事实表保留为明细与对账源。 | 单条扫描 6 万行 → 数百行，重 SQL 100ms → <5ms | 高（口径、刷新任务、对账、存储都要设计） | 立项改造 |
| **P2-2** | 前端 ECharts 渲染优化：热力图 422 格降采样、日历 30 天按需渲染、图表 dispose 复用。 | 降低前端主线程阻塞 | 中 | `LineAnalyticsView.vue` |

**明确不做（已实测排除）**：

1. 给 `capture_time` 加/强制索引 —— EXPLAIN ANALYZE 证明更慢。
2. 调大 JVM 堆或 MySQL buffer pool —— 资源本来就空闲。
3. 改统计口径换速度 —— 「图片事实表优先、无数据≠0、截断上报」是项目铁律。
4. 开 `slow_query_log` 长期记录 —— 需改生产配置，本次只读诊断不动。
