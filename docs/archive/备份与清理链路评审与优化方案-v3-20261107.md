## 0 结论

**备份链路「能跑」，清理链路「能删」，两条链路之间没有一致性契约。**

当前系统距一次**不可逆的批量裂图**还有 26 天（2026-12-03）。这不是概率风险，是已写死在代码里的确定性缺陷：`DataCleanupTask` 在 30 天删除物理文件，`DefectImageArchiveTask` 要求记录保留 730 天，而两张表 100% 指向同一批文件。

| # | 风险 | 触发条件 | 优先级 |
|---|---|---|---|
| 1 | **30 天删文件 × 730 天留记录 → 批量裂图** | 2026-12-03 02:00（无需任何操作） | **P0** |
| 2 | **数据库 root 活口令明文在 `/etc/cron.d/*.bak`，644 全局可读** | 已发生：`nobody` 可读实证 | **P0** |
| 3 | 图片文件零备份（`backup/db/images/` 是空目录） | 任意时刻单盘故障 = 全部图片丢失 | **P0** |
| 4 | 无恢复脚本、从未演练；备份「是否可恢复」无任何验证 | 真出事时才暴露 | **P0** |
| 5 | 「异机备份」实为同盘 `rsync --delete`，源被清则副本同清 | 误操作 / 脚本 bug | P1 |

## 3 本轮新增发现

### N1 ★★★ 30 天删文件与 730 天留记录冲突 —— 2026-12-03 起批量裂图

**实证**：

```sql
SELECT COUNT(*) FROM camera_images;                                   -- 9696
SELECT COUNT(*) FROM camera_images c JOIN defect_image_file f
       ON f.image_path = c.image_path;                                -- 9696（100% 重叠）
```

`camera_images` 与 `defect_image_file` 的 `image_path` **逐行完全相同**，指向同一批 `.jpg`。

**冲突链**：

| 时刻 | 动作 | 代码位置 |
|---|---|---|
| T+30 天 | `camera_images` 行删除后 `file.delete()` 删掉物理文件 | `DataCleanupTask:129-136` |
| T+31 天 | `defect_image_file` 行搬进月表，**记录保留** | `DefectImageArchiveTask` |
| T+730 天 | 月表 DROP + 磁盘目录删除 | 归档任务 / `cleanup-defect-images.sh` |

即：**文件在 30 天时就没了，记录要留到 730 天。** 30~730 天之间的每一条历史记录都指向一个不存在的文件，页面查看、导出、追溯全部 404。

**为什么现在还没爆**：最早数据是 2026-11-03 15:00，不到 30 天，`capture_time <= 2026-10-08` 匹配 0 行。**12-03 起每天约 2000 张开始失效**，两年累计约 130 万条。

**为什么这是个"新鲜"的炸弹**：`cleanup-defect-images.sh` 在 2026-11-05 已经被改成「只管磁盘、不删库记录」，但同一处逻辑在 Java 侧没有同步 —— 修复只做了半边。更关键的是，**今天 10:16 部署的新包是第一个带日志的版本，也是这个任务第一次可被观测**；没有任何人验证过它删文件的行为。

### N2 ★★★ 数据库 root 活口令明文存在于全局可读文件

```
/etc/cron.d/cleanup-defect-images.bak-20261105   644 root:root
/etc/cron.d/cleanup-defect-images.bak-20261107   644 root:root
  30 3 * * * root MYSQL_PASSWORD="<当前有效口令>" DIR=... cleanup-defect-images.sh
```

- 两个 `.bak` 文件都是历史改造时留下的副本，**内容是改造前的旧 cron 行**；
- 文件里的口令与 `/etc/default/camera-detection` 中当前的 `MYSQL_PASSWORD` **完全一致**（活口令）；
- `sudo -u nobody cat` **成功** —— 任意本地用户可直接读取数据库 root 口令；
- 文件名含 `.` 所以被 Debian cron 忽略（不会重复执行），但**权限与可读性不受此保护**；
- `verify.sh` 的「cron 无明文口令」只检查 `cleanup-defect-images` 单文件，**扫不到 `.bak`**。

这是「口令收敛」改造自身的残留物 —— 改造时把新文件写对了，旧文件没删。

复核：`grep -rl "$MYSQL_PASSWORD" /etc /opt/camera-detection-system /usr/local/bin /root` → 仅剩 `/etc/default/camera-detection`（640 root:root，预期位置）。

### N3 ★★ 图片文件零备份

- `backup-database.sh:150` 创建 `${BACKUP_DIR}/images`，**之后没有任何一行代码向它写入**；
- `offsite/` 只有 `full` 和 `binlog`；
- 也就是说：`/data` 这块盘坏掉，数据库可以恢复到 14 天内的任意时刻，**但 9763 张图片一张都回不来**。

容量测算（按当前 2 相机 ≈ 2000 张/天、124KB/张）：30 天 ≈ 7.5GB，730 天 ≈ 175GB。全量备份不现实，但「热窗口 30 天 + 异机」完全可行，且恰好覆盖「最近一个月业务追溯」这个真实需求。

### N4 ★★ 恢复能力从未被验证

- 仓库内**没有任何 restore 脚本**（`find -name "*restore*"` 为空）；
- `verify.sh` 30 项检查里**没有一项与备份相关**（只有「保留期口径」和「cron 无明文口令」两条间接项）；
- 备份只做了 `zstd -t`（压缩流完整性），**不验证 SQL 能否导入**；
- 至今唯一一次恢复演练是人工 `ZZTEST_restore`（binlog 里 09:06 的两次 DROP 就是它）。

「备份文件存在」和「备份能恢复」之间隔着一次真实演练，而这次演练从未进入交付清单。

### N5 ★★ 「异机备份」是同盘镜像，且 `--delete` 会同步删除

`offsite` 与 `full` 的 `df --output=target` 都是 `/data`（`/dev/mapper/vg0-data`）。日志却写「已同步到**异机**目录」—— 措辞与事实不符，容易让人产生错误的安全感。

更实际的问题是 `rsync -a --delete`：若 `db/full` 被误清空（脚本 bug、误 `rm`、磁盘错误），下一次 01:04 的 rsync 会把 `offsite/full` **一起清空**。副本不具备独立性。

### N6 ★ 清理任务无心跳，执行与否不可证

`journalctl` 中 `DataCleanupTask` **零条记录**，`scheduling-1` 线程只在 02:30 出现（归档任务）。旧 JAR 备份（`.bak-20261107_081349`）里的 `DataCleanupTask.class` 不含任何日志字符串，所以：

> 既不能证明它执行过，也不能证明它没执行过。

这不是「没日志」这么简单 —— 对 `camera_images` 的 30 天清理、`fact_production_30min` 的 3 月归档、`sys_operation_log` 的 6 月清理这三件事，**系统当前没有任何手段回答"上次成功是什么时候"**。今晚 02:00 是第一个可观测版本。

（附：`sys_operation_log` 现存 573 行，`operation_time` 全部落在今天 09:03 之后；`data_free=34.6MB` 证明历史上发生过大规模删除。删除动作未进 binlog，仍无法归因 —— 详见 v2 §D5，本轮复核结论未变。）

### N7 ★ 清理判据缺索引

`camera_images` 索引：`PRIMARY(id)`、`idx_camera_name`、`idx_upload_time`、`idx_bucket`。**`capture_time` 无索引**，而两处清理都用它：

- `DataCleanupTask`：`WHERE capture_time <= ? LIMIT 1000` 分批循环 → 每批一次全表扫，N 批 = N 次全表扫；
- `cleanup-defect-images.sh`：`DELETE FROM camera_images WHERE capture_time < ?` → 全表扫 + 长事务。

`defect_image_file` 侧用 `COALESCE(capture_time, upload_time, create_time)` 作判据，同样无法走索引；目前靠 `ORDER BY image_id LIMIT 5000` 沿主键提前收敛，量级上去后会退化为全表扫。

### N8 ★ 磁盘水位告警绕过了告警页

`check-disk-usage.sh` 只写 `logger`（journal）+ `/var/log/camera-detection-disk-alert.log`。它**不写 `fact_anomaly_alert`** —— 磁盘水位是唯一能提前数小时预警「服务活着但业务全错」的信号，却恰恰是唯一不进告警页的信号。

### N9 ★ 两条清理日志未纳入轮转

`/etc/logrotate.d/camera-detection` 只覆盖 `${WORK_DIR}/logs/*.log`。

| 日志 | 现状 |
|---|---|
| `/var/log/camera-detection-cleanup.log` | 3.9KB，**未轮转** |
| `/data/camera-detection/backup/cleanup_zk54.log` | 17KB，**未轮转**（每小时追加） |

`cleanup_zk54.log` 每小时 1 次、每次多行，是这两者里唯一会持续增长的（约 300KB/月），长期不轮转会缓慢吃掉 `/data` —— 而 `/data` 正是被水位监控的那块盘，形成闭环噪声。

### N10 月表 DROP 与目录删除的口径差（仅浪费空间，不裂图）

- 月表：`month < monthOf(now - 730d)` → 整月表 DROP，边界在「月」；
- 磁盘：目录名 `< yyyyMMdd(now - 730d)` → 边界在「日」。

结果：某月表被 DROP 后，该月 730 天边界之后的目录仍会多留最多 30 天。方向是「库无记录、磁盘有文件」—— 只浪费空间，不会裂图。可接受，记录在案即可。

### N11 陈旧注释与权限细节

| 位置 | 现状 | 影响 |
|---|---|---|
| `camera-detection-backup.service:22` | 「按 2.6GB 库约 60s 估算」 | 实测库 43MB / 1~2s，注释误导容量规划 |
| `backup-database.sh:242` | 注释已承认 offsite 同盘 | 但日志输出仍是「异机目录」 |
| `db/full/*.sql.zst` | `644`，靠父目录 `700` 挡住 | 可用，但不该依赖父目录 |
| `TimeoutStartSec=1800` | 30 分钟 | 与 02:00 清理任务无冲突（实测 1~2s），但无显式互斥 |

## 5 优化方案

### P0 —— 本周内（做完才算「不会丢数据」）

#### P0-1 拆掉 30 天删物理文件（H1）

**做法**（推荐 A）：

| 方案 | 改动 | 代价 | 判断 |
|---|---|---|---|
| **A. Java 侧不再删文件** | 删掉 `DataCleanupTask:129-136` 的文件删除循环，只删行 | 1 行区块，最小 | **推荐**：730 天磁盘脚本成为文件生命周期的唯一 owner，与归档口径天然一致 |
| B. 删前检查引用 | 删文件前 `SELECT 1 FROM defect_image_file WHERE image_path=?` | 每文件一次查询 | 保留"及时回收"能力，但把耦合做进了热路径 |
| C. `camera_images` 不再删行 | 取消 30 天策略，与 `defect_image_file` 同步 730 天 | 兼容表体积涨 | 若兼容表已无读方，可直接 DROP 整表 |

**验收**：构造 31 天前的 `ZZTEST` 图片 + 两表各一行 → 跑任务 → 断言「行已删、文件仍在」→ 断言 `defect_image_file` 记录仍可反查到文件。

**回归**：`AnomalyAlertDedupTest` 同类 H2 测试 + 一次现场 `--dry-run` 对照。

#### P0-2 清除 cron 目录内的口令残留（H2）—— ✅ 已执行

**做法**：
1. `rm /etc/cron.d/cleanup-defect-images.bak-20261105`、`.bak-20261107`（cron 本就不读，删除零风险）；
2. `verify.sh` 的「cron 无明文口令」从单文件改为**遍历 `/etc/cron.d/` 全目录**（含隐藏与 `.bak`），命中即 fail；

### 9.5 容量预测告警（2026-11-07 13:20 上线）

决策「保留 730 天、后期扩盘」需要一个可执行的**扩容触发信号**。原有的 85% 水位线不够：

- 百分比只说「现在多满」，不说「还有多少天」；
- 扩盘要走采购/停机流程，需要半年以上提前量；
- 相机数量增长时日增会成倍上升，85% 可能在数月内突然到达。

新增第 3 类检查（`check-disk-usage.sh`）：按 **REAL 相机近 7 天实际日增**推算 `/data` 剩余可写天数，低于 `CAPACITY_WARN_DAYS`（默认 180 天）写 `DISK_CAPACITY_LOW` 告警。

**必须排除 TEST 相机**：TEST 数据每小时被整目录回收，不累积。把它算进日增会把结论放大一个数量级 —— 本轮实测同一份数据：含 TEST 是 780MB/天（推得「必须扩盘」），只算 REAL 是 **67MB/天**（推得「剩余 7399 天」）。前者是错的。

配套改动：

| 文件 | 改动 |
|---|---|
| `check-disk-usage.sh` | 新增第 3 段容量预测；修复 `alert_once()` 去重缺陷（见下） |
| `FactAnomalyAlertController` | `OPS_ALERT_TYPES` 增加 `DISK_CAPACITY_LOW`，否则会被当业务告警沉底 |

**同时修掉一个真实缺陷**：`alert_once()` 原用 `UPDATE ...` 后读 `ROW_COUNT()` 判断是否命中，但 MySQL 的 `ROW_COUNT()` 返回「实际被修改的行数」而非「匹配的行数」。同一秒内重复执行时 `update_time=NOW()` 与原值相同 → 返回 0 → 又插一条。实测连跑两次得到 2 条。改为先 `SELECT alert_id` 再精确 `UPDATE`，与「值是否变化」解耦。修复后连跑 3 次恒为 1 条。
