## 0. 一页纸结论（给厂长）

**一句话判断：这两个模块已从「质量缺陷统计工具」迈出第一步，但尚未成为「支撑经营决策的管理驾驶舱」。** 差距的本质是**数据源缺口**，不是界面或口径的问题。

**本次已补齐的（P0+P1，代码完成、待部署）**
- 日报会**对比**了：月历每格显示缺陷框环比箭头（升红/降绿、无基线留空）、最佳/最差角标、footer 双极值。`[已实施 P0-1]`

**仍然回答不了的（数据层为空，非 UI 问题）**

**三项最高性价比动作**
1. `[已实施]` 把「已有数据未用」的环比、最佳日、五类告警、心跳累计数全部上屏——零数据造假，一个前端版本交付。

## 1. 评审框架与判定标准

从厂长视角，用六把尺子量一个统计模块是否「支撑管理与经营决策」：

| 维度 | 厂长的真实问题 | 本文判定口径 |
|---|---|---|
| 统计口径 | 这个数能不能信、怎么算的 | 口径是否单一、稳定、可解释、无隐藏假设 |
| 指标覆盖 | 我要看的数在不在这个页面 | 是否覆盖 产量/良率/节拍/停机/设备/人员/物料/交期/异常/对比 十大主题 |
| 筛选查询 | 我能不能快速定位到出问题的那条线/班/人 | 维度是否够、组合是否生效、悬空是否清理 |
| 数据对比 | 是变好还是变坏、比谁差 | 是否有环比/同比/目标/横向/趋势对比 |
| 图表呈现 | 我三秒能不能看懂重点 | 图表是否结论优先、是否有信息量、是否诚实标注截断 |
| 日报可读性 | 我早上 5 分钟能不能把厂巡完 | 是否有结论、有优先级、有可读性、有行动指向 |

评级符号：`[优]` 可直接支撑决策｜`[中]` 部分支撑、需人工补信息｜`[弱]` 形式具备但决策价值低｜`[缺]` 无数据/无功能。

## 2. 数据基础矩阵（决定能力天花板）

> 核心结论：**统计口径的问题，八成是数据源的问题。** 本表决定哪些优化「马上能做」、哪些「必须先补采集」。

| 经营主题 | 数据基础 | 数据载体 / 证据 | 本次优化后状态 |
|---|---|---|---|
| 产量 / 检测量 | `[中]` 有 | 心跳累计 `recognize_count`→`total_count`；图片通道 `defect_image_file` 行数；`fact_production_*` 表存在但现场主通道未用 | 只能得「检测总量/图片数」，**无合格产出数**；未改 |
| 合格品 / 不良品 | `[中]` 有但语义存疑 | 心跳 `correctCount`→`ok_count`、`abnormalCount`→`ng_count`（`CameraStatusServiceImpl.saveCameraStatus`） | 累计数已采集；`okTotalCum` 本次首次启用（P1-2），语义仍待现场校准 |
| 良率 | `[弱]` | 图片通道无良品样本 → `yieldRate=null`；日报用心跳差分 `counterRateKilo`（NG/检测），非合格/总产出 | 新增「心跳口径直通率」并标注待校准，**未冒充终检良率** |
| 缺陷类型 / 严重度 / 缺陷框 | `[优]` 有 | `defect_image_box.defect_type/severity`、`defect_image_file.*_count` | 完整支撑缺陷分析（当前强项） |
| 缺陷位置 | `[缺]` | `metadata` 明确 `position.supported=false`；x/y/width/area 实测全 0 | 无法做位置热力；未改 |
| 时间趋势（时/日/日历/热力） | `[优]` 有 | `defect_image_file.capture_time` | 完整支撑 |
| 设备状态 / 温度 / CPU / 内存 | `[中]` → `[中+]` | `camera_status.status/temperature/cpu_usage/memory_usage` 快照 | **P1-1 已开启** `fact_camera_heartbeat` 节流写入（1 分钟/台），新增 24h 趋势查询端点 |
| 告警 / 异常 | `[中]` → `[优]` | `fact_anomaly_alert` 五类告警 | **P0-4 已扩**为五类按日聚合 + 7 日趋势；此前日报只用温度一类 |
| 停机 / 开机 / 运行时长 / OEE | `[缺]` | 全仓库无 downtime/uptime/running 时长列 | 只能靠「0 上传小时」代理，会误判停线 vs 没排产 |
| 节拍 / cycle time / 产出间隔 | `[缺]` | 全仓库无相关字段 | 完全无法 |
| 人员 / 班组 / 工号 / 操作员 | `[缺]` | 无人员维表；只有 `shift`（班次时间段）和登录账号 | 无法责任到人（只能到相机/工位） |
| 物料批次 / BOM / 物料号 | `[缺]` | 无；`materialJoint` 是缺陷项、`batch_no` 是图片上传批次，均非物料 | 无法做物料追溯 |
| 工单 / 订单号 / 交期 | `[缺]` | 全仓库无 | 无法做交付/延误预警 |
| 同比（去年同期） | `[缺]` | 无历史年数据（现场数据自 2026 年起） | 物理上算不了 |
| 环比（日/时段） | `[中]` 有 | `dayOverDayRate`、`appendWindowCompare`、`bestDate` | **P0-1 已上屏**；产线统计侧早已有 KPI 小字环比 |

**矩阵解读**：绿色区（缺陷域）已做到优秀；黄色区（产量/设备/良率）有原始计数但缺校准/历史，本次补了设备历史与直通率口径；红色区（停机/节拍/人员/物料/交期/同比）仍是**数据真空**，再漂亮的 UI 也变不出数。

## 3. 产线统计模块评审

### 3.1 统计口径 `[中]`

**优点（必须保留）**
- 数据源优先级「图片事实表优先、聚合表兜底」，响应带 `dataSource`，避免被 `agg_*` 孤儿行骗出「筛选后比不筛选还多」。`[证据] LineAnalyticsController.buildPlantOverview/summary；PRD STAT-03`
- 诚实降级：产品筛选物理不支持时回传 `ignoredFilters`；无数据时 `yieldRate=null` + `yieldRateAvailable=false`，显示「—」绝不显示 0%/100%。`[证据] LineAnalyticsView.vue 卡片渲染；PRD STAT-08/09`
- 图片通道下主动隐藏 5 个无意义指标（quality/defectPivot/severityDistribution/stackDefectBySeverity/mappingExceptions）并注明原因。`[证据] LineAnalyticsView.vue widget 可见性判断`

**残留缺口**
1. **口径分裂、说明书藏在代码里**：同一页面并存两套 KPI（聚合通道 6 项 vs 图片通道 5 项），切换靠 `isDefectImageSource` 隐式判断，页面只在卡片小字解释。厂长看到「检测总数」在两种数据源下含义不同（一批次累计 vs 每图均含缺陷），**容易误读为数据打架**。`[证据] LineAnalyticsView.vue KPI 定义区`
2. **「缺陷率」名不副实**：图片通道每张图必带缺陷框，缺陷率恒 1000‰，无区分度；真正用心跳差分的是 `counterRateKilo`，目前仅在日报可用，产线统计主视图仍无可比质量率指标。`[状态] P1-2 直通率已在日报上屏，产线统计未同步——见 G18`
3. **良率字段语义未锁定**：心跳 `correctCount` 落 `ok_count`，但现场「识别正确」是否等于「合格品」未经校准；PRD 因此把它列入不做。在语义确认前，贸然展示「良率」会违背「数字不骗人」原则。`[状态] P1-2 以「心跳口径·待校准」名义提供，边界不变`

### 3.2 指标覆盖 `[中]`

内置「工厂质量看板（默认）」7 个 widget：`工厂总览 → 缺陷量趋势(按产线) → 产线缺陷排行 → 责任相机定位 → 缺陷类型帕累托 → 时段×类型热力 → 缺陷日历`。

- **覆盖好的**：缺陷量、缺陷趋势、产线/相机/工位责任定位、缺陷类型帕累托、时段热力、日历——「找缺陷热点」的闭环成立，逻辑顺序「总览→趋势→谁最差→什么缺陷→什么时段」是结论优先的正确设计。
- **完全缺失的经营指标**：产量达成、良率、节拍、停机时长/OEE、设备稼动、班组绩效、物料不良、订单交期风险、同比。指标选项全集 16 项全部围绕「缺陷」，无一涉及产出与交付。`[证据] LineAnalyticsView.vue wizard 指标选项`
- **严重度维度形同虚设**：现场 `severity` 实测全 HIGH，严重度构成/堆叠两个 widget 在真实数据下永远单一色块，占用版面却零信息。`[状态] 数据质量所致，未在本次改动`

### 3.3 筛选查询 `[优]`

- 时间：5 个快捷档 + 自定义区间，默认今日，localStorage 记忆。
- 产线/工位：顶部级联多选，前端同时传 `lineId`+`lineIds`，后端并集去重；页面内相机筛选按全部所选产线收敛并清悬空。`[证据] PRD STAT-05`
- 高级筛选：产品（图片通道标注不生效）、班次、相机、缺陷类型（查实际数据）、严重度。
- 维度拆分支持 time/line/workstation/camera/defectType/shift/severity 六个 supported。`[证据] LineAnalyticsController.metadata`
- `[已闭环]` `severity(部分)` 早已在 `ignoredFilters`，PRD TODO-01 是过期快照；`defectTypeId` 本次已接 `cfg_camera_defect_mapping` 解析为现场上报名再筛，未命中仍诚实上报。`[状态] P0-5 核实 / P1-4 实施`

**残留缺口**：前端没有标准缺陷类型 ID 选择器，映射命中的前提是现场维护好「标准类型→设备上报名(source_code)」；现场当前 source_code 为种子数据 p1/p2，故未加必然落空的前端控件。`[状态] 见 G18`

### 3.4 数据对比 `[中→中+]`

- **环比有但弱**：`appendWindowCompare` 给「较上一时段」+ `dayOverDayRate`（图片数环比），只作 KPI 小字。`[证据] LineAnalyticsController 窗口对比`
- **无同比**：物理无去年数据。
- **无系统目标/达成率**：PRD 明确本期不做目标基线。`[状态]` 日报侧本次加了**用户手填参考线**（P0-3），不是系统判定目标，也不改变产线统计；「今天算高还是低」在产线统计仍靠当月分位（相对）判断。
- **横向对比有**：产线/相机/工位排行、班次对比、帕累托，做得比较完整。

### 3.5 图表呈现 `[优]`

- 12 类 widget 形态、4 步编辑向导、14 条推荐预设、拖拽/改尺寸/模板管理齐备，灵活度是本项目强项。`[证据] LineAnalyticsController.metadata / LineAnalyticsView.vue 编辑器`
- 截断诚实：热力图 LIMIT 360、班次对比 LIMIT 12 均回传总量并展示告警。
- 内置看板只读（`isBuiltinBoard` 禁拖动/编辑/删除、隐藏组件库），首屏即出结论，符合「进页即答」。
- **缺口**：图表多但「信息密度 ≠ 决策密度」——7 个 widget 里有 2 个（严重度相关）在真实数据下无意义；缺少一张把产量/质量/设备揉在一起的「综合健康度」总览图。`[状态] 数据真空，P2 前置`

## 4. 统计日报模块评审

三段式（产线胶囊 → 当月月历 → 当日四维）清晰，导览提示、口径页脚、四态色阶都很用心。

### 4.1 统计口径 `[中]`

- 主口径=心跳计数日增差分，辅口径=图片数；图片口径缺陷率恒 1000‰ 已明确不作区分度。`[证据] DailyReportController 口径常量`
- 计数不可用（首日/重置/实时日）→ null + `counterPendingReason` 如实说明，页面显示「待积累」+原因。
- **口径说明偏技术**：页脚「NG计数日增/检测总数日增×1000」「计数器被重置」这类术语，厂长需要翻译成「今天每千件里有多少件不合格」才好决策。`[已闭环 G19]` 术语保留（准确性优先），另加白话悬浮提示与页脚白话解读行
- **offlineCameras 语义已修正为「当日未上报（心跳无记录，非设备离线）」**——11-20 的重要诚实性改动，务必保留。`[证据] DailyReportController 异常构造`

### 4.2 指标覆盖 `[弱→中]`

- 4 张 KPI：检测总数(日增)、缺陷数(日增)、缺陷率‰、在线相机；四宫格：缺陷类型 TOP5、相机 TOP5、时段分布、当日异常。
- `[已实施 P1-2]` 新增第 5 张 KPI「直通率（心跳口径·待现场校准）」，口径区写明「识别正确 ≠ 终检良率，不等同良率」。
- `[已实施 P0-4]` 当日异常从 4 项扩为五类告警分布 + 7 日趋势，保留「只能当线索，不当结论」口径。
- **仍是生产盲区**：没有合格产出、停机、节拍、设备稼动、班组。一个生产负责人看完日报，仍不知道「昨天产线是赚是亏、效率如何」。`[状态] 数据真空`

### 4.3 筛选查询 `[中→中+]`

- 产线胶囊 Tab（全厂+各真实产线）、月份切换、日期点击、键盘左右/Home、刷新、管理员补算。
- `[已实施 P1-3]` 后端 `computeBreakdownDetails` 的四类明细查询（缺陷类型 TOP / 相机 TOP / 时段分布 / 全量计数）共用同一筛选 WHERE，真正支持 `workstationId/cameraId/defectType`；前端加筛选条；不再上报 `ignoredFilters`，改为 `detailFilterMessage` 说明口径边界。
- **★ 二次评审新发现的口径边界**：筛选**只作用于明细块**，顶部汇总 KPI 与月历仍按所选产线整体统计。响应里虽有 `detailFilterMessage` 说明，但视觉上筛选条紧邻 KPI 区，**厂长极易误以为 KPI 也已筛选**。`[已闭环 G20]` KPI 区加醒目「口径提示」角标，响应新增 `detailFilterActive/Names`
- `[已闭环 G20]` 明细筛选新增班次下拉，复用 `dim_shift` 时间窗（与产线统计同口径），可按「夜班某类型缺陷」下钻。

### 4.4 数据对比 `[弱→中]`

- `[已实施 P0-1]` 月历每格显示缺陷框环比箭头（升红/降绿，前一天为 0 或无数据时诚实留空）、最佳/最差角标；footer 同时显示「最多/最少日」。
  - 说明：前端从月历已有 `defectCount` 按相邻自然日自行计算（口径与后端 `dayOverDayRate` 一致：缺陷框数、除零留空），因为 calendar 端点未逐日返回该字段——并非直接消费后端已有字段。
- **零同比、零系统目标、无连续趋势折线**。日报本质是「单日快照集」，不是「连续经营曲线」。`[状态]` 五类告警 7 日趋势是本次唯一跨日曲线。
- 月历色阶按当月分位 P50/P75/P90，避免跨月全红/全浅，设计正确；P0-3 目标基线叠加后，「相对异常」与「绝对超标」可区分。

## 8. 结论与边界声明

1. **当前系统的定位正从「质量缺陷统计工具」向「可判断的质量看板」过渡**——本次补齐了对比、结论、目标参照、异常趋势与设备历史，且在「数字不骗人」上的克制（无数据显示「—」、筛选不生效显式上报、计数器重置显示待积累、离线改「未上报」）全部保留。
2. **它距「厂长经营驾驶舱」的差距，本质是数据源差距，不是 UI 差距。** 产量、良率、节拍、停机、人员、物料、交期、同比八大主题在数据层为空，必须靠 P2 补采集；UI 优化只能先解决「已有数据没用好」的部分。
3. **范围边界要对外讲清**：良率/产量/OEE、目标基线、异常闭环是 PRD 明确不做项。在 P1-2 校准完成前，不得向现场承诺「良率」数字；在 P2 落地前，不得承诺 OEE/交期。
4. **下一步优先级**：先部署验证 P0/P1 与 G19/G20（§7.4）；同步启动 P2-1（PLC/MES 产量与停机采集）立项，这是解锁经营指标的唯一路径。G18（映射命中、直通率同步到产线统计）依赖现场维护 source_code 与口径校准，不提前做假控件。

> 本报告基于 2026-11-21 源码与现场数据事实。所有「已有数据未用」类结论均已逐条回源码复核；数据真空类结论基于全仓库字段检索与 PRD 范围边界。§5 状态列与 §7 实施记录为同日代码落地后的最终状态。
