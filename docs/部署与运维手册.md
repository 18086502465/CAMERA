> 配置项明细见 [`配置项清单.md`](配置项清单.md)

## 1. 系统架构概要

| 组件 | 说明 |
|---|---|
| 后端 | Spring Boot 2.7.18（Java 8），端口 **8091**，产物 `time-bucket-demo.jar` |
| 前端 | Vue 3 + Vite 5，构建产物打进 JAR（`classpath:/static`），无需独立进程 |
| 数据库 | MySQL 8.0，库名 `wms-new` |
| 图片存储 | `/data/camera-detection/images/defect-images/{yyyyMMdd}/{cameraId}/` |
| 服务器 | 10.2.77.72（Ubuntu 24.04），应用用户 `cdsys`，部署目录 `/opt/camera-detection-system` |

设备侧通过 `/api/v1/camera/status/heartbeat`（心跳）与 `/api/v1/defect-images/upload`（图片上传，现场主通道）上报。

## 2. 全新安装

```bash
# 1) 解压发布包
tar -xzf camera-detection-system-1.0.0.tar.gz && cd camera-detection-system

# 2) 以 root 执行安装（MySQL 未就绪时脚本会装完应用后以 DB_PENDING 退出，可二次执行）
sudo env MYSQL_PASSWORD='<数据库口令>' bash scripts/install.sh
```

- 口令来源三级优先级：**环境变量 → 现场既有 `/etc/default/camera-detection` → 交互式读取**；
  脚本显式拒绝 `${...}` 占位符形态（防止把占位符当口令写入）。
- 唯一密钥源 `/etc/default/camera-detection`（**640 root:root**），systemd `EnvironmentFile` 注入；
  `application.yml` 内为 `${MYSQL_PASSWORD}` / `${JWT_SECRET}` 无默认值占位 —— **缺环境变量时启动即失败**（快速失败设计）。
- 建库必须用 `sql/deploy/` 脚本（`01_init_schema_nodb → 02_final_schema_p0 → 03_system_settings → 04_align_entity_columns → 05_camera_type_migration`），`init-database.sh` 已内置该顺序与逐段校验；
  **绝不能**用 Navicat 导出的 `wms-new.sql`（缺 15 张 P0 表）或含 `USE` 语句的 `init_schema.sql`。
- 口令口径：全新库 `admin/123456`；现场机（已改密）`admin/admin123`。

## 3. 日常运维（service.sh）

```bash
bash /opt/camera-detection-system/scripts/service.sh start|stop|restart|status|logs
sudo bash /opt/camera-detection-system/scripts/service.sh version|health|config-check|rollback|cleanup [N]
```

- `health`：进程 + HTTP + 磁盘 + 数据库 + 设备心跳
- `config-check`：校验密钥文件权限与占位符注入（每次升级后必跑）
- `cleanup 5`：清理过期 JAR 备份（默认保留 5 个）
- `verify.sh` 完整自检（32 项）必须以 root + 正确口令运行：

```bash
echo '<sudo口令>' | sudo -S env VERIFY_PASSWORD='<应用口令>' MYSQL_PASSWORD='<库口令>' \
  bash /opt/camera-detection-system/scripts/verify.sh    # 正常 32/32
```

## 4. 升级流程

### 4.1 日常升级（轻量增量包，推荐 —— 传输量 53MB → ~2MB）

```bash
# 构建机：产出轻量更新包（前端构建+后端打包+抽 classes 段，一条命令）
bash installer/linux/build-release.sh --update-only

# 服务器：deploy_jar.sh 按扩展名自动识别（zip=增量 / jar=全量）
SUDO_PASSWORD='<sudo口令>' bash deploy_jar.sh /tmp/update-*.zip
```

增量原理：update 包只含 `BOOT-INF/classes/**`（自研类+前端，~2MB，**含目录条目** ——
JarLauncher 靠 `BOOT-INF/classes/` 目录条目识别类路径根，缺它整个 classes 不进 classpath）；
服务器端与线上 fat jar **在线合成**（依赖指纹一致才允许），合成成功后才停服替换，
停服窗口更短；合成失败（依赖已变更/包损坏）**不会碰服务**。

> 依赖指纹 = `BOOT-INF/lib/` 条目(名,大小,CRC)清单的 sha256，构建端与部署端共用
> `jar_manifest.py` 计算。依赖升级/新增时指纹不一致 → 明确报错，改走全量。

### 4.2 全量升级 / 首次安装

```bash
SUDO_PASSWORD='<sudo口令>' bash deploy_jar.sh /tmp/time-bucket-demo.jar
# 备份 → 停服 → 原子替换 → 启动+健康检查 → 失败自动回滚
```

升级完成后如需恢复**旧版前端 chunk**（让部署前已打开的页面继续可用）：

```bash
sudo python3 recover_legacy_chunks.py     # 从历史 JAR 备份恢复旧 chunk（增量写，不破坏 MANIFEST）
sudo python3 prune_legacy_chunks.py 3     # 按版淘汰，保留最近 3 版
sudo systemctl restart camera-detection   # 生效
```

> ⚠️ 顺序：**部署完成之后**执行恢复，且执行完必须重启；在部署流程中间改 JAR 会让服务停在 stopped。
> ⚠️ 禁止用 `jar cf` 重打包 Spring Boot JAR（会丢 `Main-Class: JarLauncher` 等启动要素），必须用 Python zipfile 增量写。

## 5. 备份与恢复

### 5.1 备份链路全貌

三种产物 + 一份跨盘副本，全部由 `camera-detection-backup.service`（systemd timer，每日 **01:00**）串起来跑：

| 产物 | 内容 | 位置 | 保留 |
|---|---|---|---|
| 数据库全量 | `mysqldump --single-transaction --quick --routines --triggers --events` → zstd | `/data/camera-detection/backup/db/full/` | **14 份** + 每份 `.sha256` |
| binlog 增量 | `mysqlbinlog --read-from-remote-server --raw`，只取**本次 dump 起点及更新**的日志 | `/data/camera-detection/backup/db/binlog/` | `BINLOG_KEEP_DAYS=14` |
| 图片热窗口 | 近 **30 天**的 `{yyyyMMdd}/` 目录，`rsync` 增量，**排除 TEST 相机** | `/var/backups/camera-detection/images/` | 按日期目录随源淘汰 + `IMAGE_BACKUP_MAX_GB` 总量上限 |
| 跨盘副本 | 上述 full / binlog 镜像到**另一块物理盘** | `/var/backups/camera-detection/db/` | 副本侧独立清理 |

> **为什么 binlog 必须一起备**：全量只有 24 小时粒度，出事最多丢一天。有 binlog 就能滚到任意时点。
> 注意 MySQL 侧 `binlog_expire_logs_seconds=2592000`（30 天），这是服务端自动过期，
> 与备份侧的 14 天是两件事 —— **别把服务端调小**，否则还没备份到就已被 MySQL 清掉。

> **为什么副本目录在 `/var` 而不在 `/data`**：两处是不同物理盘（`vg0-var` / `vg0-data`），
> 单盘故障时副本仍在。早期版本把副本放 `/data/.../offsite`（同盘），日志却写「已同步到异机目录」，
> 给出的是错误安全感 —— 2026-11-07 已改。**但仍不是异地容灾**：同一台机器，不抗整机故障。

> **`rsync` 不加 `--delete`**：备份语义是「多留一份」，镜像语义是「保持一致」。
> 加 `--delete` 时，源目录一旦被误清空，下一次同步会把副本一起清空 —— 备份跟着源一起没。

> **图片副本排除 TEST 相机（2026-11-07）**：TEST 是压测相机，源侧每小时被清、没有找回价值。
> 不排除时副本会被压测垃圾撑大：实测**副本 3.9G vs 源 283M**（仅 `20261107/DA9467294` 一个
> 目录就占了 3.5G）。现在按 `camera_type='TEST'` 生成 `--exclude=/<code>/`，并回收副本里的
> 历史遗留 TEST 目录 —— 生效后副本 3.9G → 283M。数据库查询失败时**不排除任何目录**
> （宁可多备份，不可漏备份）并在日志打 WARN。`verify.sh` 第 3d 项守卫这条规则。

> **副本总量上限 `IMAGE_BACKUP_MAX_GB`（默认 20G）**：兜底防「REAL 相机台数增长后，
> 30 天窗口本身撑满 43G 系统盘」。超限时从**最旧日期目录**开始整目录回收，
> 降到上限 90% 为止，每删一个都写 WARN 日志。

### 5.2 恢复（`restore-database.sh`）

```bash
# 恢复到临时库并逐表比对行数（推荐：演练/验证用，绝不碰生产库）
sudo env MYSQL_PASSWORD='<库口令>' bash /opt/camera-detection-system/scripts/restore-database.sh \
     --latest --verify --compare-with wms-new

# 恢复到指定备份文件
sudo env MYSQL_PASSWORD='<库口令>' bash .../restore-database.sh \
     --file /data/camera-detection/backup/db/full/wms-new_20261107_010001.sql.zst

# 演练完删除临时库
... --latest --drop-after
```

- 目标库名**白名单**：只允许 `restore_check_*` / `ZZTEST_*`，指定 `--target-db wms-new` 会被直接拒绝
  （防「演练把生产库覆盖了」这种最贵的失误）。
- `--verify` 会重建表结构并逐表 `COUNT(*)` 比对，输出差异；**差异应全部为「备份后新增」方向**。
- 首次演练结果（2026-11-07）：41 张表、7 秒导入完成，逐表差异全部符合预期。

### 5.3 备份健康检查

`verify.sh` 内置两项（会随 32 项自检一起跑）：

| 检查 | 判据 | 失败说明 |
|---|---|---|
| 备份新鲜度 | 最新 `.sql.zst` 的 mtime < **26 小时** | timer 停了 / 机器时钟漂移 / 任务静默失败 |
| 备份完整性 | 同名 `.sha256` 校验通过 | 文件被截断或损坏（只校验压缩流，不等于能导入） |

`check-disk-usage.sh`（每 30 分钟）额外做两件事并**写入告警页**：备份目录为空/超期 → `BACKUP_FAILED`；
`/` `/var` `/data` 水位超阈值 → `DISK_USAGE_HIGH`。

### 5.4 权限

备份目录 `drwx------` 属 `cdsys`，读取必须 sudo；`/data` 下建目录必须 root 建树后 chown。
`/var/backups/camera-detection` 同属 `cdsys`，权限 700。

> ⚠️ **备份是否有效，只有演练能回答**。「文件存在」和「文件能导入」在出事之前看不出区别。
> 建议每月跑一次 `--verify` 演练，不要只在出事那天第一次用它。

## 6. 磁盘与数据保留（2026-11-05 图片归档改造后）

### 6.1 两层生命周期

图片数据分两层：**主表 31 天热数据 → 按月移到 `defect_image_*_hist_YYYYMM` → 月表 730 天整表 DROP**；
磁盘文件独立按 730 天日期目录删除。各表保留期与负责者的**权威表在
[`配置项清单.md`](配置项清单.md) §五**，此处不重复。

运维只需记住三条：
- 主表 + 月表合计才是全量（归档是**移动**语义，不是复制）。
- 归档健康判据：主表最早时间不应超过 `hot-days + 30` 天，超了打 ERROR 日志（任务连续落后）。
- 磁盘与月表按同一 730 天口径淘汰，保证「库里有记录就有文件」—— 这条**只靠磁盘脚本单方保证**（见 §6.4）。

### 6.2 归档运维

```bash
# 查看归档状态（主表行数 / 最早时间 / 超期表）
sudo grep '图片归档' /var/log/...   # 或 journalctl -u camera-detection | grep 图片归档

# 手工触发一轮归档（ADMIN 令牌；返回 archivedFiles/hotFilesLeft/hotOldestTime/costMs）
TOK=$(curl -s -X POST http://127.0.0.1:8091/api/auth/login -H 'Content-Type: application/json' \
      -d '{"username":"admin","password":"<口令>"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["token"])')
curl -s -X POST http://127.0.0.1:8091/api/v1/defect-images/archive/run -H "Authorization: Bearer $TOK"

# 手工查月表分布
mysql -uroot -p -D wms-new -e "SELECT TABLE_NAME, TABLE_ROWS FROM information_schema.TABLES \
  WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME LIKE 'defect_image%hist%' ORDER BY TABLE_NAME"
```

- 归档是**移动**语义（主表删、月表增），主表+月表合计才是全量；
- 健康判据：主表最早时间不应超过 `hot-days + 30` 天，超了会打 ERROR 日志（任务连续落后）；
- 磁盘与月表按同一口径（730 天）淘汰，保证「库里有记录就有文件」；
- ⚠️ 这条一致性**只靠磁盘脚本单方保证**：Java 侧任何位置都不得删物理文件（见 §6.4）；
- 回灌历史（极端场景）：把月表行 `INSERT` 回主表即可让老数据重新进入默认查询。

### 6.3 容量与巡检

**口径必须先排除 TEST 相机**，否则估算会错一个数量级：

| 口径 | 日增 | 来源 |
|---|---|---|
| 含 TEST 相机 | 780 MB/天（最高单日 4.0 GB） | 压测流量，模拟上报可达 2.7 张/秒 |
| **只算 REAL 相机** | **67 MB/天**（近 7 天均值），单日 267~1133 张 / 7.7~128 MB | 现场真实业务 |

ZK23 两台 REAL 相机 → 730 天约 **48~93 GB**，500G `/data`（可用 487G）**余量充足，当前不需要扩盘**。

**真正的扩盘触发条件是 REAL 相机台数，不是保留天数**：按 67 MB/天/2 台 = 33.5 MB/天/台折算，
10 台约 245 GB/年 → 730 天约 490 GB 逼近上限，**10 台以上必须扩盘**。

- 测试相机数据**不累积**：`cleanup-zk54-incremental.sh`（cron 每小时 `:15`）按 `camera_type=TEST`
  整目录清理。实测一轮删除 17,443 行 / 5 个日期目录，图片总量 4.4G → 368M。
  **关闭测试设备后可移除该 cron**。
- 删目录采用「**先原子 `mv` 到中转区、再 `rm -rf`**」（2026-11-07）：TEST 相机在清理的同时仍在
  上传，直接 `rm -rf` 会在 `rmdir` 时撞上新创建的文件报 `ENOTEMPTY`，表现为**间歇性**「删除失败」
  （同一目录 18:15 失败、19:15 成功，3 秒返回，权限正常）。改名后上传端随即在原路径重建目录，
  旧目录静止，可一次删净。中转区 `…/images/.cleanup-trash`；**清不掉的残留算本轮失败**
  （否则源路径消失后下一轮会误报成功）。
- `CLEANUP_FAILED` **同一问题只占一行**：本轮仍失败则原地更新（刷新 `detect_time` 与明细），
  本轮全绿则把未恢复的全部置为已恢复（`resolved_by='cleanup-zk54'`）。告警页反映当前状态，
  不再按小时堆积。**例外**：自检发现 REAL 数据减少时不自动恢复，需人工核对 `camera_type`。
- 巡检：`check-disk-usage.sh`（每 30 分钟）覆盖 `/`、`/var`、`/data` 水位 + 备份新鲜度 +
  **容量预测**（按 REAL 相机实际日增推算剩余可写天数，低于 `CAPACITY_WARN_DAYS`=180 天告警 `DISK_CAPACITY_LOW`）。
  清理脚本末尾也打印 `/data` 使用率。

### 6.4 磁盘图片文件的唯一删除者

**`cleanup-defect-images.sh`（cron 03:30，保留 `KEEP_DAYS=730`）是磁盘图片文件的唯一 owner。**

`DataCleanupTask` 清 `camera_images` 时**只删库记录、不删磁盘文件**。原因：
`camera_images` 与 `defect_image_file` 的 `image_path` **完全重叠**（指向同一批 jpg），
记录要留 730 天，而该表记录只留 30 天 —— Java 侧一旦顺手 `file.delete()`，
从 T+30 起每条历史记录都指向不存在的文件，页面查看/导出/追溯全部 404。

> 2026-11-07 修复（`DataCleanupTaskImageTest` 守护）。**别把删文件的循环加回来。**

## 7. 现场故障速查（按现象查处置）

只列**现场高频**的 8 种现象与处置动作。根因分析、复现步骤、事故复盘见
[`踩坑速查.md`](踩坑速查.md)（13 节，按主题组织）。

| 现象 | 根因/处理 |
|---|---|
| 服务 active 但业务全错 | 配置占位符带空默认值（`${X:}`）→ 改为无默认值，启动即报 `Could not resolve placeholder` |
| 新机安装后启动即挂（Access denied） | install.sh 从占位符文件 sed 口令（已修复）；核对 `/etc/default` 内容 |
| 重启失败 `Start request repeated too quickly` | 先 `systemctl reset-failed camera-detection` 再 start |
| Linux 脚本报 `set: pipefail: invalid option name` | 脚本是 CRLF → 仓库已有 `.gitattributes` 强制 LF，勿用 Windows 工具改脚本行尾 |
| 部署后旧页面点击无反应 | 旧 chunk 404（已三层修复：前端版本守卫 + 构建保留 chunk + 恢复脚本）；现场刷新一次即可 |
| 登录后被踢出 / 权限报错 | 401=未登录（`AUTHENTICATION_REQUIRED`），403=权限不足（`ACCESS_DENIED`），前端会区分处理 |
| 图像记录页空表 | 数据源必须走 `defect-images/history`（`product_detection_history` 是冻结契约通道，现场无数据） |
| 良率显示 | 图片通道无良品样本 → 显示「—」，不显示 0%（设计行为） |

## 8. 账号与安全

- 改密：服务器执行 `reset-password.sh --password '<新口令>'`（前端无自助改密端点）
- 角色模型：`role=1` 管理员 / `role=0` 普通用户；管理端点需 ADMIN 角色
  （未登录 → 401 跳登录页；权限不足 → 403 仅提示不跳转）
- 排查脚本一律从环境变量读口令（`MYSQL_PASSWORD` / `SSH_PASSWORD`），脚本内不留明文
