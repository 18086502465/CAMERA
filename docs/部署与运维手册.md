## 2. 全新安装

**前置条件：数据盘先挂到 `/main`。** `install.sh` 会断言 `${BASE}` 与 `/` 不在同一设备，未挂载直接退出——
否则 `/main` 只是系统盘上的空目录，数据会静默写错盘，盘修好后原内容被盖住，表现成「数据全丢且无报错」。

```bash
sudo mkdir -p /main
# UUID 用 blkid -o value -s UUID /dev/<数据盘> 取；fstype 用 blkid -o value -s TYPE 取（现场机是 xfs，ext4 换掉即可）
# **绝不加 nofail**：盘没挂上时必须启动失败，不能降级成「服务照起、数据写系统盘」。
echo 'UUID=<数据盘UUID> /main xfs defaults,noatime 0 2' | sudo tee -a /etc/fstab
sudo mount /main && findmnt -n -o SOURCE,OPTIONS /main
sudo findmnt --verify --verbose      # 必须 Success, no errors or warnings
```

### 2.1 一键装机（推荐，新机首次部署）

`deploy.sh` 把「依赖 → 挂盘 → 时区 → MySQL → 安装 → 建库 → 调优 → 验收」串成 8 个**幂等**阶段，
新机一条命令即可；中途失败按提示 `--from pN` 续跑，不会重做已完成的阶段：

```bash
sudo bash scripts/deploy.sh --disk /dev/sdb --db-password '<库口令>' --app-password '<管理员口令>'
```

- **数据盘必须 `--disk` 显式指定**——不自动猜盘，猜错就是格式化别人的盘
- 盘已挂在 `/data` 且**为空**（只剩 `lost+found`）→ 自动改挂 `/main`；**非空则拒绝**并给出两条出路：老布局走迁移脚本，或确认无用后先 `umount`
- `install.sh` 就是其中的 p5 单步：只需重装应用时不跑 deploy.sh
- 目录归属与创建者见 `服务器文件布局.md` 第三节

**只装应用（依赖/库已就绪，或重装）：**

```bash
tar -xzf camera-detection-system-1.0.0.tar.gz && cd camera-detection-system
# MySQL 未就绪时脚本会装完应用后以 DB_PENDING 退出（退出码 1 ≠ 失败），可二次执行
sudo env MYSQL_PASSWORD='<数据库口令>' bash scripts/install.sh --base /main/app
```

> **已有老布局在跑的机器不要跑 install.sh**：`/opt/camera-detection-system` + `/data/camera-detection` +
> `/var/lib/camera-detection-system` 的现场，走 `migrate-to-main-app.sh`（默认 dry-run、可回滚、支持断点续跑），
> 完整步骤与实测数字见 `服务器文件布局.md` 第十五节。判断依据：`findmnt -n -o TARGET,SOURCE /data /main`。

- 口令来源优先级：**命令行 `--db-password`/`--app-password` → 环境变量 → 口令文件 `config/offline.env` → 现场既有 `/etc/default/camera-detection` → 交互式读取**；
  脚本显式拒绝 `${...}` 占位符形态（防止把占位符当口令写入）。
- 管理员口令在建库后由 p7 **真正落库**（`reset-password.sh`，BCrypt），不再只用于验收 —— 传了 `--app-password` 就能用它登录。
- 唯一密钥源 `/etc/default/camera-detection`（**640 root:root**），systemd `EnvironmentFile` 注入；
  `application.yml` 内为 `${MYSQL_PASSWORD}` / `${JWT_SECRET}` 无默认值占位 —— **缺环境变量时启动即失败**（快速失败设计）。
- 建库必须用 `sql/deploy/` 脚本（`01_init_schema_nodb → 02_final_schema_p0 → 03_system_settings → 04_align_entity_columns → 05_camera_type_migration`），`init-database.sh` 已内置该顺序与逐段校验；
  **绝不能**用 Navicat 导出的 `wms-new.sql`（缺 15 张 P0 表）或含 `USE` 语句的 `init_schema.sql`。

### 2.2 无外网 / 离线一键部署（客户内网机器）

发布包分两种，同一 `build-release.sh` 按 `offline/` 是否存在自动判定：

| 包 | 依赖来源 | 部署命令 |
|---|---|---|
| 普通全量包 | p1 走 `apt` 在线装 | `deploy.sh --disk /dev/sdb --db-password … --app-password …` |
| **离线全量包** | p1 只从包内 `offline/debs/` 用 `dpkg` 本地装，**全程不联网** | `deploy.sh --offline --disk /dev/sdb --yes` |

离线全量包部署三步：

```bash
tar -xzf camera-detection-system-1.0.0.tar.gz && cd camera-detection-system
cp config/offline.env.example config/offline.env
# 编辑 config/offline.env：填 MYSQL_PASSWORD / ADMIN_PASSWORD（去掉 <> 占位），chmod 600
sudo bash scripts/deploy.sh --offline --disk /dev/sdb --yes
```

- 一条命令串完：依赖(dpkg) → 挂盘 → 时区 → MySQL → 应用 → 建库 → **管理员口令落库** → 调优重启 → 验收。
- `--offline` 在 p0 校验包内 deb 的 sha256，p1 缺关键命令（mysql/rsync/zstd 等）即停，不留"装了一半"的现场。
- **离线口令是允许的交付方式**：口令写 `config/offline.env`（已被 `.gitignore` 排除，但会随包下发 `.example` 模板）。
  部署后口令已写入服务器 `/etc/default/camera-detection`（640 root），把 `config/offline.env` 从发布目录删除即可。
- `--skip-apt`：依赖已由运维预装时跳过 p1，仅做就绪校验。
- 适用边界：**离线 deb 是 Ubuntu 22.04 / amd64 专属**。目标机版本或架构不同会装不上——需重新生成（见 2.3）。

### 2.3 生成离线全量包（构建机，需一次性外网）

```bash
# 1) 生成离线依赖（必须在联网的 Ubuntu 22.04 amd64 上；非 Ubuntu 构建机用 Docker 模式）
sudo bash installer/linux/fetch-offline-deps.sh          # 直接跑
bash installer/linux/fetch-offline-deps.sh --docker      # 或 Docker（推荐 Windows 构建机）
#   → installer/linux/offline/debs/*.deb + manifest.sha256 + README.txt

# 2) 正常打全量包，offline/ 会被自动并入
bash installer/linux/build-release.sh
#   → dist-release/linux/camera-detection-system-<版本>.tar.gz（含 offline/ 的即离线包）
```

- 依赖清单（`mysql-server chrony curl rsync zstd apache2-utils openjdk-8-jdk`）在 `fetch-offline-deps.sh` 的 `DEP_PKGS` 定义，
  与 `deploy.sh` p1 的 `pkgs` 保持一致 —— 新增依赖必须两处同改。
- `fetch-offline-deps.sh` 会强制校验 `VERSION_CODENAME=jammy` 且 `amd64`，避免 deb 与目标机不兼容。
- 产物不入库（`.gitignore` 已排除 `installer/linux/offline/` 与 `config/offline.env`）。
- 现场故障排查见 `踩坑速查.md` §4.2、§4.3。

## 3. 日常运维（service.sh）

```bash
bash /main/app/dist/scripts/service.sh start|stop|restart|status|logs
sudo bash /main/app/dist/scripts/service.sh version|health|config-check|rollback|cleanup [N]
```

- `health`：进程 + HTTP + 磁盘 + 数据库 + 设备心跳
- `config-check`：校验密钥文件权限与占位符注入（每次升级后必跑）
- `cleanup 5`：清理过期 JAR 备份（默认保留 5 个）
- `verify.sh` 完整自检必须以 root + 正确口令运行（统一布局 **45 项**；未迁移的老布局 35 项，差值是 [3a] 布局校验）：

```bash
echo '<sudo口令>' | sudo -S env VERIFY_PASSWORD='<应用口令>' MYSQL_PASSWORD='<库口令>' \
  bash /main/app/dist/scripts/verify.sh    # 正常 43/43
```

## 4. 升级流程

### 4.1 日常升级（轻量增量包，推荐 —— 传输量 53MB → ~2MB）

```bash
# 构建机：产出轻量更新包（前端构建+后端打包+抽 classes 段，一条命令）
bash installer/linux/build-release.sh --update-only

# 服务器：deploy_jar.sh 按扩展名自动识别（zip=增量 / jar=全量）
SUDO_PASSWORD='<sudo口令>' bash deploy_jar.sh /tmp/update-*.zip
```

增量原理：update 包只含 `BOOT-INF/classes/**`（自研类+前端，~2MB，**含目录条目** ——
JarLauncher 靠 `BOOT-INF/classes/` 目录条目识别类路径根，缺它整个 classes 不进 classpath）；
服务器端与线上 fat jar **在线合成**（依赖指纹一致才允许），合成成功后才停服替换，
停服窗口更短；合成失败（依赖已变更/包损坏）**不会碰服务**。

> 依赖指纹 = `BOOT-INF/lib/` 条目(名,大小,CRC)清单的 sha256，构建端与部署端共用
> `jar_manifest.py` 计算。依赖升级/新增时指纹不一致 → 明确报错，改走全量。

### 4.2 全量升级 / 首次安装

```bash
SUDO_PASSWORD='<sudo口令>' bash deploy_jar.sh /tmp/time-bucket-demo.jar
# 备份 → 停服 → 原子替换 → 启动+健康检查 → 失败自动回滚
```

升级完成后如需恢复**旧版前端 chunk**（让部署前已打开的页面继续可用）：

```bash
sudo python3 recover_legacy_chunks.py     # 从历史 JAR 备份恢复旧 chunk（增量写，不破坏 MANIFEST）
sudo python3 prune_legacy_chunks.py 3     # 按版淘汰，保留最近 3 版
sudo systemctl restart camera-detection   # 生效
```

> ⚠️ 顺序：**部署完成之后**执行恢复，且执行完必须重启；在部署流程中间改 JAR 会让服务停在 stopped。
> ⚠️ 禁止用 `jar cf` 重打包 Spring Boot JAR（会丢 `Main-Class: JarLauncher` 等启动要素），必须用 Python zipfile 增量写。
> 两个脚本的真源在 `installer/linux/scripts/`（`docs/scripts/` 自 2026-11-12 起不留副本）。

### 4.3 构建产物目录 `dist-release/`

**全目录不入库**，由 `installer/linux/build-release.sh` 生成，删了随时重建：

| 路径 | 内容 | 是否保留 |
|---|---|---|
| `linux/camera-detection-system-1.0.0.tar.gz` | 全量交付包（~54MB） | 保留最新一份 |
| `linux/stage/` | 打包中间目录 | 可随时删，下次构建重建 |
| `linux/update/update-<时间戳>.zip` | 增量包（~2–4MB） | 只留最新一份，构建时自动清 7 天前 |
| `linux/parts/` | base64 分片上传的本地半成品 | 上传完成后即可删，构建时自动清 |

SQL 四段脚本、运维脚本、systemd 单元、配置模板的**真源**分别在
`fact-product/src/main/resources/sql/deploy/`、`installer/linux/scripts|systemd/`、`installer/templates/`，
构建时由脚本自动复制进本目录 —— **不要直接改 `dist-release/` 里的文件**，下次构建会被覆盖。

## 5. 备份与恢复

### 5.1 备份链路全貌

三种产物 + 一份跨盘副本，全部由 `camera-detection-backup.service`（systemd timer，每日 **01:00**）串起来跑：

| 产物 | 内容 | 位置 | 保留 |
|---|---|---|---|
| 数据库全量 | `mysqldump --single-transaction --quick --routines --triggers --events` → zstd | `/main/app/data/backup/db/full/` | **14 份** + 每份 `.sha256` |
| binlog 增量 | `mysqlbinlog --read-from-remote-server --raw`，只取**本次 dump 起点及更新**的日志 | `/main/app/data/backup/db/binlog/` | `BINLOG_KEEP_DAYS=14` |
| 图片热窗口 | 近 **30 天**的 `{yyyyMMdd}/` 目录，`rsync` 增量，**排除 TEST 相机** | `/var/backups/camera-detection/images/` | 按日期目录随源淘汰 + `IMAGE_BACKUP_MAX_GB` 总量上限 |
| 跨盘副本 | 上述 full / binlog 镜像到**另一块物理盘** | `/var/backups/camera-detection/db/` | 副本侧独立清理 |

> **为什么 binlog 必须一起备**：全量只有 24 小时粒度，出事最多丢一天。有 binlog 就能滚到任意时点。
> 注意 MySQL 侧 `binlog_expire_logs_seconds=2592000`（30 天），这是服务端自动过期，
> 与备份侧的 14 天是两件事 —— **别把服务端调小**，否则还没备份到就已被 MySQL 清掉。

> **为什么副本目录在 `/var` 而不在主备份目录旁**：`/main` 是数据盘、`/var` 在系统盘，两块物理盘，
> 单盘故障时副本仍在。早期版本把副本放同盘 `offsite` 目录，日志却写「已同步到异机目录」，
> 给出的是错误安全感 —— 2026-11-07 已改。**但仍不是异地容灾**：同一台机器，不抗整机故障。

> **`rsync` 不加 `--delete`**：备份语义是「多留一份」，镜像语义是「保持一致」。
> 加 `--delete` 时，源目录一旦被误清空，下一次同步会把副本一起清空 —— 备份跟着源一起没。

> **图片副本排除 TEST 相机（2026-11-07）**：TEST 是压测相机，源侧每小时被清、没有找回价值。
> 不排除时副本会被压测垃圾撑大：实测**副本 3.9G vs 源 283M**（仅 `20261107/DA9467294` 一个
> 目录就占了 3.5G）。现在按 `camera_type='TEST'` 生成 `--exclude=/<code>/`，并回收副本里的
> 历史遗留 TEST 目录 —— 生效后副本 3.9G → 283M。数据库查询失败时**不排除任何目录**
> （宁可多备份，不可漏备份）并在日志打 WARN。`verify.sh` 第 3d 项守卫这条规则。

> **副本总量上限 `IMAGE_BACKUP_MAX_GB`（默认 20G）**：兜底防「REAL 相机台数增长后，
> 30 天窗口本身撑满 43G 系统盘」。超限时从**最旧日期目录**开始整目录回收，
> 降到上限 90% 为止，每删一个都写 WARN 日志。

### 5.2 恢复（`restore-database.sh`）

```bash
# 恢复到临时库并逐表比对行数（推荐：演练/验证用，绝不碰生产库）
sudo env MYSQL_PASSWORD='<库口令>' bash /main/app/dist/scripts/restore-database.sh \
     --latest --verify --compare-with wms-new

# 恢复到指定备份文件
sudo env MYSQL_PASSWORD='<库口令>' bash .../restore-database.sh \
     --file /main/app/data/backup/db/full/wms-new_20261107_010001.sql.zst

# 演练完删除临时库
... --latest --drop-after
```

- 目标库名**白名单**：只允许 `restore_check_*` / `ZZTEST_*`，指定 `--target-db wms-new` 会被直接拒绝
  （防「演练把生产库覆盖了」这种最贵的失误）。
- `--verify` 会重建表结构并逐表 `COUNT(*)` 比对，输出差异；**差异应全部为「备份后新增」方向**。
- 首次演练结果（2026-11-07）：41 张表、7 秒导入完成，逐表差异全部符合预期。

### 5.3 备份健康检查

`verify.sh` 内置两项（会随完整自检一起跑）：

| 检查 | 判据 | 失败说明 |
|---|---|---|
| 备份新鲜度 | 最新 `.sql.zst` 的 mtime < **26 小时** | timer 停了 / 机器时钟漂移 / 任务静默失败 |
| 备份完整性 | 同名 `.sha256` 校验通过 | 文件被截断或损坏（只校验压缩流，不等于能导入） |

`check-disk-usage.sh`（每 30 分钟）额外做两件事并**写入告警页**：备份目录为空/超期 → `BACKUP_FAILED`；
`/` 与 `/main` 水位超阈值 → `DISK_USAGE_HIGH`。

### 5.4 权限

备份目录 `drwx------` 属 `cdsys`，读取必须 sudo；数据盘 `/main` 下建目录必须 root 建树后 chown。
`/var/backups/camera-detection` 同属 `cdsys`，权限 700。

> ⚠️ **备份是否有效，只有演练能回答**。「文件存在」和「文件能导入」在出事之前看不出区别。
> 建议每月跑一次 `--verify` 演练，不要只在出事那天第一次用它。

## 6. 磁盘与数据保留（2026-11-05 图片归档改造后）

### 6.1 两层生命周期

图片数据分两层：**主表 31 天热数据 → 按月移到 `defect_image_*_hist_YYYYMM` → 月表 730 天整表 DROP**；
磁盘文件独立按 730 天日期目录删除。各表保留期与负责者的**权威表在
[`配置项清单.md`](配置项清单.md) §五**，此处不重复。

运维只需记住三条：
- 主表 + 月表合计才是全量（归档是**移动**语义，不是复制）。
- 归档健康判据：主表最早时间不应超过 `hot-days + 30` 天，超了打 ERROR 日志（任务连续落后）。
- 磁盘与月表按同一 730 天口径淘汰，保证「库里有记录就有文件」—— 这条**只靠磁盘脚本单方保证**（见 §6.4）。

### 6.2 归档运维

```bash
# 查看归档状态（主表行数 / 最早时间 / 超期表）
sudo grep '图片归档' /var/log/...   # 或 journalctl -u camera-detection | grep 图片归档

# 手工触发一轮归档（ADMIN 令牌；返回 archivedFiles/hotFilesLeft/hotOldestTime/costMs）
TOK=$(curl -s -X POST http://127.0.0.1:8091/api/auth/login -H 'Content-Type: application/json' \
      -d '{"username":"admin","password":"<口令>"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["token"])')
curl -s -X POST http://127.0.0.1:8091/api/v1/defect-images/archive/run -H "Authorization: Bearer $TOK"

# 手工查月表分布
mysql -uroot -p -D wms-new -e "SELECT TABLE_NAME, TABLE_ROWS FROM information_schema.TABLES \
  WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME LIKE 'defect_image%hist%' ORDER BY TABLE_NAME"
```

- 归档是**移动**语义（主表删、月表增），主表+月表合计才是全量；
- 健康判据：主表最早时间不应超过 `hot-days + 30` 天，超了会打 ERROR 日志（任务连续落后）；
- 磁盘与月表按同一口径（730 天）淘汰，保证「库里有记录就有文件」；
- ⚠️ 这条一致性**只靠磁盘脚本单方保证**：Java 侧任何位置都不得删物理文件（见 §6.4）；
- 回灌历史（极端场景）：把月表行 `INSERT` 回主表即可让老数据重新进入默认查询。

### 6.3 容量与巡检

**口径必须先排除 TEST 相机**，否则估算会错一个数量级：

| 口径 | 日增 | 来源 |
|---|---|---|
| 含 TEST 相机 | 780 MB/天（最高单日 4.0 GB） | 压测流量，模拟上报可达 2.7 张/秒 |
| **只算 REAL 相机** | **67 MB/天**（近 7 天均值），单日 267~1133 张 / 7.7~128 MB | 现场真实业务 |

ZK23 两台 REAL 相机 → 730 天约 **48~93 GB**；老机 500G 数据盘（迁移后挂载点 `/main`）**余量充足，当前不需要扩盘**。

**真正的扩盘触发条件是 REAL 相机台数，不是保留天数**：按 67 MB/天/2 台 = 33.5 MB/天/台折算，
10 台约 245 GB/年 → 730 天约 490 GB 逼近上限，**10 台以上必须扩盘**。

- 测试相机数据**不累积**：`cleanup-test-cameras.sh`（cron 每小时 `:15`）按 `camera_type=TEST`
  整目录清理。实测一轮删除 17,443 行 / 5 个日期目录，图片总量 4.4G → 368M。
  **关闭测试设备后可移除该 cron**。
- 删目录采用「**先原子 `mv` 到中转区、再 `rm -rf`**」（2026-11-07）：TEST 相机在清理的同时仍在
  上传，直接 `rm -rf` 会在 `rmdir` 时撞上新创建的文件报 `ENOTEMPTY`，表现为**间歇性**「删除失败」
  （同一目录 18:15 失败、19:15 成功，3 秒返回，权限正常）。改名后上传端随即在原路径重建目录，
  旧目录静止，可一次删净。中转区 `…/images/.cleanup-trash`；**清不掉的残留算本轮失败**
  （否则源路径消失后下一轮会误报成功）。
- `CLEANUP_FAILED` **同一问题只占一行**：本轮仍失败则原地更新（刷新 `detect_time` 与明细），
  本轮全绿则把未恢复的全部置为已恢复（`resolved_by='cleanup-zk54'`）。告警页反映当前状态，
  不再按小时堆积。**例外**：自检发现 REAL 数据减少时不自动恢复，需人工核对 `camera_type`。
- 巡检：`check-disk-usage.sh`（每 30 分钟）覆盖 `/`、`/main` 水位 + 备份新鲜度 +
  **容量预测**（按 REAL 相机实际日增推算剩余可写天数，低于 `CAPACITY_WARN_DAYS`=180 天告警 `DISK_CAPACITY_LOW`）。
  清理脚本末尾也打印数据盘使用率。

### 6.4 磁盘图片文件的唯一删除者

**`cleanup-defect-images.sh`（cron 03:30，保留 `KEEP_DAYS=730`）是磁盘图片文件的唯一 owner。**

`DataCleanupTask` 清 `camera_images` 时**只删库记录、不删磁盘文件**。原因：

从 T+30 起每条历史记录都指向不存在的文件，页面查看/导出/追溯全部 404。

## 7. 现场故障速查（按现象查处置）

只列**现场高频**的现象与处置动作。根因分析、复现步骤、事故复盘见
[`踩坑速查.md`](踩坑速查.md)（按主题逐节累加，编号只增不改）。

| 现象 | 根因/处理 |
|---|---|
| 服务 active 但业务全错 | 配置占位符带空默认值（`${X:}`）→ 改为无默认值，启动即报 `Could not resolve placeholder` |
| 新机安装后启动即挂（Access denied） | install.sh 从占位符文件 sed 口令（已修复）；核对 `/etc/default` 内容 |
| 重启失败 `Start request repeated too quickly` | 先 `systemctl reset-failed camera-detection` 再 start |
| Linux 脚本报 `set: pipefail: invalid option name` | 脚本是 CRLF → 仓库已有 `.gitattributes` 强制 LF，勿用 Windows 工具改脚本行尾 |
| 部署后旧页面点击无反应 | 旧 chunk 404（已三层修复：前端版本守卫 + 构建保留 chunk + 恢复脚本）；现场刷新一次即可 |
| 登录后被踢出 / 权限报错 | 401=未登录（`AUTHENTICATION_REQUIRED`），403=权限不足（`ACCESS_DENIED`），前端会区分处理 |
| 图像记录页空表 | 数据源必须走 `defect-images/history`（`product_detection_history` 是冻结契约通道，现场无数据） |
| 良率显示 | 图片通道无良品样本 → 显示「—」，不显示 0%（设计行为） |
| 日报某天缺数据 | 历史日可能**没物化**：查 `fact_daily_line_report` 有无该日行；缺则用 `POST /api/v1/analytics/daily-reports/{date}/regenerate`（ADMIN）补算，幂等 |
| 日报缺陷率显示「率待积累」 | 计数口径需**两天**日终快照才能差分，首日必然为空。补算历史日**不能**拍计数快照（当前计数已含之后上传，差分必错）→ 保持 NULL 是诚实降级 |
| 日报数字与产线统计对不上 | 两者口径不同：日报缺陷率用**计数日增差分**，产线统计用图片事实表实时值。图片口径缺陷率恒 1000‰（分母=分子）本就无区分度 |
| `DAILY_REPORT_FAILED` 告警 | 日报快照任务失败（DB 异常等）。修因后重跑任务即可自动恢复（告警自动 resolve） |
| `UPLOAD_FAILED` 告警 | 设备图片上传失败（multipart 解析异常）。**看告警正文的「失败频次」**：最近 1 小时只失败 1~2 次 = 偶发网络抖动；某台设备反复失败上百次 = 设备端网络/上传队列问题（现场实例：`DA9299030` 24h 内失败 177 次，占全站 88%）。排查顺序：设备网络 → 上传队列积压 → 相机磁盘/负载 |
| 缺陷图数比产线产量多（同一时刻多张同名） | 设备端未收到响应会**重传同一张图**；服务端已做幂等（判重键 `camera_id + file_name`），但**存量重复数据**需用 `docs/scripts/purge_duplicate_images.sql` 清理（默认只预览，确认后再删；脚本会建备份表保留 7 天） |
| `SCHEMA_INDEX_MISSING` 告警 | **上传幂等的最后一道防线缺失** —— 唯一索引 `uk_defect_file_camera_file_name` 没建成，设备端重传会静默产生重复数据（缺陷框统计被放大）。处置：① `docs/scripts/purge_duplicate_images.sql` 清理重复数据（默认只预览，确认后再删；脚本会建备份表保留 7 天）② **重启服务** → 索引自动补建 ③ 确认告警已解决 |
| 告警写不进库（日志里有 `Data too long for column 'alert_message'`） | 告警正文超过列宽 → MySQL 抛 `ERROR 1406` → 整条告警丢失。已扩列到 varchar(2000) 并在 Repository 统一截断；若仍发生，检查 `ensureMessageColumnWidth()` 是否执行成功 |
| `systemctl restart` 报 `Start request repeated too quickly`（但应用其实启动成功了） | systemd `Restart=on-failure` 把**主动 stop**（exit 143=SIGTERM）也判成 failure，连续触发重启撞上 `StartLimitBurst`。处置：`systemctl reset-failed camera-detection && systemctl start camera-detection` |
| 导出的 Excel 行数是列表的 6 倍 / SUM 翻倍 | 导出口径与列表口径分裂 —— 报表端点要**逐产线明细**、列表端点要**每天一行厂级**时，就会出现这种翻倍。处置：核对 `GET /daily-reports` 与 `GET /daily-reports/export` 同区间的行数是否一致；不一致说明某个端点漏了「只取厂级行」的过滤 |
| 页面显示「良率 0.00%」但该产线其实没上报 | **无数据显示成 0** 的典型症状。`total=0` 时良率/NG 率必须是 `null`（配 `yieldRateAvailable=false`），前端显示「—」，不能给 0.00% —— 否则会被读成「良率为 0、全是废品」 |
| 图表缺格 / 班次对比只有 12 种类型 | 图表有**静默截断上限**（热力图 `LIMIT 360`、班次对比 `LIMIT 12`）。现场完整组合数达 422 / 40 种 → 缺 15%~68%。处置：看响应里的 `hourlyHeatmapTruncated` / `shiftCompareTruncated` 与 `*TotalCombos` / `*TotalTypes`，页面会显示缺了多少；要完整数据需改分页策略 |
| 「改前端没生效」 | 改了 `frontend/src` 但只跑了 `sync_static_keep_legacy.py` + `mvn package` → **dist 还是旧的**。必须 `npx vite build`（先删 dist）→ sync static → package → 部署。验证产物用**中文字符串** grep（minify 会改函数名） |
| `logrotate.service` 每天报 Failed / exit 1 | `/etc/logrotate.d/` 下有**遗留的 `.bak-*` 配置**也会被 logrotate 一并加载（不只主配置）。它若指向旧布局，通配符 + `su cdsys` + `copytruncate` 会因写权限不足报 Permission denied，并让**整个 logrotate 每天 exit 1**（掩盖真实的轮转失败）。处置：把 `camera-detection.bak-*` 移出该目录（`install.sh`/`migrate-to-main-app.sh` 现已自动清理，现场 `verify.sh` 也有对应检查项） |

### 8.1 8091 不得对外网暴露（部署检查项）

服务只监听 `0.0.0.0:8091`，自身不区分内网/外网。**上线前必须确认该端口只在受控内网可达**：

```bash
# 在服务器上确认监听地址
ss -lntp | grep 8091
# 从一台外网/办公网机器上确认不可达（应 timeout 或 refused）
curl -m 5 -sS -o /dev/null -w '%{http_code}\n' http://<现场公网IP>:8091/api/version
```

必须做到：

| 项 | 要求 |
|---|---|
| 边界防火墙 | 8091 只对内网段放行，不写入任何 DNAT/端口映射 |
| 云安全组（如适用） | 入方向仅放行内网网段，禁止 `0.0.0.0/0` |
| 反向代理 | 若经 nginx 暴露，只代理 80/443，**不要**把 8091 直接透传出去 |

原因（如实记录，勿当成已修）：`POST /api/v1/defect-images/upload` 目前只校验 `Authorization` 以 `Bearer ` 开头、**不与 `cfg_camera_token` 比对**，任何能访问 8091 的人都能写图片与缺陷数据；`/api/v1/defect-images/file/**` 也是免鉴权读取。详见 [`相机设备接口协议.md`](相机设备接口协议.md) §8.3。

> 这一项不进 `verify.sh`：脚本在服务器本机运行，无法证明外部不可达。只能由部署人在网络边界侧确认并留档。

### 9.3 三种策略与切换

| `license.expired-mode` | 过期后 | 什么时候用 |
|---|---|---|
| `warn`（默认） | 只告警，业务照跑 | 首次交付、策略未定 |
| `readonly` | 超宽限期拒绝设备写入，管理端可用 | 已确认授权流程后 |
| `block` | 再拒绝业务查询 | 严格商务约束（慎用） |

改法：环境变量 `LICENSE_EXPIRED_MODE` 或改 `application.yml` 的 `license.expired-mode`，重启生效。

> ⚠ 默认 `warn` = 不装授权也能全功能跑。要求「必须有授权才能用」时，部署完立刻切 `readonly`。

|---|---|---|
| 页面显示「未安装授权」 | 文件不存在 | 按 9.2 投放，或检查 `license.file` 是否指向 data 盘 |
| 「授权文件无效 / 签名校验失败」 | 文件被改过，或签发时用了 `--secret` 而服务器没配同一个 `LICENSE_SECRET` | 用同一密钥重新签发；核对服务端 `LICENSE_SECRET` |
| 「授权与本机不符」 | 机器码变了（换主板/重装系统/虚拟机克隆） | 取新机器码重新签发；临时可 `license.enforce-machine=false` |
| 上传报「写入授权文件失败」 | 目录属主/权限不对（曾放 `/etc` 导致 cdsys 写不进） | `chown -R cdsys:cdsys /main/app/data/license` |
| 到期后设备上报被拒（503 `LICENSE_EXPIRED`） | `readonly`/`block` 模式且超过宽限期 | 续期授权；紧急恢复可临时切 `warn` 并重启 |

## 10. 产线统计日报运维（2026-11-17 新增）

### 10.1 它是什么

新 Tab `/daily-report`，给厂长「按天掌握结论」用。每天 00:05 把昨天的结论**物化成一行**
（厂级一行 + 每产线一行），历史日查快照、当天实时算。

### 10.2 部署要确认的 3 件事

| 项 | 检查 | 不对会怎样 |
|---|---|---|
| 快照表存在 | `SHOW TABLES LIKE 'fact_daily_line_report'` | 应用启动时 `SchemaInitializer.ensureTable()` 会幂等补建，通常无需人工干预 |
| 任务在跑 | `journalctl -u camera-detection \| grep 产线日报` 看 00:05 的记录 | 缺行 → 当天查不到历史日结论 |
| cron 配置 | `app.daily-report.cron`（默认 `0 5 0 * * ?`），改后**要重启服务** | 改 yml 不重启 = 跑的还是旧 cron |

### 10.3 手工补算某天

任务失败或历史日缺快照时（ADMIN 令牌）：

```bash
curl -X POST -H "Authorization: Bearer <ADMIN令牌>" \
  http://127.0.0.1:8091/api/v1/analytics/daily-reports/2026-11-16/regenerate
```

幂等覆盖（DELETE + INSERT 同事务），重复调安全。补算完去页面对数：
**缺陷框数**应与产线统计页同区间同产线的「缺陷数」一致（偏差 <5%）。

> ⚠️ 补算**不会**补出缺陷率 —— 计数口径要两天日终快照才能差分，
> 补算时当前计数已含之后上传，硬算必错。页面显示「率待积累」是**诚实降级，不是故障**。

### 10.4 告警

任务失败落 `DAILY_REPORT_FAILED`（HIGH，运维类，在告警页**排最前**），
修因后重跑任务会自动恢复（`is_resolved=1`）。同类还有
`BACKUP_FAILED` / `CLEANUP_FAILED` / `ARCHIVE_FAILED` / `DISK_USAGE_HIGH` / `DISK_FULL`。
