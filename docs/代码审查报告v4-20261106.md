## 一、核心结论（先看这五条）

1. **现场主通道 `/api/v1/defect-images/upload` 没有任何令牌校验。** 它被 `permitAll` 放行（`SecurityConfig:163-167`），service 里只检查 `Authorization` 是否以 `Bearer ` 开头（`DefectImageServiceImpl:128-130`），token 内容**从不比对**。等于匿名可写库、写盘、污染统计。7.9 万张真实数据的通道，鉴权是空的。这是本次评审最严重的一项，v1~v3 均未发现。
2. **批量上报通道的令牌校验是 fail-open**：token 表为空或查询抛异常时直接 `return` 放行（`InspectionUploadServiceImpl:238-256`）。两条通道叠加 = 设备接入面整体无鉴权。
3. **CI 门禁实际是红的**：CI 用 JDK 8（`ci.yml:43`），而测试源码用了 `List.of()`（`CameraHeartbeatCacheKeyTest:89,146,181`，Java 9+ API）。`testCompile` 必失败。所谓"128 个用例全绿"只在本机 JDK 17 上成立 —— 门禁形同虚设。
4. **工程质量的重心已从"修 bug"转到"控制复杂度"**：最大的 `LineAnalyticsController` 1493 行 / 23 端点 / 12 个写端点 0 个 `@PreAuthorize` / 内嵌 `@Scheduled` / 自建线程池 / 自建内存任务表；`analytics` 域 4772 行是这个系统最贵的资产，也是唯一没有任何真实 SQL 测试的域。
5. **v3 五项（H-1~H-5）在工作区已经改掉了**，方向都对，但**没有提交、没有部署、没有回归**。当前 HEAD 与运行中的服务都不是这份代码 —— 报告里的"已修复"一律标注为"工作区已修，未验证"。

## 三、P0：本周必须处理

### SEC-01　图片上传主通道 token 零校验（匿名可写库写盘）

**证据**

- 白名单：`SecurityConfig.java:163-167` 对 `POST /api/v1/defect-images/upload` 直接 `permitAll()`，注释写"由 service 层用 cfg_camera_token 校验"。
- 实际：`DefectImageServiceImpl.java:128-130` 只做 `authorization.startsWith("Bearer ")`；全文 grep `token/Token` 只有这 3 行，**没有任何 `sha256`、`cfg_camera_token`、`listCameraTokens` 调用**（对比 `InspectionUploadServiceImpl:250` 是有比对的）。
- 相机身份：`upload()` 里 `cameraId = firstNotBlank(metadata.getCameraId(), deviceId)`（`:153`），不校验该 code 是否存在于 `dim_camera`；`:233` 还会 upsert 相机最新图。
- 请求体上限：`application.yml:44-45` `max-file-size 10MB` / `max-request-size 1024MB`。

**影响**

1. 任何能访问 8091 的人可批量伪造缺陷图片 → 统计看板、良率、帕累托全部失真，且数据不可区分真伪。
2. 磁盘耗尽：`/data` 500G，按 10MB × 每批多张可快速打满，打满后 DB 与日志一起挂。
3. 无凭据即无追溯，事后无法判定哪些是注入数据。

**改法（优先做，工作量约 0.5~1 天）**

1. 抽一个 `CameraTokenVerifier`（`device/app`），实现"按 camera_code 查 `cfg_camera_token` → SHA-256 → 常量时间比较（`MessageDigest.isEqual`）→ 校验有效期"，两条通道共用。
2. `DefectImageServiceImpl.upload()` 在 `validateMetadata` 之前调用它；**失败一律 401/422，不落任何盘**。
3. `camera_code` 必须存在于 `dim_camera`（`is_deleted=0`），否则 422 `UNKNOWN_CAMERA`；新相机走管理端建档，不允许上传通道隐式创建。
4. 加每相机配额：单日图片数/字节数上限（读 `sys_system_setting`，默认如 5000 张/日），超限 429。
5. 回归：`verify.sh` 增加负向用例 —— 错误 token 必须 422/401、未知 camera_code 必须 422；并在 `docs/api/接口冻结契约` 里写明"此端点必须带有效设备 token"，避免下次又被当成"仅需 Header"。

### SEC-02　批量通道令牌校验 fail-open

**证据**：`InspectionUploadServiceImpl.java:238-256`

```java
try { rows = inspectionUploadRepository.listCameraTokens(cameraId); }
catch (Exception e) { log.warn("cfg_camera_token 未就绪，仅校验 Token 必填"); return; }  // ← 放行
if (rows == null || rows.isEmpty()) { return; }                                        // ← 放行
```

另：`configured.equals(token) || configured.equalsIgnoreCase(sha256)` 使用普通 `equals`，非常量时间；且允许明文 token 与 hash 两种存法并存。

**影响**：该端点同样匿名（`SecurityConfig:165`），一旦某相机没有 token 行（新装、迁移漏配），就是完全开放。异常分支把"数据库故障"翻译成"不用校验"，属于最危险的一类兜底。

**改法**：无 token 配置 → 422 `TOKEN_NOT_CONFIGURED`（并提示去管理端生成）；查询异常 → 500/503，绝不 return 放行；比较统一走常量时间；`docs` 里删掉"开发环境兼容"的说法。

### TEST-01　CI 门禁失效（JDK 8 编译不过测试）

**证据**：`ci.yml:43`（backend job 与 verify job 均为 `java-version: '8'`）、`pom.xml:20-21`（source/target 8）；`CameraHeartbeatCacheKeyTest.java:89,146,181` 使用 `List.of()`。JDK 8 无此 API，`mvn test` 在 CI 必编译失败。

**影响**：CI 绿不绿没人信；"128 个用例全绿"只能在本机 JDK 17 复现。所有依赖 CI 的隐性保障（构建、产物一致性）都失去意义。

**改法**：① `List.of()` → `Collections.emptyList()/singletonList()`；② `pom.xml` 加 `maven.compiler.release=8`，让本机 JDK 17 也按 8 校验 API，从根上堵住这类"本机能跑、CI 挂"；③ 修好后确认 GitHub Actions 上 backend job 真的绿，并把链接贴进交付说明。

## 四、P1：两周内

### SEC-03　限速可被伪造 `X-Forwarded-For` 绕过

**证据**：`AuthController.java:187-195` 无条件取 XFF 首段作为 `clientIp`；限速键 `login|username|ip`（`:56`）、注册键 `reg|ip`（`:128`）。

**影响**：攻击者每次请求换一个 XFF 值 → 注册限速完全失效（可批量注册弱口令账号，虽角色固定为 0，但仍是垃圾数据 + BCrypt CPU 消耗）；登录端口令锁定对同一用户名仍生效，但换 IP 维度无效。

**改法**：只在"请求来自受信代理"时才采信 XFF（`server.forward-headers-strategy=native` + Tomcat `RemoteIpValve` 配内网代理网段，或自维护代理 IP 白名单）；否则用 `request.getRemoteAddr()`。注册再加一层全局限速（如全站 30 次/分钟），避免"换 IP 即无限"。

### SEC-04　token 存 localStorage、无 CSP

**证据**：`frontend/src/utils/auth.js:6,10,22`；`frontend/index.html` 无 CSP meta。当前无 `v-html`（这点是干净的），但 28 处 `console.error(e)` 会把 response 打到控制台。

**改法**：优先补 CSP（`default-src 'self'; img-src 'self' data:`）+ 生产构建 `drop_console`（vite `esbuild.drop`）。中期评估 HttpOnly cookie + 短期 access token（当前 24h 无刷新、无吊销，改密/禁用只能靠 `isDisabled` 兜）。

### SEC-05　改密功能不存在 + 第二个登录口

**证据**：`SysUserController.java:117` 有 `POST /api/user/login`（无 `@PreAuthorize`、无强度校验、无限速），与 `/api/auth/login` 重复实现；它目前只靠 `SecurityConfig:195-199` 的 `/api/user/**` → `hasRole("ADMIN")` 兜着（等于只有管理员能调这个登录口，逻辑上是废的，但路径规则一放宽即成洞）。全仓无 change-password 端点，前端 `api/auth.js:27-32` 直接 `Promise.reject`，`Profile.vue:124` 却走成功分支（永远走不到）。

**影响**：现场无法自助改密（README 要求"投产前必须改口令"，只能上服务器跑 `reset-password.sh`）；两个登录口 = 两套鉴权语义，路径规则一旦放宽即成洞。

**改法**：① 新增 `PUT /api/auth/password`（校验旧口令 → 强度校验 → 更新 hash → 递增 `token_version` 让旧 token 失效）；② 删除 `/api/user/login`（前端已确认只用 `/auth/login`）；③ 前端 Profile 改密接真接口，或先隐藏表单。

### PERF-01　首屏 2.9MB，element-plus 与 echarts 全量引入

**证据**：`main.js:3-5` 全量 `ElementPlus` + `element-plus/dist/index.css`；`import * as echarts` 出现在 12 个文件；`vite.config.js` 无 `manualChunks`；实测 `index-Umx_xh2d.js` 1.8MB（gz 565KB）+ `index-Bb6yjXMn.js` 1012KB（gz 343KB）。

**影响**：弱网/现场工控机首屏 >3s；每次发版整包失效（虽有版本守卫兜底，但用户会被强制刷新）。

**改法**：`unplugin-vue-components` + `ElementPlusResolver` 按需注册（样式同步按需）；echarts 改 `echarts/core` + 按需 `use([BarChart, LineChart, PieChart, GridComponent, TooltipComponent, LegendComponent])`；`build.rollupOptions.manualChunks` 拆 `echarts`/`element-plus`/`vendor`。预期首屏降到 ~800KB（gz ~250KB）。

### PERF-02　图表不释放、轮询不暂停

**证据**：`Dashboard.vue:310,324,336,345` 初始化 4 个实例，全文无 `onBeforeUnmount/onUnmounted`；`DefectsView.vue:142`、`YieldView.vue:174` 同样只在重取数据时 dispose；`CameraStatusView.vue:437` `setInterval(refreshAll, 30000)` 无 `visibilitychange` 暂停，`watch(filterParams, loadData)` 与轮询并发无请求序号（旧响应可覆盖新结果）。

**改法**：统一走 `EChart.vue`（内部 `onMounted` init / `onBeforeUnmount` dispose / `ResizeObserver`）；轮询用"页面可见才跑 + `inFlight` 标志 + 请求序号"，可直接照抄 `ServerMonitorView.vue:461-479` 的现成写法。

### ARCH-01　`LineAnalyticsController` 1493 行，职责过载

**证据**：23 个端点、12 个写端点 `@PreAuthorize` 数量为 **0**（仅靠 `/api/v1/analytics/**` 路径规则）；`@Scheduled` 直接挂在 Controller 上（`:792, :832`）；自建 `Executors.newSingleThreadExecutor`（`:85`，无 shutdown、非 Spring 管理）；`aggregationJobs` 这个 `ConcurrentHashMap` 字段（`:91`）已无任何读写方（死字段）。

**影响**：报表口径、聚合调度、看板 CRUD、导出四类关注点耦合在一个类里；任何改动都要回归全站统计；写端点护栏只存在于一处容易漂移的路径规则里。

**改法（分两步，不必一次做完）**
1. 拆分：`AnalyticsReportController`（读）/ `DashboardAdminController`（看板与组件 CRUD）/ `AggregationAdminController`（任务与调度）/ `AggregationService`（重建逻辑与线程池）；`@Scheduled` 移到 `analytics/infra/task/DailyAggregationTask`。
2. 12 个写端点补 `@PreAuthorize("hasRole('ADMIN')")`（与路径规则双保险，SEC-02 修复时已验证该模式）；线程池换成注入的 `TaskExecutor`（bean 名 `analyticsAggregationExecutor`，`shutdown` 交给容器）。

### ERR-01　业务失败仍 HTTP 200，前端大面积不判码

**证据**：`ResultVO.fail/error` 全仓 **80 处**（v3 记 93，已迁一部分），HTTP 恒 200；`ApiStatusAdvice` 只认 `ApiErrorCode` 登记过的码（设计上"存量零影响"）。前端 `res.data.data` 直读 **48 处**，只有 3 处判 `code !== 200`（`ConfigView.vue:736,979`、`LineAnalyticsView.vue:874`）。

**影响**：后端返回 `code:500` 时前端把错误当数据渲染（空表/0/NaN），现场表现为"没数据"而不是"出错了"；监控无法按状态码告警。

**改法**：① 前端在 `utils/request.js` 的响应拦截器统一解包：`code !== 200 → ElMessage.error + reject`，这一处改动收益最大（57 处不用逐个改）；② 后端按族迁移：登录/上传/设备三类先迁到 `ApiErrorCode`（有监控价值），其余随迭代；③ 迁移时同步删掉 Controller 里手写的 `ResultVO.fail`。

### TEST-02　测试分布失衡，最贵的域没有 SQL 测试

**证据**：19 个类 / 128 `@Test`，按域分布 device 39、analytics 27（全部 Mock 4 个 Repository 的控制器外壳）、defect 24、system 18、shared 11、inspection 4、iam 3、masterdata 1。`@SpringBootTest` 0 个、`@WebMvcTest` 0 个；唯一真 SQL 测试是 `DefectImageRepositoryCameraSummariesTest`（H2 内联建表）。analytics 的 1023 行 Repository 零覆盖。

**影响**：聚合表重建、缺陷图片事实表/聚合表切换、`UNION ALL` 历史路由这些"改错就静默出错数"的逻辑，全靠人眼。

**改法**：① 用 H2（MySQL 模式）为 `LineAnalyticsQueryRepository` 与 `AnalyticsAggregationRepository` 建 6~10 个真 SQL 用例（输入固定数据 → 断言产量/良率/缺陷分布）；② iam 补 `@WebMvcTest` + 完整 advice 的鉴权切片（401/403/ADMIN 越权），替代现有 standalone 模式；③ 每个 Controller 至少 1 个 MockMvc 用例，作为新增端点的准入条件。

### OPS-01　没有健康端点，部署脚本的"健康检查"是假的

**证据**：无 actuator 依赖、无 `management.*` 配置；`deploy_jar.sh:40` `HEALTH_URL=http://127.0.0.1:8091/`，`:117-118` 只判 HTTP 200 —— 根路径由静态 `index.html` 返回，与 DB 无关；`:126-143` 回滚后只循环等 200、**不校验结果**就打印"已自动回滚"；脚本仅 `set -u`。

**影响**：DB 挂死、Mapper 全错、连接池耗尽时，部署仍判成功，问题留到用户点页面才暴露；回滚失败也报成功，是最坏的一种"假绿"。

**改法**：① 加 `spring-boot-starter-actuator`，暴露 `health`（含 `db`）并只绑 127.0.0.1；② `deploy_jar.sh` 改 `curl -fsS http://127.0.0.1:8091/actuator/health | grep -q '"status":"UP"'`；③ 回滚后同样校验，失败 `die`；④ 补 `set -euo pipefail`，逐条显式处理允许失败的命令。
