# 踩坑速查 — 产线缺陷在线AI检测系统

> 从历史事故中提炼的"会再踩"清单。每条都标注了**现象 → 根因 → 正确做法**。
> 详细的排查过程见 `.workbuddy/memory/` 每日日志与 `docs/` 下的评审报告。

## 一、配置与密钥

### 1.1 占位符不能带空默认值

- **现象**：服务 `active`、HTTP 200，但业务全错（连不上库）
- **根因**：`password: ${MYSQL_PASSWORD:}` —— 缺环境变量时应用能启动，连库时才炸
- **正确做法**：`password: ${MYSQL_PASSWORD}`（无默认值）→ 启动即失败并明确报
  `Could not resolve placeholder 'MYSQL_PASSWORD'`

### 1.2 install.sh 口令来源

- **现象**：新机装完服务启动即挂
- **根因**：用 sed 从 `application.yml` 提取口令 —— 那是占位符 `${MYSQL_PASSWORD}`，
  被当成口令写进 `/etc/default`
- **正确做法**：顺序必须是 **环境变量 → 现场既有 `/etc/default` → 交互式读取**，
  且显式拒绝 `${...}` 形态

### 1.3 install.sh 删 JWT_SECRET

- **现象**：重装后 JWT 密钥消失，所有登录失效
- **根因**：第 8c 节 sed 删了 `JWT_SECRET` 却只写回 `MYSQL_PASSWORD`
- **正确做法**：删后必写回
- **回归**：`docs/scripts/test_install_password_source.sh`（11 项断言）

## 二、相机身份与数据关联

### 2.1 必须用 camera_code，不能用 camera_name

- **现象**：两台重名相机的计数互相串
- **根因**：`camera_name` 现场重名（`CV1_Cam1`/`CV2_Cam1` 各 2 行）；
  原实现心跳按 name 先匹配 `LIMIT 1`，图片通道是**无优先级 OR 链**+`LIMIT 1` → 命中行不确定
- **正确做法**：两处统一 **code-first**（`uk_camera_code` 是唯一索引）；
  名称兜底**必须唯一**，多行则拒写 + WARN

### 2.2 设备上报名与系统配置名不一致

- **现象**：至今未触发串号
- **根因**：设备上报名是中文（"正面检测"），系统配置存英文代号（`CV1_Cam1`）
- **状态**：这个不一致正是串号至今未触发的原因，**是否统一待用户确认**

### 2.3 图片关联字段

- `defect_image_file.camera_id` 存的是 **camera_code**（如 `DA9200622`）
- 关联要 `JOIN dim_camera c ON c.camera_code = f.camera_id`

### 2.4 两条上报通道写两套表

| 通道 | 写入表 | 现场 |
|---|---|---|
| `defect-images/upload`（**真正在用**） | `defect_image_batch/_file/_box` | ✅ 7.9 万+ 张 |
| `batch-upload`（冻结契约） | `fact_inspection_*` + `agg_quality_30m` / `agg_defect_type_30m` | ❌ 基本不用 |

- 只读 `agg_*` 的统计接口现场永远为 0 → 必须做 `defect_image_*` 兜底（带 `dataSource`）
- `product_detection_history` 实测 **0 行** → 检测记录页必须用 `defect-images/history`
- 图片通道**无良品样本** → `okCount=0`、`yieldRate=null`，前端显示「—」，**绝不显示 0%**

## 三、接口与权限

### 3.1 前端 API 路径曾断裂

| 前端写的 | 后端实际 | 后果 |
|---|---|---|
| `/users` | `/api/user`（**单数**） | 404 |
| `/anomaly/alerts` | `/api/alerts/active` | 404 |
| `resolveAlert` 用 GET | 实际是 **POST** | 405 |
| `/profile/password` | **无此端点** | 405，改密走服务器 `reset-password.sh` |

- **核对方法**：`grep -rhoE '@RequestMapping\("[^"]+"\)' controller/*.java` 对比 `api/*.js`
- **回归**：`docs/scripts/probe_api_paths.sh`

### 3.2 重定向兼容桩导致视图永不加载

路由 `/system/users`、`/factories`、`/lines`、`/workstations`、`/companies`、`/brands`、
`/defect-types`、`/holidays` 都是**重定向兼容桩**（→ `/system/config`），
所以 `UserList.vue` 永不加载 —— 这是其假数据长期未被发现的原因。
`SystemSettings.vue` 同理（无路由引用），前端 15 个孤立视图约 4,192 LOC。

### 3.3 401 与 403 必须区分

改造前 Spring Security 2.7 对"未认证"和"权限不足"**都返回 403**，响应体完全相同，
无 `WWW-Authenticate` → 前端无法区分。

| 场景 | 状态码 | reason |
|---|---|---|
| 无 token / 无效 / 过期 | **401** | `AUTHENTICATION_REQUIRED` |
| 已登录但角色不足 | **403** | `ACCESS_DENIED` |

- 后端：`SecurityConfig` 显式配置 `restAuthenticationEntryPoint()` / `restAccessDeniedHandler()`。
  `JwtRequestFilter` **不写响应**，只不写 SecurityContext，由 `ExceptionTranslationFilter` 分派
- 前端 `utils/auth-redirect.js` 集中判定 + `request.js` 响应拦截器统一处理：
  401 → 清 token + 存上下文 + 跳登录；403 → **仅未登录才跳**，权限不足只透传提示
- 上下文存 sessionStorage `camera_login_redirect`，**用后即焚**；
  回跳走 `isSafeRedirect()` 白名单（防开放重定向）

### 3.4 安全模型

- 白名单必须精确到方法与路径，禁止任何 `/**` 兜底放行
- 路径级 `hasRole("ADMIN")` + 方法级 `@PreAuthorize` + `@EnableGlobalMethodSecurity`
- 新增管理端点必须同改三处：`SecurityConfig` 路径规则、Controller `@PreAuthorize`、`verify.sh` 回归项
- 图片静态读取 `/api/v1/defect-images/file/**`、`/api/v1/camera/image/**` **必须放行**
- 登录页提示用橙色 `.notice-msg`（区别于红色密码错误 `.error-msg`）

## 四、部署

### 4.1 部署后旧页面必然失效（每次部署必现）

- **现象**：浏览器里开着**部署前**的页面 → 点懒加载路由 → **URL 不变、页面不刷新、无后端请求**
- **根因**：Vite chunk 名带内容哈希 → 每次构建全部改名 → 旧标签页路由表指向旧 chunk → 404 →
  `"Failed to fetch dynamically imported module"` → vue-router 导航 Promise 被 reject →
  **导航静默中断**（无 `router.onError` 时零反馈）
- **关键**：自动化每次新开页面（当前 index.html）→ **永远测不出**；
  只有**跨部署的旧标签页**才触发
- **三层修复**：
  1. `frontend/src/utils/resource-version.js`：3 分钟轮询 + 切回前台比对入口 chunk 哈希 →
     提示刷新；捕获 `error`/`unhandledrejection`/`router.onError` → 自动刷新一次
     （sessionStorage 防死循环）
  2. `installer/linux/build-release.sh`：**保留上一版 chunk** 与新版共存，
     `assets/.versions` 记归属，`KEEP_STATIC_VERSIONS`（默认 3）控版数
  3. `docs/scripts/recover_legacy_chunks.py` + `prune_legacy_chunks.py`
- **踩过的坑**：
  - 改注释**不改变产物哈希**（tree-shake）→ 验证要用改变行为的改动
  - `vite build` **不清空 dist** → 构建前必须清空
  - 版本标记顺序必须**先标 current（仅本次 dist）再标历史**，否则统计恒为 0
  - **zipfile 增量写 JAR** 时跳过所有 assets 条目统一重写，否则 `Duplicate name`
  - **绝不能用 `jar cf` 重打包 Spring Boot JAR** → 会丢 `Main-Class: JarLauncher`/`Start-Class`/`classpath.idx`
  - 恢复脚本与部署脚本**顺序冲突** → 必须「部署完 → 恢复 chunk → 重启」，
    部署流程中间动 JAR 会让服务停在 stopped

### 4.2 Linux 部署脚本踩过的坑（已全修，勿回退）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | `JAVA_OPTS` 未加引号 → 空格截断 → status=127 | 必须加引号（run.sh 用 bash source） |
| 2 | `StartLimitIntervalSec`/`StartLimitBurst` 写在错误段 | 必须在 `[Unit]` 段 |
| 3 | `systemctl list-unit-files \| grep -q` 在 `pipefail` 下误判（SIGPIPE） | 用 `grep -c` |
| 4 | `systemctl restart` 返回 0 只代表排队成功 | 要轮询 `is-active` |
| 5 | `StartLimitBurst=3` 触发后无法重启 | 先 `systemctl reset-failed` |
| 6 | `tar -czf` 打成 644（Windows 不保留权限位） | 用 Python `tarfile` 手工设 mode；`os.path.relpath` 返回**反斜杠**须 `.replace("\\","/")` |
| 7 | shell 脚本 CRLF → `set: pipefail: invalid option name` | 必须 LF 行尾 |
| 8 | `sudo -S` 与 heredoc 冲突 | 独立脚本文件 + `sudo -S python3 file.py` |
| 9 | `install.sh` 数据库未建时 `exit 1` | 装完按 `DB_PENDING` 返回 0/1/2 |
| 10 | `install.sh` 写 `/etc/default` 不幂等 | 追加前剥离整个段落含注释行 |
| 11 | `/etc/default` 权限不是 640 | 必须 640（含 DB 与管理员口令） |
| 12 | bash 变量拼 mysql 命令丢引号 | 写函数 `run_sql(){ mysql -uroot -p"$1" ...; }` |
| 13 | 640 root 文件普通用户读不到 → 误报"密钥缺失" | `service.sh` 里 grep/stat 需用 sudo |
| 14 | `grep -qE "^K=..+"` 匹配不到带引号的值 | 应写 `=.+` |
| 15 | `sudo -S` 提示混入 stdout → `grep -c` 变 "00" | 用 `grep -oE '[0-9]+' \| tail -1` |
| 16 | `set -u` 下变量未初始化即引用 | 会直接退出（`db_pw: unbound variable`） |
| 17 | **静默失败是最大的坑** | `echo "${SUDO_PASSWORD:-}" \| sudo -S ... 2>/dev/null` → 未设口令时传空串 → 备份与替换全失败，但脚本仍打印"服务已 active" → 必须：**前置检查 + 不吞错误 + 每步校验返回码** |
| 18 | `tar -tv` 权限位是 10 字符（含类型位） | 与 9 字符比较恒不相等 → 取末 9 位 |

### 4.3 大文件上传到服务器（本机 → 10.2.77.72）

- `scp` **不支持 SSH_ASKPASS** → 必须用 Python
- paramiko **SFTP 子系统不可用**（报 ENOENT）
- paramiko **管道传 61MB 被服务端断开**（"Socket is closed"）
  → 唯一可行：**base64 分块 + 普通命令通道**（`docs/scripts/upload_jar_b64.py`）
- Git Bash 会把 `/home/...` 转成 Windows 路径 → 需 `MSYS_NO_PATHCONV=1`
- `/etc/default/camera-detection` 口令格式 `MYSQL_PASSWORD="xxx"`（带引号），解析要去引号
- 非交互下 `sudo -n` 拿不到文件 → 必须 `sudo -S`

### 4.4 verify.sh 必须 root + 正确口令

否则 7 项误报失败：
```bash
echo '<sudo口令>' | sudo -S env VERIFY_PASSWORD='<应用口令>' MYSQL_PASSWORD='<库口令>' \
  bash /opt/camera-detection-system/scripts/verify.sh
```
→ 正常 **28/28 全通过**

### 4.5 GitHub 推送（本机代理拦 github.com）

- **现象**：原生 `git push` 报 `CONNECT tunnel failed, response 502` 或
  `schannel: server closed abruptly` —— 本机代理只对 `api.github.com` 放行，
  而 git 的 smart-HTTP 协议必须走 `github.com`
- **解法**：走 Git Data API（`docs/scripts/push_via_github_api.py`）
- **大文件限制**：Git Data API 拒绝 base64 后的大请求体
  （实测 78.6MB → HTTP 422 `Sorry, your input was too large to process`）
  → 已修：超 `MAX_BLOB_BYTES`（默认 40MB）的 blob **复用远端已有 sha**，
  跳过的文件会在输出中列出
- **token 传递有坑**：
  ```bash
  # ❌ 这样会 401 —— shell 二次解析把 token 搞坏
  export GITHUB_TOKEN=$(git credential fill | grep password= | cut -d= -f2-) && python3 push.py
  ```
  → **用 Python 取值后放进 `env` 传子进程**：
  ```python
  out = subprocess.run(['git','credential','fill'],
                       input='protocol=https\nhost=github.com\n\n',
                       capture_output=True, text=True).stdout
  token = [l.split('=',1)[1].strip() for l in out.splitlines() if l.startswith('password=')][0]
  env = dict(os.environ); env['GITHUB_TOKEN'] = token
  subprocess.run([sys.executable, 'push.py'], env=env)
  ```
- token 来源：`git credential fill`（Git Credential Manager，`ghp_` 前缀）
- **远端大文件的现状**：5 个二进制产物（jar/tar.gz/exe，约 270MB）在远端
  **保持旧版本**，本地构建产物始终最新 —— 不影响交付
- **查远端状态要用 `/commits?sha=main`**：
  `/commits/main` 会走缓存，可能显示旧 sha 让人误判"没推上去"
- ⚠️ **脚本里写日志别用 `/tmp/xxx.log`** —— Windows 上 Python 会解析成
  `D:\tmp\xxx.log`，目录不存在直接抛 `FileNotFoundError`，
  **把已成功的推送结果给丢了**。用 `os.path.join(os.environ['TEMP'], ...)`

### 5.1 基线实测

| 项 | 值 |

- 图片 → `/data/camera-detection/images/defect-images/{yyyyMMdd}/{cameraId}/{HHmmssSSS}_{uuid8}.{ext}`

### 5.3 图片清理的真实机制

- **`defect_image_file`/`_box`/`_batch` 无定时任务** → 靠 `cleanup-defect-images.sh`（cron 03:30）
- 保留期：`defect_image_file`/`_box` **7 天**、`_batch` 30 天、`camera_images` 30 天
- 清理**必须先删库记录再删磁盘文件**
- 图片显示走**相对路径**解析，换机只需拷到同一相对位置

## 七、DDD 重构（P3）专属

### 7.1 SQL 搬运铁律

1. **SQL 逐字搬运，零优化**（含参数拼接方式），只做物理位置迁移
2. 实体 ID 类型必须与 Repository 签名一致 —— `DimProductionLine`/`DimWorkstation`/`CameraStatus`
   的 ID 是 **`Integer`**，`CameraStatus.id` 是 `Long`（写错编译能过但行为可能变）
3. 写操作超过 5 个参数就用 DTO（如 `CameraDefectMappingRow` 19 列），防位置参数错位
4. `@PostConstruct` 里的 `ensure*` 建表本阶段留在 Repository，P5 再统一到 `SchemaInitializer`

### 7.2 验证顺序（每阶段必走）

```
mvn test → 打包 → 部署 → verify.sh 28/28
  → 键结构树 diff（compare_structure.py，只比键路径、忽略值）
  → 写接口业务回归（ZZTEST* 数据）
  → 浏览器回归（真实数据 + 0 JS 错误）
  → 清理 ZZTEST 数据 + 核验现场数据完整性
```

**为什么用键结构树比对**：`api_snapshot.py` 的 diff 比对**归一化后的值**，
运行时数据漂移（相机实时上报、看板聚合、CPU 瞬时值）会报出来，需人工判定；
`compare_structure.py` 只比**键路径集合**，是「行为不变」的硬指标。

### 7.2.1 ⚠️ 验证写接口时不要改动既有数据的状态

- **现象**：批次③ 键结构比对报 `analytics_line_summary` 少了一组键
- **根因**：批次② 验证时用 `PUT /api/v1/config/mapping-exceptions/34/close`
  关闭了**唯一一条**映射异常 → 它不再出现在"待处理异常"列表里 →
  `mappingExceptions` 从 1 条变 0 条 → 键路径树少了一层
- **不是代码问题**，但**测试动了现场数据**
- **正确做法**：
  1. 验证写接口时优先挑**不改变既有数据状态**的端点；
  2. 必须改状态的（如 close）要**记录并还原**：
     `UPDATE ... SET status='OPEN', handled_time=NULL WHERE exception_id=34`
  3. 每次验证后核对现场数据量（`camera_status` / `dim_camera` / `defect_image_file`）

### 7.2.2 异常语义必须原样保留（重构时最易改坏）

| 场景 | 原语义 | 改错的后果 |
|---|---|---|
| `CameraDashboardController.count()` | **catch 掉所有异常返回 0** | 依赖检查失败会阻断删除流程 |
| `CameraStatusServiceImpl.ensureColumn()` | catch **在方法内部**，失败仅记 WARN 后继续 | 字段检查失败会抛到启动流程 |
| `CameraStatusServiceImpl.insertAnomalyAlert()` | 只 catch `DataAccessException`（不是 Exception） | 扩大 catch 会吞掉非数据库异常 |
| 告警写入的 `line_id`/`workstation_id` | 为空时写 **0** 而非 NULL | 改变数据语义 |
| 相机删除 | **两表都逻辑删除** + 映射/令牌级联清理 | 物理删除会不可恢复、留孤儿数据 |

### 7.2.3 跨域归属：SQL 按表所属域下沉，不是按调用方分置

批次③确立的原则。例：`CameraStatusServiceImpl`（device 域）里的三处 SQL ——
- `sys_system_setting` 查询 → **system 域** Repository
- `fact_anomaly_alert` 写入 → **analytics 域** Repository
- `camera_status` 的列检查 → **device 域** Repository

这样 P4 抽跨域接口（`CameraDirectory`）时边界才清晰。
**反例**：把三个域的 SQL 全塞进 device 域的一个 Repository —— 看着省事，
但会让 device 域反向依赖 system/analytics 的表结构，P4 拆分时反而更麻烦。

### 7.3 ResultVO 工厂方法语义（写契约测试常搞反）

| 方法 | code | message | data |
|---|---|---|---|
| `success(data, message)` | 200 | 自定义 | data |
| `success(data)` | 200 | **"操作成功"** | data ← **文案在这里** |
| `fail(message)` | 500 | **自定义** | null |
| `fail(message, data)` | 500 | 自定义 | data |
| `fail(code, message, data)` | 自定义 | 自定义 | data |

### 7.4 Spring MVC 边界

- `@RequestBody` 传 `null` → **在进入 Controller 前就返回 400**，
  代码里 `if (body == null)` 分支实际不可达（防御代码），测试要用 `{}` 而非 `null`
- `@PathVariable Long id` 与实体 `Integer` ID 不同源，注意转换

### 7.5 P2 搬包时踩过的坑

- 批量 mv 脚本把包名当全限定名 → 类被错位到 `<层名>.java`（35 个错位）
  → **恢复靠 git status 的 `R` 记录**（rename 保留 old→new 映射）→ 反向 `git mv` + 按目录重写 package
- 教训：① 批量 mv 脚本必须先在副本演练；② git 的 rename 记录是精确恢复的救命稻草；
  ③ package 声明校验 = 「目录路径即包名」全量重写最稳
- `OperationLogAspect` 切点 `com.wms.controller..*` → 改域后必须同步改为 `com.wms.*.api..*`
  （不改会**静默失效**，不报错）
