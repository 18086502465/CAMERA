## 1.4 构建与发布流程

### 现状链路

```
build-release.sh (Git Bash / Linux)
  ① 前端构建 → ② 同步到 static → ③ mvn package → ④ 测试
  → ⑤ rm -rf stage → 组装 → ⑥ 建库脚本 → ⑦ 部署脚本+unit → ⑧ tarfile 打包
        ↓
  camera-detection-system-1.0.0.tar.gz (52.8 MB)
        ↓  【人工】scp → 【人工】sudo tar → 【人工】install.sh
  /opt/camera-detection-system/
```

### 存在的问题与风险点

| #   | 问题                                                                | 风险等级                                                               |
| --- | ----------------------------------------------------------------- | ------------------------------------------------------------------ |
| R1  | **产物中混入 52.8MB tar.gz 与 58.3MB JAR 并入库**                          | 高 —— GitHub 每次提交产生 100MB+ 二进制 diff；`.git` 已 459MB（size-pack 294MB） |
| R2  | **无 CI/CD** —— 无 `.github/workflows`、无 GitLab CI                  | 高 —— 构建与测试全靠人工，任何一次提交都可能带病上线                                       |

| R4  | **无灰度/蓝绿机制** —— 唯一发布方式就是覆盖 JAR                                    | 中 —— 现场只有一台服务器，无流量切换手段                                             |
| R5  | **无回滚命令** —— 备份了 20 个 JAR（1.3GB），但没有一键回滚脚本                        | **高** —— 出事时要手工翻文件名                                                |
| R6  | **JAR 备份无上限、无清理** —— 20 个备份占 1.3GB，含 11-02 的陈旧版本                  | 中 —— 磁盘浪费，且找不到"上一次好的版本"                                            |

| R9  | **发布步骤全人工** —— scp / tar / install / 验证 共 5 步手工                   | 中 —— 步骤多、易漏、不可追溯                                                   |

# 第二部分： 

## 2.1 优化目标与设计原则

**目标**：更精简、更易维护、更易回滚，减少手动步骤与重复操作。

**核心原则**：

1. **一份事实源** —— 产物、版本号、配置项、日志路径只在 `installer/linux/` 定义一次
2. **配置与代码分离** —— 产物永远不含密钥
3. **一切可回滚** —— 每个变更动作都有对应的反向动作，且反向动作同样是一键
4. **发布即验证** —— 部署脚本内置健康检查，不健康自动回退
5. **人在环内** —— 保留人工确认点（生产环境），但不让人执行机械步骤

## 2.2 改进项清单

### A. 构建产物的组织方式

| #       | 现状问题                                                                        | 建议方案                                                                                                                         | 预期收益                                                      | 难度 |
| ------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | -- |
| **A-1** | `dist-release/` 同时入库 52.8MB tar.gz + 58.3MB JAR + stage 全量副本，`.git` 达 459MB | **产物不进 Git**，改由 CI Artifacts / Release 附件分发；`.gitignore` 排除 `dist-release/linux/*.tar.gz` 与 `stage/app/*.jar`，仓库只保留构建脚本与安装脚本 | 仓库体积可从 459MB 降至 <50MB；GitHub 推送不再触发 GH001 警告；clone 速度大幅提升 | 低  |
| **A-2** | JAR 固定名 `time-bucket-demo.jar`，无法从文件名识别版本                                   | 产物改名为 `camera-detection-<版本>-<git短sha>.jar`，同时在 `/opt/.../app/` 保留 `current.jar` 软链                                          | 一眼看出线上版本；回滚目标明确                                           | 低  |
| **A-3** | `VERSION` 硬编码在 `build-release.sh` 里                                         | 从 Git tag 或 `git describe --tags --always` 自动推导；无 tag 时用短 sha                                                                | 版本与代码一一对应，杜绝"改了代码没改版本号"                                   | 低  |
| **A-4** | stage 是"打包中间目录"却整体入库，且 `rm -rf` 会连带删掉里面手工加的文件                               | stage 明确为**纯中间目录**（加入 `.gitignore`），只保留 `installer/linux/` 里的源文件                                                             | 消除"stage 里到底该放什么"的困惑                                      | 低  |

### B. 脚本与命令的自动化程度

| #       | 现状问题                                                    | 建议方案                                                                                                                       | 预期收益                                   | 难度 |
| ------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | -- |
| **B-1** | `service.sh` 只提供 `start/stop/restart/status/logs` 5 个命令 | 扩展为统一运维入口：`update`（部署新版本，含健康检查与自动回滚）、`rollback`（回滚指定/上一版本）、`health`（健康检查）、`version`（显示版本与构建时间）、`backup`/`restore`、`verify` | 运维动作收敛到一个脚本，现场不再需要记 scp/tar/install 组合 | 中  |
| **B-2** | 发布需 5 步人工（scp → tar → install.sh → curl 验证 → 看日志）       | `service.sh update <pkg.tar.gz>` 一步完成：校验包 → 备份当前 JAR → 原子替换 → 启动 → 健康检查 → 失败自动回滚                                           | 手动步骤从 5 步降到 1 步；发布可追溯                  | 中  |
| **B-3** | 各脚本各自实现 mysql 调用、sudo 调用、日志输出，风格不统一                     | 抽出 `scripts/lib/common.sh`：统一 `log/ok/die`、统一 `mysql_exec`（口令走环境变量）、统一 `require_root`、统一 `retry_wait`                      | 减少重复代码；新脚本编写成本降低；风格统一                  | 低  |
| **B-4** | `verify.sh` 382 行但只能人工跑，且不区分"脚本用法错误"与"真故障"              | 保留为 `service.sh verify`；同时在 `check-disk-usage.sh` 基础上增加"业务健康"探测（数据库连通、图片目录可写、心跳近 5 分钟内有更新）                                 | 一条命令判断系统是否真的健康，而不只是"进程活着"              | 中  |

> 改造过程还暴露并修复了一个**静默失败**：  
> |  |  |  
> | --- | --- |  
> 旧 `deploy_jar.sh` 用 `echo "${SUDO_PASSWORD:-}" | sudo -S ... 2>/dev/null`，  
> 环境变量未设置时传入空串 → sudo 认证失败 → 备份与替换全部失败，  
> 但错误被 `2>/dev/null` 吞掉，脚本仍打印「服务已 active」——  
> **JAR 根本没换**，排查时极具误导性。现已改为：前置检查口令、  
> 不吞错误、每步校验返回码、替换后校验大小、健康检查失败自动回滚。

### 已落地 2：`service.sh` 扩展为统一运维入口（B-1 / F-2 / G-1 / G-2 / D-3）

新增 5 个子命令，实机全部验证通过：

| 命令                         | 能力                               | 实测结果                                           |
| -------------------------- | -------------------------------- | ---------------------------------------------- |
| `service.sh version`       | 版本、JAR 大小、SHA256、修改时间、可回滚备份清单    | 正常输出                                           |
| `service.sh health`        | 进程 + HTTP + 三分区磁盘 + 数据库连通 + 设备心跳 | 结论「健康」（13 台心跳）                                 |
| `service.sh config-check`  | 密钥文件权限、密钥是否注入、配置是否残留明文           | 结论「配置与密钥管理正常」                                  |
| `service.sh rollback [版本]` | 回滚到指定/上一版本，回滚前自动另存当前版本，回滚后健康检查   | 已实现                                            |
| `service.sh cleanup [保留数]` | 清理过量 JAR 备份                      | 已执行：删除 16 个，**1.3GB → 414MB**，`/` 磁盘 13% → 10% |

### 已落地 3：部署脚本增强（`deploy_jar.sh`）

- 前置检查 `SUDO_PASSWORD`，缺失即退出（不再静默失败）
- **原子替换**：先写 `.new` 再 `mv`，避免服务读到半个文件
- 替换后校验 JAR 大小与源一致
- 启动后轮询健康检查（最多 40 秒）
- **健康检查失败自动回滚**到上一版本并明确告警
- 输出回滚命令，便于人工二次确认

### 已落地 4：构建脚本权限自检修复（顺带）

`tar -tv` 输出的权限位是 10 字符（含文件类型位 `-rwxr-xr-x`），  
原实现与 9 字符的 `rwxr-xr-x` 比较恒不相等 → 打包在最后一步误报失败。  
改为取末 9 位再比较。
