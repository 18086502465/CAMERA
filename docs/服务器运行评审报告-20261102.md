## 3. ★ P1：每分钟 4 次重复 DDL —— 慢查询日志被自己的建表语句淹没

### 3.1 现象

MySQL 慢查询日志 `/var/log/mysql/slow.log` 里，**近期的慢查询全是同一条建表语句**：

```
# Time: 2026-11-01T20:16:24.300856Z
# Query_time: 7.411144  Lock_time: 0.000003  Rows_sent: 0  Rows_examined: 0
CREATE TABLE IF NOT EXISTS analytics_aggregation_schedule (...);

# Time: 2026-11-01T18:30:11  → Query_time: 1.221507
# Time: 2026-11-01T20:12:16  → Query_time: 1.766413
# Time: 2026-11-01T20:44:27  → Query_time: 2.251190
# Time: 2026-11-01T21:23:29  → Query_time: 2.031355
```

历史压缩包 `slow.log.2.gz`（10-31 10:11）里还有 1 条 —— 说明**从 10-31 就在持续产生**。

### 3.2 根因

`LineAnalyticsController` 有 3 个 `ensure*` 方法，**每次被调用都执行一遍 `CREATE TABLE IF NOT EXISTS`**：

```java
private void ensureAggregationScheduleTable() {
    jdbcTemplate.execute("CREATE TABLE IF NOT EXISTS analytics_aggregation_schedule (...)");  // ← 每次都跑
    ...
}
private void ensureDailyAggregationTables() {  // 2 条 DDL
private void ensureAggregationJobTable()    {  // 1 条 DDL + 3 条 ALTER
```

而它们被这个定时任务每分钟调一次：

```java
@Scheduled(fixedDelay = 60000)
public void runScheduledDailyAggregationIfNeeded() {
    ensureAggregationScheduleTable();     // ← 每分钟
    ...
}
```

**每分钟 = 每天 5760 次无谓 DDL。**

### 3.3 危害

| # | 危害 | 实测/推理依据 |
|---|---|---|
| 1 | **元数据锁（MDL）阻塞** | DDL 要拿 MDL，期间该表上所有查询排队。实测单次最慢 **7.4 秒** |
| 2 | **DDL 是 InnoDB 最重的操作** | 不可回滚、不能与事务共存、会刷 redo/binlog |
| 3 | **慢查询日志被淹没** | 真实业务慢查根本找不到（现在慢日志 100% 是这条 DDL） |
| 4 | **binlog 污染** | 每天 5760 条 DDL 事件进 binlog |
| 5 | **表被误删后无法自愈** | 反过来讲，`ensure*` 的本意是"表没了就建"，改成只执行一次后需要重启应用 —— 这是可接受的取舍 |

### 3.4 修复

三个 `ensure*` 各加一个 `AtomicBoolean` 守卫，**DDL 只在进程内首次调用时执行一次**：

```java
private final AtomicBoolean scheduleTableEnsured = new AtomicBoolean(false);

private void ensureAggregationScheduleTable() {
    if (!scheduleTableEnsured.compareAndSet(false, true)) {
        return;   // ★ 已建过，直接跳过，不再重复执行 DDL
    }
    try {
        jdbcTemplate.execute("CREATE TABLE IF NOT EXISTS ...");
        ...
    } catch (Exception e) {
        scheduleTableEnsured.set(false);   // 建表失败要复位，否则再也不会尝试
        throw e;
    }
}
```

> **失败复位**是关键：否则第一次建表失败（比如 MySQL 短暂不可用），
> 标志位会永久停在 `true`，应用再也不会建表 —— 那才是真的故障。
> 用 `compareAndSet` 而非 `get()+set()`，保证多线程下也只建一次。

### 3.5 修复后实测 ✅

```
部署 → 等待 100 秒（覆盖 1+ 个定时周期）→ 手动再调一次接口
  GET /api/v1/analytics/aggregation/schedule -> 200

慢查询日志中 analytics_aggregation_schedule 的条数：
  部署前：5    部署后 +100 秒 + 手动调接口：仍是 5   ← 不再增长 ✅
```

> 修复前：每分钟 +4 条。修复后：**0 条新增**。

## 4. ★ P2：自检脚本每次运行都往生产库写脏数据

### 4.1 现象

`fact_inspection_mapping_exception`（映射异常表）里躺着：

```
exception_id  batch_id         source_code       create_time
21            VERIFY-UNMAPPED  __NOT_MAPPED__    2026-10-31 16:36:35
20            VERIFY-UNMAPPED  __NOT_MAPPED__    2026-10-31 16:36:11
```

`batch_id = VERIFY-UNMAPPED` —— 这是**自检脚本自己造的**。

### 4.2 根因

`verify.sh` 第 7 节要验证"未映射编码应返回 422"，就发了一条真实上报：

```bash
curl -X POST ... -H "X-Batch-Id: VERIFY-UNMAPPED-$(date +%s)" \
  -d '{"batchId":"VERIFY-UNMAPPED", ..., "defects":[{"sourceCode":"__NOT_MAPPED__","count":1}]}' \
  "${BASE_URL}/api/v1/camera/inspection/batch-upload"
```

服务端**如实处理**并写库：
- `fact_inspection_mapping_exception` +1 条（UNMAPPED 异常）
- `fact_inspection_batch` +1 条（批次）
- `fact_inspection_defect_count` +1 条

而这两张表**没有任何定时清理任务**（`sys_data_retention_policy` 表只是元数据，代码从不读它）。

### 4.3 实测证据（跑一次自检，前后对比）

```
执行前：异常表 3 条，VERIFY 批次 1 条
  → 执行 verify.sh
执行后：异常表 0 条，VERIFY 批次 0 条
```

修复前是"执行后 4 条 / 1 条"（只增不减）。

### 4.4 危害

1. **污染业务数据**：这些假异常会出现在"映射异常统计"里，
   让现场误以为设备真的有映射问题，白白排查半天
2. **无限累积**：自检跑得越多，垃圾越多
3. **误导验收**：验收时看库里有 UNMAPPED 记录，分不清是测试造的还是设备真报的

### 4.5 修复

`verify.sh` 末尾新增第 8 节，**自检结束后立刻清掉自己造的数据**：

```bash
# 只按 batch_id 精确匹配，不误伤真实数据
DELETE FROM fact_inspection_mapping_exception WHERE batch_id LIKE 'VERIFY%';
DELETE FROM fact_inspection_batch                WHERE batch_id LIKE 'VERIFY%';
DELETE FROM fact_inspection_defect_count         WHERE batch_id LIKE 'VERIFY%';
```

- 口令从 `/etc/default/camera-detection` 读取（640 root）
- 清理前后各查一次条数，清理不彻底则**自检判失败**（不放过）
- 只匹配 `VERIFY%` 前缀 —— 真实设备的 batch_id 不会是这个前缀

### 4.6 修复后实测 ✅

```
[8] 清理自检数据
  通过  清理自检数据       已清理 异常 4 条 / 批次 1 条

  通过 26 项，失败 0 项
  全部自检通过

执行后：异常表 0 条，VERIFY 批次 0 条   ← 自检不再留痕 ✅
```

> 自检项数从 25 增到 **26**。

## 10. 结论

**这台服务器现在可以放心跑**：服务零重启、0 ERROR、备份 11 连胜且可恢复、
安全回归全绿、资源极度宽裕、上轮修的 2 个 P0 没复发。

**本轮的两项发现（1 个 P1 + 1 个 P2）有一个共同特征**：
> **它们都是"应用/脚本在无人值守时自己做的傻事"，没人看着就一直在发生。**
>
> - 应用每分钟建一次表（DDL + MDL + binlog 污染）
> - 自检每次跑都往生产库写假异常
>
> 这类问题**不会让服务挂掉**，所以在"只看服务活没活"的巡检里**永远不会暴露**。
> 暴露它们靠的是**去看慢查询日志、看业务表里有没有奇怪的数据**。

**下一步优先级**：
① 接产线前做真实图片联调（这是唯一还没验证过的路径）
→ ② 建专用 MySQL 账号 → ③ 引入 actuator 提供健康端点
→ ④ 关公开注册 → ⑤ 收窄 syslog 轮转策略。

**一个观察**：连续三轮评审，每轮都能挖出 3–4 个此前没发现的问题，
而**没有一轮是"服务挂了"导致的** —— 全部是"跑得好好的，但内部在犯傻"。
**建议把巡检重点从"服务是否存活"转向"慢查询日志 / 业务表数据 / 定时任务实际产出"。**
