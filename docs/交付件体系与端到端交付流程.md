## 0. 核心结论（先看这里）

| 结论 | 事实依据 | 处置 |
|---|---|---|
| 交付件本身齐全，缺的是**阶段门禁与责任定义** | 仓库内 47 份受控 `.md`：现行 12、归档 31、脚本索引 2；但没有任何一份文档定义「需求→上线」各阶段的输入输出与放行人 | 本文件补齐 9 个阶段门禁 + RACI + DoD |
| 最易出错的是**真源散落与口径漂移** | 同一路径散在 `/etc/default`、`application.yml`、脚本默认值、systemd unit、cron 五处；SQL 数量出现 4/5/7 三种口径；端点数出现 146/147/148 三种写法 | 本轮统一 SQL 清单与守卫；端点数只由 `gen_api_doc.py` 回写 |
| 最不便捷的是**临时文件泄漏与旧路径失效** | 构建残留 `.static-tmp.*` 4 个约 108MB；增量部署 `/tmp/merged-*.jar` 现场 16 份约 947MB；两个 chunk 工具硬编码 `/opt/camera-detection-system` | 本轮修补 5 处脚本 + 增强旧路径守卫 |
| 归档索引滞后，**历史结论找不到** | `archive/README.md` 停在 2026-11-13，此后新增的 11 份归档未登记 | 本轮补齐登记并标注有效/被推翻 |
| 模板缺失导致每次交付「重新发明格式」 | 仓库里没有 PRD/方案/测试/评审/发布/验收模板；授权交付规划里提的模板至今不存在 | 本轮新增 `templates/` 10 份模板 |
| **授权是第二条交付线，且「制作授权的软件」不可随主程序交付** | 签发工具 `issue_license.py` / GUI 与密钥 `secrets/<客户>.key` 是厂商资产，打包时被显式剔除；客户侧只拿机器码包与授权包。运维手册 §9.2 却仍教客户跑已剔除的 `gen_license.py` | 本轮补齐授权交付件清单、4 步流程、3 份授权模板，并修正手册旧流程 |

**本轮不改业务功能、不提交推送。** 脚本修补与授权交付件在未提交工作树中，生效于下一次构建/发版。

> **两条交付线要分开管**：主程序交付（tar.gz / update.zip）走 S0～S8；
> 授权交付（机器码包 / 授权包 / 密钥）走 §3.6 的独立链路，二者只在中标签字处汇合。

## 2. 阶段门禁与责任分工（RACI）

角色：`PO` 产品负责人 ｜ `DEV` 研发负责人 ｜ `QA` 测试/验证 ｜ `OP` 现场运维 ｜ `CR` 客户代表。
R=执行、A=最终批准（每阶段唯一）、C=协作、I=知会。小团队可一人兼多角，但 **A 不能空缺、不能自批自审同一阶段**。

| 阶段 | R | A | C / I | 输入 | 输出（交付件） | 放行门禁（不通过不得进入下一阶段） |
|---|---|---|---|---|---|---|
| S0 需求立项 | PO | CR | DEV/I、OP/I | 现场问题/业务目标 | PRD（`templates/01`） | 目标可度量；口径（分母/分子/时间窗）写死；明确「不做」；需求编号已分配 |
| S1 方案设计 | DEV | PO | OP/C、QA/I | PRD、架构说明 | 技术方案（`templates/02`） | 方案对比至少 2 个选项并给出取舍；影响面列到端点/表/脚本；风险按 high/medium/low 分级 |
| S2 实现 | DEV | DEV | PO/I | 方案、踩坑速查 | 代码 + 配置 + SQL + 接口文档重新生成 | 后端 `mvn test` 全绿；前端 `npm ci && npm test && npm run lint && npm run build` 全绿；静态守卫通过 |
| S3 测试 | QA | PO | DEV/C | 可构建产物、口径定义 | 测试报告（`templates/03`） | 口径断言用真实数据；浏览器回归 0 JS 错误；发现项全部有状态（已修/已知/延期） |
| S4 评审 | PO | CR | DEV/C、OP/C | 测试报告、变更清单 | 评审报告（`templates/04`） | 结论只有「通过/有条件通过/不通过」三种；遗留项有责任人与期限 |
| S5 构建打包 | DEV | DEV | OP/I | S2～S4 全部放行 | 全量 tar.gz 或增量 update.zip + 发布记录草稿（`templates/05`） | `build-release.sh` 自检通过；配置 key 对账通过；包内不含签发工具；jar_manifest.py 在包内 |
| S6 部署 | OP | OP | DEV/C | 发布包 + 回滚预案（`templates/07`） | `deploy_jar.sh` 执行日志 + 备份点 | 先备份、原子替换、健康检查通过；失败自动回滚；**改 cron/systemd 必须同步重写现场文件** |
| S7 验证验收 | QA | CR | OP/C、DEV/I | 已部署服务 | verify.sh 报告 + 浏览器回归 + 验收单（`templates/06`） | 45 项自检全绿；对应浏览器回归全绿；接口键结构无意外变化；验收单客户签字 |
| S8 归档与推送 | PO | PO | DEV/I、OP/I | 全部交付记录 | 归档索引更新 + 代码推送 | 一次性文档当日入 archive 并登记；凭据扫描为空；**git push 需客户/项目负责人显式授权** |

> 授权例外：项目约定「Git 提交/推送需显式授权」。S8 的 A 由项目负责人担任，不得由执行推送的人自己批准。

## 3. 端到端流程（实际命令序列）

### 3.1 本地门禁（S2）

```bash
bash docs/scripts/preflight.sh                     # 发版前只读预检（代码状态/SQL/上次门禁/产物）
cd fact-product && mvn -B test                     # 后端全量测试
cd frontend && npm ci && npm test && npm run lint && npm run build
cd .. && python docs/scripts/gen_api_doc.py       # 端点变更后重新生成接口文档
python docs/scripts/check_doc_links.py            # 链接/锚点/结构
python docs/scripts/check_legacy_paths.py         # 旧布局路径回流
python installer/linux/scripts/check_config_parity.py  # 两份 application.yml key 对账
```

### 3.2 构建（S5）

```bash
bash installer/linux/build-release.sh              # 全量包 tar.gz
bash installer/linux/build-release.sh --update-only # 增量包 update-*.zip（日常首选）
```

构建产物在 `dist-release/linux/`，**只读、可随时重建**；不要手改。改前端必须重新构建再打包，顺序不可颠倒。

### 3.3 上传与部署（S6）

```bash
export SSH_HOST=10.2.77.72 SSH_USER=lims SSH_PASSWORD='<从安全渠道取>'
MSYS_NO_PATHCONV=1 python3 docs/scripts/upload_jar_b64.py \
  dist-release/linux/update/update-*.zip /tmp/update.zip

# 服务器端
export SUDO_PASSWORD='<从 /etc/default 取或用 600 临时文件喂给 sudo -S>'
bash /tmp/scripts/deploy_jar.sh /tmp/update.zip     # zip=增量 / jar=全量，失败自动回滚
```

口令不进命令行历史、不进仓库。建库只在全新机执行 `init-database.sh`（01→05 顺序导入），06/07 是幂等补丁；
`02_final_schema_p0.sql` 会 DROP 重建 21 张表，**生产禁止全量重建**。

### 3.4 验证与验收（S7）

```bash
sudo env VERIFY_PASSWORD='<应用口令>' MYSQL_PASSWORD='<库口令>' \
  bash /main/app/dist/scripts/verify.sh             # 统一布局 45 项
sudo env VERIFY_PASSWORD='<应用口令>' MYSQL_PASSWORD='<库口令>' \
  bash /main/app/dist/scripts/verify.sh --delivery  # 授权交付自检（LIC-10）：+4 项断言，写 licenseSelfCheck.json
node docs/scripts/verify_line_analytics_browser.cjs # 按本次变更选对应回归脚本
node docs/scripts/verify_daily_report_browser.cjs
```

顺序固定：**test → 打包 → 部署 → verify → 浏览器回归 → 清 ZZTEST 测试数据**。
`verify.sh` 会写测试心跳再自清理，跑完必须确认无 `ZZTEST*` 残留。

### 3.5 回滚

```bash
sudo bash /main/app/dist/scripts/service.sh rollback [版本时间戳]   # 推荐：统一入口
sudo cp -p <备份JAR> /main/app/dist/app/time-bucket-demo.jar && sudo systemctl restart camera-detection
```

只回滚应用，不回滚数据库；数据库恢复走 `restore-database.sh` 到临时库核对后再决定。

### 3.6 授权交付线（第二条链路，与主程序分开）

**先分清两类「授权软件交付件」**——混在一起会直接造成客户拿到签发工具：

| 类别 | 交付件 | 给谁 | 能否进客户包 |
|---|---|---|---|
| 制作授权的软件（厂商内部） | `installer/license-tool/issue_license.py`（CLI）、`issue_license_gui.py`（GUI）、`secrets/<客户>.key`、`ledger.csv` | 研发/商务 | **绝不进**。`build-release.sh` 打包剔除并断言；密钥不进命令行、不进文档 |
| 发给客户的授权件 | `license-<单号>.zip`（含 `license.lic`/`order.json`/`授权说明.txt`/`MANIFEST.sha256`）、客户版导入手册、设计文档 | 客户 | 是（设计文档已随包；手册见 `templates/09`） |
| 客户自产回传件 | `machine-<16位码>-<时间>.zip`（4 文件，无口令/密钥） | 客户 → 研发 | 是（客户页面生成） |

四步流程（离线、客户环境无外网）：

| 步 | 动作 | 执行/批准 | 输入 → 输出 | 门禁 |
|---|---|---|---|---|
| ① 定档 | 商务给单号、客户、期限、相机数、过期策略 | CR / PO | 合同 → 单号 | 期限与相机数写进合同；切 `readonly` 前确认授权已装好 |
| ② 客户生成机器码包 | 页面「服务器授权 → 下载机器码包」回传研发 | OP / DEV | 页面 → `machine-*.zip` | schema + `MANIFEST.sha256` 校验；指纹不可读报 `LIC-MACHINE-002` |
| ③ 研发签发授权包 | `issue_license.py issue` + `inspect` 自检 + `ledger` 追加 | DEV / DEV | 机器码包 + 密钥 → `license-<单号>.zip` | 用 `--secret-file`（新单禁用内置默认密钥）；载荷 v2、到期日/相机数/机器码与合同逐项一致；记录包 sha256 |
| ④ 客户两步导入 | 页面预览（`previewToken` 5min）→ 确认导入（`ackQuota`） | OP / CR | 授权包 → `license.lic` | 验签通过、状态 `VALID`、旧件自动备份；**零重启**；授权页与 `/api/license` 一致 |

关键纪律：

- **一客户一密钥**：`keygen` 生成 64 hex 写 `secrets/<slug>.key`（600），台账只存 `sha256(secret)[:8]`。
- **换密钥=存量授权全失效**：现场默认密钥自签的试点授权（到期 2029-11-12）迁移必须按
  `templates/10` 的五步序执行，顺序错会同时失去新旧两张授权；该待办记为 LIC-09，**未完成前不得切 `LICENSE_SECRET`**。
- **备份纳管**：`backup-database.sh` 已把 `data/license/` 纳入本地与跨盘副本；授权文件不随数据库恢复演练覆盖生产。
- **已知限制随单告知**：对称密钥在 jar 内可反编译自签，不承诺「无法破解」；授权不约束 8091 设备直连；默认 `warn` 过期不停线。

遗留：LIC-10（`verify.sh --delivery` 四项断言 + `licenseSelfCheck.json`，脚本已改、**待部署生效**）、LIC-12（到期写 `fact_anomaly_alert` 并同步 `OPS_ALERT_TYPES`）仍未实现，不在本次交付流程内放行。

## 4. 问题识别与改进措施

等级：high=会导致数据丢失/线上故障/合规问题；medium=易误判或明显低效；low=体验与整洁度。

| ID | 问题与证据 | 影响 | 等级 | 改进措施 | 本轮状态 |
|---|---|---|---|---|---|
| H-1 | 归档索引停在 2026-11-13，此后 11 份评审/测试/性能/授权文档未登记 | 新协作者按索引找不到有效结论，可能照抄被推翻的数字 | high | 补登记并标注「有效/被推翻/过程稿」；规定当日归档 | ✅ 已修 |
| H-2 | `build-release.sh:138` 的 `.static-tmp.*` 不在清扫列表，现场残留 4 个约 108MB | 构建盘持续膨胀，排障时误判为包损坏 | high | 清扫时保留最近 1 份便于排障，其余删除 | ✅ 已修 |
| H-3 | `deploy_jar.sh:68` 的 `/tmp/merged-*.jar` 无清理，现场 16 份约 947MB | 系统盘被非交付产物吃满 | high | EXIT trap 只删本次合成文件；开跑前清理 60 分钟以上的历史残留 | ✅ 已修 |

## 6. 验收标准（DoD）

一个需求只有同时满足以下五项才算交付完成：

1. **功能**：PRD 中每条需求的状态为「已实现」，追溯矩阵指向具体端点/页面/SQL。
2. **质量**：后端 `mvn -B test` 全绿；前端 `npm test`/`npm run lint`/`npm run build` 全绿；对应浏览器回归全绿且 0 JS 错误。
3. **口径**：统计类需求必须与 PRD 的分母/分子/时间窗/过滤范围逐项对齐；多选、空数据、无样本降级三态都有断言。
4. **现场**：verify.sh 45 项全绿（授权交付另跑 `--delivery`，四项交付断言全绿且 `licenseSelfCheck.json` 的 `overall=PASS`）；升级包能回滚；cron/systemd 改动已同步到现场文件；无 `ZZTEST*` 残留。
5. **交付件**：PRD/方案/测试报告/评审报告/发布记录/验收单齐全并按第 1 节归位；一次性文档已入 `archive/` 且索引已登记；git 推送已获显式授权且 tree 校验一致。

验收单按 [`templates/06-验收单模板.md`](templates/06-验收单模板.md) 填写，客户代表签字才算 S7 通过。

**授权交付单独放行**（满足以上五项不自动等于授权可交付）：

- 签发工具与密钥未进客户包（打包断言 + 产物检查）；
- `templates/08` 的 4 项自检全绿，载荷 v2 字段与合同逐项一致，包 sha256 已记录；现场 `verify.sh --delivery` 的 `licenseSelfCheck.json` 四项断言全绿；
- 客户按 `templates/09` 完成预览+导入，状态 `VALID`、旧件已备份、零重启；
- `templates/10` 台账已登记密钥指纹，客户侧无密钥文件；
- 若涉及切 `LICENSE_SECRET`，五步序已执行且原授权迁移完成（LIC-09 关闭），否则不得放行。
