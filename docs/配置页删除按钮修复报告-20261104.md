## 二、根本原因分析

### 缺陷 1（致命）：工位删除抛 SQL 异常 —— 这才是"按钮无效"的直接原因

`DimWorkstationController.delete` 中有一行：

```java
jdbcTemplate.update("UPDATE dim_camera SET workstation_id = NULL WHERE workstation_id = ?", id);
```

但 `dim_camera.workstation_id` 是 **NOT NULL** 列。服务器实测日志：

```
ERROR o.a.c.c.C.[.[.[/].[dispatcherServlet] : Request processing failed;
nested exception is org.springframework.dao.DataIntegrityViolationException:
PreparedStatementCallback; SQL [UPDATE dim_camera SET workstation_id = NULL WHERE workstation_id = ?];
nested exception is java.sql.SQLIntegrityConstraintViolationException:
Column 'workstation_id' cannot be null
```

异常在 `removeById` 之前抛出 → 整个 DELETE 请求 500 → 前端 `catch` 分支提示"删除失败"，
**用户点删除后什么都没发生**。这与截图现象完全一致。

### 缺陷 2：前端门禁比后端更严，导致删除永远被"禁止"

`useConfigRiskConfirm.js` 原用**一份跨类型通用**的 `BLOCKING_KEYS`：

```js
const BLOCKING_KEYS = ['lineCount','stationCount','cameraCount','userCount',
  'imageCount','defectBoxCount','productionCount','defectCount','heartbeatCount']
```

与后端实际拦截条件逐项比对：

| 类型 | 前端阻断键 | 后端实际拦截 | 差异 |
|---|---|---|---|
| 工位 | cameraCount, **productionCount, defectCount** | 仅 `cameraCount>0` | **前端多拦 2 项** |
| 产线 | stationCount, cameraCount, productionCount, defectCount | `stationCount>0 \|\| cameraCount>0` | 基本一致 |
| 工厂 | lineCount, **stationCount, cameraCount**, userCount | `lineCount>0 \|\| userCount>0` | **前端多拦 2 项** |
| 相机 | imageCount, defectBoxCount, heartbeatCount | `imageCount+compat>0 \|\| heartbeat>0` | 实质一致 |

前端比后端严 → 用户点删除只看到"禁止删除"弹窗 → **观感上就是按钮失灵**。

且阻断文案只说"请先迁移/解绑下级配置"，没有指出**具体该先删哪个**，用户无从下手。

### 缺陷 3：工位实体缺逻辑删除映射 → 删除是物理删除，不可恢复

`dim_workstation` 表**本来就有** `is_deleted` 列，但 `DimWorkstation` 实体：

- 没有 `@TableLogic` 注解
- 没有 `isDeleted` 字段映射

于是 `workstationService.removeById(id)` 执行的是**物理删除**，
与产线/工厂/相机的逻辑删除行为不一致，工位一旦删除**无法恢复**。

### 缺陷 4：依赖检查未过滤 `is_deleted` → 上级永远删不掉

补上 `@TableLogic` 后，工位变成逻辑删除，但依赖检查 SQL 没同步过滤：

```java
// DimProductionLineController —— 工位已逻辑删除，但仍被算作依赖
int stationCount = count("SELECT COUNT(*) FROM dim_workstation WHERE line_id = ?", id);
```

实测：两个测试工位删完后，产线 `dependencies` 仍返回 `stationCount: 2, riskLevel: HIGH` → **产线永远删不掉**。
`DimFactoryController` 的 `stationCount` 同样问题。

### 缺陷 5：工厂与相机删除接口缺权限注解（安全漏洞）

```java
// DimFactoryController
@DeleteMapping("/{id}")              // ← 没有 @PreAuthorize
public ResultVO<String> delete(...)

// CameraDashboardController
@DeleteMapping("/{id}")              // ← 没有 @PreAuthorize
@Transactional
public ResultVO<String> delete(...)
```

而产线/工位/用户删除都有 `@PreAuthorize("hasRole('ADMIN')")`。
路径级 `SecurityConfig` 只把 `POST/PUT/DELETE /api/cameras/**`、`/api/factories/**` 的一部分纳入 ADMIN 保护，
**DELETE 方法未覆盖** → 任何已登录用户都能删工厂和相机。

### 缺陷 6：依赖检查查错表（`camera_status` vs `dim_camera`）

`DimProductionLineController` 与 `DimFactoryController` 的相机依赖查的是 `camera_status`
（状态快照，可能没有对应行），而**相机与产线/工位的绑定关系真实维护在 `dim_camera`**。
`camera_status` 里没有的行会让依赖计数偏小 → 门禁失效。

## 三、修复内容

### 3.1 前端：`frontend/src/views/system/config/useConfigRiskConfirm.js`

**改动 1：阻断键改为按类型定义，与后端严格一一对应**

```js
const BLOCKING_KEYS_BY_TYPE = {
  factory:     ['lineCount', 'userCount'],                          // 后端：lineCount>0 || userCount>0
  line:        ['stationCount', 'cameraCount'],                    // 后端：stationCount>0 || cameraCount>0
  workstation: ['cameraCount'],                                    // 后端：cameraCount>0
  camera:      ['imageCount', 'heartbeatCount'],                   // 后端：imageCount+compat>0 || heartbeat>0
  user:        []
}
const hasBlockingDependency = (deps = {}, type = '') => {
  const keys = BLOCKING_KEYS_BY_TYPE[type]
  if (!keys) return false
  return keys.some((key) => Number(deps[key]) > 0)
}
```

**改动 2：阻断提示给出可操作指引**（新增 `blockingAdvice(type, deps)`）

原来只说"禁止删除，请先迁移/解绑"，现在明确指出下一步：

- 工厂 → 「先删除该工厂下的产线（产线需先清空下属工位与相机）；先解绑该工厂下的用户」
- 产线 → 「先删除该产线下的工位；先删除或迁移该产线下的相机」
- 工位 → 「先删除或改绑该工位下的相机」
- 相机 → 「该相机已有历史图片记录，需先完成数据归档」

### 3.2 后端

| 文件 | 改动 |
|---|---|
| `DimWorkstationController.java` | ① 删除 `SET workstation_id = NULL`（NOT NULL 违规），改为**停用绑定相机**并回报数量<br>② 依赖检查 SQL 保持查 `dim_camera`（原已正确）<br>③ 返回 message 修正为 `ResultVO.success(data, message)` 的正确参数顺序 |
| `DimWorkstation.java`（实体） | 新增 `isDeleted` 字段 + `@TableLogic` + `isEnabled` 字段映射 → 工位删除改为**逻辑删除** |
| `DimProductionLineController.java` | ① 依赖检查 `dim_workstation` 加 `IFNULL(is_deleted,0)=0`（2 处）<br>② 相机依赖从 `camera_status` 改为 `dim_camera`（2 处） |
| `DimFactoryController.java` | ① 依赖检查 `dim_workstation` 加 `IFNULL(ws.is_deleted,0)=0`<br>② 相机依赖从 `camera_status` 改为 `dim_camera`<br>③ **补 `@PreAuthorize("hasRole('ADMIN')")`** |
| `CameraDashboardController.java` | **补 `@PreAuthorize("hasRole('ADMIN')")`** |
| `SysOperationLogController.java` | 日志删除/清空补 `@PreAuthorize("hasRole('ADMIN')")`（双保险，路径级已有保护） |

> 接口路径、请求参数、响应结构**全部未变**，符合"保持现有业务逻辑与接口约定不变"的要求。

## 六、遗留说明

1. **相机/工位删除仍受历史数据门禁保护** —— 有历史图片的相机、有相机绑定的工位会被拦截，
   这是**有意的保护**（避免破坏历史统计），现在会明确告知下一步该做什么。
   如需强制删除，需先完成数据归档，这属于业务流程决策，本次未改。
2. **`camera_status` 与 `dim_camera` 双表结构**仍是历史包袱：
   相机删除时两表都要更新（`is_active=0` + `is_deleted=1`）。
   建议后续做一次数据模型合并，本次仅修正依赖查询指向正确的表。
3. **Git 未提交** —— 按用户新约定，本次改动未 `commit`/`push`，等明确指示。
