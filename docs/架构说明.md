# 产线缺陷在线 AI 检测系统 —— 后端架构说明

> 版本：1.0（2026-11-05，DDD 重构 P0~P5 完成后定稿）
> 范围：后端 `fact-product`（Spring Boot 2.7.15 / Java 8 / artifact `time-bucket-demo`）
> 配套文档：《模块设计》《接口文档》《部署与运维手册》《使用说明》《配置项清单》

## 1. 系统概览

本系统为产线缺陷在线 AI 检测平台的后端服务，负责相机接入（心跳/图片上报）、缺陷图片存储与检索、产线统计分析、系统配置管理。单服务单体架构，按领域驱动设计（DDD）划分**七业务域 + 共享内核**，各域可独立维护与演进。

| 项 | 值 |
|---|---|
| 技术栈 | Spring Boot 2.7.15 / MyBatis-Plus / JdbcTemplate（Repository 层）/ MySQL 8.0 |
| 前端 | Vue 3.5 + Vite 5（构建产物打进 JAR 的 `BOOT-INF/classes/static`） |
| 端口 | 8091 |
| 规模 | 151 个 Java 文件 ≈ 17,900 行；28 个 Controller / 134 个端点；14 个 Repository / 17 个 Mapper |
| 测试 | 79 个用例（含 3 条 ArchUnit 架构守护规则） |
| 配置 | 唯一密钥源 `/etc/default/camera-detection`（systemd EnvironmentFile 注入，DB/JWT 均为占位符） |

## 2. 分层与领域划分

### 2.1 包结构

```
com.wms
├── TimeBucketApplication        # 装配根（@MapperScan 七包列表）
├── init/                        # SchemaInitializer —— 统一启动期建表入口（P5）
├── shared/                      # 共享内核（零业务依赖，铁律②）
│   ├── common/  ResultVO
│   ├── util/    ExcelUtils / ShiftCalculator / CodeGenerator
│   ├── config/  MybatisPlusConfig / DefectImageUploadLimitConfig
│   └── web/     SpaFallbackController（SPA 前端兜底路由）
├── iam/         认证、用户、操作日志          17 文件 / 2,219 行
├── masterdata/  工厂/产线/工位/品牌/班次档案   37 文件 / 1,773 行
├── device/      相机档案、心跳、状态快照      19 文件 / 2,364 行
├── defect/      缺陷图片上传/检索（现场主通道） 6 文件 / 2,349 行
├── inspection/  批量上报冻结契约（agg_* 体系） 20 文件 / 1,757 行
├── analytics/   产线统计、看板、聚合          29 文件 / 4,328 行
└── system/      系统设置、数据清理、导入导出   15 文件 / 2,305 行
```

### 2.2 域内分层

每域统一四层（按需裁剪，小域可合并）：

```
<domain>
├── api/            Controller + DTO/VO（HTTP 协议层）
├── app/            应用服务（业务编排）+ 事件 + 跨域端口定义
├── domain/model/   实体（被动模型，铁律③：纯净）
└── infra/          mapper/（MyBatis-Plus）+ repository/（JdbcTemplate）+ task/ + adapter/
```

**依赖规则（ArchUnit 已固化，测试 `com.wms.arch.ArchitectureTest`）**：

| 铁律 | 规则 | 当前状态 |
|---|---|---|
| ① 跨域只走 app | 业务域类不得依赖**其他域**的 infra（Repository/Mapper 各域私有） | 12 处存量冻结（FROZEN_CROSS_DOMAIN），只许清零不许新增 |
| ② shared 零业务依赖 | 共享内核不得反向依赖业务域 | ✅ 合规 |
| ③ domain/model 纯净 | 实体不依赖 api/app/infra | ✅ 合规 |

设计例外（不受规则约束）：`com.wms.init.SchemaInitializer`（P5 统一建表需跨域调度各域 Repository）、`TimeBucketApplication` 装配根。

### 2.3 跨域协作两种模式

1. **进程内事件**（Spring ApplicationEvent，同步）：`device` 发布 `CameraAlertEvent`（5 类心跳告警）→ `analytics` 的 `CameraAlertEventListener` 落库 `fact_anomaly_alert`。监听器吞 `DataAccessException`，不影响心跳主流程。
2. **端口-适配器**（消费方定义接口、提供方适配）：
   - `device.app.CameraDirectory`（14 方法）← analytics 看板消费，`CameraDirectoryAdapter` 适配
   - `device.app.SystemSettingReader` ← device 心跳读告警阈值，`system.infra.SystemSettingReaderAdapter` 适配

## 3. 关键机制

### 3.1 表结构生命周期（P5 收敛后）

- **启动期**：`SchemaInitializer`（@PostConstruct）按 system → defect → analytics 顺序统一执行各域 ensure（幂等，INFORMATION_SCHEMA 判断"表在则不执行 DDL"），失败记 ERROR 不阻断启动。
- **请求期守卫（保留）**：设置页 `ensureSettingTable` 幂等守卫；缺陷图片通道 5 分钟限频自愈（表运行期被删最多 5 分钟内自愈）。
- **SQL 归属**：DDL 文本全部在各域 `infra/repository`（api/app 层执行语句清零）；正式建库以 `sql/deploy/` 四段脚本为准（`01_init_schema_nodb` → `02_final_schema_p0` → `03_system_settings` → `04_align_entity_columns`）。**生产升级绝不能跑 02 全量**（DROP 重建 21 表清数据）。

### 3.2 两条上报通道（重要业务口径）

| | `defect-images/upload`（现场在用） | `batch-upload`（冻结契约） |
|---|---|---|
| 数据表 | `defect_image_file/_box/_batch` + `camera_images` | `fact_inspection_*` + `agg_*` |
| 现状 | **主通道**，7 天保留 | 基本不用 |
| 统计 | 只读 `agg_*` 的接口现场永远为 0 → 必须做 `defect_image_*` 兜底（响应带 `dataSource` 字段） | — |

### 3.3 相机身份（camera_code first）

`camera_code` 是唯一身份（`uk_camera_code`）；`camera_name` 现场会重名。心跳/图片通道一律 code-first，名称兜底必须唯一，多行拒写 + WARN。`defect_image_file.camera_id` 实际存 camera_code（JOIN 用 `c.camera_code = f.camera_id`）。

### 3.4 认证与权限语义

| 场景 | 状态码 | reason |
|---|---|---|
| 无 token / 无效 / 过期 | **401** | `AUTHENTICATION_REQUIRED` |
| 已登录但角色不足 | **403** | `ACCESS_DENIED` |

前端 `utils/auth-redirect.js` 集中判定：401 清 token 跳登录；403 仅未登录才跳。白名单精确到方法+路径，禁止 `/**` 兜底；新增管理端点须同改 `SecurityConfig` / `@PreAuthorize` / `verify.sh` 三处。

### 3.5 数据保留（2026-11-05 图片归档改造）

**两层生命周期**，保证「图片存 2 年 + 默认查询恒定毫秒级」：

| 层 | 保留 | 机制 |
|---|---|---|
| 数据库主表 `defect_image_file/_box/_batch` | **31 天** | `DefectImageArchiveTask`（`app.archive.images.cron`，默认 02:30）把超期记录按 `COALESCE(capture_time,upload_time,create_time)` 的月份**移动**到 `defect_image_*_hist_YYYYMM` —— `INSERT…SELECT` 按 5000 行/批、每批独立事务（避免长事务锁表；失败只回滚该批，幂等可重跑） |
| 月度归档表 | **730 天** | 超期整表 `DROP`（表名白名单 `^defect_image_(file|box|batch)_hist_\d{6}$` + 730 天闸门） |
| 磁盘图片文件 | **730 天** | `cleanup-defect-images.sh`（03:30）按 `{yyyyMMdd}` 日期目录整目录删除；**不再删库记录**（职责单一化） |

**查询路由**（`DefectImageRepository.listHistoryPage`）：无时间范围或范围全在 31 天内 → 只查主表；
范围涉及更早 → 主表（仅热区行）`UNION ALL` 各月月表，再走原 JOIN/过滤/分页；缺月表跳过。
月表查询用 `capture_time` 命中 `idx_defect_file_capture_time`（主表沿用 `COALESCE` 口径，因数据量恒定）。
接口签名与返回结构不变，前端仅提示「历史查询可能较慢」。图片文件 2 年内均在，`/file/**` 照常回放。

其他表：`camera_images` 30 天、`fact_production_30min` 3 个月（归档后删）、`sys_operation_log` 6 个月
（`DataCleanupTask` 02:00 硬编码）。`sys_data_retention_policy` 表代码从不读，改它不生效。
另有 ZK54 测试相机每小时增量清理 cron（`/usr/local/bin/cleanup_zk54_incremental.sh`）。

## 4. 工程纪律（改代码前必读）

1. **SQL 逐字搬运，零优化**——重构时含参数拼接方式原样保留；列名用 `docs/scripts/check_sql_columns.py` 静态校验（information_schema 反查）。
2. **验证顺序**：`mvn test` → 打包 → 增量部署 → verify.sh 28/28 → 接口快照 diff（键结构树）→ 浏览器回归 → 清 ZZTEST 测试数据。
3. **轻量发版**：`build-release.sh --update-only` 产 2.1MB 增量包（只含 `BOOT-INF/classes/**`，**含目录条目**——JarLauncher 依赖根目录条目识别类路径）；`deploy_jar.sh` 按扩展名自动识别 zip=增量/jar=全量；依赖指纹不一致强制走全量。
4. **前端产物**：`emptyOutDir false` 会堆积旧 chunk → 构建前先清空；`build-release.sh` 保留上一版 chunk（KEEP_STATIC_VERSIONS=3）防部署后旧标签页路由静默失效。
5. **Git**：提交前扫描明文口令（CI 强制）；推送优先原生 `git push`，被代理拦截时用 `docs/scripts/push_via_github_api.py`。
