# 配置项清单

> **用途**：现场改配置有据可依，不必翻源码。
> **基准日期**：2026-11-07
> **适用范围**：Linux 版（`installer/linux/`）。Windows 版已停止维护。

---

## 一、配置分层与加载顺序

```
优先级从低到高：
  ① JAR 内置  fact-product/src/main/resources/application.yml   （开发默认值，无凭据）
  ② 外部配置  /main/app/dist/config/application.yml （现场实际生效，权限 640）
  ③ 环境变量  /etc/default/camera-detection                       （640 root:root，只放密钥）
```

**关键规则（2026-11-04 安全改造后）**：

- 外部配置与模板中**不再出现任何明文口令**，一律用 `${MYSQL_PASSWORD}` / `${JWT_SECRET}` 占位。
- 占位符**没有默认值**（写成 `${MYSQL_PASSWORD}` 而非 `${MYSQL_PASSWORD:}`）：
  环境变量缺失时应用**启动即失败**，并在日志明确报 `Could not resolve placeholder`。
  这比"能启动但连不上库"好得多 —— 后者表现为"服务 active 但业务全错"，极难排查。
- 外部配置按 **key 合并**（不是整文件替换）：外部配置里**省略的 key 仍取 JAR 内置值**。
  因此两份 `application.yml`（JAR 内置 与 `installer/templates/` 模板）必须认识**同一套 key** ——
  只在一边新增配置项，结果就是"现场改了不生效"或"客户根本看不到这一项"，且两边都不报错。
  这一条由 `installer/linux/scripts/check_config_parity.py` 守（构建时自动跑，只比 key 路径不比 value；
  值本来就有意不同，见该脚本头部说明）。新增配置项时若确实是单边专用，登记到脚本的 `KV_ALLOW` 并写理由。

  生产环境必须显式覆盖以下两项，否则会用开发期的 DEBUG 日志与 StdOut 日志实现：

  ```yaml
  mybatis-plus:
    configuration:
      log-impl: org.apache.ibatis.logging.slf4j.Slf4jImpl   # 必须是 Slf4jImpl
  logging:
    level:
      com.wms.mapper: INFO                                  # 必须是 INFO
  ```

## 二、环境变量（`/etc/default/camera-detection`，640 root:root）

| 键 | 是否敏感 | 默认值 | 作用 | 备注 |
|---|---|---|---|---|
| `JAVA_OPTS` | 否 | `-Xms512m -Xmx1024m` | JVM 堆参数 | **必须带引号**。run.sh 用 `source` 读取本文件，不加引号时空格会截断 → `-Xmx1024m: command not found` → 启动失败 |
| `INSTALL_DIR` | 否 | `/main/app/dist` | 程序安装目录 | 改路径需同步 systemd `ReadWritePaths` |
| `WORK_DIR` | 否 | `/main/app` | 运行数据目录（日志、上传落盘） | |
| `APP_HOME` | 否 | 同 `WORK_DIR` | 应用主目录，决定日志与图片落盘位置 | |
| `JAVA_HOME` | 否 | `/usr/lib/jvm/java-8-openjdk-amd64` | Java 运行时 | 留空则依次尝试 内置 jre → JAVA_HOME → PATH |
| `CONFIG_FILE` | 否 | `${INSTALL_DIR}/config/application.yml` | 外部配置文件路径 | |
| `MYSQL_PASSWORD` | **是** | 无 | MySQL root 口令 | **必填**。缺失则服务启动失败 |
| `JWT_SECRET` | **是** | 无（install.sh 生成 64 位随机十六进制） | JWT 签名密钥 | **必填**。轮换会使已签发令牌失效 |
| `ADMIN_USER` | 否 | `admin` | 管理员账号名 | |
| `ADMIN_PASSWORD` | **是** | 无 | 管理员口令（BCrypt 存库） | 改密用 `reset-password.sh` |
| `BACKUP_DIR` | 否 | `/main/app/data/backup/db` | 数据库备份目录 | |
| `KEEP_FULL_DAYS` | 否 | `14` | 全量备份保留份数 | 与 `BINLOG_KEEP_DAYS` 对齐 |
| `MAX_DISK_USE` | 否 | `85` | 备份前磁盘使用率上限（%），超过则跳过备份 | |
| `OFFSITE_DIR` | 否 | `/var/backups/camera-detection/db` | 跨盘副本目录 | ⚠️ **必须与 `BACKUP_DIR` 不在同一文件系统**，否则脚本告警「该副本不能抵御磁盘故障」 |
| `IMAGES_SRC` | 否 | `/main/app/data/images/defect-images` | 图片备份源 | |
| `IMAGES_DST` | 否 | `/var/backups/camera-detection/images` | 图片备份目标（热窗口 30 天） | 首轮约 4GB，之后日增数十 MB |
| `BINLOG_KEEP_DAYS` | 否 | `14` | binlog 副本保留天数 | MySQL 侧 `binlog_expire_logs_seconds=2592000`（30 天），**别调小** |
| `IMAGE_BACKUP_KEEP_DAYS` | 否 | `30` | 图片备份热窗口天数 | 只备近 30 天，覆盖「最近一个月追溯」 |
| `IMAGE_BACKUP_MAX_GB` | 否 | `20` | 图片副本总量上限（GB） | 超限从**最旧日期目录**开始回收，降到上限 90% 为止。兜底防「REAL 台数增长后 30 天窗口撑满系统盘」 |

> **TEST 相机不进图片副本**：`backup-database.sh` 按 `dim_camera`/`camera_status` 的
> `camera_type='TEST'` 生成 `--exclude=/<code>/`，并回收副本里历史遗留的 TEST 目录。
> 实测生效后副本 3.9G → 283M。查询失败时**不排除任何目录**（宁可多备，不可漏备），
> 并在日志打 WARN。`verify.sh` 第 3d 项会检查副本里是否又混进 TEST 目录。

### 3.3 业务相关

| 键 | 默认值 | 作用 | 现场是否需改 |
|---|---|---|---|
| `app.home` | `${APP_HOME:./runtime}` | 应用主目录 | 启动时由 `-Dapp.home` 覆盖 |
| `defect-image.max-batch-images` | `100` | 单批缺陷图上限 | 设备端批量超此值会返回 413 |
| `defect-image.upload.dir` | `/main/app/data/images/defect-images/` | **缺陷图片实际落盘目录** | **改路径必须同步 systemd `ReadWritePaths`**；目录名里的 `defect-images` 不可改（读图白名单） |

| `app.server-metrics.history-size` | `120` | 指标历史点数（120×5s = 10 分钟窗口） | 同上 |
| `camera.token.strict` | `false` | 设备令牌严格模式 | `false`：未配令牌的相机放行 + WARN；`true`：未配置即拒绝。**配了令牌但传错在两种模式下都拒绝** |
| `license.enabled` | `true` | 授权校验总开关 | `false` → 状态 DISABLED，全部放行。仅排障时关 |

| `license.file` | `${app.home}/data/license/license.lic` | 授权文件路径 | 必须放 data 盘（应用用户可写）。放 `/etc` 会导致上传新授权失败 |
| `license.expired-mode` | `warn` | 过期策略 | `warn` 只告警不阻断；`readonly` 过宽限期拒绝设备写入；`block` 再拒绝业务查询 |
| `license.grace-days` | `7` | 过期后宽限天数 | 宽限期内即使 `readonly`/`block` 也不拦 |
| `license.warn-days` | `30` | 即将到期阈值 | 剩余天数 ≤ 该值进入 EXPIRING，页面与日志提示续期 |
| `license.enforce-machine` | `true` | 机器绑定校验 | 虚拟机克隆后指纹变化，排障时可临时关闭 |

## 五、数据保留策略（2026-11-05 图片归档改造后）

| 数据 | 保留期 | 负责者 | 机制 |
|---|---|---|---|
| `defect_image_file` / `_box` / `_batch`（**主表**） | **31 天** | 应用 `DefectImageArchiveTask`（每日 02:30） | 超期记录按月**移动**到 `defect_image_*_hist_YYYYMM` 月表（`INSERT…SELECT` 分批 5000 行） |
| 月度归档表 `defect_image_*_hist_YYYYMM` | **730 天（2 年）** | 同上 | 超期整表 `DROP`（白名单校验 + 730 天闸门） |
| 磁盘图片文件 | **730 天（2 年）** | `cleanup-defect-images.sh`（cron 03:30） | 按 `{yyyyMMdd}` 日期目录整目录删除；**这是磁盘文件的唯一删除者** |
| `camera_images`（兼容表） | **30 天** | `DataCleanupTask` 02:00 | DELETE —— **只删行、不删磁盘文件**（两表 `image_path` 完全重叠，删文件会造成批量裂图） |
| `sys_operation_log` | 6 个月 | `DataCleanupTask` 02:00 | DELETE |
| `fact_production_30min` | 3 个月 | `DataCleanupTask` | 归档到 `_archive` 后删除 |

**归档配置项**（`application.yml` 的 `app.archive.images.*`）：

| 键 | 默认 | 说明 |
|---|---|---|
| `cron` | `0 30 2 * * ?` | 归档任务 cron（每日 02:30） |
| `hot-days` | `31` | 主表热数据保留天数（同时决定查询路由的分界线） |
| `retain-days` | `730` | 月表保留天数，超期 DROP |
| `batch-size` | `5000` | 每批搬移行数（小事务避免锁表） |

**手工触发归档**（运维/验证）：`POST /api/v1/defect-images/archive/run`（ADMIN 令牌），
返回 `archivedFiles/archivedBatches/hotFilesLeft/hotOldestTime/costMs`。

> ⚠️ `sys_data_retention_policy` 表里存了 5 条策略，系统设置页也能编辑，但**没有任何清理任务消费它**
> （只有 `SystemSettingsController` / `SystemSettingsRepository` 读写它用于展示）。上表的真实机制是
> `DataCleanupTask` 硬编码 + 归档任务 + `cleanup-defect-images.sh`。**改那张表不生效**——
> 2026-11-13 已在前端页面加显式提示（「仅记录运维意向，不驱动清理」），避免运维误以为调了就生效。

> ⚠️ **容量口径必须排除 TEST 相机**：含压测是 780 MB/天，只算 REAL 是 **67 MB/天**（差一个数量级）。
> 扩盘触发条件是 REAL 相机台数（≈33.5 MB/天/台），不是保留天数 —— 实测数据与推算见
> [`部署与运维手册.md`](部署与运维手册.md) §6.3。

## 六、快速排查入口

| 想知道 | 执行 |
|---|---|
| 服务是否健康 | `sudo /main/app/dist/scripts/service.sh health` |
| 配置与密钥是否正常 | `sudo /main/app/dist/scripts/service.sh config-check` |
| 线上跑的是哪个版本 | `sudo /main/app/dist/scripts/service.sh version` |
| 回滚到上一版本 | `sudo /main/app/dist/scripts/service.sh rollback` |
| 清理过量 JAR 备份 | `sudo /main/app/dist/scripts/service.sh cleanup 5` |
| 完整自检（统一布局 42 项 / 老布局 35 项） | `sudo -S env VERIFY_PASSWORD='<管理员口令>' MYSQL_PASSWORD='<数据库口令>' bash /main/app/dist/scripts/verify.sh` |

> `verify.sh` **必须以 root + 正确口令运行**，否则会有 7 项误报失败
> （640 root 的 `/etc/default` 普通用户读不到，DB 连通性检查无法执行）。

## 七、巡检脚本可配置变量（`check-disk-usage.sh`）

以 `/etc/cron.d/check-disk-usage` 每 30 分钟执行，无需重启服务即可通过环境变量调整：

| 键 | 默认 | 作用 |
|---|---|---|
| `THRESHOLD` | `85` | 分区水位告警阈值（%）→ `DISK_USAGE_HIGH` |
| `MOUNTS` | `/ /main` | 巡检分区列表（`/` 必须在内：系统配置与跨盘副本在系统盘；`/main` 是数据盘挂载点） |
| `BACKUP_FULL_DIR` | `/main/app/data/backup/db/full` | 备份新鲜度检查目录 |
| `BACKUP_MAX_AGE_H` | `26` | 最新备份允许的最大年龄（小时）→ `BACKUP_FAILED` |
| `CAPACITY_WARN_DAYS` | `180` | 容量预测告警阈值（天）→ `DISK_CAPACITY_LOW` |
| `CAPACITY_MOUNT` | `/main` | 容量预测针对的分区（数据盘） |

**新增脚本告警类型时必须同步 `FactAnomalyAlertController.OPS_ALERT_TYPES`**，
否则该类型会被当成业务告警排到后面（甚至被 `LIMIT` 截掉），运维看不到。
当前运维类：`BACKUP_FAILED` / `CLEANUP_FAILED` / `ARCHIVE_FAILED` / `DISK_USAGE_HIGH` / `DISK_FULL` / `DISK_CAPACITY_LOW`。

## 八、清理脚本可配置变量

### 8.1 测试相机清理（`cleanup-test-cameras.sh`，cron `15 * * * *` root）

| 键 | 默认 | 作用 |
|---|---|---|
| `IMG_ROOT` | `/main/app/data/images/defect-images` | 图片根目录（按 `{yyyyMMdd}/{camera_code}/` 两级判定） |
| `MAX_SINGLE_DELETE` | `50000` | 单轮待删 `defect_image_file` 行数阈值，超限中止（退出码 4）→ 防一次误判清空整库 |
| `PROTECTED_CODES` | 空 | 临时额外保护的真实相机编号（逗号分隔），不必改代码 |
| `TRASH` | `/main/app/data/images/.cleanup-trash` | 待删中转区。**必须与 `IMG_ROOT` 同文件系统**，且**不得放在 `IMG_ROOT` 内部** |

退出码：`0` 成功 ｜ `2` 有步骤失败 ｜ `3` 保护集合为空而中止 ｜ `4` 超阈值中止 ｜ `5` 未获锁跳过。

### 8.2 磁盘图片清理（`cleanup-defect-images.sh`，cron `30 3 * * *` root）

| 键 | 默认 | 作用 |
|---|---|---|
| `DIR` | `/main/app/data/images/defect-images` | 图片根目录 |
| `KEEP_DAYS` | `730` | 日期目录保留天数，按目录名 `yyyyMMdd` 整目录删 |
| `KEEP_CAMERA_IMAGES_DAYS` | `30` | `camera_images` 表记录保留天数（**只删行不删文件**） |

> `KEEP_DAYS` 与 `app.archive.images.retain-days` 必须一致，`verify.sh` 会比对两者，
> 不一致直接报红（历史事故：cron 写 7 天而归档写 730 天，重装即造成大面积裂图）。
