# 相机设备接口协议

> 面向对象：相机端固件 / 算法进程开发者、现场对接工程师。
> 本文只写**服务端当前真实实现**（逐行核对源码，2026-11-13）。与代码不一致时以代码为准，并回头改本文。
> 端点清单（含管理端）见 [`接口文档.md`](接口文档.md)；本文只覆盖**设备侧**调用的四个端点。

## 一、设备可用的四个端点

| # | 用途 | 方法与路径 | 是否需要设备令牌 | 落库位置 | 现场状态 |
|---|---|---|---|---|---|
| A | 心跳 / 计数 / 资源 | `POST /api/v1/camera/status/heartbeat` | 是（`cfg_camera_token`） | `camera_status` | 在跑，5 秒/台 |
| B | **缺陷图片上传（主通道）** | `POST /api/v1/defect-images/upload` | ⚠️ 仅校验 Bearer 前缀（见 §八） | `defect_image_*` + `camera_images` | 在跑，实测 4.4 万张 |
| C | 批量检测上报（冻结契约） | `POST /api/v1/camera/inspection/batch-upload` | 是（`cfg_camera_token`） | `fact_inspection_*` + `agg_*` | 冻结，现场恒 0 |
| D | 单图上传（旧） | `POST /api/v1/camera/image/upload` | 否，需**登录用户 JWT** | `camera_images` | 仅供调试，勿用于产线 |

**选型**：产线对接用 **B（图片） + A（心跳）**。C 只在需要按缺陷类型做聚合统计、且已配好缺陷映射时启用；它与 B 写两套表，同时启用会让统计口径分叉。D 不要用——它要求人工登录令牌，且不受设备鉴权体系管辖。

## 二、通用约定

| 项 | 约定 |
|---|---|
| Base URL | `http://<服务器IP>:8091`，`context-path` 为 `/`，无额外前缀 |
| 编码 | UTF-8；JSON 字段名大小写敏感 |
| 传输 | 除 B 为 `multipart/form-data`，其余为 `application/json` |
| 时间格式 | `yyyy-MM-dd HH:mm:ss` 或 `yyyy-MM-dd HH:mm:ss.SSS` 或 ISO `yyyy-MM-ddTHH:mm:ss`（**不带时区**，一律按服务器本地时间解释） |
| 时间容错 | 时间字段解析失败**不报错**，静默回落到服务器当前时间或批次 `uploadTime` |
| 认证头 | `Authorization: Bearer <token>`（注意 `Bearer` 后有一个空格） |
| 设备标识头 | `X-Device-Id: <camera_code>` —— 这是设备的**唯一身份**，不是名称 |

### 2.1 响应信封（所有端点统一）

```json
{
  "code": 200,
  "errorCode": null,
  "message": "状态已更新",
  "data": { }
}
```

| 字段 | 含义 |
|---|---|
| `code` | `200` 成功；`500` 失败；`422` 参数校验失败；`503` 授权失效（**HTTP 仍是 200**） |
| `errorCode` | 机器可读错误标识，成功时为 `null`。**新的对接逻辑请以此判断，不要匹配中文 message** |
| `message` | 人类可读描述，仅供日志与排障 |
| `data` | 业务数据；失败时可能为 `null`，也可能带结构化失败详情 |

> ⚠️ **最重要的坑：HTTP 状态码与 `body.code` 是两条轨道。**
> - 心跳（A）的所有失败分支都是 **HTTP 200 + `code:500`**；
> - 图片上传（B）的参数错误是 **HTTP 422 + `code:422`**，单张图片失败却是 **HTTP 200 + `code:200` + `data.success:false`**；
> - 授权失效是 **HTTP 200 + `code:503`**。
>
> 设备端**必须解析 body 的 `code`**，只判断 HTTP 状态码会把「任务被拒绝」当成「上传成功」。

### 2.2 重试策略

| `code` | 是否重试 | 建议 |
|---|---|---|
| 200 且 `data.success=true` | — | 成功，无需重试 |
| 200 且 `data.success=false` | 仅重试失败的那几张 | 按 `results[].fileName` 挑出来重传，不要整批重传（会产生重复图） |
| 422 | ❌ 不重试 | 参数/文件问题，重试必然再失败。按 `errorCode` 修设备端逻辑 |
| 500 | ⚠️ 有限重试 | 指数退避（5s/15s/60s），超过 3 次停手并上报本地告警 |
| 503 | ❌ 不重试（改为降级缓存） | 服务器授权失效，**不是网络故障**。继续狂重试只会刷满日志；应本地缓存图片与计数，等运维续期后补传 |

## 三、端点 A：相机心跳

### 3.1 请求

```http
POST /api/v1/camera/status/heartbeat HTTP/1.1
Host: 10.2.77.72:8091
Authorization: Bearer CAM-001-dev-token
X-Device-Id: DA4733319
Content-Type: application/json
```

```json
{
  "cameraName": "CV1_Cam1",
  "productName": "18650-3.5Ah",
  "timestamp": "2026-11-13 10:30:00.123",
  "cameraStatus": 1,
  "recognizeCount": 348952,
  "correctCount": 348700,
  "abnormalCount": 252,
  "cpuUsage": 42.5,
  "memoryUsage": 61.0,
  "temperature": 55.5,
  "errorMessage": null,
  "resetFlag": false
}
```

| 字段 | 类型 | 必填 | 取值范围 / 说明 |
|---|---|---|---|
| `cameraName` | string | **是** | 相机展示名。**名称现场会跨产线重名**，仅作展示；身份以 `X-Device-Id` 为准 |
| `productName` | string | 否 | 当前生产产品名，写入 `camera_status.product_name` |
| `timestamp` | string | 否 | 设备侧上报时间。缺省或格式非法 → 用服务器时间 |
| `cameraStatus` | int | 否 | `0`-停止 `1`-运行 `2`-故障 `3`-待机。**越界值直接拒绝**；缺省按 `OFFLINE` 落库 |
| `recognizeCount` | int | 否 | **累计**识别总数（不是增量） |
| `correctCount` | int | 否 | **累计**识别正确数（OK） |
| `abnormalCount` | int | 否 | **累计**识别异常数（NG） |
| `cpuUsage` | double | 否 | 0–100，单位 % |
| `memoryUsage` | double | 否 | 0–100，单位 % |
| `temperature` | double | 否 | 摄氏度 |
| `errorMessage` | string | 否 | `cameraStatus=2` 时应填写，会进告警正文 |
| `resetFlag` | bool | 否 | `true` 表示设备端计数器已归零 → 服务端清掉该相机的计数缓存，避免误判「计数器重置」 |

**计数语义（必读）**：三个计数都是**自设备启动以来的累计值**，服务端每次用新值**覆盖**。上传增量、上报累计——两者不要混。服务端只在新值**小于**旧值时打一条 `检测到 xxx 计数器重置` 的日志，不会拒绝；若设备确实重启归零，请同时带上 `"resetFlag": true`。

### 3.2 成功响应

```json
{
  "code": 200,
  "errorCode": null,
  "message": "状态已更新",
  "data": {
    "serverTime": "2026-11-13 10:30:00",
    "nextInterval": 5000,
    "configVersion": "v1.0.0"
  }
}
```

`nextInterval` 当前**固定 5000 毫秒**（服务端硬编码，不接受设备协商）；`configVersion` 固定 `v1.0.0`，是协议版本位，不随配置变化。设备端应按 `nextInterval` 定时，不要自行写死。

### 3.3 失败分支（全部 HTTP 200）

| `message` | 原因 | 处理 |
|---|---|---|
| `缺少认证令牌` | 无 `Authorization` 或不以 `Bearer ` 开头 | 补请求头 |
| `缺少设备ID` | 无 `X-Device-Id` | 补请求头 |
| `设备令牌无效或已过期` | 令牌与 `cfg_camera_token` 不匹配（含传空） | 核对令牌；**这是唯一「配了令牌但传错」的拒绝路径** |
| `该相机未配置设备令牌` | 该相机无令牌记录，且服务端开启了 `camera.token.strict` | 运维配令牌，或关严格模式 |
| `cameraName 不能为空` | 必填缺失 | 补字段 |
| `无效的相机状态，状态值应为 0-停止, 1-运行, 2-故障, 3-待机` | `cameraStatus` 越界 | 修正枚举 |
| `设备未在系统配置中维护: XXX` | `X-Device-Id` 在 `camera_status.camera_code` 中查不到 | **先建档再上报**（与图片上传不同，心跳强制要求相机已存在） |
| `相机名称重复，无法确定目标设备: XXX` | 未传/传错 `X-Device-Id`，且 `cameraName` 命中多行配置 | 改用 `camera_code` 上报 |
| `服务器内部错误：...` | 服务端异常 | 查服务端日志 |

### 3.4 心跳触发的告警（会写告警表，设备端需知）

| 告警类型 | 级别 | 触发条件 | 可配项（`system_settings`） |
|---|---|---|---|
| `CAMERA_FAULT` | CRITICAL | `cameraStatus == 2` | — |
| `COUNT_MISMATCH` | WARNING | `\|recognizeCount - (correctCount + abnormalCount)\| > 1` | — |
| `CPU_HIGH` | WARNING | `cpuUsage > 阈值` | `alert.cpuWarning`（默认 90） |
| `MEMORY_HIGH` | WARNING | `memoryUsage > 阈值` | `alert.memoryWarning`（默认 90） |
| `TEMPERATURE_HIGH` | WARNING | `temperature > 阈值` | `alert.temperatureWarning`（默认 70） |

节流规则：同一相机同一类型 **30 分钟内只落 1 条**；条件消失后需**稳定 2 分钟**才判定恢复。所以设备端不要指望「每次上报都产生一条告警」，也不要在故障期间靠反复上报求关注。

> `COUNT_MISMATCH` 是最常见的误报来源：`ok+ng` 与 `total` 差 2 以上就报。设备端如果存在「漏检」或「重检」计数，请保证三者自洽。

## 四、端点 B：缺陷图片上传（主通道）

### 4.1 请求

```http
POST /api/v1/defect-images/upload HTTP/1.1
Host: 10.2.77.72:8091
Authorization: Bearer CAM-001-dev-token
X-Device-Id: DA4733319
Content-Type: multipart/form-data; boundary=----X
```

multipart 三部分：

| part 名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `files` | file[] | 二选一 | 图片数组。**推荐**用这个字段名 |
| `file` | file[] | 二选一 | 兼容字段，服务端会把 `files` 与 `file` 合并 |
| `metadata` | text | **是** | JSON 字符串（不是文件），结构见下 |

### 4.2 metadata 结构

```json
{
  "cameraId": "DA4733319",
  "cameraName": "CV1_Cam1",
  "uploadTime": "2026-11-13 10:30:00.123",
  "images": [
    {
      "fileName": "20261113_103000_001.jpg",
      "captureTime": "2026-11-13 10:30:00.050",
      "defects": [
        { "type": "SCRATCH", "severity": "HIGH",
          "x": 120.5, "y": 80.0, "width": 30.0, "height": 12.0, "area": 360.0 }
      ]
    }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `cameraId` | string | **是** | 相机编号。落库与目录用它，**服务端以它为准**（缺失才回落 header `X-Device-Id`）。⚠️ 服务端**不校验**两者是否相同，设备端必须自己保证一致，否则图片会挂到错误的相机下 |
| `cameraName` | string | 否 | 展示名，缺省回落 `cameraId` |
| `uploadTime` | string | 否 | 本批上传时间，缺省用服务器接收时间。同时决定落盘日期目录 |
| `images[].fileName` | string | **是** | 必须与 multipart 中某个文件的**原始文件名完全一致**（含扩展名） |
| `images[].captureTime` | string | 否 | 采集时刻，缺省用 `uploadTime` |
| `images[].defects` | array | 否 | 缺省/null 视为「无缺陷」（良品） |
| `defects[].type` | string | 否 | 缺陷类型自由文本，原样落库，服务端不做字典校验 |
| `defects[].severity` | string | 否 | 见下方归一化规则；缺省按 `LOW` |
| `defects[].x/y/width/height/area` | double | 否 | 像素坐标与面积，原样落库；缺省按 0 |

**`severity` 归一化（服务端自动转换，设备端传哪种都行）**

| 输入 | 归一化结果 |
|---|---|
| `HIGH`、`严重`、`高` | `HIGH` |
| `MEDIUM`、`MAJOR`、`中`、`重大` | `MEDIUM` |
| 其它任何值 / 空 | `LOW` |

### 4.3 校验规则（任一不满足 → HTTP 422，整批拒绝）

| 规则 | 具体判定 |
|---|---|
| 令牌 | `Authorization` 存在且以 `Bearer ` 开头（⚠️ 见 §八） |
| 设备号 | `X-Device-Id` 非空 |
| 文件 | 至少 1 个非空文件 |
| 批量上限 | 文件数 ≤ `defect-image.max-batch-images`（默认 **100**），且 `images` 数组长度也 ≤ 100 |
| metadata | 非空；JSON 可解析；容忍开头 BOM |
| cameraId | 非空 |
| images | 非空；每项 `fileName` 非空 |
| 一一对应 | 上传文件名集合 与 `images[].fileName` 集合**必须完全相等**（多一个、少一个都拒） |
| 文件名唯一 | 两侧都不允许重复文件名 |
| 扩展名白名单 | `jpg` `jpeg` `png` `bmp` `gif` `webp` —— **`svg` 被明确禁止**（可携带脚本，存储型 XSS） |
| 内容可解码 | `jpg/jpeg/png/bmp/gif` 必须能被服务端解码；`webp` 不强制 |
| 尺寸 | 宽或高 ≤ 2px 判为占位图，拒绝 |

**文件名比对口径**：去路径 + `trim` + **转小写**后比较。所以 `A.JPG` 与 `a.jpg` 视为同名（会判重复）。服务端落盘时用自己生成的名字，**不会**用设备端的原始文件名。

**单文件大小**：受 `spring.servlet.multipart.max-file-size` 限制，默认 **10MB/文件**，单请求总量上限 1024MB。超限时由容器直接返回 HTTP 413/500，**不进业务校验**——设备端应先自查文件大小。

### 4.4 成功响应

```json
{
  "code": 200,
  "errorCode": null,
  "message": "缺陷图片上传成功",
  "data": {
    "success": true,
    "batchNo": "DA4733319-20261113103000123-a1b2c3d4",
    "batchId": 10231,
    "cameraId": "DA4733319",
    "cameraName": "CV1_Cam1",
    "imageCount": 1,
    "successCount": 1,
    "failCount": 0,
    "defectCount": 1,
    "highCount": 1,
    "mediumCount": 0,
    "lowCount": 0,
    "results": [
      {
        "fileName": "20261113_103000_001.jpg",
        "success": true,
        "imageId": 884422,
        "imageUrl": "/api/v1/defect-images/file/20261113/DA4733319/103000123_9f3c1a7b.jpg",
        "errorCode": null,
        "message": "上传成功",
        "failureReason": null,
        "handlingAdvice": null
      }
    ]
  }
}
```

| 字段 | 说明 |
|---|---|
| `success` | **整批全成功才为 `true`**；有任一张失败即 `false`，但其余图片已入库 |
| `batchNo` | `cameraId-yyyyMMddHHmmssSSS-uuid8`，服务端生成 |
| `batchId` | `defect_image_batch` 主键，排障时用它查库 |
| `defectCount / highCount / mediumCount / lowCount` | 按 `severity` 归一化后统计 |
| `results[]` | **逐文件**结果，顺序与 `metadata.images` 一致 |

**部分成功**：`data.success=false` + `failCount>0`，HTTP 仍为 **200 / code 200**，`message` 变成「缺陷图片部分上传失败」。设备端应遍历 `results`，只重传 `success=false` 的项。

### 4.5 逐文件失败码（`results[].errorCode`）

| errorCode | 含义 | 建议动作 |
|---|---|---|
| `FILE_NAME_MISMATCH` | metadata 声明的文件名在 multipart 里找不到 | 核对文件名（含扩展名、大小写） |
| `IMAGE_CONTENT_INVALID` | 文件损坏 / 空文件 / 扩展名与内容不符 | 重新导出原图 |
| `UNSUPPORTED_IMAGE_FORMAT` | 扩展名不在白名单 | 转 jpg/png |
| `IMAGE_SIZE_INVALID` | 尺寸 ≤ 2px，疑似占位图 | 检查采集链路 |
| `UPLOAD_FAILED` | 其它（含磁盘写入失败） | 查服务端日志与磁盘容量 |

### 4.6 整批失败码（HTTP 422 时 `body.errorCode`）

| errorCode | 触发条件 |
|---|---|
| `UPLOAD_BATCH_SIZE_EXCEEDED` | 文件数或 `images` 数超过上限 |
| `UPLOAD_FILE_NAME_MISMATCH` | 文件名不一一对应 / 有重复 |
| `UPLOAD_METADATA_INVALID` | metadata 缺失或 JSON 结构错 |
| `AUTH_DEVICE_UNAUTHORIZED` | 缺 `Authorization` 或 `X-Device-Id` |
| `PARAM_INVALID` | 其它参数问题 |

422 时 `data` 里仍会带一个 `results[]`，`fileName` 填的是**问题文件名**（能识别时），并附 `failureReason` 与 `handlingAdvice` 中文说明。

### 4.7 落盘与访问

```
<defect-image.upload.dir>/yyyyMMdd/<cameraId>/HHmmssSSS_<uuid8>.<ext>
生产：/main/app/data/images/defect-images/20261113/DA4733319/103000123_9f3c1a7b.jpg
```

- `cameraId` 中非 `[A-Za-z0-9._-]` 的字符会被替换为 `_`
- 文件名由服务端生成，`HHmmssSSS` + 8 位 uuid，**天然不重名**
- 访问 URL：`/api/v1/defect-images/file/<相对路径>`，例如
  `http://10.2.77.72:8091/api/v1/defect-images/file/20261113/DA4733319/103000123_9f3c1a7b.jpg`
- 该 URL **免鉴权**（`/defect-images/file/**` 在白名单内），知道路径即可读

### 4.8 落库行为

| 表 | 写入内容 |
|---|---|
| `defect_image_batch` | 批次行（batchNo、相机、上传时间、声明张数、成功/失败/缺陷统计） |
| `defect_image_file` | 每张图一行（路径、尺寸、大小、采集时间、缺陷计数） |
| `defect_image_box` | 每个缺陷框一行（type/severity/坐标/面积） |
| `camera_images` | 兼容旧表的镜像行 |
| `camera_status` | 仅更新 `latest_image_path` 与 `last_upload_at` |

**未建档相机也能上传成功**——服务端只在更新「最新图片」时找不到行就静默跳过。但这样这些图片在按产线/工位筛选的页面里查不到（没有 `line_id/workstation_id`），所以**上线前必须先建档**。

## 五、端点 C：批量检测上报（冻结契约）

> 状态：**冻结**。现场未启用（`fact_inspection_*` 恒 0 行），缺陷映射 `cfg_camera_defect_mapping` 需先配。除非甲方明确要求按缺陷类型出聚合报表，否则不要接这条。

### 5.1 请求

```http
POST /api/v1/camera/inspection/batch-upload
Authorization: Bearer <device-token>
X-Device-Id: DA4733319
X-Batch-Id: ZK23-DA4733319-20261113103000     ← 可选，body 里没有 batchId 时用它
Content-Type: application/json
```

```json
{
  "schemaVersion": "2.0",
  "batchId": "ZK23-DA4733319-20261113103000",
  "requestId": "req-0001",
  "cameraCode": "DA4733319",
  "productName": "18650-3.5Ah",
  "reportTime": "2026-11-13 10:30:00",
  "timeRange": { "startTime": "2026-11-13 10:00:00", "endTime": "2026-11-13 10:30:00" },
  "counterMode": "INCREMENTAL",
  "summary": { "totalCount": 1200, "okCount": 1180, "ngCount": 20 },
  "defects": [
    { "sourceCode": "P0", "count": 12 },
    { "sourceCode": "P1", "count": 8 }
  ]
}
```

| 字段 | 必填 | 规则 |
|---|---|---|
| `schemaVersion` | **是** | 必须是字符串 `"2.0"`，否则 422 |
| `batchId` | **是**（或 header `X-Batch-Id`） | 幂等键，同相机重复提交按已接收处理 |
| `requestId` | 否 | 排障用，落 `fact_inspection_batch` |
| `cameraCode` | **是** | 必须在 `dim_camera` 中存在且未删除 |
| `productName` | **是** | 必须与产品配置**完全一致**（含大小写） |
| `reportTime` | **是** | 批次上报时间，决定 30 分钟时间桶 |
| `timeRange.startTime/endTime` | **是** | 统计区间 |
| `counterMode` | **是** | 只接受 `INCREMENTAL`（大小写不敏感） |
| `summary.totalCount/okCount/ngCount` | **是** | 见下方一致性规则 |
| `defects[].sourceCode` | 否 | 缺陷源编码，需在 `cfg_camera_defect_mapping` 有映射 |
| `defects[].count` | 否 | **增量**条数 |

**强制一致性（任一不满足 → 422，整批不入库）**

1. `totalCount == okCount + ngCount`
2. `ngCount == Σ defects[].count`
3. 相机、产品、缺陷映射必须已配置

**幂等**：按 `(cameraId, batchId)` 判重。重复提交返回 `accepted=true, duplicate=true`，**不重复入库**，并回填首次的 `inspectionBatchId`。

## 七、授权闸门（会让上报突然全部失败）

服务端启用了 License 授权。当授权过期或即将过期进入受限状态时，三个设备写入端点会被拦截：

```http
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8
```

```json
{
  "code": 503,
  "errorCode": "LICENSE_EXPIRED",
  "message": "授权已过期（...），已暂停接收设备上报；请联系管理员续期授权后恢复。",
  "data": null
}
```

| errorCode | 含义 |
|---|---|
| `LICENSE_EXPIRED` | 授权已过期且已过宽限期 → 所有设备写入被拒 |
| `LICENSE_BLOCKED` | 全站受限（更严重）→ 除登录/授权页/告警查询外全部 403 语义 |

**为什么是 HTTP 200**：设备固件按 body 里的 `code` 判断结果，改 HTTP 状态码会让它们当成网络故障无限重试。

**设备端要求**：收到 `code=503` 后**必须停止无条件重试**，转为本地缓存（图片落本地盘、计数落本地文件），并上报一条本地告警。当前现场授权状态：

```bash
curl -s http://10.2.77.72:8091/api/license | python -m json.tool
```

## 八、鉴权体系与现状缺口

### 8.1 设备令牌表 `cfg_camera_token`

```sql
CREATE TABLE cfg_camera_token (
  token_id    BIGINT AUTO_INCREMENT PRIMARY KEY,
  camera_id   BIGINT       NOT NULL,        -- dim_camera.camera_id
  camera_code VARCHAR(50)  NOT NULL,        -- 冗余，便于排查
  token_hash  VARCHAR(255) NOT NULL,        -- 明文 或 sha256 十六进制，两种都认
  token_name  VARCHAR(100) DEFAULT NULL,
  expire_time DATETIME     DEFAULT NULL,    -- NULL = 永不过期
  is_enabled  TINYINT      NOT NULL DEFAULT 1,
  create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_camera (camera_id),
  KEY idx_enabled_expire (is_enabled, expire_time)
);
```

生效条件：`is_enabled = 1 AND (expire_time IS NULL OR expire_time > NOW())`。

**当前没有令牌管理界面，也没有 REST 接口**——只能由运维直接写库：

```sql
-- 明文写法（联调方便，生产建议用 sha256）
INSERT INTO cfg_camera_token (camera_id, camera_code, token_hash, token_name, expire_time)
SELECT camera_id, camera_code, 'CAM-001-dev-token', 'ZK23-1号线-CCD1', '2029-12-31 23:59:59'
FROM dim_camera WHERE camera_code = 'DA4733319' AND IFNULL(is_deleted,0) = 0;

-- sha256 写法：token_hash = sha256(原始令牌)
-- echo -n 'my-strong-token' | sha256sum
```

### 8.2 严格模式开关

```yaml
camera:
  token:
    strict: false   # false（默认）：未配令牌的相机放行 + WARN；true：一律拒绝
```

- **未配令牌**（该相机在 `cfg_camera_token` 无有效记录）：由 `strict` 决定
- **配了令牌但传错**：两种模式下**都拒绝**（这是 2026-11-12 修掉的洞：原先只判 `Bearer ` 前缀，token 取了就丢）

生产建议：全部相机配齐令牌后把 `strict` 置 `true`，否则任何知道相机编号的人都能伪造心跳与计数。

### 8.3 ⚠️ 三个已知缺口（如实记录，勿当成已解决）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| 1 | **`POST /api/v1/defect-images/upload` 未与 `cfg_camera_token` 比对**，只校验 `Authorization` 以 `Bearer ` 开头 | 主通道无实质鉴权：任何能访问 8091 的人，带任意非空 Bearer 串 + 合法 `X-Device-Id` 即可写入图片与统计，污染产线数据与良率口径 | 复用 `CameraTokenVerifier.verify(token, deviceId)`，与心跳口径对齐（改动小，风险低） |
| 2 | 心跳/上传都会**按 `cameraName` 兜底匹配**（仅当名称唯一） | 名称重名时行为与「按编号」不同，容易误判 | 设备端**始终**传正确的 `X-Device-Id` 与 `metadata.cameraId`，不要依赖名称兜底 |
| 3 | 图片读取端点 `/api/v1/defect-images/file/**` 免鉴权 | 知道路径即可下载任意缺陷图，路径可枚举（日期+相机+8 位随机后缀，枚举成本较高但非零） | 对外网暴露时必须加网关鉴权或改签名 URL |

### 9.1 第 5–7 项：后端有端点，前端没页面

后端 `/api/v1/config/products`、`/config/defect-types`、`/config/camera-defect-mappings` 三个端点（`FinalConfigController`）**全部存在且可用**，但前端对应路由是**重定向桩**：

```
/system/brands        → redirect /system/config   （产品/品牌）
/system/defect-types  → redirect /system/config   （缺陷分类）
```

而 `/system/config` 页面的导航只有 6 项：配置总览、产线管理、工位管理、相机管理、用户管理、操作记录。**产品、缺陷类型、缺陷映射都不在其中**。`frontend/src/views/defect/DefectTypeList.vue` 文件仍在，但没有任何路由指向它（`frontend/src/api/final-config.js` 也无人 import）。

这是既有问题（同批 15 个视图被改成重定向桩），本次未修。当前可行的三条路：

1. **直接调 API**（需 ADMIN 角色的 JWT）——最推荐，字段校验由服务端负责；
2. **SQL 预置**——批量、可脚本化，适合新线开局；
3. 前端临时把路由改回去——需重新验证该页与当前后端字段是否一致，不建议在交付期动。

SQL 预置示例（按你自己的编码表替换）：

```sql
-- 产品（端点 C 的 productName 必须与 product_name 逐字一致）
INSERT INTO dim_product (product_code, product_name, product_spec, brand_name, sort_order, is_enabled)
VALUES ('PROD-X', '亲宝宝L码', '规格X', '默认品牌', 10, 1);

-- 缺陷类型（先拿到 defect_type_id）
INSERT INTO dim_defect_type (product_id, defect_code, defect_name, defect_category,
                             default_position_code, default_position_name, default_severity, sort_order)
VALUES (NULL, 'SCRATCH', '划伤', '外观', 'INNER', '内装区域', 'MEDIUM', 20);

-- 相机缺陷映射：设备上报的 sourceCode → 标准缺陷
INSERT INTO cfg_camera_defect_mapping
  (factory_id, line_id, workstation_id, camera_id, camera_code, product_id, product_name,
   source_code, defect_type_id, defect_code, defect_name,
   position_id, position_code, position_name, severity, is_ng, effective_start)
SELECT c.factory_id, c.line_id, c.workstation_id, c.camera_id, c.camera_code,
       p.product_id, p.product_name,
       'SCRATCH', dt.defect_type_id, dt.defect_code, dt.defect_name,
       dt.default_position_id, dt.default_position_code, dt.default_position_name,
       dt.default_severity, dt.is_ng, '2026-01-01 00:00:00'
FROM dim_camera c
JOIN dim_product p ON p.product_name = '亲宝宝L码'
JOIN dim_defect_type dt ON dt.defect_code = 'SCRATCH'
WHERE c.camera_code = 'DA4733319';
```

> 映射的 `product_id` 可为 `NULL`（表示对全部产品生效）；查询时**产品精确匹配优先**，其次才取 `product_id IS NULL` 的那条（`ORDER BY CASE WHEN product_id = ? THEN 0 ELSE 1 END`）。同 `sourceCode` 有多条时取 `effective_start` 最新的那条。

### 9.2 第 8 项：令牌表没有任何写入方

`cfg_camera_token` 在全部 Java 代码里只有三种操作——`SELECT token_hash`、`DELETE`（删相机时连带清理）、`COUNT`（删相机前依赖检查）。**没有任何 INSERT / UPDATE**，前端也搜不到该表（`frontend/src` 里 `camera_token` 只命中登录 token 相关文件）。

也就是说：**令牌必须由运维直接写库**。

```sql
-- token_hash 同时兼容「明文」与「sha256 十六进制」，见 §8.2
INSERT INTO cfg_camera_token (camera_id, camera_code, token_hash, token_name, expire_time, is_enabled)
SELECT camera_id, camera_code, SHA2('现场真实令牌串', 256), '产线令牌', NULL, 1
FROM dim_camera
WHERE camera_code = 'DA4733319' AND IFNULL(is_deleted, 0) = 0;
```

| 写法 | 结果 | 建议 |
|---|---|---|
| `SHA2('...', 256)` | 与设备传的明文做 sha256 比对，命中 | ✅ 生产用这个 |
| 直接写明文 | 与设备传的明文逐字比对，命中 | 仅调试。等于把令牌明文落库 |

> 注意：`camera.token.strict=false`（默认）时，**未配令牌的相机是放行的**，只在日志里 WARN。所以"没配令牌"不会报错，会让你误以为鉴权已生效。投产前务必按 §8.2 收紧。

### 9.3 新装库的默认种子（会误导对接）

`fact-product/src/main/resources/sql/deploy/02_final_schema_p0.sql`（建库脚本，现场经 `installer` 按 01→05 顺序执行）在**建库时**会灌入以下数据：

| 表 | 默认内容 | 后果 |
|---|---|---|
| `cfg_camera_token` | 每台相机一条，`token_hash = 'dev-token'`（**明文**） | 等于全网公开令牌，投产前必须全部替换 |
| `cfg_camera_defect_mapping` | 每台相机 × 每个产品 × 每种缺陷类型，`source_code = p{sort_order}`（`p0`/`p1`/`p2`…） | 设备端若用自有编码（`SCRATCH`、`GLUE_SMALL`），直接全部 `UNMAPPED` |
| `dim_product` | `产品A` / `产品B` | 设备上报其他名称 → `PRODUCT_NOT_FOUND` |
| `dim_defect_type` | `P0_INNER_GLUE_SMALL` 等若干条 | 仅作示例 |

**这些种子只在会 `DROP` 重建 21 张表的 02 脚本里，生产升级绝不能执行该脚本。** 现场补数据只能手工 INSERT/UPDATE 或走 9.1 的 API——这也是为什么第 5–7 项必须有清楚的手工路径。

### 9.4 上线前用 SQL 自检

```sql
-- ① 哪些相机没有可用令牌（strict=true 时这些相机会被拒）
SELECT c.camera_code, c.camera_name, t.expire_time
FROM dim_camera c
LEFT JOIN cfg_camera_token t
       ON t.camera_id = c.camera_id AND t.is_enabled = 1
      AND (t.expire_time IS NULL OR t.expire_time > NOW())
WHERE IFNULL(c.is_deleted, 0) = 0 AND t.token_id IS NULL
ORDER BY c.camera_code;

-- ② 产品清单（设备 productName 只能取这里的值）
SELECT product_code, product_name FROM dim_product WHERE is_deleted = 0 AND is_enabled = 1;

-- ③ 每台相机已配多少 sourceCode（0 表示该相机无法走端点 C）
SELECT c.camera_code, COUNT(m.mapping_id) AS active_mappings,
       GROUP_CONCAT(DISTINCT m.source_code ORDER BY m.source_code) AS source_codes
FROM dim_camera c
LEFT JOIN cfg_camera_defect_mapping m ON m.camera_id = c.camera_id AND m.is_enabled = 1
WHERE IFNULL(c.is_deleted, 0) = 0
GROUP BY c.camera_id, c.camera_code
ORDER BY active_mappings, c.camera_code;
```

## 十、联调自检清单

上线前逐项确认，全部通过再接入产线：

- [ ] `X-Device-Id` 用的是 **`camera_code`**（如 `DA4733319`），不是相机名称
- [ ] `camera_status` 与 `dim_camera` 里该 `camera_code` **已建档**（心跳强制依赖）
- [ ] `cfg_camera_token` 已配该相机令牌，且 `expire_time` 未过
- [ ] 心跳能稳定返回 `code=200`，`nextInterval` 被正确采纳为定时周期
- [ ] 三个累计计数（total/ok/ng）**自洽**（`total == ok + ng`），不触发 `COUNT_MISMATCH`
- [ ] 上传的 `metadata.images[].fileName` 与 multipart 文件名**逐字一致**（含扩展名）
- [ ] 单文件 < 10MB，单批 ≤ 100 张
- [ ] 设备端能正确处理「HTTP 200 + `data.success=false`」的部分失败，只重传失败项
- [ ] 设备端读到 `code=503` 会**停止重试并本地缓存**
- [ ] 服务器磁盘有空间（20 相机 × 5 张/分 ≈ 144000 张/天，单张 350KB ≈ 48GB/天）

### 10.1 冒烟脚本

```bash
BASE=http://10.2.77.72:8091
TOKEN='CAM-001-dev-token'
DEV='DA4733319'

# 1) 心跳
curl -s -X POST "$BASE/api/v1/camera/status/heartbeat" \
  -H "Authorization: Bearer $TOKEN" -H "X-Device-Id: $DEV" \
  -H 'Content-Type: application/json' \
  -d "{\"cameraName\":\"CV1_Cam1\",\"cameraStatus\":1,\"recognizeCount\":100,\"correctCount\":98,\"abnormalCount\":2,\"cpuUsage\":30,\"memoryUsage\":40,\"temperature\":50}" \
  | python -m json.tool

# 2) 图片上传（当前目录放一张 test.jpg）
curl -s -X POST "$BASE/api/v1/defect-images/upload" \
  -H "Authorization: Bearer $TOKEN" -H "X-Device-Id: $DEV" \
  -F 'files=@test.jpg;filename=test.jpg' \
  -F "metadata={\"cameraId\":\"$DEV\",\"cameraName\":\"CV1_Cam1\",\"uploadTime\":\"2026-11-13 10:30:00\",\"images\":[{\"fileName\":\"test.jpg\",\"defects\":[{\"type\":\"SCRATCH\",\"severity\":\"HIGH\",\"x\":10,\"y\":10,\"width\":20,\"height\":20,\"area\":400}]}]}" \
  | python -m json.tool
```

> `-F 'files=@test.jpg;filename=test.jpg'` 里的 `filename=` 不能省：`curl` 默认传完整路径，服务端虽然会剥离路径，但显式指定最省事。

### 10.2 推荐接入顺序

按这个顺序调，每一步都能在页面上看到结果，出问题容易定位：

1. **心跳** → 相机管理页能看到该相机在线（能到这一步说明：建档、令牌、`X-Device-Id` 三样都对）
2. **图片上传** → 图像记录页能看到图片（说明 metadata 与文件名的对应、`cameraId` 都对）
3. **批量上报** → 产线统计页 KPI 与图表有数（说明产品名、`sourceCode` 映射、计数自洽都对）

> 顺序反过来会很难查：端点 C 的 `errorCode` 有十几种（§5.3），但其中「相机未建档」「令牌不对」「缺 header」和端点 A 是同一批前置条件，先用心跳把这些排掉。

### 10.3 最小联调用例

| 编号 | 用例 | 预期结果 | 验证点 |
|---|---|---|---|
| T01 | 正常心跳 `cameraStatus=1` | `code=200`，相机状态变为运行 | 建档 + 令牌 + `X-Device-Id` |
| T02 | 故障心跳 `cameraStatus=2` | `code=200`，相机状态故障，产生 `CAMERA_FAULT` 告警 | 告警落库（30 分钟去重，重试不会多出告警） |
| T03 | 两张图片 + 正确 metadata | `data.success=true`，图像记录展示 2 张 | metadata 与 multipart 文件名一一对应 |
| T04 | `metadata.images[].fileName` 与文件名不一致 | HTTP 422，`body.errorCode=UPLOAD_FILE_NAME_MISMATCH`，`results[0].errorCode=FILE_NAME_MISMATCH` | 严格相等校验（含扩展名，小写后比较） |
| T05 | 正常批量上报 | `accepted=true`，产线统计 KPI 增加 | `total = ok + ng`、`ng = Σcount` |
| T06 | 上报未配置映射的 `sourceCode` | HTTP 422，`errorCode=UNMAPPED`，并写 `fact_inspection_mapping_exception` | 映射表（见 9.1） |
| T07 | 重复 `batchId` 再发一次 | `code=200`，`duplicate=true`，统计不翻倍 | 幂等键是「相机 + `batchId`」 |
| T08 | 单批 101 张图片 | HTTP 422，`errorCode=UPLOAD_BATCH_SIZE_EXCEEDED` | 拆批重传（默认上限 100） |

> 用例 T02 额外提示：告警有 30 分钟同类型去重与 2 分钟恢复稳定期，**不要用"连发 3 次故障心跳看是否 3 条告警"来验收**，会误判为功能失效。

### 10.4 Postman 调试注意事项

| 端点 | Body 类型 | 要点 |
|---|---|---|
| 心跳 / 批量上报 | `raw` → `JSON` | `Content-Type: application/json` |
| 图片上传 | `form-data` | 文件字段名用 **`files`**（旧字段名 `file` 也兼容，不要两个都传）；可多行同名 |

四条必查：

1. `metadata` 字段类型选 **`Text`**（不是 `File`），值必须是**合法 JSON 字符串**——多一个逗号就是 HTTP 422 `UPLOAD_METADATA_INVALID`（`results[0].errorCode` 为 `METADATA_INVALID`）。
2. Header 必须有 `Authorization: Bearer <token>` 与 `X-Device-Id: <camera_code>`。
3. Postman 选文件后会带本地路径，`metadata.images[].fileName` 只写**文件名**（不含路径），否则 `FILE_NAME_MISMATCH`。
4. 中文文件名建议先在设备端转 ASCII——路径与 `metadata` 两处都做，避免编码差异导致比对失败。

### 10.5 「上传返回成功，但页面看不到图」

按顺序排，四步内必定位：

1. **`metadata.cameraId` 是不是 `camera_code`**（不是相机名称、不是数据库自增 `camera_id`）。图片会照常落盘、`defect_image_file` 也有行，但图像记录页要 `JOIN dim_camera` 才能显示——**未建档的编码查不出来**，表现为"上传成功但没图"。
2. **`metadata.images[].fileName` 与真实文件名是否逐字一致**。不一致时该图进 `results[].errorCode = FILE_NAME_MISMATCH`，但整批仍可能是 `code=200`。
3. **图片本身能否解析**。空文件、损坏、扩展名与内容不符 → `IMAGE_CONTENT_INVALID`；1–2px 占位图 → `IMAGE_SIZE_INVALID`。
4. **页面筛选条件**：图像记录页默认带工厂/产线/工位/时间范围筛选，新图落在筛选范围外就不会显示。先清空筛选再查。

> 如果四步都对还看不到，直接查库：`SELECT * FROM defect_image_file WHERE camera_id = '<camera_code>' ORDER BY create_time DESC LIMIT 5;`（该列存的是 **camera_code**，不是数字 ID）。
