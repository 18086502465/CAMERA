## 3. 本轮实测发现并已修掉的 3 个缺陷

### 3.1 ★ P0：匿名可注册管理员账号

**这是本项目目前发现的最严重安全问题**，且是**完整复现**过的。

#### 根因（两处叠加）

**① `AuthController.register()` 直接采信请求传入的角色**

```java
user.setRole(request.getRole() != null ? request.getRole() : 0);   // ← 致命
```

**② `/api/auth/register` 在 `SecurityConfig` 白名单里**（匿名可调）。

#### 实测复现（2026-10-31，服务器上真实执行）

```
① 匿名 POST /api/auth/register
   body: {"username":"evil_admin_01","password":"Evil@123456","realName":"黑客","role":1}
   → HTTP 200 {"code":200,"message":"操作成功","data":"注册成功"}

② 查库确认：
     admin         | role=1 | 系统管理员
     evil_admin_01 | role=1 | hacker          ← ★ 真的写成了管理员

③ 用 evil_admin_01 登录 → 拿到 token（长度 168）

④ 用该 token 访问管理员接口：
     /api/user                 → HTTP 200
     /api/v1/system/settings   → HTTP 200
     /api/logs/operation       → HTTP 200
```

**危害**：**无需任何凭据**即可获得管理员权限 —— 比"普通用户删管理员"更严重，
因为门槛从"有一个工人账号"降到"能访问到 8091 端口"。

#### 修复

角色改由**服务端**决定，**永远为普通用户（0）**，请求里传什么都不采信：

```java
// 角色固定为普通用户，不接受请求传入的角色
user.setRole(0);
```

同时补了入参判空（`username` / `password` 为 null 或空白直接拒绝），
避免 `passwordEncoder.encode(null)` 抛同样的异常。

#### 修复后实测

```
匿名注册带 role:1 → HTTP 200「注册成功」
查库：evil_test_02 | role=0        ← ★ 已是普通用户，提权被堵死
```

> **建议后续（需业务确认）**：生产环境把 `/api/auth/register` 从白名单移除，
> 关闭自助注册 —— 前端注册页保留但接口不开放，工人账号一律由管理员在
> 「系统设置 → 用户管理」里建。这样连"工人账号被批量注册污染 sys_user"也一并消除。

### 3.2 P1：登录接口 `password` 字段缺失 → HTTP 500

#### 实测（修复前）

| 请求体 | 响应 |
|---|---|
| `{"username":"admin"}`（无 password 字段） | **HTTP 500 + Spring 默认错误页** |
| `{"username":"admin","password":""}` | HTTP 200 + 「用户名或密码错误」 |
| `{"username":"admin","password":"wrong"}` | HTTP 200 + 「用户名或密码错误」 |

日志里伴随整段堆栈：

```
ERROR ... IllegalArgumentException: rawPassword cannot be null
  at org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder.matches
```

#### 根因

`BCryptPasswordEncoder.matches(null, hash)` 抛 `IllegalArgumentException`，
被 Spring 兜成 500 —— 既不像业务失败，也在日志里刷堆栈。

顺带发现第二个隐患：`isDisabled` 是 `Integer`，`user.getIsDisabled() == 1`
是**自动拆箱比较**，库中该字段为 NULL 时会 NPE。

#### 修复

```java
String username = (request == null) ? null : trimToNull(request.getUsername());
String password = (request == null) ? null : request.getPassword();
if (username == null || password == null || password.isEmpty()) {
    return ResultVO.error("用户名或密码错误");
}
SysUser user = userService.findByUsername(username);
if (user == null || (user.getIsDisabled() != null && user.getIsDisabled() == 1)) { ... }
```

#### 修复后实测

| 请求体 | 响应 |
|---|---|
| `{"username":"admin"}` | HTTP 200 + 「用户名或密码错误」✅ |
| `{"username":"admin","password":""}` | HTTP 200 + 「用户名或密码错误」✅ |
| `{"username":"admin","password":"wrong"}` | HTTP 200 + 「用户名或密码错误」✅ |
| `{"username":"admin","password":"admin123"}` | HTTP 200 + 「操作成功」✅ |

**四种情况全部正确，无 500。**

### 3.3 P1：清理脚本「图片目录不存在」时跳过库记录清理

#### 实测（服务器日志连续 3 天）

```
[cleanup] 目录不存在：/data/camera-detection/images/defect-images（跳过）
```

#### 根因

`cleanup-defect-images.sh` 在**第 69 行** `exit 0`，
而**库记录统计在第 126 行、库记录删除在第 207 行** ——
目录一旦不存在，**整段库记录清理被完全跳过**。

**触发条件很常见**：首次部署未上传过图片、或目录被压测/清理脚本删掉
（本例就是 10-28 压测后 `--purge-db` 把目录删了）。

**后果**：库里的过期 `defect_image_file` / `_box` / `_batch` / `camera_images`
**永远不会被清理，会无限堆积**。

#### 修复

目录不存在时只置 `SKIP_DISK=1` 跳过「删磁盘文件」，
**库记录清理照常执行**：

```bash
SKIP_DISK=0
if [[ ! -d "$DIR" ]]; then
  log "图片目录不存在：${DIR}（本次只清理库记录，跳过磁盘文件）"
  SKIP_DISK=1
fi
```

#### 修复后实测

```
造 4 条过期记录（file/box/batch/camera_images 各 1），图片目录确认不存在
→ 清理前 file=1 box=1 batch=1 camera_images=1
→ 执行清理：
   [cleanup] 将清理：图片记录 1 条 / 缺陷框 1 条 / 批次 1 条
   [cleanup] ✓ 库记录已清理
   [cleanup] 跳过磁盘文件删除（图片目录不存在）
→ 清理后 file=0 box=0 batch=0 camera_images=0     ← ★ 全部清空
```

### 4.1 顺带修正了手册里的恢复演练命令（实测跑不通）

**第一次演练失败**：`ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: NO)`

**根因**：这台机器的 root 插件是 **`mysql_native_password`**（不是 Ubuntu 默认的 `auth_socket`），
所以手册里写的 `sudo mysql -e "..."`（socket 免密）**必然失败**。

> 我第一次误判成"备份不可恢复"，改用 `MYSQL_PWD` + TCP 后**演练完全通过** ——
> 备份本身没问题，是**手册里的命令有问题**。

**手册已补认证插件分支**（`auth_socket` vs `mysql_native_password` 两种写法），
并统一给出「最稳写法」：

```bash
export MYSQL_PWD='你的数据库口令'
mysql -h127.0.0.1 -uroot -e "SELECT 1"
```

> 顺带提醒：`sudo` **不继承** `MYSQL_PWD`，
> 要在 `sudo bash -c '...'` 里用口令必须写 `sudo MYSQL_PWD='xxx' bash -c '...'`。

### 6.1 MySQL 421 MB 的构成

| 组成 | 大小 | 占比 |

## 9. 结论

**这台服务器的运行质量是好的**：服务 4 天零重启、备份连续 8 次成功且实测可恢复、
慢查询日志里没有一条业务慢查询、内存用了 13%、磁盘用了 2%、日志治理到位。

**但两件事必须说清楚**：

1. **它还是空转的** —— 一帧产线图片都没有。所有"接了产线才会暴露"的问题
   （高并发上传、图片清理真实行为、库表增长）**都还没被验证**。
   接产线前必须做一次真实图片的联调。

2. **本轮实测挖出 3 个此前所有轮次都没发现的缺陷**，其中一个是 P0 级
   （**匿名可注册管理员**，完整复现过）。这说明**代码走查发现不了这类问题** ——
   `register` 里那行 `request.getRole()` 看起来完全无害，只有真的调一次接口才知道。
   **安全项必须靠实测清单，不能靠读代码。**

**下一步优先级**：
① 补角色鉴权（P0，3–5 小时）→ ② 关公开注册 → ③ 接产线前做真实图片联调 →
④ 删遗留目录与脏数据。
