# 产线缺陷在线 AI 检测系统 —— 产品介绍

> 版本：v1.0.0 ｜ 文档日期：2026-11-02
> 代码库：`D:/031_45344camera` ｜ 部署形态：单一 Spring Boot JAR（含前端静态资源）+ MySQL 8.0
> 适用读者：产线管理者、质量工程师、系统运维人员、评估选型的潜在用户

## 一、产品概述

### 1.1 产品定位

面向**离散制造产线**的在线缺陷检测数据中台。工业相机在产线运行过程中持续上报状态与检测数据，
系统在服务端完成 **接收 → 校验 → 映射 → 聚合 → 展示** 的完整链路，
把相机侧的原始检测记录转化为产线管理层可直接消费的**良率、缺陷分布与异常告警**。

> **重要澄清（避免误解）**：本系统**不包含图像识别算法**。
> 相机端（或相机配套的上位机）已完成缺陷判定，系统接收的是**判定结果**
> ——缺陷类型、位置、面积、严重度。系统负责把这些结果**管起来、算出来、看出来**。

### 1.2 目标用户与各自的核心诉求

| 角色 | 主要入口 | 核心诉求 | 对应功能 |
|---|---|---|---|
| **产线操作员** | 相机状态页、实时监控看板 | 相机是否在线？当班产量与良率多少？ | 相机状态总览、实时看板 |
| **质量工程师** | 产线统计、缺陷统计、良率分析、缺陷图库 | 缺陷分布是什么？趋势如何？问题品长什么样？ | 多维聚合统计、缺陷图库、趋势分析 |
| **生产/设备工程师** | 相机监控、相机详情、异常告警 | 哪台设备异常？什么时候开始的？ | 相机监控、告警中心与处理 |
| **系统管理员** | 系统配置、系统设置、操作日志 | 组织与产品怎么配？缺陷编码怎么映射？ | 配置中心、缺陷映射、操作日志审计 |

### 1.3 解决的核心问题

| # | 痛点 | 系统的解法 | 技术落点 |
|---|---|---|---|
| 1 | **设备数据进不来** —— 相机各说各话，格式不统一 | 冻结 3 个设备端 HTTP 接口，字段与错误码全部标准化 | 设备 Token 鉴权 + 严格入参校验 + 幂等批次 |
| 2 | **缺陷编码对不上** —— 相机报的编码与系统标准缺陷类型不是一回事 | 维护「产品 + 相机 + 来源编码 → 标准缺陷类型」的一对一映射；未映射**明确报错**而非静默入库 | `cfg_camera_defect_mapping` 映射表 + `UNMAPPED` 422 |
| 3 | **看板查询慢** —— 直接扫明细表，数据量大了就卡 | 数据入库时**同步写入 30 分钟粒度聚合表**，看板只读聚合表 | `agg_quality_30m` / `agg_defect_type_30m` |
| 4 | **设备掉线没人知道** | 心跳上报 + CPU/内存/温度/计数异常阈值判定，自动生成告警 | `fact_anomaly_alert` + 系统设置阈值 |
| 5 | **现场网络条件差** —— 不能依赖公网/云服务 | 单 JAR 内含前端，离线内网服务器一键部署，无外部依赖 | 可执行 JAR + systemd + 建库脚本 |
| 6 | **数据会丢** | 自动全量备份 + SHA-256 校验 + 定期清理 | systemd timer + cron 兜底脚本 |

### 1.4 整体价值主张

- **对产线**：把"相机在跑"变成"良率在涨/在跌"，异常从"事后翻录像"变成"实时告警"。
- **对质量**：缺陷分布与趋势从人工统计 Excel 变成系统自动聚合，且缺陷图片可回溯到具体样本。
- **对运维**：单个 JAR + 一个数据库，无中间件依赖；自动备份、自动清理、自检脚本齐全。
- **对决策**：所有指标有明确的数据来源（维度表 + 事实表 + 聚合表），可追溯、可审计。

### 1.5 明确的非目标

| 不做什么 | 说明 |
|---|---|
| 不做图像识别算法 | 接收相机端已完成的判定结果，不解析图片做推理 |
| 不做设备端 SDK | 只定义设备与服务端之间的 HTTP 契约，设备端实现方式不限 |
| 不做多租户 | 当前是单组织（公司 → 工厂 → 产线 → 工位 → 相机）部署模型 |
| 不做设备管控 | 不下发参数、不远程控制相机，只接收上报 |
| 不做实时流式计算 | 采用 30 分钟粒度预聚合，非秒级流处理 |

## 二、功能清单

### 2.1 设备接入层（面向相机/上位机）

#### 2.1.1 相机心跳上报

| 项 | 内容 |
|---|---|
| **端点** | `POST /api/v1/camera/status/heartbeat` |
| **作用** | 采集相机运行状态与资源指标，驱动状态页、看板与告警判定 |
| **输入** | Header：`Authorization: Bearer <设备Token>`、`X-Device-Id`；Body：相机名/编号、时间戳、状态枚举、识别总数/正确数/异常数、CPU/内存/温度、错误信息、计数器重置标识 |
| **输出** | `ResultVO<CameraHeartbeatResponseDTO>`：`serverTime`、`nextInterval`（建议心跳间隔，默认 5000 ms）、`configVersion` |
| **副作用** | 写 `fact_camera_heartbeat`（原始心跳）、`fact_camera_status_current`（当前状态快照）、`camera_status`（兼容表）；同步相机最新图片路径；触发异常告警判定 |
| **状态枚举** | `cameraStatus`：`0=停止` `1=运行` `2=故障` `3=待机` |

#### 2.1.2 检测统计批量上报（核心链路）

| 项 | 内容 |
|---|---|
| **端点** | `POST /api/v1/camera/inspection/batch-upload` |
| **作用** | 接收一个时间窗内的检测总数、良率与缺陷明细，落库并同步聚合 |
| **输入** | Header：设备 Token、`X-Device-Id`、`X-Batch-Id`（建议）；Body：`schemaVersion`（**必须为 `"2.0"`**）、`batchId`、`cameraCode`、`productName`、`reportTime`、`counterMode`（**仅支持 `INCREMENTAL`**）、`timeRange`、`summary{totalCount,okCount,ngCount}`、`defects[]{sourceCode,count}` |
| **输出** | `ResultVO`：`accepted`、`duplicate`（幂等命中标记）、`batchId`、`inspectionBatchId`、`cameraId/Code`、`productId/Name`、`totalCount/okCount/ngCount`、`mappedDefectCount`、`unmappedDefectCount`、`timeBucket30m`、`mappedDefects[]`、`issues[]` |
| **副作用** | 写 `fact_inspection_batch`、`fact_inspection_defect_count`、`fact_inspection_mapping_exception`（未映射时）；upsert `agg_quality_30m`、`agg_defect_type_30m`、`fact_camera_status_current` |
| **幂等性** | `batchId` 唯一。重复上报**不重复写入**，返回 `duplicate: true` 与既有 `inspectionBatchId` |

#### 2.1.3 缺陷图片批量上传

| 项 | 内容 |
|---|---|
| **端点** | `POST /api/v1/defect-images/upload`（`multipart/form-data`） |
| **作用** | 接收缺陷图片及其缺陷框坐标，落盘供图库与回溯查看 |
| **输入** | `files`（图片数组，必填）、`file`（兼容字段，与 `files` 合并）、`metadata`（JSON 字符串，必填）：`cameraId`、`cameraName`、`uploadTime`、`images[]{fileName, captureTime, defects[]{type,severity,x,y,width,height,area}}` |
| **输出** | `ResultVO<DefectImageUploadResultDTO>`：`success`、`batchNo`、`batchId`、`imageCount`、`successCount`、`failCount`、`defectCount`、`highCount/mediumCount/lowCount`、`results[]{fileName,success,imageId,imageUrl,message,errorCode,failureReason,handlingAdvice}` |
| **落盘规则** | `{配置根目录}/{yyyyMMdd}/{cameraId}/{HHmmssSSS}_{uuid8}.{ext}` |
| **读取方式** | `GET /api/v1/defect-images/file/**` —— 按配置根目录 + URL 相对路径解析，**不依赖数据库里的绝对路径**，换机器只需拷贝图片目录即可继续显示 |
| **限制** | 单批 ≤ **100** 张（超出返回 **HTTP 413**，前置按 `X-Image-Count` 头提前拒绝）；单文件 ≤ 10 MB；整批 ≤ 1024 MB；文件名必须与 `metadata.images[].fileName` 完全一致；支持 jpg/jpeg/png/bmp/gif/webp/svg |

> **为什么图片读取接口要匿名可访问**：前端用 `<img src="...">` 展示图片，
> 浏览器标签**不会携带 Authorization 头**，若要求令牌会导致所有图片裂图。
> 该路径使用不可猜测的文件名（日期/相机/毫秒时间戳 + 8 位随机串）。

### 2.5 运维与数据治理

| 能力 | 频率/触发 | 说明 |
|---|---|---|
| **数据库全量备份** | 每日 01:0x（systemd timer） | `mysqldump --single-transaction`（不锁表）+ zstd 压缩 + SHA-256 校验文件；默认保留 14 份 |

| **磁盘水位巡检** | 每 30 分钟 | 检查 `/var` 与 `/data` 使用率，超 85% 写 journald 告警 + 本地告警文件，退出码 1 |
| **服务器资源监控** | 每 5 秒采集，前端轮询 | 实时展示**本机** CPU 使用率、内存使用率、各分区容量、**磁盘读写速率与 IOPS**；后端后台定时采集 + 内存环形缓存（120 点 = 10 分钟窗口），支持 10 分钟趋势曲线。依赖 OSHI 6.9.3 + JNA（跨 Windows / Linux，无需分别实现） |
| **安装自检** | 手工执行 `verify.sh` | **28 项**检查：运行环境、程序文件、工作目录、服务状态、端口监听、功能自检、安全回归（8 个管理端点匿名必须 403）、设备上报接口、**自检数据自动清理**、**服务器监控接口与采集可用性** |
| **操作日志审计** | 每次调用受控接口 | AOP 切面记录用户、操作类型、模块、请求方法/URI/参数、IP、耗时、结果；查询/导出/清空动作本身不再记录 |
| **密码重置工具** | 手工执行 | `reset-password.sh` 用 BCrypt（`htpasswd`，无则退回 `python3 crypt`）生成哈希改口令，并把凭据记入 `/etc/default/camera-detection`（640 root）供自检自动登录 |

## 三、典型使用场景

### 场景 1：相机掉线与设备异常告警（产线操作员 / 设备工程师）

**触发**：相机持续离线，或资源指标超阈值。

```
① 相机每 5 秒发一次心跳
   POST /api/v1/camera/status/heartbeat
   { "cameraName":"上料相机A", "cameraStatus":1,
     "recognizeCount":1000, "correctCount":960, "abnormalCount":40,
     "cpuUsage":45.5, "memoryUsage":60.0, "temperature":38.2 }
   Header: Authorization: Bearer <设备Token>, X-Device-Id: CAM-001

② 服务端判定：
   cameraStatus == 2            → 告警 CAMERA_FAULT（CRITICAL）
   识别总数 ≠ 正确数 + 异常数    → 告警 COUNT_MISMATCH（WARNING）
   cpuUsage    > 90 %           → 告警 CPU_HIGH（WARNING）
   memoryUsage > 90 %           → 告警 MEMORY_HIGH（WARNING）
   temperature > 70 ℃           → 告警 TEMPERATURE_HIGH（WARNING）
   （阈值全部来自系统设置表，可在线调整）

③ 结果：
   → 状态页"相机状态"页该相机显示为离线/异常
   → 异常告警页出现一条告警记录
   → 管理员在告警页点"处理"标记为已解决
```

**验收要点**：把某台相机的 `cpuUsage` 改成 `99` 上报，状态页与告警页应立即出现该相机的 CPU 告警。

### 场景 2：一次批量检测数据入库与良率刷新（系统自动）

**触发**：相机完成一个时间窗的检测（如 11:30–12:00）。

```
POST /api/v1/camera/inspection/batch-upload
{ "schemaVersion":"2.0", "batchId":"BATCH-HZ-001",
  "cameraCode":"CAM-001", "productName":"产品A",
  "reportTime":"2026-11-02 12:00:00", "counterMode":"INCREMENTAL",
  "timeRange":{"startTime":"2026-11-02 11:30:00","endTime":"2026-11-02 12:00:00"},
  "summary":{"totalCount":100,"okCount":95,"ngCount":5},
  "defects":[{"sourceCode":"p0","count":5}] }
```

**服务端处理链**：
```
① 基础校验   schemaVersion=="2.0"、batchId/cameraCode/productName 非空、
              counterMode=="INCREMENTAL"、summary 计数自洽
② 令牌校验   查 cfg_camera_token（SHA-256 比对 + 有效期 + 启用状态）
③ 定位实体   dim_camera 按 cameraCode/deviceId；dim_product 按 productName
④ 幂等检查   batchId 已存在 → 直接返回 duplicate:true，不重复写
⑤ 缺陷映射   cfg_camera_defect_mapping 按 相机+编码+产品+生效期 查标准缺陷类型
              未命中 → 返回 422 UNMAPPED，并记 fact_inspection_mapping_exception
⑥ 落库       fact_inspection_batch + fact_inspection_defect_count
⑦ 聚合       upsert agg_quality_30m（30 分钟桶）+ agg_defect_type_30m
⑧ 状态同步   upsert fact_camera_status_current + camera_status
```

**结果**：实时监控看板的当日产量、良率、缺陷分布立即刷新；
**班次归属自动计算**（白班 08:00–20:00 / 晚班 20:00–08:00 跨天）。

### 场景 3：缺陷图片入库与问题品回溯（质量工程师）

### 场景 4：映射缺失导致数据被拒（系统管理员排查）

**现象**：相机上报 `sourceCode = "p9"`，但系统未配置该编码的映射。

```
→ HTTP 422
{ "code":422, "message":"缺陷编码未配置一对一映射",
  "data":{"accepted":false,
          "issues":[{"sourceCode":"p9",
                     "issueType":"UNMAPPED_DEFECT_CODE",
                     "message":"缺陷编码未配置一对一映射",
                     "suggestion":"请在系统配置-映射配置中维护产品、相机、缺陷编码映射"}]}}
→ 同时 fact_inspection_mapping_exception 新增一条 OPEN 状态异常记录
```

**处置**：管理员在系统配置中补齐「产品 + 相机 + p9 → 标准缺陷类型」映射，
相机重新上报即可成功入库。**系统坚持"未映射就报错"，不会把缺陷静默归为"未知类型"** ——
这是为了避免质量统计出现无法追溯的黑洞数据。

| # | 限制 | 实测依据 | 影响面 |
|---|---|---|---|
| 1 | **「检测记录」「异常告警」「用户管理」三个页面的数据是前端假数据** | 源码中这三处各有一行 `// TODO: 替换为真实 API`；这三个路由可达，页面能打开但列表内容非真实接口数据 | ⚠️ **重要** —— 这三个页面当前**不能用于实际业务判断**。后端接口（`/api/detection-history/query`、`/api/alerts/*`、`/api/user`）均已实现可用，只是这三个前端页面尚未接入 |
| 2 | **13 条旧菜单路径为重定向桩** | `/companies`、`/factories`、`/lines`、`/workstations`、`/users`、`/brands`、`/defect-types`、`/holidays` 等均 `redirect` 到 `/system/config` | 旧书签不失效，但对应独立页面不加载 |
| 3 | **15 个孤立视图不被路由加载** | 约 4,700 行代码（如 `CompanyList.vue`、`FactoryList.vue`、`UserList.vue`）已成孤立 | 维护成本，无功能影响 |
| 4 | **产品品牌的增删改后端未实现** | `DimProductBrandController` 只有类级路径无方法级映射；品牌只读接口在 `GET /api/stats/brands` | 前端 `brand.js` 的增删改调用会 404 |
| 5 | **缺陷类型批量导入未覆盖** | Excel 导入目前覆盖工厂/产线/工位/相机，缺陷类型与映射需在页面逐条维护 | 大批量初始配置需手工 |
| 6 | **`sys_data_retention_policy` 策略表不被代码读取** | 表内 5 条策略是元数据；真实保留期由 `DataCleanupTask` 硬编码与清理脚本参数决定 | 修改策略表**不会改变实际行为**，容易误解 |
| 7 | **保留策略两处口径不同** | 应用内清理图片记录 30 天；`cleanup-defect-images.sh` 对缺陷图片文件按 7 天清理 | 两个口径各自生效，注意区分表与文件 |
| 8 | **业务日志文件为空** | 应用日志实际全部进 journald；`logging.file.name` 指向的文件无 appender | 排查须用 `journalctl`，不能 `tail` 该文件 |
| 9 | **接口文档与实现存在版本差异** | 冻结契约文档示例写 `schemaVersion: "1.0"`，**代码实测只接受 `"2.0"`**（`INVALID_SCHEMA_VERSION`） | 设备端对接以 `"2.0"` 为准，文档示例需订正 |
| 10 | **心跳接口部分校验失败仍返回 HTTP 200 + code=500** | 冻结契约 §4 已注明"先冻结现状" | 设备端不能只看 HTTP 状态码，须读 body `code` |
| 11 | **部分系统设置项"存了但不生效"** | 实测：`alert.cpuWarning`、`alert.memoryWarning`、`alert.temperatureWarning` **确实被业务读取**（告警判定实时查库）；但 `heartbeat.onlineSeconds`、`heartbeat.offlineSeconds`、`defectImage.maxBatchImages`、`defectImage.maxFileSizeMb`、`analytics.dailyAggregationTime` **只写入表，业务侧从不读取** | 改动这 5 项**不会改变实际行为**。其中：图片批量上限实际由 `application.yml` 的 `defect-image.max-batch-images` 决定；相机在线判定在前端**硬编码** 30 秒/120 秒（`deriveTimeliness`）。⚠️ 修改设置表前请确认该项是否真被读取 |
| 12 | **服务器监控只覆盖本机，且历史不落库** | 页面展示的是**应用部署所在的那台服务器**，不是任意远程主机；10 分钟历史曲线存在**进程内存**中 —— **应用重启后曲线清零**（当前值与累计量不受影响） | 如需长期趋势或监控多台，需另建采集代理与历史表 |
| 13 | **磁盘 IO 速率首次采样无值** | 首次采样没有做差基准，速率字段返回 `null`（页面显示 `--`），第二次刷新后才有 | 正常行为，不是故障。切勿改成返回 0，否则会被误读为"磁盘空闲" |
| 14 | **Windows 无系统负载均值** | `loadAverage1/5/15` 仅 Linux 有，Windows 返回 `null`（页面显示"不适用"） | 平台差异，无替代方案 |
| 15 | **日聚合调度时间有两处来源** | `analytics.dailyAggregationTime`（设置表，默认 02:00）与 `analytics_aggregation_schedule` 表（运行时自建，由 `/api/v1/analytics/aggregation/schedule` 接口维护，`enabled=1`、`schedule_time=02:00:00`） | 实际生效的是**后者**（`@Scheduled` 每分钟检查该表）。修改设置表的时间**不生效**，需调该接口 |

## 五、术语与配置说明

### 5.1 关键术语

| 术语 | 含义 |
|---|---|
| **设备 Token** | 相机调用上报接口时携带的凭据（`Authorization: Bearer <token>`），按相机在 `cfg_camera_token` 维护，支持 SHA-256 哈希存储与有效期 |
| **`sourceCode`** | **设备侧**的缺陷编码（如 `p0`、`p1`）。由相机厂商定义，各不相同 |
| **标准缺陷类型** | **系统侧**统一后的缺陷字典项（`dim_defect_type`），带编码、名称、严重度、是否判 NG |
| **缺陷映射** | 「产品 + 相机 + `sourceCode` → 标准缺陷类型」的一对一规则（`cfg_camera_defect_mapping`），含生效期与启用开关 |
| **未映射（UNMAPPED）** | 设备上报的 `sourceCode` 在映射表中找不到对应规则。系统**拒绝该批次入库并返回 422**，同时记一条待处理异常 |
| **30 分钟桶（timeBucket30m）** | 时间聚合的最小粒度。同一 30 分钟内的多次上报合并到同一条聚合记录 |
| **增量计数（INCREMENTAL）** | 设备上报的是"本时间段新增的"检测数，而非累计值。当前**仅支持**这一种计数模式 |
| **批次幂等** | 同一 `batchId` 重复上报不会产生重复数据，接口返回 `duplicate: true` |
| **班次** | 白班 08:00–20:00（`shift_id=1`）、晚班 20:00–08:00（`shift_id=2`，跨天） |
| **工作日** | 默认周一至周五；节假日表标记为休息日的日期不计入 |
| **聚合表（agg_*）** | 预先算好的汇总表，看板只读这些表而不扫明细，是查询不慢的关键 |
| **维度表（dim_*）** | 描述"是什么"的字典表：公司、工厂、产线、工位、相机、缺陷类型、产品、品牌、班次、时间桶 |
| **事实表（fact_*）** | 描述"发生了什么"的事件表：检测批次、缺陷计数、映射异常、心跳、产量、告警 |
| **配置表（cfg_*）** | 协议与展示配置：设备令牌、缺陷映射、看板与部件定义 |
| **角色** | `role=1` 管理员（可改配置与用户）、`role=0` 普通用户（只读业务数据）。后端按 `ROLE_ADMIN`/`ROLE_USER` 校验 |
